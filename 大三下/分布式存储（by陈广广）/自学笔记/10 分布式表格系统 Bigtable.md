# 10 分布式表格系统 Bigtable

整理自 `分布式存储笔记.pdf` 第 149 到 169 页（第六章全部）。Bigtable 和 Dynamo 经常放在一张卷子上对比考，最后一节的系统对比表建议背下来。

## 本章要点

- Bigtable 是双层结构：底下是 GFS 负责持久化，上面是一层分布式索引。这一句能答半道题。
- 数据模型是三维映射 `(row, column, timestamp) -> string`，列族要预先定义，qualifier 不用。
- 三种表格：用户表、元数据表、根表；根表的位置存在 Chubby 里，叫引导信息。
- 三层定位的容量账：子表 128MB、元信息 1KB，一级撑 16TB，两级撑 2048PB。
- 容错全靠 Chubby 的互斥锁：Tablet Server 启动时抢锁，Master 靠锁判断它是死了还是 Chubby 挂了。
- 分裂只改内存索引和元数据表，不拷数据；合并由 Master 发起，要先把两个子表迁到一起。

## 第六章开篇：分布式表格系统的定位

分布式表格系统用于存储关系较为复杂的半结构化数据。与分布式键值系统相比，它不仅支持简单的 CRUD 操作，还支持扫描某个主键范围。

- 以表格为单位组织数据，每个表格包括很多行，通过主键标识一行，支持根据主键的 CRUD 和范围查找。
- 借鉴了很多关系数据库的技术，例如支持某种程度上的事务：单行事务，或者某个实体组（Entity Group，一个用户下的所有数据往往构成一个实体组）下的多行事务。
- 典型系统：Google Bigtable、Google Megastore、Microsoft Azure Table Storage、Amazon DynamoDB。

与分布式数据库相比，表格系统主要支持针对单张表格的操作，不支持多表关联、多表联接、嵌套子查询这些复杂操作；同一个表格的多个数据行也不要求包含相同类型的列，适合半结构化数据。课件对它的评价是"一种很好的权衡"：可以做到超大规模，功能也比键值系统多，代价是实现复杂、有一定使用门槛。

把三类系统放在一条线上看就清楚了：

| | 键值系统 | 表格系统 | 分布式数据库 |
| --- | --- | --- | --- |
| 单位 | key-value | 表格的行 | 表格的行 |
| 主键操作 | 支持 | 支持 | 支持 |
| 范围扫描 | 不支持 | 支持 | 支持 |
| 多表关联 | 不支持 | 不支持 | 支持 |
| 事务 | 无 | 单行或实体组内多行 | 完整事务 |
| 代表 | Dynamo、Tair | Bigtable、HBase | MySQL 分库分表、Spanner |

## 6.1 简介与数据模型

### 简介

整个表格在系统中全局有序，所以用的是顺序分布（对比 06 里的顺序分布那一节）。Bigtable 是分布式表格系统的始祖，采用双层结构，底层采用 GFS 作为持久化存储层。

定位与规模：

- 面向高可用性的分布式存储系统，支持半结构化数据。课件举的三类数据是 URL（content、metadata、links、anchors、page rank）、用户数据（preferences、account info、recent queries）、地理数据（roads、satellite images、points of interest、annotations）。
- 规模：PB 级别数据、数以千计的服务器、数十亿的 URL（多版本）、数亿万用户、每秒数千个查询、100TB 以上的遥感数据。
- 能力：数千台节点、TB 级别内存存储、PB 级别持久化存储、每秒百万级读写、高效扫描数据；服务器可以动态加入和退出，系统自己做负载均衡。

**为什么不用传统数据库**：可扩展性不够、成本高；自己实现则内部维护和更新更方便，也更有可能针对性能做优化。

**三个设计目标**：

1. 支持异步数据访问，每秒百万级访问请求。
2. 支持顺序访问数据，所以数据需要排序。
3. 保证数据一致性，所以需要锁。

这三条各自对应后面的一个部件：高吞吐对应子表切分与多 Tablet Server，排序对应 SSTable 与 LSM 树，锁对应 Chubby。

GFS 加 Bigtable 的双层架构是里程碑式的架构，Microsoft 的 Windows Azure Storage 以及开源的 Hadoop（HDFS 加 HBase）都是它的模仿者。Bigtable 的设计理念和 Google 的其他系统一样：构建在廉价硬件之上，通过软件层面提供自动化容错和线性可扩展能力。

### 数据模型（重点）

Bigtable 系统由很多表格组成，每个表格包含很多行，每行通过一个主键（Row Key）唯一标识，每行又包含很多列（Column）。某一行的某一列构成一个单元（Cell），每个单元包含多个版本的数据，用时间戳区分。整体上是一个**分布式多维映射表**：

```
(row: string, column: string, timestamp: int64) -> string
```

**列族（column family）**

Bigtable 把多个列组织成列族，列名由两部分组成：`(column family, qualifier)`。

- 列族是 Bigtable 中**访问控制的基本单元**，访问权限设置在列族这一级别上。
- 列族需要在创建表格的时候预先定义好，个数也不允许过多。
- 每个列族包含哪些 qualifier 不需要预先定义，qualifier 可以任意多个，适合表示半结构化数据。
- 一个列族中的数据通常是一种类型。
- Bigtable 的表格一般比较大，而且稀疏。

课件把这一点概括为"结构化（列族）和非结构化（限定词）的平衡"：需要预先规划、数量受限的那一层负责权限和存储布局，任意增删的那一层负责容纳半结构化数据。

**行主键**

- 可以是任意的字符串，最大不超过 64KB。
- 表中的数据按照行主键**字典序**排序，所以 key 值相近的数据临近存储：`AAAA`、`AAAB`、`AABA` 会挨在一起。
- 对一行的数据访问是原子的（靠行锁）。
- 不支持关系模型，不支持多行的事务，但可以对多个单行做连续操作。

**课件的例子**：行主键 `com.cnn.www` 是域名 `www.cnn.com` 变换后的结果。这样做的好处是让 `www.cnn.com` 下的所有子域名在系统中连续存放。这一行数据包含两个列族 `contents` 和 `anchor`，其中 `anchor` 又包含两个列，qualifier 分别为 `cnnsi.com` 和 `my:look.ca`。

对着这个例子拆一遍完整的单元名：`anchor:cnnsi.com` 这个列存的是 `cnnsi.com` 这个页面指向 CNN 时用的锚文本，值是 `"<CNN>"`。反转域名这个技巧是每年都可能考的小点，问的是"为什么要把 `www.cnn.com` 写成 `com.cnn.www`"，答案是让顺序分布把同一站点的数据切到同一批子表里，扫描一个站点只需要访问少数几台机器。

**时间戳与版本**

Google 的很多服务（比如 Web 检索和用户的个性化设置）需要保存不同时间的数据，这些版本必须通过时间戳区分。课件图中的 t4、t5、t6 表示保存了三个时间点获取的网页。为了简化版本管理，Bigtable 提供两种设置：

1. 保留最近的 N 个不同版本。
2. 保留限定时间内的所有不同版本，比如最近 10 天的所有版本。

失效的版本由 Bigtable 的垃圾回收机制自动删除。

## 6.2 系统架构

Bigtable 构建在 GFS 之上，为文件系统增加一层分布式索引层。另外它依赖 Google 的 Chubby（分布式锁服务）进行服务器选举及全局信息维护。

### 系统依赖

| 依赖 | 作用 |
| --- | --- |
| GFS | 可靠、并发、可扩展的持久化存储 |
| 调度器 | 实现分布式系统中的任务调度 |
| Chubby | 分布式锁服务，实现选举和全局信息维护 |
| MapReduce | 实现大规模数据处理，Bigtable 可以作为它的输入和输出 |

### 全局共享信息管理与 Chubby

保证数据一致性就需要锁，分布式系统中共享信息的管理交给 Chubby（ZooKeeper 正是参照它做的）。Bigtable 对全局信息的需求有七条：

- 命名空间一致性
- 原子性的读写文件
- 选举唯一主节点
- 保存启动位置信息（bootstrap location）
- 系统节点信息维护
- 表格 schema 信息维护
- 访问控制

**Chubby 锁服务**

Chubby 底层的核心算法是 Paxos（Paxos 算法的首次工业实现）。

- Paxos 的执行过程需要一个多数派就某个值达成一致，因此只要一半以上的节点不发生故障，Chubby 就能正常提供服务。
- 典型部署是**两地三数据中心五副本**：同城的两个数据中心分别部署两个副本，异地的数据中心部署一个副本。任何一个数据中心整体发生故障都不影响正常服务。
- 至少 5 个服务器构成一个 Chubby Cell，服务于多个分布式客户端，必须保证一半以上节点正常工作。

算一下为什么是五副本：五副本能容忍两台故障。同城两个中心各两副本、异地一副本的布局下，任何一个数据中心整体挂掉最多带走两个副本，剩下三个仍然是多数派。如果只放三副本、同城两个中心分 2 加 1，那么挂掉放了两副本的那个中心就只剩一个副本，达不到多数派。

Paxos 的两阶段流程（课件在第 155 页把 3.10 节的内容原样重复了一遍）详见 [05 事务、并发控制与分布式协议.md](<05 事务、并发控制与分布式协议.md>)，这里不重复。

### 三种表格

| 表格 | 存什么 |
| --- | --- |
| 用户表 User Table | 用户实际数据 |
| 元数据表 Meta Table | 用户表的元数据，如子表位置信息、SSTable 及操作日志文件编号、日志回放点 |
| 根表 Root Table | 元数据表的元数据 |

根表的元数据（也就是根表自己的位置信息）又称为 **Bigtable 引导信息**，存放在 Chubby 系统中。这是整条定位链的起点。

### 三个组成部分

Bigtable 把大表划分为大小在 100 到 200MB 的子表（tablet），每个子表对应一个连续的数据范围。系统主要由三部分组成：

| 组件 | 职责 |
| --- | --- |
| 客户端程序库 Client | 提供 Bigtable 到应用程序的接口，应用通过它对表格的数据单元做增删查改。客户端通过 Chubby 锁服务获取一些控制信息，但所有表格的数据内容都在客户端与子表服务器之间**直接传送** |
| 主控服务器 Master | 管理所有子表服务器：分配子表、指导子表合并、接受子表分裂消息、监控子表服务器、负载均衡、故障恢复 |
| 子表服务器 Tablet Server | 子表的装载与卸出、表格内容的读写、子表的合并和分裂。它服务的数据（操作日志和每个子表上的 SSTable 数据）都存储在底层的 GFS 中 |

客户端、主控服务器和子表服务器执行过程中都需要依赖 Chubby，**如果 Chubby 发生故障，Bigtable 系统整体不可用**。

典型 Bigtable 系统一句话：分布式文件存储系统加分布式索引层，外加任务调度和分布式锁（共享信息管理）。

数据不经过 Master 这一点和 GFS 是同一个套路：Master 只管元数据，把大流量的读写下放给工作节点直接和客户端对接。

## 6.3 数据分布

### 表格和子表

表格中行的操作是原子的。按照行数量把表格分为子表（Tablet）：

- 一定范围内连续的行
- 数据分布和负载均衡的基本单位
- 行号相近的子表尽量存储于一台服务器上
- 访问行号相近的子表时涉及较少的服务器间通信
- 需要合理设计 row key 来保证数据本地化

课件给的 row key 例子是把 `www.jlu.edu.cn`、`ccst.jlu.edu.cn` 写成 `cn.jlu.edu.www`、`cn.jlu.edu.ccst`（原文最后一个写作 `cn.jlu.edu.csw`，按上下文应为把 `ccst` 反转域名后的结果）。反转之后同一个域下的页面前缀相同，顺序分布会把它们放在相邻的子表里。

### 顺序数据分布

大的数据表格按照行的连续范围顺序分成子表：数据按 key 排序，按 key 值连续范围划分成子区域，子区域单独管理，子区域元数据和全局元数据分开存放。

### 子表数据分布的规模

- 每个 tablet 100 到 200MB
- 每个 server 存储 10 到 1000 个 tablet

这个规模设计带来两个好处：

- **快速容错**。假设 100 台服务器、每台 100 个 tablet，某台机器挂掉时它的 100 个子表可以分散给其余 99 台，每台只额外承担 1 个子表的临时存储和加载工作，恢复几乎察觉不到。
- **负载均衡**。过载机器上的子表被迁移到其他机器，主节点负责制订负载均衡决策。

这就是 06 里"异构系统"那一节讲的思想在 Bigtable 上的具体落地：分片够小够多，故障恢复才能由整个集群分摊。

### 定位子表（重点）

要解决的问题是：如何定位某行数据在集群中的存储位置。子表的属性是起始行号和终止行号（`startrowindex`、`endrowindex`），所以流程是先查找 tablet，再定位 row。

**方案一：通过主节点查找**，问题是可能引起主节点性能瓶颈。

**方案二（Bigtable 采用的）**：把子表位置信息存储为元数据表格，元数据表格与其他表格一样存储于 Bigtable 系统中。那么元数据表格自己怎么找？把根表的位置信息（bootstrap）共享在 Chubby 中。

**三层分层查找机制，复杂度 $O(1)$**：

| 层 | 做什么 |
| --- | --- |
| 第 1 层 | 从 Chubby 服务读 bootstrap，找到一级元数据位置（Root 表） |
| 第 2 层 | 利用一级元数据查找二级元数据表（META 表） |
| 第 3 层 | 使用二级元数据表查找某表格的子表 tablet 信息 |

补充几点：

- 位置信息就是服务器 IP 地址。
- 整体是类似 B+ 树的平衡结构：Root 表存 META 表信息（元数据子表），META 表存用户表信息（用户数据子表）。
- 二级元数据表也可以被分裂成多个子表 tablet；Root 表不分裂，永远只有一个子表，这是"三层"而不是"更多层"的原因。

**容量计算**（标准计算题）

Bigtable 中的数据切分为 100 到 200MB 的子表，所有数据按行主键全局排序，包含两级元数据（元数据表和根表）。用户表做某些操作（比如子表分裂）时需要修改元数据表，元数据表的某些操作又需要修改根表。使用两级元数据提高了系统能够支持的数据量。

假设平均一个子表大小为 128MB、每个子表的元信息为 1KB：

$$\text{一级元数据支持的数据量} = 128\text{MB} \times \frac{128\text{MB}}{1\text{KB}} = 128\text{MB} \times 131072 = 16\text{TB}$$

$$\text{两级元数据支持的数据量} = 16\text{TB} \times \frac{128\text{MB}}{1\text{KB}} = 2048\text{PB}$$

这两式复核过都对，算式见 [11 典型计算与数值复核.md](<11 典型计算与数值复核.md>)。读法是：一个 128MB 的元数据子表能装 `128MB/1KB = 131072` 条子表元信息，每条元信息指向一个 128MB 的数据子表，所以一级能覆盖 16TB；再往上套一层，每条根表记录指向一个能覆盖 16TB 的元数据子表，于是两级覆盖 2048PB。

### 客户端查询过程

客户端查询时先从 Chubby 中读取根表的位置，接着从根表读取所需的元数据子表的位置，最后从元数据子表中找到待查询的用户子表的位置。

为了减少访问开销，客户端使用了**缓存（cache）和预取（prefetch）**：

- 子表的位置信息被缓存在客户端。寻址时首先查找缓存，一旦缓存为空或者缓存信息过期，客户端就需要请求上一级元数据表获取位置信息：用户子表缓存过期要请求元数据表，元数据子表缓存过期要请求根表，根表缓存过期要读取 Chubby 中的引导信息。
- **缓存为空时最多三次请求；缓存信息过期时最多六次请求**，其中三次用来确定信息是过期的，另外三次获取新的地址。
- 预取是指每次访问元数据表时不仅读取所需的子表元数据，而是读取连续的多个子表元数据，这样查找下一个子表时不需要再次访问元数据表。

"三次和六次"这个数字是考点。记法是：空缓存只要顺着链条走三层；过期缓存要先撞三次南墙（每层各发现一次自己手里的地址是旧的），再重新走三层。

### 数据分布讨论

- 支持随机访问（索引结构）
- 支持顺序访问（row key 排序）
- 易于实现负载均衡
- 多级元数据结构易于扩展

## 6.4 存储实现

### 子表的数据存储

- 每个子表存储一定范围的行，行是有序的。
- 基于 SSTable 存储，多个子表格构成数据表。
- **Tablet 不在多个表格之间共享。**
- **Tablet 不存在数据重叠，但是 SSTable 可以重叠。**

最后两条容易混。子表之间的行范围是不重叠的（这是顺序分布的定义），但一个子表内部的多个 SSTable 文件是不同时期 dump 出来的，它们的 key 范围会互相覆盖，读的时候要合并。

### LSM 树与 SSTable

这一节和 04 里 LevelDB 那节是同一套内容，课件在第 155 和 162 页重复了两遍。推导链条：

索引的作用是加快读的速度、减慢写的速度。日志结构流派的 Bitcask 用 `<key, offset>` 索引、数据无序存储，有两个局限：内存容量限制；区间查询性能差（key 值无序）。于是引入排序字符表 SSTable：

- 稀疏索引、不在内存存放全部索引，解决内存容量限制
- key 值有序，解决区间查询性能差

内存中维护有序的数据结构（平衡树）实现 key 值排序功能；内存中数据过大时创建 SSTable 文件写入磁盘完成持久化。

写入路径：先写日志，再写 MemTable。

**Google SSTable 的特点**：

- 为流式 IO 和 `<key, value>` 数据类型优化
- 提供持久的排序索引表，属于日志流派
- 存储于内存或外存，日志缓存于内存
- 对行的增、删、改都走日志流派的追加方式，再定期合并

### Merge-dump 引擎

**数据写入**：

1. 写操作日志
2. 成功后应用到内存 MemTable
3. 内存超载时 dump 到 SSTable 文件
4. 从旧到新按照时间顺序合并
5. 定时合并 SSTable 数据

**数据读取**：按照时间顺序合并多个相关 SSTable 记录，返回最终数据结果。

### 数据分布的实现：两类节点的分工

| 子表服务器 | 主节点 |
| --- | --- |
| 可以在线进入或退出集群 | 分配 Tablet 到子表服务器 |
| 存储 1 到 1000 个 Tablet 子表 | 负载均衡，基本单位是子表 |
| 处理 Tablet 读写 | 垃圾回收 |
| 处理子表分裂和合并 | 维护表结构 |

### 子表分配

每个 Tablet 只存储在一个子表服务器上。主节点启动后的动作顺序：

1. 向 Chubby 申请锁，避免出现多个主节点。
2. 获取活跃子表服务器信息。
3. 获取每个子表服务器存储的子表信息。
4. 扫描 META 表，获取用户数据和子表信息。
5. 找到未分配的子表信息，建立子表列表，分配负载。

第 3 步和第 4 步一起做才能得出"未分配子表"：第 4 步知道系统里应该有哪些子表，第 3 步知道哪些已经有人在服务，两者作差就是待分配的。

### GFS 持久化存储

- **操作日志**：日志文件存储于 GFS 中，用于故障恢复过程中回放操作。
- **SSTable 数据**：内存 MemTable 数据量过大时以 SSTable 形式存储于 GFS，SSTable 文件分块，定期合并回收空间。

## 6.5 复制与一致性

Bigtable 系统保证**强一致性**：同一个时刻同一个子表只能被一台 Tablet Server 服务。Master 将子表分配给某个 Tablet Server 时需要确保没有其他 Tablet Server 正在服务这个子表，这是通过 **Chubby 的互斥锁**机制保证的。Tablet Server 启动时需要获取 Chubby 互斥锁；当 Tablet Server 出现故障时，Master 需要等到它的互斥锁失效，才能把它上面的子表迁移到其他 Tablet Server。

底层的 GFS 本质上是一个**弱一致性**系统，一致性模型只保证"同一个记录至少成功写入一次"，可能存在重复记录，也可能存在一些补零（padding）记录。Bigtable 写入 GFS 的数据分两种，各有一套去重办法：

| 写入 GFS 的数据 | 怎么处理 GFS 的重复 |
| --- | --- |
| 操作日志 | 每条操作日志都有唯一的序号，加载子表回放日志时通过序号去除重复的操作日志 |
| 子表包含的 SSTable 数据 | 写入 GFS 失败可以重试并产生多条重复记录，但 Bigtable 只索引**最后一条写入成功**的记录 |

Tablet Server 发生故障时，它服务的子表会被集群中的其他 Tablet Server 加载继续提供服务，加载时可能需要回放操作日志。

课件的结论：Bigtable 本质上是构建在 GFS 之上的一层分布式索引，通过它解决了 GFS 遗留的一致性问题，大大简化了用户使用。这条正好接上 07 里那句"对于上层的 Bigtable 有两种处理方式，后面将会介绍"。

## 6.6 容错和负载分配

### 容错

**Master 怎么监控 Tablet Server**

Master 对 Tablet Server 的监控通过 Chubby 完成。Tablet Server 在初始化时都会从 Chubby 中获取一个独占锁，所有 Tablet Server 的基本信息被保存在 Chubby 中一个称为**服务器目录（Server Directory）**的特殊目录里。Master 检测这个目录以随时获取最新的 Tablet Server 信息，包括目前活跃的 Tablet Server，以及每个 Tablet Server 上现已分配的子表。

对于每个 Tablet Server，Master 会定期询问其独占锁的状态。如果锁丢失或者没有回应，可能有两种情况：Chubby 出现了问题，或者 Tablet Server 出现了问题。**Master 的区分办法是自己尝试获取这个独占锁**：

- 获取失败，说明是 Chubby 服务出现问题。
- 获取成功，说明是 Tablet Server 出现了问题。Master 将中止这个 Tablet Server 并将其上的子表全部迁移到其他 Tablet Server（进入 unassigned state 后重新分配）。

这个判别方法是本章最容易出简答题的地方。它的巧妙之处在于用同一个动作同时排除了两种可能：Master 能抢到锁，说明 Chubby 是活的（否则抢锁这个操作本身就会失败），同时说明原持有者已经丢锁。

**子表服务器的数据恢复**

每个子表持久化的数据包含两部分：操作日志和 SSTable。Tablet Server 发生故障时某些子表的一些更新操作还在内存中，需要通过回放操作日志来恢复。

为了提高性能，Tablet Server 没有为它服务的每个子表写一个操作日志文件，而是把**所有它服务的子表的操作日志混在一起写入 GFS**，每条日志通过 `<表格编号, 行主键, 日志序列号>` 唯一标识。

混写带来一个新麻烦：某个 Tablet Server 宕机后，Master 把它服务的子表分给多台其他 Tablet Server，每台都得从这一大坨混在一起的日志里挑出属于自己的那部分。为了减少 Tablet Server 从 GFS 读取的日志数据量，**Master 会选择一些 Tablet Server 对日志进行分段排序**，排好序后同一个子表的操作日志连续存放，恢复某个子表时只需要读取该子表对应的操作日志。Master 需要尽可能选择负载低的 Tablet Server 执行排序，并且需要处理排序任务失败的情况。

恢复过程小结：子表服务器的持久化数据依靠 GFS 恢复（操作日志和 SSTable 数据），通过回放操作日志恢复内存状态。

**Master 自己的容错**

Bigtable Master 启动时需要从 Chubby 中获取一个独占锁。如果 Master 发生故障，它的独占锁将过期，管理程序会自动指定一个新的 Master 服务器，新 Master 从 Chubby 成功获取独占锁后可以继续提供服务。

流程四步：Master 在 Chubby 租约到期后结束服务；集群管理系统检测到主节点无响应；选择一个新的主节点，向 Chubby 申请锁；继续提供主节点服务。

### 负载均衡

**子表是 Bigtable 负载均衡的基本单位。** Tablet Server 定期向 Master 汇报状态，发现某个 Tablet Server 负载过重时，Master 自动执行子表迁移操作。

**子表迁移两步**：

1. 请求原有的 Tablet Server 卸载子表，原有 Tablet Server 解除加在子表上的互斥锁。
2. 选择一台负载较低的 Tablet Server 加载子表，加载时需要首先获取互斥锁。

如果原有 Tablet Server 发生故障，新的 Tablet Server 需要等待原有 Tablet Server 加在子表上的互斥锁过期。

**两次 Minor Compaction 的技巧**（考点）

子表迁移前原有的 Tablet Server 会对其执行 Minor Compaction，把内存中的更新操作以 SSTable 文件的形式转储到 GFS 中，因此负载均衡带来的子表迁移在新的 Tablet Server 上**不需要回放操作日志**。

子表迁移过程中有短暂时间需要停服务。为了尽可能减少停服务时间，Bigtable 内部采用两次 Minor Compaction 的策略：

1. 原 Tablet Server 对子表执行一次 Minor Compaction，**操作过程中仍然允许写操作**。
2. 停止子表的写服务，对子表再次执行一次 Minor Compaction。由于第一次过程中写入的数据一般比较少，第二次的时间会比较短。

这个技巧的本质是把"长时间的转储"和"停服务"错开：第一次不停服务，把绝大部分数据搬走；第二次停服务，只搬第一次期间新增的那一点残余。

由于负载均衡过程中会停一会读写服务，**负载均衡策略不应当过于激进**。负载均衡涉及的因素很多，Tablet Server 通过心跳定时把读、写个数、磁盘、内存负载等信息发送给 Master，Master 根据负载计算公式算出需要迁移的子表，然后放入迁移队列等待执行。

## 6.7 分裂和合并

随着数据不断写入和删除，某些子表可能太大、某些可能太小，需要执行分裂与合并操作。

顺序分布与哈希分布的区别在于：**哈希分布往往是静态的，而顺序分布是动态的**，需要通过分裂与合并操作动态调整，维持子表容量相当。

### 分裂操作

Bigtable 每个子表的数据分为内存中的 MemTable 和 GFS 中的多个 SSTable。由于同一个子表只被一台 Tablet Server 服务，分裂时比较简单。

**不需要进行实际的数据拷贝**，只需要把内存中的索引信息分成两份：分裂前子表的范围为 `(起始主键, 结束主键]`，在内存中将索引分成 `(起始主键, 分裂主键]` 和 `(分裂主键, 结束主键]` 两个范围。

例：某个子表 `(1, 10]` 的分裂主键为 5，那么分裂后生成的两个子表的数据范围为 `(1, 5]` 和 `(5, 10]`。

分裂以后两个子表各自写不同的 MemTable，等到执行 Compaction 时再根据分裂后的子表范围生成不同的 SSTable，无用的数据自然成为垃圾被回收。

**元数据的修改**：分裂操作由 Tablet Server 发起，需要修改元数据。用户表的分裂需要修改元数据表，元数据表的分裂需要修改根表。分裂操作需要增加一个子表，相当于在元数据表中增加一行，通过 Bigtable 的**行事务**保证原子性。只要修改元数据表成功，分裂操作就算成功。

**汇报丢失怎么办**：分裂成功后 Tablet Server 将向 Master 汇报。如果出现 Tablet Server 故障，Master 可能丢失分裂消息；新的 Tablet Server 加载这个子表时将发现它已经分裂，并通知 Master。这是一个"以元数据表为准、汇报只是加速"的设计，元数据表已经改了就算数，丢了消息也能在下次加载时补上。

### 合并操作

合并操作由 **Master** 发起，相比分裂要更加复杂。由于待合并的两个子表可能被不同的 Tablet Server 加载，合并的第一步需要**迁移其中一个子表**，使它们在同一个 Tablet Server 上，接着通知 Tablet Server 执行子表合并。课件原话是"子表合并操作具体实现时非常麻烦，有兴趣的读者可以自行思考"，没有展开。

分裂和合并的对照：

| | 分裂 | 合并 |
| --- | --- | --- |
| 谁发起 | Tablet Server | Master |
| 触发原因 | 子表太大 | 相邻子表都太小（通常由删除引起） |
| 要不要搬数据 | 不用，只切内存索引 | 要，先把两个子表迁到同一台机器 |
| 元数据 | 元数据表加一行，行事务保原子性 | 元数据表减一行 |
| 复杂度 | 简单 | 复杂 |

## 6.8 对比和应用

**优点**：

- 兼顾一致性和可用性：Bigtable 负责一致性 C 和容错，GFS 负责可用性 A 和可靠性 P。
- 分布式文件存储系统加分布式索引层的分层结构。
- 线性可扩展，数千台。
- 易于实现故障恢复，1 分钟内。

**缺点**：

- 单副本带来短暂性服务中断（故障恢复期间），不适合实时性要求高的场景。
- 架构复杂，子系统依赖较复杂。

"单副本"指的是服务层：同一时刻一个子表只有一台 Tablet Server 在服务，这台机器挂了就必须等检测加重新加载，期间这部分数据读写不可用。Dynamo 那种多副本都能服务的系统就没有这个空窗期，代价是一致性弱。

### 系统对比表（第 169 页原表，重点）

| | Bigtable 表格存储 | Dynamo 键值存储 |
| --- | --- | --- |
| 数据分布 | Key 范围顺序 | 一致性哈希 |
| 架构 | 主从 | P2P 环 |
| 数据模型 | 表格 | 键值 |
| 接口 | Get / Put / Scan / Delete | Get / Put |
| 存储 | SSTable、GFS | 索引 |
| 一句话 | Distributed index (DB) built on GFS | Distributed hash table |

把 07、09、10 三份笔记的系统放在一起，用同样五个问题过一遍：

| | GFS | Dynamo | Bigtable |
| --- | --- | --- | --- |
| 数据怎么分布 | 文件切 64MB chunk，Master 决定放哪 | 一致性哈希加虚拟节点 | 按 row key 顺序切 100 到 200MB 子表 |
| 副本怎么放 | 3 副本，跨机架 | N 副本，顺时针 N 个节点 | 服务层单副本，持久化层交给 GFS 的 3 副本 |
| 一致性 | 弱，追加至少成功一次，可能重复和 padding | 最终一致， $W+R>N$ 保证读到最新版本之一 | 强一致，Chubby 互斥锁保证一个子表只有一个服务者 |
| 故障怎么恢复 | Master 靠日志加 checkpoint 加影子；chunk 靠副本补齐 | Hinted Handoff 加 Merkle 树同步加读取修复 | Chubby 锁判活，子表重新分配加回放日志 |
| 负载怎么均衡 | Master 调整副本位置 | 调整虚拟节点 token 分配 | Master 迁移子表，两次 Minor Compaction 减少停服 |

## 典型题

**Q1. Bigtable 的数据模型是什么？列族和 qualifier 的区别是什么？**

数据模型是一个三维映射 `(row: string, column: string, timestamp: int64) -> string`：行主键唯一标识一行，列名由列族和 qualifier 两段组成，同一个单元可以有多个时间戳版本。列族必须在建表时预先定义、个数受限，它是访问控制的基本单元，同一列族的数据通常是同一种类型；qualifier 不需要预先定义、数量可以任意多、每行还可以不同，用来容纳半结构化数据。课件的例子是 `anchor` 列族下有 `cnnsi.com` 和 `my:look.ca` 两个 qualifier。

**Q2. 描述 Bigtable 的三层定位结构，并计算它能支持的数据量。**

三层是 Chubby 里的引导信息指向根表、根表指向元数据子表、元数据子表指向用户子表。客户端查询时依次读这三层，查找复杂度 $O(1)$。容量按子表 128MB、单条元信息 1KB 算：一个元数据子表能放 `128MB / 1KB = 131072` 条记录，所以一级元数据覆盖 `128MB × 131072 = 16TB`；根表的每条记录又指向一个这样的元数据子表，两级覆盖 `16TB × 131072 = 2048PB`。客户端会缓存位置信息，缓存为空时最多三次请求，缓存过期时最多六次。

**Q3. 为什么 Bigtable 要把行主键写成反转域名？**

因为 Bigtable 用顺序分布，数据按行主键字典序排列并切成连续范围的子表。把 `www.cnn.com` 写成 `com.cnn.www` 之后，`cnn.com` 下所有子域名的主键都以 `com.cnn` 开头，会落在相邻位置甚至同一个子表里。扫描一个站点的全部页面就只需要访问少数几台 Tablet Server，而不是散落全集群。反过来，如果直接用原始域名，`www.cnn.com` 和 `tech.cnn.com` 会被排到完全不同的地方。

**Q4. Master 怎么判断是 Tablet Server 挂了还是 Chubby 挂了？**

Tablet Server 启动时会在 Chubby 的服务器目录下持有一个独占锁，Master 定期询问锁的状态。如果锁丢失或者 Tablet Server 不回应，Master 自己去尝试获取这把锁：抢不到说明 Chubby 本身有问题（此时不能贸然迁移子表）；抢到了说明 Chubby 是好的、而原持有者确实已经丢了锁，于是判定 Tablet Server 故障，中止它并把它的子表全部重新分配出去。一个动作同时验证了两件事，这是这道题的答题重点。

**Q5. Bigtable 的子表分裂和合并分别由谁发起？为什么合并更复杂？**

分裂由 Tablet Server 发起。因为一个子表只被一台 Tablet Server 服务，分裂时不用搬数据，只要在内存里把索引区间一切为二（`(1,10]` 按分裂主键 5 切成 `(1,5]` 和 `(5,10]`），再往元数据表里加一行，用行事务保证原子性即可。合并由 Master 发起，复杂在于待合并的两个子表可能在不同的 Tablet Server 上，必须先把其中一个迁移过去让它们汇合，才谈得上合并，迁移本身又涉及卸载、抢锁、短暂停服。

**Q6. Bigtable 底下的 GFS 是弱一致性的，Bigtable 怎么做到强一致性？**

分两层回答。服务层：靠 Chubby 互斥锁保证同一时刻一个子表只有一台 Tablet Server 在服务，所有读写都经过这一个入口，天然串行化，所以对外是强一致的。存储层：GFS 只保证记录至少写成功一次，可能留下重复记录和 padding，Bigtable 针对两类数据各有对策，操作日志每条带唯一序号，回放时按序号去重；SSTable 数据即使重复写入多份，Bigtable 的索引只指向最后一条写入成功的记录。所以课件说 Bigtable 是 GFS 之上的一层分布式索引，它把 GFS 遗留的一致性问题在索引层解决掉了。

**Q7. 对比 Bigtable 和 Dynamo。**

按课件那张表的六行答：数据分布上 Bigtable 是 key 范围顺序切子表、Dynamo 是一致性哈希；架构上一个主从、一个 P2P 环；数据模型一个表格、一个键值；接口一个是 Get/Put/Scan/Delete、一个只有 Get/Put；存储一个是 GFS 上的 SSTable、一个是本地索引加日志；一句话概括是 "Distributed index (DB) built on GFS" 对 "Distributed hash table"。往深一层说，两者的分歧来自 CAP 取舍：Bigtable 选 CP，用单服务副本加 Chubby 锁换强一致，代价是故障恢复期间这部分数据不可用；Dynamo 选 AP，用 always writeable 换可用性，代价是要在读路径上处理版本冲突。
