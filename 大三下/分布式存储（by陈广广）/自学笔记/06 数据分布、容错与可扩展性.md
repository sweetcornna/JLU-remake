# 06 数据分布、容错与可扩展性

整理自 `分布式存储笔记.pdf` 第 65 到 81 页（3.7 数据分布、3.8 故障恢复和容错、3.9 可扩展性）。这三节是全课的机制核心，后面 Dynamo 和 Bigtable 的做法都能在这里找到出处。

## 本章要点

- 数据分布两条路线：哈希分布（代表 Dynamo）和顺序分布（代表 Bigtable）。
- 传统哈希取模的致命伤是扩容时 N 变化导致全量重分布，两种解法：元数据服务器托管映射、一致性哈希。
- 一致性哈希三种位置信息维护方式对应 $O(1)$、$O(\log N)$、$O(N)$ 三种空间开销。
- REDO 日志的约束规则（先写日志后改内存）和幂等性要求。
- 心跳假设服务正常，租约假设服务随时可能中断，两者取向相反。
- 同构系统增加副本慢，异构系统故障恢复快，这是线性可扩展的关键。

## 3.7 数据分布

分布式系统区别于传统单机系统，在于能把数据分布到多个节点并在多个节点之间实现负载均衡。数据分布方式主要两种：

1. **哈希分布**，如一致性哈希，代表系统是 Amazon 的 Dynamo。
2. **顺序分布**，即每张表格上的数据按主键整体有序，代表系统是 Google 的 Bigtable。

### 哈希分布

哈希取模：根据数据的某一种特征计算哈希值，并将哈希值与集群中的服务器建立映射关系，从而把不同哈希值的数据分布到不同服务器。

数据特征可以是 key-value 系统中的主键（key），也可以是其他与业务逻辑相关的值。

**散列性问题**

哈希函数散列特性好的话，可以把数据比较均匀地分布到集群中，而且需要记录的元信息非常简单：每个节点只需要知道哈希函数的计算方式以及模的服务器个数。

但找一个散列特性很好的哈希函数很难，两难在于：

- 按主键散列：同一个用户 id 下的数据可能被分散到多台服务器，一次操作同一个用户下的多条记录变得困难。
- 按用户 id 散列：容易出现**数据倾斜**（data skew），某些大用户的数据量很大，无论集群规模多大，这些用户始终由一台服务器处理。

处理大用户问题的两种方式：

- **手动拆分**：线下标记系统中的大用户（例如跑一次 MapReduce 作业），根据数据量把大用户拆分到多台服务器。相当于在哈希分布的基础上针对大用户特殊处理。
- **自动拆分**：数据分布算法能够动态调整，自动把大用户的数据拆分到多台服务器。

**传统哈希分布的第二个问题**

服务器上线或者下线时 $N$ 值发生变化，数据映射完全被打乱，几乎所有数据都需要重新分布，带来大量数据迁移。

两种解决思路：

1. 不再简单地把哈希值和服务器个数做除法取模，而是把哈希值与服务器的对应关系作为**元数据**交给专门的元数据服务器管理。访问数据时先计算哈希值，再查询元数据服务器获得该哈希值对应的服务器。集群扩容时可以把部分哈希值分配给新机器并迁移对应数据。
2. 采用**一致性哈希**（Distributed Hash Table，DHT）算法。

### 一致性哈希 DHT

**算法思想**：给系统中每个节点分配一个随机 token，这些 token 构成一个哈希环。执行数据存放操作时，先计算 key（主键）的哈希值，然后存放到顺时针方向第一个大于或等于该哈希值的 token 所在的节点。

**优点**：节点加入或删除时只会影响到哈希环中相邻的节点，对其他节点没有影响。

**实现步骤**：

1. 假设哈希空间为 $0 \sim 2^n$。
2. 求出每个服务器的 hash 值，配置到这个 $0 \sim 2^n$ 的圆环区间上。
3. 用同样的方法求出待存储对象的主键哈希值，也配置到圆环上。
4. 从数据映射的位置开始顺时针查找，将数据分布到找到的第一个服务器节点。

**三种位置信息维护方式**（考点，必须能说出三者的空间与时间权衡）

| 方式 | 每个节点存什么 | 空间复杂度 | 查找时间复杂度 | 代表 |
| --- | --- | --- | --- | --- |
| 前后邻居 | 它的前一个和后一个节点的位置 | $O(1)$ | $O(N)$，可能遍历整个环 | 最朴素的 DHT |
| 路由表 finger table | 大小为 $n$ 的路由表 | $O(\log N)$ | $O(\log N)$ | Chord |
| 全量信息 | 集群中所有服务器的位置 | $O(N)$ | $O(1)$ | Dynamo |

Chord 的路由表定义（第 69 页原图）：假设哈希空间为 $0 \sim 2^n$，即 $N = 2^n$，每台服务器维护一个大小为 $n$ 的路由表

$$FT_P[i] = succ(p + 2^{i-1})$$

其中 $p$ 为服务器在哈希环中的编号，路由表中的第 $i$ 个元素记录编号为 $p + 2^{i-1}$ 的后继节点。维护 $O(\log N)$ 的位置信息后查找时间复杂度改进为 $O(\log N)$。

（source.md 里这条公式因为是行间公式没提取出来，上面的版本是从 PDF 第 69 页原图读出来的。）

第三种做法是 Dynamo 用的：牺牲空间换时间，每台服务器维护整个集群中所有服务器的位置信息，查找时间复杂度降为 $O(1)$。工程上一般都采用这种做法。Dynamo 这样的 P2P 系统在每个服务器节点上都维护所有服务器的位置信息，而带有总控节点的存储系统往往由总控节点统一维护。

**一致性哈希的负载均衡问题**

一致性哈希还需要考虑负载均衡。增加服务节点 node5 后，虽然只影响到 node5 的后继（即 node3）的数据分布，但 node3 需要迁移的数据过多，整个集群的负载不均衡。

自然的想法是把需要迁移的数据分散到整个集群，每台服务器只需要迁移 $1/N$ 的数据量。为此 Dynamo 引入**虚拟节点**的概念（详见 [09 分布式键值系统 Dynamo.md](<09 分布式键值系统 Dynamo.md>)）。

### 顺序分布

哈希散列破坏了数据的有序性，只支持随机读取，不能支持顺序扫描。

某些系统可以在应用层做折中：互联网应用经常按照用户来拆分数据并通过哈希方法分布，同一个用户的数据分布到相同的存储节点，允许对同一个用户的数据执行顺序扫描，由应用层解决跨多个用户的操作问题。缺点是可能出现某些用户数据量太大的问题，因为用户的数据限定在一个存储节点，无法发挥多机并行处理能力。

顺序分布在分布式表格系统中比较常见。一般做法是把大表顺序划分为连续的范围，每个范围称为一个**子表**，总控服务器负责把这些子表按照一定的策略分配到存储节点上。

例（第 69 页图）：用户表（User 表）的主键范围为 1 到 7000，划分为多个子表，分别对应数据范围 1 到 1000、1001 到 2000、直到 6001 到 7000。Meta 表是可选的，某些系统只有根表（Root 表）一级索引，在 Root 表中维护 User 子表的位置信息。

为了支持更大的集群规模，Bigtable 这样的系统把索引分为两级：根表和元数据表（Meta 表）。Meta 表维护 User 表的位置信息，Root 表维护 Meta 表的位置信息。读 User 表时需要通过 Meta 表查找相应的 User 子表所在的存储节点，而读取 Meta 表又需要通过 Root 表查找相应的 Meta 子表所在的存储节点。

顺序分布与 B+ 树数据结构比较类似，每个子表相当于叶子节点。随着数据的插入和删除，某些子表可能变得很大、某些变得很小，数据分布不均匀。所以采用顺序分布时，系统设计需要考虑子表的分裂与合并，这会极大增加系统复杂度：

- **子表分裂**：一个子表太大超过一定阈值时需要分裂为两个子表，从而有机会通过负载均衡机制分散到多个存储节点。
- **子表合并**：一般由数据删除引起，相邻的两个子表都很小时可以合并为一个。单个服务节点能够服务的子表数量是有限的，比如 4000 到 10000 个，合并的目的是防止系统中出现过多太小的子表、减少元数据。

### 两种分布方式对比（第 71 页原表）

| | 哈希分布 | 顺序分布 |
| --- | --- | --- |
| 设计 | 一致性哈希 | 划分子表 |
| 功能 | 随机读 | 顺序读 |
| 优点 | 节点动态上下线容易 | 顺序扫描 |
| 缺点 | 负载均衡、可扩展性 | 主从结构 |
| 适用 | 键值对存储 | 关系、表格 |
| 一句话 | 一致性哈希环 | 子表分层索引 |

### 负载均衡和数据迁移

分布式存储系统的每个集群中一般有一个**总控节点**，其他节点为**工作节点**。总控节点根据全局负载信息进行整体调度：工作节点刚上线时总控节点需要把数据迁移到该节点；运行过程中也需要不断执行迁移任务，把数据从负载较高的工作节点迁移到负载较低的工作节点。

工作节点通过**心跳包**（Heartbeat，定时发送）把节点负载相关的信息发给主控节点，包括 CPU、内存、磁盘、网络等资源使用率，读写次数及读写数据量。主控节点算出工作节点的负载以及需要迁移的数据，生成迁移任务放入迁移队列等待执行。

**负载均衡操作需要控制节奏**：一台全新的工作节点刚上线时负载最低，如果主控节点把大量数据同时迁移过去，整个系统在新增机器的过程中服务能力会大幅下降。一般从新机器加入到集群负载达到比较均衡的状态需要较长一段时间，比如 30 分钟到一个小时。

**数据迁移操作过程**（三步，考点）

分布式存储系统中往往存储数据的多个副本，其中一个为主副本、其他为备副本，由主副本对外提供服务。迁移备副本不会对服务造成影响，迁移主副本也可以首先把读写服务切换到其他备副本，整个迁移过程不中断服务，对用户完全透明。

假设数据分片 D 有两个副本 D1 和 D2，分别存储在工作节点 A1 和 A2，D1 为主副本提供读写服务，D2 为备副本。要把 D1 从 A1 迁移出去：

1. 将数据分片 D 的读写服务由工作节点 A1 切换到 A2，D2 变成主副本。
2. 增加副本：选择某个节点例如 B 节点，增加 D 的副本，即 B 节点从 A2 节点获取 D 的副本数据（D2）并与之保持同步。
3. 删除工作节点 A1 上的 D1 副本。

顺序很重要：先切主、再补副本、最后删旧副本。任何时刻副本数都不少于原来的水平。

## 3.8 故障恢复和容错

### 数据库故障恢复与操作日志

数据库运行过程中可能发生故障，某些事务可能执行到一半但没有提交。系统重启时需要能够恢复到一致的状态，即要么提交整个事务，要么回滚。一般采用**操作日志**（有时称为提交日志，Commit Log）技术实现故障恢复。

三种操作日志：

| 日志类型 | 记录什么 | 例子（事务 T 对 X 执行加 10，初始 X=5，更新后 X=15） |
| --- | --- | --- |
| 回滚日志 UNDO Log | 事务修改**前**的状态 | `<T, X, 5>` |
| 重做日志 REDO Log | 事务修改**后**的状态 | `<T, X, 15>` |
| UNDO/REDO 日志 | 前后都记 | `<T, X, 5, 15>` |

为什么要有日志：数据库操作需要持久化到磁盘，如果每次操作都随机更新磁盘的某个数据块，性能会很差。通过操作日志顺序记录每个操作并在内存中执行，内存中的数据定期刷新到磁盘，就把**随机写请求转化为顺序写请求**。

关系数据库系统一般采用 UNDO/REDO 日志。可以把关系数据库存储模型做两点简化：

1. 假设内存足够大，每次事务的修改操作都可以缓存在内存中。
2. 数据库的每个事务只包含一个操作，即每个事务都必须立即提交（Auto Commit）。

REDO 日志要求把所有未提交事务修改的数据块保留在内存中。简化后的存储模型可以采用单一的 REDO 日志，大大简化了故障恢复。

### 重做日志 REDO

写操作流程三步：

1. 将 REDO 日志以追加写的方式写入磁盘的日志文件。
2. 将 REDO 日志的修改操作应用到内存中。
3. 返回操作成功或者失败。

**REDO 日志的约束规则**：在修改内存中的元素 X 之前，要确保与这一修改相关的操作日志必须先刷入到磁盘中。

用 REDO 日志做故障恢复，只需要从头到尾读取日志文件中的修改操作并逐个应用到内存中，即重做一遍。

**为什么必须先写日志再改内存**：假如先修改内存中的数据，用户就能立刻读到修改后的结果。一旦在完成内存修改与写入日志之间发生故障，最近的修改操作无法恢复，然而之前的用户可能已经读取了修改后的结果，这就产生了不一致。

### 优化手段一：成组提交

存储系统要求先把 REDO 日志刷入磁盘才可以更新内存中的数据。如果每个事务都要求把日志立即刷入磁盘，系统吞吐量会很差。所以存储系统往往有一个是否立即刷盘的选项：一致性要求很高的应用设置为立即刷入；要求不高的应用先把 REDO 日志缓存到操作系统或存储系统的内存缓冲区，定期刷盘。后者的问题是意外故障时可能丢失最后一部分更新操作。

**成组提交（Group Commit）** 是有效的优化。REDO 日志首先写入到存储系统的日志缓冲区，满足以下两个条件之一时，把缓冲区中的多个事务操作一次性刷入磁盘，接着一次性把多个事务的修改操作应用到内存中并逐个返回客户端结果：

- 日志缓冲区中的数据量超过一定大小，比如 512KB
- 距离上次刷入磁盘超过一定时间，比如 10ms

与"定期刷入磁盘"的关键差别：成组提交保证 REDO 日志成功刷入磁盘后才返回写操作成功。这种做法可能牺牲写事务的延时，但大大提高了系统的吞吐量。

### 优化手段二：检查点 checkpoint

如果所有数据都保存在内存中，会出现两个问题：

- 故障恢复时需要回放所有的 REDO 日志，效率较低。日志超过 100GB 时恢复时间无法接受。
- 内存不足。即使内存足够大，存储系统往往也只能缓存最近较长一段时间的更新操作。

所以需要把内存中的数据定期转储（Dump）到磁盘，这就是 checkpoint 技术。系统定期把内存中的操作以某种易于加载的形式（checkpoint 文件）转储到磁盘，并记录 checkpoint 时刻的日志回放点，以后故障恢复只需要回放该回放点之后的 REDO 日志。

由于转储需要很长时间，而这段时间还可能有新的更新操作，checkpoint 必须找到一个一致的状态。

**checkpoint 流程**：

1. 日志文件中记录 `START CKPT`。
2. 将内存中的数据以某种易于加载的组织方式转储到磁盘，形成 checkpoint 文件。文件中往往记录 `START CKPT` 的日志回放点，用于故障恢复。
3. 日志文件中记录 `END CKPT`。

**故障恢复流程**：

1. 将 checkpoint 文件加载到内存中，这一步往往只需要加载索引数据，效率很高。
2. 读取 checkpoint 文件中记录的 `START CKPT` 日志回放点，回放之后的 REDO 日志。

**幂等性要求**（容易被忽略的考点）

上述恢复方式依赖"REDO 日志中记录的都是修改后的结果"这一特性：即使 checkpoint 文件中已经包含了某些操作的结果，重新回放一次或多次这些操作的 REDO 日志也不会造成数据错误。如果同一个操作执行一次与重复执行多次效果相同，这种操作具有**幂等性**。

有些操作不具备幂等性，例如加法操作、追加操作。如果 REDO 日志记录的是这种操作，checkpoint 文件中的数据一定不能包含 `START CKPT` 与 `END CKPT` 之间的操作。两种处理方法：

1. checkpoint 过程中停止写服务，所有修改操作直接失败。实现简单，但不适合在线业务。
2. 内存数据结构支持快照。执行 checkpoint 时先对内存数据结构做一次快照，接着把快照中的数据转储到磁盘生成 checkpoint 文件，并记录此时对应的 REDO 日志回放点。生成过程中允许写操作，但 checkpoint 文件中的快照数据不会包含这些操作的结果。

### 分布式系统中的常见故障

随着系统规模增大，故障率增加。课件引用了 Google 某数据中心一年的运行故障统计，结论有三条：

- 单机故障和磁盘故障发生概率最高，几乎每天都有多起事故，系统设计首先需要对单台服务器故障进行容错处理。一般做法是保存多份数据，其中一份数据所在服务器故障时通过其他副本继续提供服务。
- 机架故障发生的概率相对也比较高，需要避免把数据的所有副本都分布在同一个机架内。
- 还可能出现磁盘响应慢、内存错误、机器配置错误、数据中心之间网络连接不稳定等。

### 故障检测：心跳与租约

容错处理的第一步是故障检测。

**心跳**：总控机 A 每隔一段时间（比如 1 秒）向工作机 B 发送一个心跳包。一切正常时 B 响应 A 的心跳包，否则 A 重试一定次数后认为 B 发生了故障。

心跳的问题：A 收不到 B 的心跳，并不能确保 B 发生故障并停止了服务。可能是 A 与 B 之间网络发生问题，也可能是 B 过于繁忙无法响应。由于 B 故障后往往需要把它上面的服务迁移到其他服务器，为了保证强一致性，必须确保 B 不再提供服务，否则会出现多台服务器同时服务同一份数据导致数据不一致。

**租约（Lease）**：基于同步时钟的机制，租约就是带有超时时间的一种授权。

A 给 B 发放租约，B 持有的租约在有效期内才允许提供服务，否则主动停止服务。B 的租约快到期时向 A 重新申请租约。正常情况下 B 通过不断申请租约延长有效期；当 B 出现故障或者与 A 之间网络故障时，B 的租约将过期，从而 A 能够确保 B 不再提供服务，B 的服务可以被安全地迁移到其他服务器。

实现租约时需要考虑一个**提前量**：假设 B 的租约有效期为 10 秒，那么 A 需要加上一个提前量、比如到 11 秒时才认为 B 的租约过期。这样即使 A 和 B 的时钟不一致，只要相差不太大，都可以保证 B 的租约到期并且已经不再提供服务。

两者的根本差异（课件原话，值得背）：

- **心跳函数假设服务正常，检测服务出错。**
- **租约机制假设服务可能随时中断。**

所以心跳收不到只能说明"可能有问题"，而租约过期能保证"对方一定已经停服"，这就是强一致性场景下必须用租约的原因。

### 故障恢复：迁移服务

常见的分布式存储系统分两种结构：

- **单层结构**：大部分系统属于这类，对每个数据分片维护多个副本。
- **双层结构**：只有类 Bigtable 系统是这种，把存储和服务分为两层，存储层对每个数据分片维护多个副本，服务层只有一个副本提供服务。

**单层结构的故障恢复**

维护了多个副本（例如 3 个），主备副本之间通过操作日志同步。主副本出错时选举新的主副本。

例：某系统有 3 个数据分片 A、B、C，每个存 3 个副本。A1、B1、C1 为主副本，分别存在节点 1、2、3。节点 1 故障被总控节点检测到，总控节点选择一个最新的副本（A2 或 A3）替换 A1 成为新的主副本并提供写服务。

节点下线分两种情况：

- **临时故障**：节点过一段时间将重新上线。
- **永久性故障**：比如硬盘损坏。

总控节点一般需要等待一段时间（比如 1 个小时），如果之前下线的节点重新上线可以认为是临时性故障，否则认为是永久性故障。永久性故障需要执行增加副本操作，即选择某个节点拷贝 A 的数据成为 A 的备副本。

**双层结构的故障恢复**

所有数据持久化写入底层的分布式文件系统，每个数据分片同一时刻只有一个提供服务的节点。服务副本出错时，从文件系统中复制一份即可。

例：某系统有 3 个数据分片 A、B、C，分别被节点 1、2、3 服务。节点 1 故障时，总控节点选择一个工作节点（比如节点 2）加载 A 的服务。由于 A 的所有数据都存在共享的分布式文件系统中，节点 2 只需要从底层文件系统读取 A 的数据并加载到内存。

**停服务时间**

节点故障会影响系统服务，在故障检测以及故障恢复的过程中不能提供写服务及强一致性读服务。停服务时间包含两部分：

- **故障检测时间**：一般在几秒到十几秒，和集群规模密切相关。集群规模越大，故障检测对总控节点造成的压力越大，检测时间越长。
- **故障恢复时间**：一般很短。单层结构的备副本和主副本保持实时同步，切换为主副本的时间很短；双层结构往往实现成只需要把数据的索引而不是所有数据加载到内存。

**总控节点的故障恢复**

总控节点自身也可能故障。为了实现高可用性（High Availability），总控节点的状态也实时同步到备机，故障时通过外部服务选举某个备机作为新的总控节点，而这个外部服务也必须是高可用的。为了选主或维护系统中重要的全局信息，可以维护一套通过 Paxos 协议实现的分布式锁服务，比如 Google Chubby 或它的开源实现 Apache ZooKeeper。

## 3.9 可扩展性

### 总控节点 Master

分布式存储系统中往往有一个总控节点，用于维护数据分布信息、执行工作机管理、数据定位、故障检测和恢复、负载均衡等全局调度工作。引入总控节点可以使设计更简单，更容易做到强一致性，对用户友好。

- Master 节点负责：全局调度、文件目录、数据索引
- 规模：GFS 支持 8K nodes，HDFS 支持 3K nodes
- 设计上的妥协（compromise）：GFS 不支持小文件，HDFS 不支持数据更新
- 无 Master 节点的方案：一致性哈希，代价是系统维护代价高

### 总控节点会不会成为性能瓶颈

分两种情况：

1. **分布式文件系统**的总控节点除了全局调度，还需要维护文件系统目录树，**内存容量**可能率先成为瓶颈。
2. **其他分布式存储系统**的总控节点只需要维护数据分片的位置信息，一般不会成为瓶颈。

即使是分布式文件系统，只要设计合理也能扩展到几千台服务器。GFS 能扩展到 8000 台以上，Hadoop 能扩展到 3000 台以上（HDFS 不支持数据更新）。设计时需要减少总控节点的负载，GFS 的三个做法是：舍弃对小文件的支持、把数据的读写控制权下放到工作机 ChunkServer、通过客户端缓存元数据减少对总控节点的访问。

### 元数据分层提高可扩展性

如果总控节点成为瓶颈（例如需要支持超过一万台的集群，或者需要支持海量小文件），可以采用两级结构：在总控机与工作机之间增加一层**元数据节点**，每个元数据节点只维护一部分而不是整个文件系统的元数据。这样总控机也只需要维护元数据节点的元数据，不可能成为性能瓶颈。

- 客户端缓存元数据，进一步减小延迟
- 每个元数据节点保存部分元数据

算一笔账：假设 DFS 中有 100 个元数据节点，每个服务 1 亿个文件，系统总共可以服务 100 亿个文件。

客户端定位 DFS 工作机时，需要先访问 DFS 总控机找到 DFS 元数据服务器，再通过元数据服务器找到 DFS 工作机。看似增加了一次网络请求，但客户端总是能够缓存总控机上的元数据，因此不会带来额外开销。

### 数据库扩容

**扩容方法**

数据库可扩展性的实现手段：

- 通过**主从复制**提高系统的读取能力
- 通过**垂直拆分**和**水平拆分**把数据分布到多个存储节点
  - 垂直拆分：一个 DB 到多个 DB（按业务把不同表拆开）
  - 水平拆分：一个节点到多个节点（同一张表按哈希拆开）
- 通过主从复制把系统扩展到多个数据中心
- 主节点故障时可以将服务切换到从节点；整体服务能力不足时可以根据业务特点重新拆分数据进行扩容

典型结构：数据库中有三张表 table1、table2、table3，先按业务垂直拆分到不同 DB，再把每张表通过哈希水平拆分到不同存储节点，每个拆分后的 DB 通过主从复制维护多个副本且允许分布到多个数据中心。

- 读取能力不足：增加副本。
- 写入能力不足：根据业务特点重新拆分数据，常见做法是**双倍扩容**，即把每个分片的数据拆分为两个分片，扩容过程中需要迁移一半的数据到新加入的存储节点。

**传统数据库架构的三个可扩展性问题**

1. **扩容不够灵活**。一般采用双倍扩容，很难按需扩容。假设系统中已有 16 个存储节点，如果希望把服务能力提高 5%，只需要新增 1 个而不是 16 个存储节点。
2. **扩容不够自动化**。扩容时需要迁移大量数据，整个过程时间较长，容易发生异常，且数据划分的规则往往和业务相关，很难自动化。
3. **增加副本时间长**。如果某个主节点出现永久性故障（比如硬盘故障），需要增加一个副本，整个过程需要拷贝大量数据，耗时很长。

### 同构系统与异构系统（重点对比）

**同构系统**（固定元数据信息）

把存储节点分为若干组，每个组内的节点服务完全相同的数据，其中有一个主节点、其他为备节点。由于同一组内的节点服务相同的数据，称为同构系统。

- 不同节点存储相同数据
- 副本创建时间长
- 灵活性不好

同构系统的问题在于增加副本需要迁移的数据量太大。假设每个存储节点服务的数据量为 1TB，内部传输带宽限制为 20MB/s，那么增加副本拷贝数据需要的时间为

$$\frac{1\ \text{TB}}{20\ \text{MB/s}} \approx 5 \times 10^4\ \text{s} \approx 14\ \text{小时}$$

课件写的是"50000s，大约十几个小时"。按十进制 $1\text{TB} = 10^{12}$ 字节算正好是 50000 秒（13.9 小时），按二进制 $1\text{TB} = 2^{40}$ 字节算是 52429 秒（14.6 小时），课件用的是前一种读法。拷贝过程中存储节点再次发生故障的概率很高，所以这样的架构很难自动化，不适用于大规模分布式存储系统。

**异构系统**（动态元数据，不同节点存储不同数据）

为了实现线性可扩展性，存储节点之间是异构的。异构系统把数据划分为很多大小接近的分片，每个分片的多个副本可以分布到集群中的任何一个存储节点。某个节点发生故障时，原有的服务由**整个集群**而不是某几个固定的存储节点来恢复。

- 数据分片，每个分片多副本
- 服务并发性好、容错性高、错误恢复快
- 关键问题：如何决定数据副本的存储位置（数据分布）

例：系统中有五个分片 A、B、C、D、E，每个分片三个副本（如分片 A 的三个副本为 A1、A2、A3）。假设节点 1 发生永久性故障，可以从剩余的节点中任意选择健康的节点来增加 A、B 以及 E 的副本。由于整个集群都参与到节点 1 的故障恢复过程，故障恢复时间很短，而且集群规模越大优势越明显。

用数字说明这个差别：同构系统恢复一个 1TB 的节点，数据只能从那一组的兄弟节点单线程拷过来，十几个小时；异构系统里这 1TB 被切成几千个分片散在全集群，恢复时几百台机器同时往外拷自己那一小份，时间被除以并行度，从小时量级降到分钟量级。

## 典型题

**Q1. 传统哈希取模为什么不适合扩容？一致性哈希怎么解决？**

传统做法是 `hash(key) % N`，N 一变，几乎所有 key 的映射都变了，要做全量数据迁移。一致性哈希把节点和数据都映射到同一个环上，数据归顺时针第一个节点管。加一个节点只会从它的后继那里切走一段区间，其他节点完全不动，迁移量从 100% 降到大约 $1/N$。

**Q2. 一致性哈希里查找节点的三种实现，各自的时空复杂度？**

只存前后邻居：空间 $O(1)$，查找要沿环走一圈，时间 $O(N)$。Chord 的 finger table：每节点存 $n = \log N$ 项，第 $i$ 项指向 $succ(p + 2^{i-1})$，空间和时间都是 $O(\log N)$。Dynamo 的全量表：每节点存所有节点位置，空间 $O(N)$，查找 $O(1)$。工程上机器数量通常不过几千台，全量表才几十 KB，所以实际系统多选第三种。

**Q3. 为什么 REDO 日志必须先于内存修改落盘？**

如果先改内存，用户马上能读到新值。此时若在写日志之前宕机，这次修改在日志里没有记录、恢复不回来，但已经有用户读到过它，系统对外表现就前后矛盾了。先写日志后改内存能保证"凡是被别人看见的修改，一定已经在磁盘上有据可查"。

**Q4. checkpoint 为什么要求操作具有幂等性？不幂等怎么办？**

恢复流程是"加载 checkpoint 文件 + 回放 START CKPT 之后的日志"。checkpoint 文件里可能已经包含了 START CKPT 之后某些操作的结果（因为转储需要时间），这些操作会被重放第二次。如果日志记的是"X 改成 15"这种带结果的操作，重放多少次结果都一样；如果记的是"X 加 10"这种增量操作，重放一次就多加了 10。不幂等的处理办法有两个：checkpoint 期间停写服务，或者对内存数据结构做快照、保证 checkpoint 文件里只有 START CKPT 之前的状态。

**Q5. 心跳和租约的区别？为什么强一致性场景必须用租约？**

心跳的假设是服务正常，用来检测异常，收不到心跳只能说明"可能坏了"，也可能只是网络抖动或对方太忙。租约的假设是服务随时可能中断，只有持有未过期的租约才允许提供服务，租约一过期对方会主动停服。强一致性要求同一份数据同一时刻只能有一个节点提供写服务，只有租约能保证"我这边认为它过期了"蕴含"它那边一定停了"，心跳做不到这一点，会出现双主写同一份数据。

**Q6. 同构系统和异构系统的核心差别是什么？**

同构系统里一组节点存完全相同的数据，副本位置是固定的，补副本只能从同组的兄弟那里整体拷贝，1TB 加 20MB/s 就要十几个小时，期间再坏一台就危险了。异构系统把数据切成大量小分片，分片的副本可以落在集群里任何节点，某台机器坏了由整个集群一起补副本，恢复时间随集群规模下降。线性可扩展只有异构系统才做得到。
