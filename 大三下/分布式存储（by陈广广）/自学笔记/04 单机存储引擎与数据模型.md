## 本章要点

- 三种引擎按"支不支持顺序扫描"和"写是随机还是顺序"两条线区分：哈希（只随机读、顺序写）、B 树（都支持、随机写）、LSM（都支持、顺序写但有写放大）。
- Bitcask 的核心假设：value 长度远大于 key 长度，所以内存放索引、磁盘放数据划算。
- LevelDB 的五个部件：MemTable、Immutable MemTable、Current 文件、Manifest 文件、Commit Log、SSTable。
- 缓冲区替换从 LRU 到 LIRS 的演进原因是全表扫描污染缓冲池。
- 数据模型三类：文件模型、关系模型、键值模型；对象模型是文件模型的特例。

## 分布式存储系统总述（第三章开篇）

定义：分布式存储系统是大量普通 PC 服务器通过 Internet 互联，对外作为一个整体提供存储服务。

四个特性：

- **可扩展**。可以扩展到几百台甚至几千台的集群规模，而且随着集群规模增长，系统整体性能表现为线性增长。
- **低成本**。自动容错、自动负载均衡机制使其可以构建在普通 PC 机之上；线性扩展能力使得增减机器方便，可以自动运维。
- **高性能**。无论整个集群还是单台服务器都要求高性能。
- **易用**。提供易用的对外接口，具备完善的监控、运维工具，能方便地与其他系统集成。

核心挑战：数据和状态信息的持久化，要求在自动迁移、自动容错、并发读写的过程中保证数据的一致性。

三类数据需求：

- **非结构化数据**：所有格式的办公文档、文本、图片、图像、音频、视频。

## 3.1 单机存储系统

- 单机存储**引擎**：哈希表、B 树等数据结构在机械磁盘、SSD 等持久化介质上的实现。
- 单机存储**系统**：单机存储引擎的一种封装，对外提供文件、键值、表格或者关系模型。

单机存储系统的理论来源于关系数据库。数据库把一个或多个操作组成一组称作事务，事务必须满足 ACID（原子性、一致性、隔离性、持久性）。

存储引擎是存储系统的发动机，直接决定了存储系统能够提供的性能和功能。存储系统的基本功能是增、删、读、改，其中读取又分随机读取和顺序扫描。

常见的三种单机存储引擎：哈希存储引擎、B 树存储引擎、LSM 树存储引擎。

## 3.2 哈希存储引擎：Bitcask

### 基本定位

哈希存储引擎是哈希表的持久化实现，支持增、删、改以及随机读取，**不支持顺序扫描**。对应的存储系统是键值存储系统。哈希表支持快速查找和插入，复杂度 $O(1)$。

Bitcask 是一个基于哈希表结构的键值存储系统，特点是仅支持追加操作（append-only），所有写操作只追加而不修改老数据，属于日志结构流派。

文件组织：每个文件有大小限制，增长到限制就产生一个新文件，老文件只读不写。任意时刻只有一个文件可写，用于数据追加，称为**活跃数据文件**（active data file）；已达大小限制的叫**老数据文件**（older data file）。

### 数据结构

磁盘上每条记录的字段：主键 `key`、内容 `value`、主键长度 `key_sz`、value 长度 `value_sz`、时间戳 `timestamp`、crc 校验值。删除操作也不删除旧条目，而是把 value 设为一个特殊值作标识（tombstone value，墓碑值）。

内存中是基于哈希表的索引，通过主键快速定位 value 的位置。每一项包含三个定位信息：

- 文件编号 `file_id`
- value 在文件中的位置 `value_pos`
- value 长度 `value_sz`

### 读写实现

- **读取**：读 `file_id` 对应文件从 `value_pos` 开始的 `value_sz` 个字节，就得到了 value。一次磁盘读。
- **写入**：先把 key-value 记录追加到活跃数据文件末尾（顺序写），再更新内存哈希表让当前 key 指向新的 value 位置（内存操作）。一次顺序磁盘写加一次内存操作。旧记录仍然留在磁盘上。

### 为什么不支持顺序读取

三条原因：

1. 哈希索引结构天然适合点查询，不维护数据的有序性。
2. 数据在磁盘上的物理排列不按键的顺序，而是按写入顺序散落。
3. 没有 B+ 树那样的连续块指针结构，无法高效遍历相邻键。

所以像"读取 key 从 1 到 100"这类区间查询，效率很差。

### 定期合并 Compaction

问题：记录删除或更新后，原来的记录成为垃圾数据，一直保存下去文件会无限膨胀。

解决：定期执行合并操作做垃圾回收。把所有老数据文件中的数据扫描一遍生成新的数据文件，对同一个 key 的多个操作只保留最新的一个。每次合并后新生成的数据文件不再有冗余数据。

### 快速恢复：hint file

问题：哈希索引存在内存中，服务器断电重启后重建哈希表需要扫描一遍数据文件，数据文件很大时非常耗时。

解决：用索引文件（hint file）提高重建速度。索引文件就是把内存中的哈希索引表转储到磁盘生成的结果文件。

Bitcask 对老数据文件做合并时会产生新的数据文件，同时产生一个索引文件，记录每条记录的哈希索引信息。和数据文件不同的是，索引文件不存具体的 value 值，只存 value 的位置（和内存哈希表一样）。重建哈希表时不需要扫描所有数据文件，只需把索引文件中的数据一行行读取并重建，大大减少重启后的恢复时间。

### 容量计算

系统基于一个假设：value 的长度远大于主键的长度。

课件给了两组数：

- value 平均长度 1KB，每条记录在内存中的索引信息 32 字节，磁盘内存比为 32:1。32GB 内存索引的数据量为 $32\text{GB} \times 32 = 1\text{TB}$。
- value 长度 4KB 时，$32\text{GB} / 32 \times 4\text{KB} = 4\text{TB}$。

两式复核过都对，算式见 [11 典型计算与数值复核.md](<11 典型计算与数值复核.md>)。注意第一组的写法 `32GB×32` 是"内存量乘以磁盘内存比"，第二组的写法 `32GB/32*4KB` 是"索引条数乘以单条 value 大小"，两种写法等价，考试时用第二种更不容易出错。

### 小结

- 主要设计：内存存索引（key 到位置），磁盘文件存实际内容。
- 存在问题：存储容量受内存容量限制。
- 假设：value 长度远大于 key 长度。
- 优点：逻辑简单、性能稳定 $O(1)$；写性能好（1 次磁盘写加 1 次内存操作）；读性能好（1 次磁盘读）；便于实现故障恢复。
- 缺点：不支持顺序扫描；区间查询效率差；存储规模受内存限制。

## 3.3 B 树存储引擎：InnoDB

### 基本定位

B 树存储引擎是 B 树的持久化实现，支持单条记录的增、删、读、改，**还支持顺序扫描**，对应的存储系统是关系数据库。相比哈希引擎，多出来的能力就是范围扫描。关系数据库中通过索引访问数据。

### InnoDB 的数据结构

InnoDB 是 MySQL 的存储引擎。其中有一个特殊索引叫**聚集索引**，行的数据就存在其中，组织成 B+ 树。

按页面（Page）组织数据，每个页面对应 B+ 树的一个节点：

- 叶子节点保存每行的完整数据
- 非叶子节点保存索引信息

**读取过程**：数据在每个节点中有序存储，查询时从根节点开始二分查找直到叶子节点，每次读取一个节点，页面不在内存时从磁盘读并缓存。B+ 树的根节点常驻内存，因此一次检索最多需要 $h-1$ 次磁盘 IO，复杂度为

$$O(h) = O(\log_d N)$$

其中 $N$ 为元素个数，$d$ 为每个节点的出度，$h$ 为 B+ 树高度。

**修改过程**：先记录提交日志，再修改内存中的 B+ 树。内存中被修改过的页面超过一定比率时，后台线程把这些页面刷到磁盘持久化。

### 缓冲区管理

缓冲区管理器负责把可用内存划分成缓冲区，缓冲区是与页面同等大小的区域，磁盘块的内容可以传送到缓冲区中。**关键在于替换策略**，即选择把哪些页面淘汰出缓冲池。

**LRU（最近最少使用）**

按访问时间存储链表，淘汰最长时间没有读或写过的块。要求缓冲区管理器按页面最后一次被访问的时间组成链表，每次淘汰链表尾部的页面。基于双向链表加 HashMap 实现 $O(1)$ 时间复杂度。

问题：一次全表扫描会把缓冲池中的大量页面（可能包含很快会被访问的热点页面）替换掉，污染缓冲池。也就是"全表扫描导致真正高频的数据被替换"。

**LFU（最少使用）**

按访问频次淘汰。

**LIRS**

现代数据库一般采用 LIRS，把缓冲池分为两级：

- 数据首先进入第一级，如果在较短时间内被访问两次或以上，则成为热点数据进入第二级，每一级内部还是用 LRU。
- **IRR**（Inter-Reference Recency）：页面最近连续两次访问之间访问其他块的个数，衡量是否频繁。IRR 小说明是热数据 LIR，IRR 大说明是冷数据 HIR。
- **R**（Recency）：页面最近一次访问到当前时间内访问其他块的个数，衡量是否近期。

根据 IRR 建立两级缓冲池：数据先进冷数据缓冲；短时间多次访问（2 次或以上）移入热数据缓冲；每级缓冲内部用 R 实现 LRU。

**InnoDB 的实现**：内部 LRU 链表分为新子链表（new sublist）和老子链表（old sublist），默认前者占 5/8、后者占 3/8。页面首先插入到老子链表，InnoDB 要求页面在老子链表停留超过一定时间（比如 1 秒）才有可能转移到新子链表。出现全表扫描时，数据页面载入老子链表，因为停留时间不够而不会转移到新子链表，这就避免了新子链表中的页面被替换出去。

作用是细化数据访问频率行为，避免缓冲池污染。

### 优缺点

- 优点：采用 B+ 树索引结构；随机读和顺序扫描都支持；随机读性能稳定。
- 缺点：针对频繁访问的数据没有优化（指原生 LRU；LIRS 就是为了补这个）。写入是随机写，更新性能不如 LSM 树。

## 3.4 LSM 树存储引擎：LevelDB

### 基本思想

LSM 树（Log-Structured Merge Tree）存储引擎和 B 树一样支持增、删、改、随机读取以及顺序扫描。它通过**批量转储技术规避磁盘随机写入问题**，广泛应用于互联网的后台存储系统，例如 Google Bigtable、Google LevelDB 以及 Facebook 开源的 Cassandra。

思想很朴素：把对数据的修改增量保持在内存中，达到指定的大小限制后将这些修改操作批量写入磁盘；读取时需要合并磁盘中的历史数据和内存中最近的修改操作。

优势是有效规避了磁盘随机写入问题，代价是读取时可能需要访问较多的磁盘文件。

### 从 Bitcask 到 SSTable 的推导

这段逻辑值得单独记，因为它解释了 SSTable 为什么长这样：

索引的作用是加快读的速度、减慢写的速度。Bitcask 那种 `<key, offset>` 索引、数据无序存储的做法有两个局限：

1. 内存容量限制（索引全在内存）
2. 区间查询性能差（key 值无序）

对症下药就得到排序字符表 SSTable（Sorted String Table）：

- 稀疏索引、分布式索引、不在内存存放全部索引，解决内存容量限制
- key 值有序，解决区间查询性能差

### LevelDB 的存储结构

- 内存中的 MemTable
- 不可变 MemTable（Immutable MemTable，也叫 Frozen MemTable，冻结 MemTable）
- 磁盘上的四种文件：
  - 当前（Current）文件
  - 清单（Manifest）文件
  - 操作日志（Commit Log，提交日志）文件
  - SSTable 文件

### 写入过程

应用写入一条记录时，LevelDB 先把修改操作写入操作日志文件，成功后再把修改操作应用到 MemTable，写入就完成了。

### 换出过程（Minor Compaction）

MemTable 占用的内存达到上限后，需要把内存数据转储到外存文件：

1. 把原先的 MemTable 冻结成为不可变 MemTable，并生成一个新的 MemTable。
2. 新到来的数据记入新的操作日志文件和新生成的 MemTable。
3. 后台线程把不可变 MemTable 的数据排序后转储到磁盘，形成一个新的 SSTable 文件。

SSTable 文件是内存中的数据不断 Compaction 后形成的，所有文件构成层级结构，第 0 层为 Level 0，第 1 层为 Level 1，以此类推。

SSTable 中的文件按记录的主键排序，每个文件有最小主键和最大主键。**清单文件**记录这些元数据，包括属于哪个层级、文件名称、最小主键和最大主键。**当前文件**记录当前使用的清单文件名。运行过程中随着 Compaction 进行，SSTable 文件会变化，新文件产生、老文件废弃，往往会生成新的清单文件来记载变化，而当前文件用来指出哪个清单文件才是有效的。

### 查询过程

直观上每次查询都要从老到新读取每个层级的 SSTable 文件以及内存中的 MemTable。LevelDB 做了优化：由于对外只支持随机读取单条记录，查询时按以下顺序找，找到就返回：

1. 内存中的 MemTable
2. 同样处于内存中的不可变 MemTable
3. 依次从新到老读取磁盘中的 SSTable 文件

### 两种 Compaction

| 类型 | 触发条件 | 做什么 |
| --- | --- | --- |
| minor compaction | 内存中的 MemTable 大小到了一定值 | 把内存数据转储到 SSTable 文件中 |
| major compaction | 某个层级下的 SSTable 文件数目超过设置值 | 从该层级选择 SSTable 文件，与高一层级的 SSTable 文件合并 |

major compaction 相当于执行一次多路归并：按主键顺序依次迭代出所有 SSTable 文件中的记录，没有保存价值的直接抛弃，否则写入新生成的 SSTable 文件。

### 三种放大

| 放大 | 含义 |
| --- | --- |
| 写放大 | 一次写入请求造成多次磁盘写（合并压缩带来的） |
| 读放大 | 读取的数据量大于用户需要的数据量 |
| 空间放大 | 日志模式下，过期数据删除不及时 |

Compaction 可以减少读放大、缩小空间放大，但会带来写放大。三者是一个此消彼长的关系，调参就是在三者之间选位置。

### 三种引擎对比（重点表）

| | 哈希（Bitcask） | B 树（InnoDB） | LSM 树（LevelDB） |
| --- | --- | --- | --- |
| 数据结构 | 内存哈希表加磁盘日志 | B+ 树 | MemTable 加分层 SSTable |
| 增删改 | 支持 | 支持 | 支持 |
| 随机读 | 支持，$O(1)$ | 支持，$O(\log_d N)$ | 支持，可能查多层 |
| 顺序扫描 | 不支持 | 支持 | 支持 |
| 磁盘写 | 顺序追加 | 随机写 | 顺序写，有写放大 |
| 索引位置 | 全部在内存 | 磁盘上的非叶子节点 | 稀疏索引，不全在内存 |
| 容量瓶颈 | 内存 | 磁盘 | 磁盘 |
| 对应系统 | 键值存储 | 关系数据库 | Bigtable、LevelDB、Cassandra |

课件的三句话总结：

- LSM 树是维护 key 排序的、分布式索引的日志流派存储引擎。
- 日志流派（哈希索引、LSM 树）写入快，适合大规模存储，属于空间换时间。
- B 树读取快，性能稳定，工业界应用广泛。

## 3.5 数据模型

存储引擎是存储系统的发动机，数据模型是存储系统的外壳，在存储引擎外围实现存储系统功能。数据模型主要三类：文件模型、关系模型、键值模型。

### 文件模型

文件系统以目录树的形式组织文件。以类 UNIX 系统为例，根目录为 `/`，包含 `/usr`、`/bin`、`/home` 等子目录，每个子目录又包含其他子目录或文件。

POSIX（Portable Operating System Interface）是应用程序访问文件系统的 API 标准，定义了文件系统存储接口及操作集：

| 接口 | 作用 |
| --- | --- |
| `open` / `close` | 打开或关闭一个文件，获取文件描述符 |
| `read` / `write` | 读取文件或往文件中写入数据 |
| `opendir` / `closedir` | 打开或关闭一个目录 |
| `readdir` | 遍历目录 |

POSIX 不仅定义接口，还定义读写操作语义。例如要求读写并发时保证操作的原子性，读操作要么读到所有结果要么什么也读不到；要求读操作能读到之前所有写操作的结果。

**POSIX 标准适合单机文件系统，分布式文件系统出于性能考虑一般不会完全遵守。** 这句话是考点，GFS 就明确说自己不遵循 POSIX。

反例：NFS 允许客户端缓存文件数据，多个客户端并发修改同一个文件时可能不一致。客户端 A 和 B 同时修改 NFS 服务器上的某个文件，每个客户端都在本地缓存了副本，A 修改后先提交、B 后提交，那么即使 A 和 B 改的是文件的不同位置，也会出现 B 的修改覆盖 A 的情况。

### 特例：对象模型

对象模型与文件模型类似，用于存储图片、视频、文档等二进制数据块，典型系统包括 Amazon S3（Simple Storage Service）、Taobao File System（TFS）。这些系统弱化了目录树的概念：S3 只支持一级目录不支持子目录，TFS 甚至不支持目录结构。

与文件模型的关键区别：**对象模型要求对象一次性写入系统，只能删除整个对象，不允许修改其中某个部分。**

对象模型可以看作一种特殊的文件模型或键值模型，适合大规模数据存储。

### 关系模型

每个关系是一个表格，由多个元组（行）构成，每个元组包含多个属性（列）。关系名、属性名以及属性类型称作该关系的模式（schema）。

例：Movie 关系的模式为 `Movie(title, year, length)`，其中三个属性的类型分别为字符串、整数、整数。

关系模型的实例化就是关系型数据库，如 Oracle、SQL Server、DB2、MySQL。

SQL 的修改包含 `INSERT`、`DELETE`、`UPDATE` 三条命令，查询通过 select-from-where 语句表达。不考虑查询优化时，Select 查询的计算过程：

1. 取 `FROM` 子句中列出的各个关系的元组的所有可能组合。
2. 将不符合 `WHERE` 子句条件的元组去掉。
3. 有 `GROUP BY` 就按给出的属性的值分组。
4. 有 `HAVING` 就按条件检查每一组，去掉不符合条件的组。
5. 按 `SELECT` 子句的说明，对指定的属性和属性上的聚集（例如求和）计算出结果元组。
6. 按 `ORDER BY` 中的属性列的值对结果元组排序。

SQL 还允许在 `WHERE`、`FROM`、`HAVING` 子句中使用子查询。

SQL 的两个重要特性：

- **索引**：减少 SQL 执行时扫描的数据量，提高读取性能。
- **事务**：规定各个数据库操作的语义，保证多个操作并发执行时的 ACID 特性。

ACID 四条（详细展开见 [05 事务、并发控制与分布式协议.md](<05 事务、并发控制与分布式协议.md>)）：

- Atomicity（原子性）：一个事务中的所有操作，要么全部完成，要么全部不完成，不会结束在中间某个环节。
- Consistency（一致性）：事务开始之前和结束以后，数据库的完整性没有被破坏。
- Isolation（隔离性）：数据库允许多个并发事务同时读写和修改数据的能力，隔离性防止并发执行时由于交叉执行导致数据不一致。事务隔离分不同级别。
- Durability（持久性）：事务处理结束后对数据的修改是永久的，即便系统故障也不会丢失。

### 键值模型与表格模型

**键值模型**：每行记录是键值二元组 `<key, value>`。大量 NoSQL（not only SQL）系统采用，支持基于主键的三个操作：

- `Put`：保存一个 Key-Value 对
- `Get`：读取一个 Key-Value 对
- `Delete`：删除一个 Key-Value 对

典型键值系统是 Dynamo，特点是敏捷快速的随机读、去中心化。

**表格模型**：Key-Value 模型过于简单，应用场景有限，NoSQL 中使用更广的是表格模型。它弱化了关系模型中的多表关联，支持基于单表的简单操作。典型系统是 Google Bigtable 及其开源 Java 实现 HBase。

表格模型除了基于主键的操作，还支持范围扫描和基于列的操作：

| 操作 | 说明 |
| --- | --- |
| `Insert` | 插入一行数据，每行包括若干列 |
| `Delete` | 删除一行数据 |
| `Update` | 更新整行或其中某些列的数据 |
| `Get` | 读取整行或其中某些列数据 |
| `Scan` | 扫描一段范围的数据，根据主键确定范围，支持扫描部分列，支持按列过滤、排序、分组 |

关系模型与表格模型的区别：表格模型一般不支持多表关联操作，Bigtable 这样的系统也不支持二级索引，事务支持比较弱，各系统功能差异较大且没有统一标准。另外表格模型往往支持无模式（schema-less）特性，不需要预先定义每行包括哪些列以及列的类型，多行之间允许包含不同列。

### SQL 与 NoSQL

关系数据库在海量数据场景面临的四个挑战：

| 挑战 | 说明 |
| --- | --- |
| 事务 | 关系模型要求 ACID。分布式系统中多个操作属于不同服务器时，保证原子性需要两阶段提交协议，性能很低且不能容忍服务器故障 |
| 联表 | 传统设计需要满足范式（第三范式要求一个关系中不能出现在其他关系中已包含的非主键信息）。海量数据场景为了避免多表关联，往往用数据冗余等违反范式的手段，实践表明收益远高于成本 |
| 性能 | 关系数据库用 B 树存储引擎，更新性能不如 LSM 树。只有基于主键的增删查改时，性能也不如专门定制的 Key-Value 存储系统 |
| 规模 | 较难大规模扩展 |

第三范式的例子：部门信息表里有部门编号、部门名称、部门简介，那么员工信息表里列出部门编号后就不能再加部门名称、部门简介，否则会有大量数据冗余。

NoSQL 系统自己的四个问题：

- **缺少统一标准**。关系数据库有 SQL 这样的业界标准和完整生态链，NoSQL 各系统使用方法不同，切换成本高，很难通用。
- **使用和运维复杂**。选型和使用都有很大学问，往往需要理解系统的实现，缺乏专业的运维工具和运维人员。
- 一般不支持多表格（关系）关联操作。
- 事务性较弱。

最后一句话概括：这里做的权衡（trade-off）是在一致性、可用性、持久性三者之间。

## 典型题

**Q1. 为什么 Bitcask 假设 value 长度远大于 key 长度？**

因为它把索引全部放在内存、数据放在磁盘。内存中每条索引固定占 32 字节左右（文件号、偏移、长度），如果 value 也很小，那内存就要按 1:1 的比例陪着数据涨，这个设计就不划算了。value 是 1KB 时磁盘内存比是 32:1，32GB 内存能索引 1TB 数据；value 是 4KB 时能索引 4TB。

**Q2. LSM 树为什么写得快？代价是什么？**

写得快是因为写路径上只有一次顺序日志追加加一次内存操作，完全避开了磁盘随机写。代价有三个：读放大（可能要从 MemTable 一路查到最老的 SSTable）、写放大（Compaction 让同一份数据被反复重写）、空间放大（过期数据没被及时清掉）。

**Q3. 为什么 LRU 在数据库里效果不好？LIRS 怎么改的？**

一次全表扫描会顺序读入大量只用一次的页面，把真正的热点页面挤出缓冲池，这叫缓冲池污染。LIRS 把缓冲池分两级，新页面先进冷区，只有在短时间内被访问两次以上才升进热区，每级内部还是 LRU。全表扫描读进来的页面只被访问一次，停在冷区很快被淘汰，不影响热区。InnoDB 的做法是新老子链表按 5:3 分，并要求页面在老子链表停留超过 1 秒才允许升级。

**Q4. 对象模型和文件模型有什么区别？**

对象模型弱化甚至取消目录树（S3 只有一级目录，TFS 没有目录），而且对象必须一次性写入、只能整体删除、不能修改其中一部分；文件模型有完整目录树，支持在文件任意位置读写。

**Q5. 为什么分布式文件系统一般不完全遵守 POSIX？**

POSIX 要求并发读写的原子性，还要求读操作能读到之前所有写的结果。在分布式环境下做到这两点需要跨节点的强同步，代价太高。实际系统会放松语义换性能：NFS 允许客户端缓存导致并发写互相覆盖，GFS 干脆提供一组不遵循 POSIX 的专用接口。
