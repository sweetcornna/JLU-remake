## 5.1 键值对存储概述

分布式键值系统用于存储关系简单的半结构化数据，只提供基于主键的 CRUD（Create/Read/Update/Delete）功能。典型系统有 Amazon Dynamo 和 Taobao Tair。

从数据结构的角度看，分布式键值系统与传统的哈希表比较类似，不同的是它支持把数据分布到集群中的多个存储节点。分布式键值系统是分布式表格系统的一种简化实现，一般用作缓存，比如淘宝 Tair 和 Memcache。一致性哈希是分布式键值系统中常用的数据分布技术，因为被 Amazon DynamoDB 使用而变得相当有名。

分布式键值模型可以看成分布式表格模型的一种特例。由于它只支持针对单个 key-value 的增删查改，因此适用哈希分布算法。

### 存储模型与操作

最基本的两个接口：

- `Put(Key, Value)`：把 Key 及对应的 Value 存储到系统中。
- `Value = Get(Key)`：依据 Key 获得对应的 Value，没有则返回空（一个特殊的值）。

为了保证接口的完整性，还需要提供删除接口 `Delete(Key)`，删除接口使得整个系统可以进行数据缩减。

还有一个比较特殊的接口，**范围查询** `Query(Start_Key, End_Key)`，把位于两个键之间的所有值提取出来。

范围查询在某些应用中可能没有必要，但大部分数据库应用对它依赖较强。**是否提供范围查询直接影响键值对存储的内部存储结构**：

- 不支持范围查询：用哈希的数据结构就可以快速实现其他 3 个接口。
- 需要支持范围查询：需要排序的数据结构（排序数组、B 树、B+ 树等），无法直接用哈希表实现。

### 三种基本存储形式

| 形式 | 优点 | 缺点 | 适合做什么 |
| --- | --- | --- | --- |
| 哈希表 | 定位快，计算复杂度常数级 | 导致大量磁盘随机读写，消耗磁盘转动时间；把有序序列变成非有序，不支持范围查询 | 在内存中作索引，帮助应用程序定位具体的值 |
| 排序表 | 支持范围查询 | 读写查找复杂度 $O(\log n)$；在内存和磁盘中维护都比较复杂，例如在排好序的数组中间插入一个单元可能需要移动大量数据 | 作索引的数据结构，支持范围查询 |
| 日志 | 顺序写，对磁盘最友好，避免随机写入 | 只支持写入，不支持读取，或者说读取复杂度很高需要遍历所有日志；没有索引，不能从键的信息得到值的位置 | 最基本的存数据形式，必须配合索引使用 |

三者的关系是互补的：快速的键值对存储往往使用日志作为最基本的存储数据形式，但仍然需要配合哈希表或者排序表作为索引来找到对应的数据，或者通过日志归并的方法保存数据（相当于做了一次排序）。这正好解释了 04 里 Bitcask（日志加哈希索引）和 LevelDB（日志加排序索引）两种设计的由来。

### 哈希表加日志的组合

课件给的组合方案（第 127 到 128 页图）：

- **写入流程**：先把数据写入磁盘的日志中，完成这一步就可以认为写入操作已经完成，向客户端返回写入成功。之后更新内存中的索引项，下一次读取就能获得最新写入的数据。
- **读取流程**：先查内存中的数据结构获得值在磁盘中的位置，再读取对应的值。为了提高读取速度，可以依据内存大小进行数据缓存。
- **数据删除**：删除操作其实等同于写入操作，`Delete(Key)` 可以通过 `Put(Key, NULL)` 完成。写入的日志是删除操作本身，内存哈希结构中对应的数据项被删除。这种方式会在磁盘上留下许多本该删除的数据，浪费磁盘空间，这些垃圾数据通过后台的垃圾收集程序删除。

## 5.2 Dynamo 简介与架构

### CAP 理论

背景：分布式系统频繁出现故障，可能造成数据损坏甚至服务中断；底层拓扑结构复杂，有异构系统和多数据中心的复杂网络拓扑。问题是如何在这类大规模分布式系统中权衡容错性、一致性和可用性。

三个特性：

| 字母 | 名称 | 课件的定义 |
| --- | --- | --- |
| C | 一致性 | 并发操作的结果与串行操作结果一致 |
| A | 可用性 | 读写延迟小 |
| P | 分区容错性 | 部分节点故障的情况下能持续提供服务 |

CAP 理论认为分布式系统只能兼顾其中两个特性，即出现 CA、CP、AP 三种情况。课件给的归类：

| 组合 | 代表系统 |
| --- | --- |
| CP（一致性加容错性） | NoSQL（HBase、Bigtable）、HDFS |
| AP（可用性加容错性） | DynamoDB、GFS |
| CA（一致性加可用性） | MySQL、Oracle、NFS |

### Dynamo 的目标与假设

需要一个这样的分布式存储系统：

- 可扩展
- 支持 key-value 形式的数据和操作
- 高可用性（牺牲一致性换来）
- 保证服务质量 Service Level Agreements（SLA）

**系统假设**：

- 简单的读写操作（simple query model），单个 key-value 的增删改查。
- 数据有一个唯一的 ID（Key）。
- 大多数 Amazon 的服务都需要这样一个简单的查询操作，不是必须要关系模型。
- 存储对象一般较小，数据小于 1MB。

**一致性保证**：应用中发现符合 ACID 的分布式存储系统往往可用性较差，因此放宽一致性要求来提高系统的可用性（high availability）。

**其他假设**：假设系统运行环境没有入侵危险，不考虑安全性问题（如授权和认证等）。

**服务质量 SLA**：服务可以根据指定的时间限制来提供服务，有界的交付时间（bounded deliver time），基于截止时间的工作流程。课件的例子是：服务保证能在 99.9% 的情况下、在 300ms 内提供响应，支持最大并发度为每秒 500 个请求。

注意 SLA 用的是 99.9 分位而不是平均值，这正是"可用性等于读写延迟小"的工程化表述。

### 设计思路

**设计思路（1）**

- 牺牲强一致性换取可用性。
- 较弱的一致性会导致数据冲突，怎么办？**读的时候解决数据冲突，而不是写的时候来解决。**
- 支持数据随时可写 always writeable。

"读时解决冲突"是 Dynamo 最有个性的一条决策：写路径上不做任何协调，写永远成功；把合并冲突的成本推到读路径和应用层。购物车场景下这是对的，用户往购物车里加东西永远不该失败，两个并发版本合并成并集就行。

**设计思路（2）**

- 支持按需扩展。
- 对称系统架构（P2P）：系统中所有节点担负相同的责任。
- 去中心化：避免中心化带来的潜在瓶颈问题。
- 异构性和动态性：支持异构机器进出系统。
- 支持随时可写：符合大规模并发写的需求。

### 设计问题及解决方案（第 132 页原表，重点）

Dynamo 以很简单的键值方式存储数据，不支持复杂的查询。Dynamo 中存储的是数据值的原始形式，不解析数据的具体内容。主要用于 Amazon 的购物车及 S3 云存储服务。Dynamo 通过组合 P2P 的各种技术打造了线上可运行的分布式键值系统：

| 问题 | 采取的技术 |
| --- | --- |
| 数据分布 | 改进的一致性哈希（虚拟节点） |
| 复制协议 | 复制写协议（Replicated-write protocol，NWR 参数可调） |
| 数据冲突处理 | 向量时钟 |
| 临时故障处理 | 数据回传机制（Hinted handoff） |
| 永久故障后的恢复 | Merkle 哈希树 |
| 成员资格及错误检测 | 基于 Gossip 的成员资格和错误检测协议 |

## 5.3 数据分布

### 从哈希分布到一致性哈希

哈希：根据数据的某种特性计算哈希值，建立哈希值与位置的映射关系，再建立哈希值和节点之间的映射关系。问题是服务器上下线时 $N$ 发生变化，数据映射发生变化，需要大范围数据迁移。

Dynamo 系统采用一致性哈希算法把数据分布到多个存储节点。

**算法思想**：给系统中每个节点分配一个随机 token，这些 token 构成一个哈希环。执行数据存放操作时，先计算主键的哈希值，然后存放到顺时针方向第一个大于或者等于该哈希值的 token 所在的节点。

**优点**：节点加入或删除时只会影响到哈希环中相邻的节点，对其他节点没有影响。

**算法步骤**：

1. 求每个服务器的 hash 值，分配到 $0 \sim 2^n$ 的环上。
2. 用同样的方法求待存储数据的主键 hash 值，放于环上。
3. 从数据映射的位置顺时针查找第一个服务器。

添加服务器时，按照一致性哈希方法调整部分数据的存储位置，避免了大范围数据迁移。

### 异构系统带来的问题

异构服务器的服务能力不同：

- 一致性哈希平均分配负载
- 服务器能力差异导致总体性能下降，也就是水桶效应

### 改进的一致性哈希：虚拟节点（重点）

考虑到节点的异构性，不同节点的处理能力差别可能很大，Dynamo 使用了改进的一致性哈希算法：

- 每个物理节点根据其性能的差异分配**多个 token**，每个 token 对应一个"虚拟节点"。每个虚拟节点的处理能力基本相当，并随机分布在哈希空间中。
- 存储时数据按照哈希值落到某个虚拟节点负责的区域，然后被存储在该虚拟节点所对应的物理节点中。
- 物理节点可以根据服务能力承载多个虚拟节点。

虚拟节点的两个好处：

- 一个物理节点失效时，其承担的虚拟节点可以被**分配给其他多个可用物理节点**，负载分散而不是全压给后继。
- 一个物理节点上线时，可以从其他物理节点调整一定数量的虚拟节点负载到新加入的物理节点。

**虚拟节点的本质**：分离负载映射和资源映射，实现存储负载细分。

**课件的例子**：某 Dynamo 集群中原来有 3 个节点，每个节点分配了 3 个 token：

- 节点 1：(1, 4, 7)
- 节点 2：(2, 3, 8)
- 节点 3：(0, 5, 6)

存放数据时先算主键哈希值，根据哈希值存到对应 token 所在的节点。假设增加节点 4，Dynamo 集群可能会分别把节点 1 的 token 1 和节点 3 的 token 5 迁移到节点 4，token 分配变为：

- 节点 1：(4, 7)
- 节点 2：(2, 3, 8)
- 节点 3：(0, 6)
- 节点 4：(1, 5)

这样就实现了自动负载均衡。注意迁移是从**多个**原有节点各分一点给新节点，而不是只从一个后继节点切走一大块，这正是虚拟节点要解决的问题。

### 虚拟节点的信息更新

如何记录服务器在环中的位置（和 06 里的三种方式是同一套）：

| 空间开销 | 每台服务器记什么 | 查找时间 |
| --- | --- | --- |
| $O(1)$ | 前后邻居位置 | $O(N)$ |
| $O(N)$ | 所有主机信息 | $O(1)$，Dynamo 采用 |
| $O(\log N)$ | $\log N$ 台主机信息（路由表） | $O(\log N)$ |

Dynamo 系统中每个节点维护整个集群的信息，客户端也缓存整个集群的信息，因此绝大部分请求能够一次定位到目标节点。

### Gossip 协议

由于机器或者人为的因素，节点成员加入或删除经常发生。为了保证每个节点缓存的都是集群中最新的成员信息，所有节点每隔固定时间（比如 1s）通过 Gossip 协议的方式从其他节点中任意选择一个与之通信的节点，如果连接成功，双方交换各自保存的集群信息。

Gossip 协议用于 P2P 系统中自治的节点协调对整个集群的认识，比如集群的节点状态、负载情况。

**每个节点按间隔时间（1s）执行的五步**：

1. 从其他节点中任选一个与之交换信息。
2. A 告诉 B 其管理的所有节点的版本，包括 Down 状态和 Up 状态的节点。
3. B 告诉 A 哪些版本它比较旧了、哪些版本它有最新的，然后把最新的那些节点发给 A（处于 Down 状态的节点由于版本没有发生更新所以不会被关注）。
4. A 将 B 中比较旧的节点发送给 B，同时将 B 发送来的最新节点信息做本地更新。
5. B 收到 A 发来的最新节点信息后，对本地缓存的比较旧的节点做更新。

**节点上下线**

由于**种子节点**的存在，新节点加入可以做得比较简单：新节点加入时首先与种子节点交换集群信息，从而对集群有了认识。DHT 环中原有的其他节点也会定期和种子节点交换集群信息，从而发现新节点的加入。

集群不断变化，可能随时有机器下线，因此每个节点还需要定期通过 Gossip 协议同其他节点交换集群信息。如果发现某个节点很长时间状态都没有更新（距离上次更新的时间间隔超过一定阈值），则认为该节点已经下线。

## 5.4 一致性与复制

### 数据副本

为了处理节点失效的情况（DHT 环中删除节点），需要对节点的数据进行复制、创建数据副本。思路：

- 假设数据存储 $N$ 份，DHT 定位到的数据所属节点为 $K$，则数据存储在节点 $K, K+1, \dots, K+N-1$ 上。
- 如果第 $K+i$（$0 \le i \le N-1$）台机器宕机，则往后找一台机器 $K+N$ 临时替代。
- 如果第 $K+i$ 台机器重启，临时替代的机器 $K+N$ 能够通过 Gossip 协议发现，它会把这些临时数据归还 $K+i$，这个过程在 Dynamo 中叫做**数据回传（Hinted Handoff）**。
- 机器 $K+i$ 宕机的这段时间内，所有的读写均落入到机器 $[K, K+i-1]$ 和 $[K+i+1, K+N]$ 中。
- 如果机器 $K+i$ 永久失效，机器 $K+N$ 需要进行数据同步操作。
- 一般来说从宕机到被认定为永久失效的时间不会太长，积累的写操作也不会太多，可以利用 **Merkle 树**对机器的数据文件进行快速同步。

### NWR 机制（重点）

要求多副本随时可写，不能使用分布式锁。随时写导致不一致的情况下如何保证读有效？

假设 $N$ 个副本：

- 最少 $R$ 个成功读操作，则读成功
- 最少 $W$ 个成功写操作，则写成功

$N$ 表示复制的备份数，$R$ 指成功读操作的最少节点数，$W$ 指成功写操作的最少节点数。

**核心条件**：

$$W + R > N$$

满足这个不等式，就保证不超过一台机器故障时，可以读到至少一份可用数据。

原理是抽屉原理：写成功意味着至少 $W$ 个副本拿到了新值，读会访问 $R$ 个副本，$W + R > N$ 时这两个集合必然至少有一个交集，所以读一定能看到至少一份最新数据。

**按需调整 NWR 配置**：

| 目标 | 配置 | 说明 |
| --- | --- | --- |
| 重视读效率 | $W = N$，$R = 1$ | 同步复制，写必须全成功，读一个就够 |
| 重视写性能 | $W = 1$，$R = N$ | 写一个就返回，读要读全部 |
| 读写平衡 | $N = 3$，$W = 2$，$R = 2$ | Dynamo 的默认推荐 |
| 可损失一些更新 | $W = 1$，$R = 1$，$N = 3$ | $W + R = 2 \le N$，不再保证读到最新数据 |

注意最后一行不满足 $W + R > N$，课件明确标了它"可损失一些更新"。

### 随时可写带来的弱一致性问题

存在的问题：多个节点存储的信息不一致（更新顺序不同）。

- 写操作 `put()` 可能在数据更新在所有节点完成之前就返回（更新顺序和完成先后都不确定）。
- `get()` 可能返回一个数据的多个版本。

挑战是每一个数据对象有多个不同的修改记录版本，方案是向量时钟。

### 向量时钟（重点）

在 Dynamo 这样的 P2P 集群中，由于每个节点存储的集群信息有所不同，可能出现同一条记录被多个节点同时更新的情况，无法保证多个节点之间的更新顺序。为此 Dynamo 引入向量时钟（Vector Clock）来尝试解决冲突。

Dynamo 中的向量时钟用一个 `[nodes, counter]` 对表示：

- `nodes` 表示节点
- `counter` 是一个计数器，初始为 0，节点每次更新操作加 1

**课件的完整示例**（第 139 到 140 页，考试直接考这张图）：

1. Sx 对某个对象进行一次写操作，产生版本 D1（`[Sx, 1]`）。
2. Sx 再次操作，counter 值更新为 2，产生第二个版本 D2（`[Sx, 2]`）。
3. Sy 和 Sz **同时**对该对象进行写操作。Sy 把自身的信息加入向量时钟，产生新版本 D3（`[Sx, 2], [Sy, 1]`）；Sz 同样产生新版本 D4（`[Sx, 2], [Sz, 1]`）。这时系统中有了两个冲突的版本。
4. 客户端读到 D3 和 D4 两个版本，在应用层解决冲突后由 Sx 写回，产生 D5（`[Sx, 3], [Sy, 1], [Sz, 1]`）。D5 就是读处理冲突后的状态。

**判断规则**：如果第一个分支节点上的向量时钟**早于**第二个分支的，则第一个分支可以被忽略。这里的"早于"指的是逐项比较，每一项都小于等于且至少有一项严格小于。D2 早于 D3（`[Sx,2]` 对 `[Sx,2],[Sy,1]`），所以 D2 可以丢弃；而 D3 和 D4 互相都不"早于"对方，这就是冲突。

**两种最常见的冲突解决方法**：

- 通过客户端逻辑来解决，比如购物车应用（把两个版本的商品取并集）。
- "last write wins"，即选择时间戳最新的副本。这个策略依赖集群内节点之间的时钟同步算法，不能完全保证准确性。

系统出现故障的时候，preference list 以外的机器也可能处理写操作，具有最新时间戳的数据状态会被存储。

向量时钟可以设置存储上限（如 10 个）来节约空间，超出就丢掉最老的条目。

### 向量时钟的局限

向量时钟不能完美解决冲突。即使满足 $W + R > N$，Dynamo 也只能保证每个读取操作能读到所有的更新版本，**这些版本可能冲突，需要进行版本合并**。Dynamo 只保证**最终一致性**，如果多个节点之间的更新顺序不一致，客户端可能读取不到期望的结果。这个不一致问题需要注意，因为影响到了应用程序的设计和对整个系统的测试工作。

（更正：原文这段写作"即使 N+W＞R"。按上下文和 NWR 的定义应为 $W + R > N$，原文把三个字母的位置写乱了。）

多个版本冲突的处理分两种情形：

- **并发写**：记录向量时钟，不处理冲突。
- **并发读**：需要处理冲突。冲突解决方式是 last write wins（依赖同步时钟）或用户层解决。
- 只能保证最终统一，因为更新顺序可能不一致。

## 5.5 容错和负载分配

### 两类异常

Dynamo 把异常分为两种类型：

- **临时性异常**：比如机器假死、网络延迟，短时间可以恢复。
- **永久性异常**：如硬盘报修或机器报废，持续时间太长。

### 容错机制总纲

$N$ 个健康副本才能保证读到最新的数据：保证在 $N$ 个副本上读 $R$ 个、写 $W$ 个，合理设置 $R$ 和 $W$ 满足 $R + W > N$。

出错情况下不满足 NWR 的条件怎么办？两个机制：

- **Sloppy Quorum（宽松的法定人数）**：数据写入到临时节点，保证写操作的可用性。
- **数据回传技术**：节点恢复后，回传数据。

### 宽松计数和数据回传 Hinted Handoff

一份数据被写到 $K, K+1, \dots, K+N-1$ 这 $N$ 台机器上。如果机器 $K+i$（$0 \le i \le N-1$）宕机，原本写入该机器的数据转移到机器 $K+N$。如果在指定的时间 $T$ 内 $K+i$ 重新提供服务，机器 $K+N$ 将通过 Gossip 协议发现，并启动传输任务把暂存的数据回传给机器 $K+i$。

风险：如果 $K+i$ 长时间得不到恢复，$K+N$ 可能也会面临错误，可能造成临时接管的 $K+i$ 数据同时丢失，造成数据副本不一致。

$K+i$ 永久失效的处理：由 $K+N$ 长期节点接管，从其他节点同步数据。

### Merkle 树同步（重点）

如果超过了时间 $T$ 机器 $K+i$ 还是宕机状态，这种异常被认为是永久性的，需要借助 Merkle 树机制从其他副本同步数据。

数据同步面临两个问题：如何查找不一致的数据；如何减小数据传输量。

**Merkle 树的原理**：

- 叶子节点对应单个数据文件，值为文件内容的哈希值。
- 每个非叶子节点对应多个文件，值为其所有子节点值组合以后的哈希值。

这样，任何一个数据文件不匹配都将导致从该文件对应的叶子节点到根节点的所有节点值不同。

每台机器对每一段范围的数据维护一棵 Merkle 树。机器同步时首先传输 Merkle 树信息，只需要同步从根到叶子的所有节点值均不相同的文件。也就是：机器之间传输 Merkle 树信息，检测 Merkle 树结构，找到不一致的数据，再同步数据。

**优点**：

- 节点之间传输数据量小（先检查索引树）
- 检测效率高（检测到不一致，按需同步文件）
- 检测速度快（树遍历、按需检测）

**缺点**：与虚拟节点挂钩，Key 重新分布需要重算 Merkle 树。

比较两棵树时，从根开始比：根相同就说明整段数据完全一致，一次比较结束；根不同就往下比两个子节点，只沿不一致的分支下探。$n$ 个文件里有一个不一致时，只需要 $O(\log n)$ 次比较就能定位。

### 读取修复 Read Repair

假设 $N = 3$、$W = 2$、$R = 2$，机器 $K$ 宕机。可能有部分写操作已经返回客户端成功但没有完全同步到所有副本。如果机器 $K$ 出现永久性异常（比如磁盘故障），三个副本之间的数据会一直不一致。

客户端的读取操作如果发现某些副本版本太老，则启动异步的读取修复任务。该任务会合并多个副本的数据，并用合并后的结果更新过期的副本，从而使副本之间保持一致。

三种修复途径放在一起记：读取时顺手修（Read Repair）、临时故障恢复后回传（Hinted Handoff）、永久故障用 Merkle 树整段比对同步。

## 5.6 负载分配

**数据倾斜**：某一范围内值多于其他范围，不同虚拟节点负担不同。

Dynamo 的负载均衡取决于如何给每台机器分配虚拟节点号（token）。由于集群环境的异构性，每台物理机器包含多个虚拟节点。两种分配方法：

### 方法一：随机负载分配

- **分配方法**：每台物理节点加入时根据其配置情况随机分配 $S$ 个 Token。
- **优点**：负载平衡效果还是不错的，因为自然界的数据大致比较随机。虽然可能出现某段范围的数据特别多的情况（如某些大型网站域名下的网页特别多），但只要切分足够细，即 $S$ 足够大，负载还是比较均衡的。
- **缺点**：可控性较差。新节点加入或离开系统时，集群中的原有节点都需要扫描**所有**的数据从而找出属于新节点的数据，Merkle 树也需要全部更新；另外增量归档或备份变得几乎不可能。

### 方法二：数据范围等分加随机分配

- **分配方法**：首先把数据的哈希空间等分为 $Q = N \times S$ 份（$N$ 是机器个数，$S$ 是每台机器的虚拟节点数），然后每台机器随机选择 $S$ 个分割点作为 Token，每台机器维护每个数据范围的 Merkle 树。
- **优点**：负载也比较均衡，并且每台机器可以对属于每个范围的数据维护一棵逻辑上的 Merkle 树。新节点加入或离开时只需**扫描部分数据**进行同步，并更新这部分数据对应的逻辑 Merkle 树，增量归档也变得简单。
- **缺点**：提前确定数据范围（哈希空间）不容易。

一句话对比：方法一是先分 token 再看数据落哪，方法二是先把哈希空间切成固定的 $Q$ 段、再把段分给机器。固定分段让"一段数据"成为稳定的同步单位，Merkle 树才不用重算。

### 前后台任务的资源分配

Dynamo 中同步操作、写操作重试等后台任务较多。为了不影响正常的读写服务，需要对后台任务能够使用的资源做出限制。Dynamo 维护一个**资源授权系统**：把整个机器的资源切分成多个片，监控 60 秒内的磁盘读写响应时间、事务超时时间及锁冲突情况，根据监控信息算出机器负载，从而动态调整分配给后台任务的资源片个数。

## 5.7 读写流程与应用

### 选择服务节点的策略

两种：

| 策略 | 做法 | 优点 |
| --- | --- | --- |
| 客户端决定（直接） | 客户端存储分区信息（元数据） | 节省中转代价，访问延迟低 |
| 协调者选取（代理） | 依据每个节点的负载情况选择 | 客户端与服务端隔离性好 |

课件在第二种上打了星号，表示它是 Dynamo 更推荐的方式。

### 写流程（五步）

1. 根据一致性哈希算法计算出每个数据副本所在的存储节点，其中一个副本作为本次写操作的**协调者**。
2. 协调者并发地往所有其他副本发送写请求，每个副本把接收到的数据写入本地，协调者也把数据写入本地。
3. 某个副本写入成功后回复协调者。如果发给某个副本的写请求失败，协调者会把它加入重试列表不断重试。
4. 等到 $W-1$ 个副本回复写入成功后（即加上协调者共 $W$ 个副本写入成功），协调者可以回复客户端写入成功。
5. 协调者回复客户端成功后，还会继续等待或者重试，直到所有的副本都写入成功。

注意第 5 步：返回客户端成功不等于流程结束，后台还在补齐剩下的副本，这是"最终一致"的来源之一。

### 读流程（六步）

1. 根据一致性哈希算法计算出每个副本所在的存储节点，其中一个副本作为本次读操作的协调者。
2. 协调者根据负载策略选择 $R$ 个副本，并发地向它们发送读请求。
3. 每个副本读取本地数据，协调者也读取本地数据。某个副本读取成功后回复协调者读取结果。
4. 等到 $R-1$ 个副本回复读取成功后（即加上协调者共 $R$ 个副本读取成功），协调者可以回复客户端。分两种情况：
   - 如果 $R$ 个副本返回的数据完全一致，把某个副本的读取结果回复客户端；
   - 否则，需要根据冲突处理规则合并多个副本的读取结果。
5. Dynamo 系统默认的策略是根据修改时间戳选择最新的数据，用户也可以自定义冲突处理方法。
6. 读取过程中如果发现某些副本上的数据版本太旧，Dynamo 内部会异步发起一次读取修复操作，用冲突解决后的结果修正错误的副本（离线进行）。

### 系统优缺点

**优点**：

- 访问性能好：Key-value 形式查询、哈希性能、访问延迟低
- 可扩展性
- 负载均衡
- 设计完美主义（课件原话，指各个机制配合得很完整）

**缺点**：

- 数据记录容量小（UTF-8 编码，400K）
- 查询功能较单一，不支持关系（Join）
- 一致性较差：写顺序乱序、并发操作结果难预期
- 哈希维护代价

## 典型题

**Q1. 简述 CAP 理论，Dynamo 做了什么取舍？**

C 是一致性（并发操作的结果与串行操作一致）、A 是可用性（读写延迟小）、P 是分区容错性（部分节点故障仍能提供服务），三者只能兼顾两个。Dynamo 选 AP：网络分区时优先保证读写都能成功（always writeable），放弃强一致性，只提供最终一致性，冲突留到读的时候由客户端或 last write wins 解决。

**Q2. 一致性哈希为什么要引入虚拟节点？**

两个原因。一是负载不均：纯一致性哈希下每个节点在环上占的弧长是随机的，有的节点分到的数据可能是别人的好几倍；而且新增一个节点只从它的后继切走数据，后继一个人扛下全部迁移量。二是异构性：机器性能不同，均分负载会出现水桶效应，弱机拖慢整体。虚拟节点让每个物理节点按性能持有多个 token，数据落到虚拟节点、虚拟节点映射到物理节点。这样负载按 token 数分配（性能强的多拿几个），节点上下线时迁移量分摊到多个物理节点上，每台只挪大约 $1/N$。本质是把负载映射和资源映射分开。

**Q3. NWR 机制中为什么要求 $W + R > N$？给出三组典型配置。**

因为要让写集合和读集合必然相交。写成功意味着至少 $W$ 个副本有新值，读会访问 $R$ 个副本，两个集合大小之和超过 $N$ 时按抽屉原理必有交集，读就一定能看到至少一份最新数据。三组配置：$W=N, R=1$ 偏读（同步复制，读最快）；$W=1, R=N$ 偏写（写最快）；$N=3, W=2, R=2$ 读写平衡，这是常用的默认值。$W=1, R=1, N=3$ 不满足条件，可能读不到最新更新。

**Q4. 向量时钟怎么判断两个版本是否冲突？它能彻底解决冲突吗？**

向量时钟是一组 `[节点, 计数器]` 对，某节点每次更新就把自己那一项加 1。比较两个版本时逐项对比：如果 A 的每一项都小于等于 B 的对应项，说明 A 是 B 的祖先，可以直接丢掉 A；如果互相都不满足这个关系，说明两者是并发产生的，就是冲突。

它不能彻底解决冲突，只能**检测**出冲突。检测出来之后怎么合并得靠业务：购物车用取并集，通用场景用 last write wins 选时间戳最新的（依赖时钟同步，不完全可靠）。所以 Dynamo 只保证最终一致性。

**Q5. Dynamo 怎么处理临时故障和永久故障？**

临时故障用 Sloppy Quorum 加 Hinted Handoff：目标节点 $K+i$ 挂了，本该写它的数据临时写到 $K+N$ 上并打个标记，写操作照样算成功（可用性优先）；$K+i$ 在时间 $T$ 内恢复后，$K+N$ 通过 Gossip 发现它回来了，把暂存的数据回传。

永久故障用 Merkle 树：超过时间 $T$ 还没恢复就判定为永久失效，由 $K+N$ 长期接管，并从其他副本同步数据。同步时先交换 Merkle 树，从根往下比较哈希值，只沿不一致的分支下探，最后只传输真正不同的那几个文件，$n$ 个文件里定位一个差异只要 $O(\log n)$ 次比较。

另外还有一条兜底：读取修复。客户端读到版本太旧的副本时，异步合并多副本数据并回写修正。

**Q6. Dynamo 的两种虚拟节点分配方法各有什么问题？**

随机分配：每台机器加入时随机取 $S$ 个 token。负载还算均衡（$S$ 足够大时），但新节点加入或离开时，所有原有节点都得扫描全部数据来找出该迁走的部分，Merkle 树要整棵重算，增量归档几乎做不了。

数据范围等分加随机分配：先把哈希空间等分成 $Q = N \times S$ 段，每台机器随机选 $S$ 个分割点。因为段的边界是固定的，每段可以各自维护一棵 Merkle 树，节点变动时只扫描相关的几段、只更新对应的树，增量归档也简单。缺点是 $Q$ 要提前定好，而提前确定合适的哈希空间划分并不容易。
