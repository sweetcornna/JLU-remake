## 2.4 并行计算环境

### 物理问题在并行机上求解的三步

1. 抽象：将物理问题分解并抽象为并行计算模型和并行求解模型，利用并行机的多处理器优势。
2. 细化：将模型细化为具体的计算算法和求解算法，确保适合并行环境并能高效运行。
3. 实现：使用并行编程语言将算法转化为可执行的并行程序，在并行机上运行。

### 并行编程模型

概念：使得并行计算问题可以用并行程序来表达，从而编译和运行。编程模型的价值通常由通用性决定，也就是它能多好地表达各种不同的问题，以及这些问题在不同架构上执行的效果。

- 通用性看两点：适用问题范围、兼容平台。
- 实现形式：库函数（MPI、PVM）、语言扩展（OpenMP）等。

并行程序设计方法按实现形式分两种：

- 库函数法：在串行语言库函数基础上引入支持并行操作的库函数，如 MPI、MapReduce。
- 编译制导法：源程序设计语言不变，引入编译制导 Pragmas 格式注释。

### 四类并行编程模型

| 模型 | 举例 | 粒度 | 子作业数量 | 关键特点 |
| --- | --- | --- | --- | --- |
| 隐式并行 | Fortran 自动并行化、JVM | 由编译器决定 | 不可控 | 简单、自动、不可控 |
| 数据并行 | SIMD、MapReduce | 中小粒度 | 大 | 大规模并行 |
| 消息传递 | PVM、MPI | 大粒度 | 适中 | 紧密耦合同构处理器，显式同步，多线程或多进程 |
| 共享变量 | OpenMP | 适合多核 | 相对少 | 单一地址空间，编程简单，需要同步机制 |

消息传递模型的定义：驻留在不同处理器节点上的进程可以传递消息、相互通信，消息可以是指令、数据、同步信号或中断信号。

## MPI 并行编程模型

### 简介

MPI（Message Passing Interface，消息传递接口）是一个消息传递接口标准，广泛用于分布式内存系统中的高性能计算。

- 起源：1993 到 1994 年由工业界、政府和学术界的研究人员共同开发，确立了并行编程的首个标准。
- 支持语言：C、C++、Java、FORTRAN。
- 三个特点：可移植性（不同平台上运行）、高效性（优化通信性能）、灵活性（适应多种并行计算需求）。

MPI **不**负责的三件事（考点）：进程管理（如启动任务）、虚拟机配置、输入输出支持。

### 版本演进

| 版本 | 年份 | 新增 |
| --- | --- | --- |
| MPI 1.1 | 1995 | MPICH 是最流行的非专利实现，由 Argonne 国家实验室和密西西比州立大学联合开发，可移植性好 |
| MPI 1.2 到 2.0 | 1997 | 动态进程、并行 I/O、远程存储访问、支持 F90 和 C++ |
| MPI 3 | 2012 | 邻居集合通信（Neighborhood collective communication） |
| MPI 4 | 2021 | |

常见实现：MPICH、LAM、CHIMP。

### 第一个 MPI 程序

源笔记里的 Hello World 代码有几处手抄错误（`arge` 应为 `argc`，`%sin` 应为 `%s\n`，`void main` 不是标准写法）。下面是改正后的版本：

```c
#include "mpi.h"
#include <stdio.h>
#include <math.h>

int main(int argc, char *argv[])
{
    int myid, numprocs;
    int namelen;
    char processor_name[MPI_MAX_PROCESSOR_NAME];

    MPI_Init(&argc, &argv);
    MPI_Comm_rank(MPI_COMM_WORLD, &myid);
    MPI_Comm_size(MPI_COMM_WORLD, &numprocs);
    MPI_Get_processor_name(processor_name, &namelen);

    fprintf(stderr, "Hello World! Process %d of %d on %s\n",
            myid, numprocs, processor_name);

    MPI_Finalize();
    return 0;
}
```

（更正：原文作 `void main(argc,argv) int arge; char *argv[];` 和 `"Hello World! Process %d of %d on %sin"`，前者是 K&R 老式写法且把 `argc` 拼成了 `arge`，后者的 `in` 应为换行符 `\n`。）

### 六个基本函数组成的 MPI 子集

课件里的第二个例子是所有非 0 号进程向 0 号进程问好：

```c
#include <stdio.h>
#include <string.h>
#include "mpi.h"

int main(int argc, char **argv) {
    int my_rank;            /* 本进程编号 */
    int p;                  /* 进程总数 */
    int source;             /* 发送方编号 */
    int dest;               /* 接收方编号 */
    int tag = 50;           /* 消息标签 */
    char message[100];      /* 消息缓冲区 */
    MPI_Status status;      /* 接收状态 */

    MPI_Init(&argc, &argv);                     /* MPI 的初始化函数 */
    MPI_Comm_rank(MPI_COMM_WORLD, &my_rank);    /* 该进程编号 */
    MPI_Comm_size(MPI_COMM_WORLD, &p);          /* 总进程数目 */

    if (my_rank != 0) {
        sprintf(message, "Greetings from process %d!", my_rank);
        dest = 0;
        /* strlen(message)+1 是为了带上结尾的 '\0' */
        MPI_Send(message, strlen(message) + 1, MPI_CHAR,
                 dest, tag, MPI_COMM_WORLD);
    } else {                                     /* my_rank == 0 */
        for (source = 1; source < p; source++) {
            MPI_Recv(message, 100, MPI_CHAR, source, tag,
                     MPI_COMM_WORLD, &status);
            printf("%s\n", message);
        }
    }
    MPI_Finalize();                              /* MPI 的结束函数 */
    return 0;
}
```

进程编号 ranks 取 `0, 1, ..., p-1`。运行结果：

- `np=2` 时输出一行 `Greetings from process 1!`
- `np=4` 时输出三行，分别来自进程 1、2、3

注意 0 号进程是循环按 `source` 从 1 到 p-1 依次接收的，所以输出顺序是确定的。如果把 `MPI_Recv` 的 source 改成 `MPI_ANY_SOURCE`，输出顺序就不确定了，这是常见的改编考点。

六个函数的原型：

| 功能 | 原型 |
| --- | --- |
| 初始化 | `int MPI_Init(int *argc, char ***argv)` |
| 结束 | `int MPI_Finalize(void)` |
| 取本进程编号 | `int MPI_Comm_rank(MPI_Comm comm, int *rank)` |
| 取通信域进程数 | `int MPI_Comm_size(MPI_Comm comm, int *size)` |
| 发送 | `int MPI_Send(void *buf, int count, MPI_Datatype datatype, int dest, int tag, MPI_Comm comm)` |
| 接收 | `int MPI_Recv(void *buf, int count, MPI_Datatype datatype, int source, int tag, MPI_Comm comm, MPI_Status *status)` |

三个用途的一句话说明：`MPI_Comm_rank` 让进程把自身与其他进程区分开；`MPI_Comm_size` 让进程确定自己该完成的任务比例；`MPI_Init` 和 `MPI_Finalize` 是进出 MPI 环境的门。

### 点对点通信

点对点通信指发送端和接收端都是一个 task；群组通信指发送端或接收端多于一个 task。

MPI 的点对点通信同时提供阻塞和非阻塞两种通信机制，也支持多种通信模式，两者组合出很多函数。

**阻塞与非阻塞的区别在于返回后缓冲区是否可用**，这句话是考点。阻塞通信返回的条件是：

- 通信操作已经完成，即消息已经发送或接收；
- 调用的缓冲区可用。发送操作时缓冲区可以被其他操作更新；接收操作时缓冲区的数据已经完整，可以被正确引用。

非阻塞通信返回后并不意味着通信操作完成，需要用 `MPI_Wait` 或 `MPI_Test` 检测完成情况。

**通信模式**指缓冲管理，以及发送方和接收方之间的同步方式，共四种：

1. 同步（synchronous）
2. 缓冲（buffered）
3. 标准（standard）
4. 就绪（ready）

算一笔账：发送操作支持四种通信模式，配上阻塞、非阻塞两种机制，得到 $4 \times 2 = 8$ 种发送操作；接收操作只有阻塞接收和非阻塞接收两种。

**为什么要非阻塞**：一条三进程的流水线，每个进程从左边进程收一个数据、算一个新值、发给右边进程。阻塞通信下，通信没结束处理器只能干等，计算资源浪费。常见技术是让计算与通信重叠，非阻塞通信正是为此。

**双缓冲**是非阻塞通信中的常用方法：为 X 和 Y 各准备两个缓冲，接收进程往一个缓冲里放下一个 X 时，计算进程可以从另一个缓冲里读当前的 X。前提是确信缓冲中的数据在被更新之前已经用过。

### 群集通信

概念：群集通信（Collective Communications）是一个进程组中所有进程都参加的全局通信操作。

三个功能：

- 通信：完成组内数据的传输；
- 聚集：在通信的基础上对给定的数据完成一定的操作；
- 同步：实现组内所有进程在执行进度上取得一致。

按通信方向分三种：

- 一对多：一个进程向其他所有进程发消息，发送方叫 Root 进程；
- 多对一：一个进程从其他所有进程收消息，接收方叫 Root 进程；
- 多对多：每个进程都向其他所有进程发送或接收消息。

五个通信函数：

| 操作 | 方向 | 调用格式 | 要点 |
| --- | --- | --- | --- |
| 广播 Bcast | 一对多 | `MPI_Bcast(Address, Count, Datatype, Root, Comm)` | Root 把**相同**的消息发给通信域内所有进程。对 Root 来说三元组既是发送缓冲也是接收缓冲，对其他进程只是接收缓冲 |
| 收集 Gather | 多对一 | `MPI_Gather(SendAddress, SendCount, SendDatatype, RecvAddress, RecvCount, RecvDatatype, Root, Comm)` | Root 从所有进程（含自己）收消息，n 个消息按 rank 排序拼接存进 Root 的接收缓冲。非 Root 进程忽略接收缓冲 |
| 散播 Scatter | 一对多 | `MPI_Scatter(...同上...)` | Gather 的逆操作。Root 给每个进程（含自己）发一个**不同**的消息，n 个消息在 Root 发送缓冲里按 rank 有序存放。非 Root 进程忽略发送缓冲 |
| 全局收集 Allgather | 多对多 | `MPI_Allgather(SendAddress, SendCount, SendDatatype, RecvAddress, RecvCount, RecvDatatype, Comm)` | 相当于每个进程都作为 Root 执行了一次 Gather |
| 全局交换 Alltoall | 多对多 | `MPI_Alltoall(...同上...)` | 每个进程给所有进程（含自己）发一个消息，等价于每个进程作为 Root 执行了一次 Scatter |

区分 Bcast 和 Scatter 的一句话：广播发的是同一份数据，散播发的是切开的不同数据块。

### 聚集功能：归约和扫描

群集通信的聚集功能让 MPI 在通信的同时完成一定的处理操作，分三步实现：先把消息发到目标进程，再执行计算功能，最后把处理结果放入指定的接收缓冲区。

**归约** `MPI_Reduce(SendAddress, RecvAddress, Count, Datatype, Op, Root, Comm)`

- 对每个进程发送缓冲区中的数据按给定操作运算，最终结果存放在 Root 进程的接收缓冲区。
- 数据类型在 `Datatype` 域定义，归约操作由 `Op` 域定义。
- 归约操作可以是 MPI 预定义的，也可以是用户自定义的。
- 允许每个进程贡献向量值而不只是标量，向量长度由 `Count` 定义。

`MPI_Allreduce` 与 `MPI_Reduce` 的差别：前者所有进程都拿到结果，后者只有 Root 拿到。恒等式 `MPI_Allreduce = ReduceScatter + AllGather`，这种实现方式的特点是单链路通信量小、通信均衡无瓶颈，但大规模下性能较差。

MPI 预定义的归约操作（第 28 页表格）：

| 操作 | 含义 | 操作 | 含义 |
| --- | --- | --- | --- |
| `MPI_MAX` | 最大值 | `MPI_LOR` | 逻辑或 |
| `MPI_MIN` | 最小值 | `MPI_BOR` | 按位或 |
| `MPI_SUM` | 求和 | `MPI_LXOR` | 逻辑异或 |
| `MPI_PROD` | 求积 | `MPI_BXOR` | 按位异或 |
| `MPI_LAND` | 逻辑与 | `MPI_MAXLOC` | 最大值且相应位置 |
| `MPI_BAND` | 按位与 | `MPI_MINLOC` | 最小值且相应位置 |

**扫描** `MPI_scan(SendAddress, RecvAddress, Count, Datatype, Op, Comm)`

- 可以看作一种特殊的归约：每个进程都对排在它前面的进程做归约。
- 对进程 i，结果是对进程 $0, 1, \dots, i$ 的发送缓冲区数据做指定归约操作。
- 同样允许向量值。

以三进程、每进程三个元素、`Op=MPI_SUM` 为例（第 29 页）：

| 进程 | 扫描前发送缓冲 | 扫描后接收缓冲 |
| --- | --- | --- |
| P0 | A0, A1, A2 | A0, A1, A2 |
| P1 | B0, B1, B2 | A0+B0, A1+B1, A2+B2 |
| P2 | C0, C1, C2 | A0+B0+C0, A1+B1+C1, A2+B2+C2 |

注意归约是按"列"做的，也就是同下标的元素相加，不是把一个进程内部的三个数加起来。

### 同步：路障

`MPI_Barrier(Comm)`。通信域 Comm 中的所有进程相互同步，调用返回后可以保证组内所有进程都执行完了调用之前的所有操作。这是 MPI 目前支持的唯一同步操作。

## 2.5 集群架构

### 集群系统的优点

- 性能与价格比高
- 可扩展性
- 容错性能
- 支持异构的软件和硬件
- 支持串行、并行、工作流等不同类型的作业
- 有功能强大的机群管理系统（机群操作系统），具体实现如 LSF、SGE、PBS、Condor

最后一条要和并行计算环境（PVM、MPI）区分开：机群 OS 管的是"谁来跑、在哪跑"，并行计算环境管的是"跑起来之后进程之间怎么通信"。

### 分布式系统的模块

硬件：

- 主机：最多上万台主机、50 万核量级
- 共享存储：TB 到 PB 级
- 网络：以太网 1GB、光纤 20GB、Infiniband 40GB

软件：

- 操作系统：Unix、Linux、Windows Server
- 资源调度器：LSF、SGE、PBS
- 存储系统：NFS、Lustre、HDFS、S3、HBase、Dynamo
- 并行计算环境：MPI、PVM、Hadoop MapReduce
- 应用程序：数值模拟类（Fluent、LS-Dyna、VASP、WRF）、大数据类（Blast、AutoDoc、web 日志分析）

## 2.6 共享信息管理

### NIS

NIS（Network Information Service，网络信息服务）是一套用来管理电脑网络中所有与系统管理相关的设置档（用户账号、密码、主机名称、组群等）的主从式目录服务协议。

- 最早由 Sun 公司开发。推出时的旧名 Yellow Page（黄页）已被英国电信集团注册为商标，于是改名 NIS，但所有指令和函数仍以 `yp` 起首。
- 用户名和密码保存在 NIS 密码数据库后，可以在网络中任何一台运行 NIS 客户程序的机器上登录，整个网络看起来像一个独立系统。这就是**单点登录**。

NIS 提供的数据（服务器端文件）：

| 文件 | 内容 |
| --- | --- |
| `/etc/passwd` | 使用者账号、UID、GID、家目录、Shell |
| `/etc/group` | 群组数据、GID 对应、群组成员 |
| `/etc/hosts` | 主机名称与 IP 的对应，常用于私有 IP 的主机名对应 |
| `/etc/services` | 每种服务（daemons）对应的端口号 |
| `/etc/protocols` | 基础 TCP/IP 封包协议，如 TCP、UDP、ICMP |
| `/etc/netgroup` | 网络群组的定义与使用 |
| `/etc/rpc` | 每种 RPC 服务器对应的程序号码 |
| `/var/yp/ypservers` | NIS 服务器提供的数据库 |

### ZooKeeper

ZooKeeper 是一个开源的分布式的、为分布式应用提供协调服务的 Apache 项目。

从设计模式角度理解：它是一个基于观察者模式设计的分布式服务管理框架，负责存储和管理大家都关心的数据，接受观察者的注册，一旦数据状态发生变化就通知已注册的观察者做出反应。

功能定位：

- 配置信息、命名服务、分布式锁、集群信息
- 解决通用性、伸缩性和资源浪费问题
- 简单、高效、高可用

**分层命名空间**

- 基本单位是 Znode，类似 Unix 文件系统结构
- 每个 Znode 默认存储 1MB 数据
- 每个 Znode 都有唯一路径标识

**数据维护和更新**

- 短暂节点（Ephemeral）：会话失效后节点失效，不能有子节点
- 持久节点（Persistent）：会话结束后不失效
- 更新和监听（watch）：可以监听节点数据变化、监听子节点增减变化

**数据一致性管理**（这四条是必背项）

- 一个 Leader 和多个 Follower，总数为奇数
- 选主规则：大 ID 胜出、半数投票、先来后到
- Leader 负责协调数据更新，大多数 Server 更新成功即算成功
- 半数机制：半数以上 Server 存活即可用

**应用场景**

- 共享信息管理（地址、域名、服务与配置信息）
- 统一命名空间（用户自定义、一直更新）
- 分布式锁
- 监控节点状态变化

课件举的两个例子：保证"一个 HDFS 系统只有一个 NameNode"；把"某一个 DataNode 的状态更新为失效"通知出去。

## 2.7 集群资源管理

### 集群系统软件要解决的三个问题

1. **异构性**：廉价服务器通过网络连成集群，软硬件都是异构的。
2. **负载平衡（作业调度问题）**：系统负载有突发性，任务分布不均衡，机器的任务负载也不均衡。负载共享指调整系统负载在所有主机上的分布，提高处理能力和资源可用性。
3. **使用者的要求越来越多**：作业管理复杂（多种作业类型）、资源管理复杂（多种资源类型）、用户管理复杂（多用户群组、权限）。

### LSF

LSF（Load Sharing Facility）是 IBM 旗下的分布式集群管理系统软件，负责计算资源的管理和批处理作业的调度。它给用户提供统一的集群资源访问接口，让用户透明地访问整个集群资源，同时提供丰富的功能和可定制的策略，有良好的可伸缩性和高可用性，支持几乎所有主流操作系统。

主要功能六项：作业管理、作业执行机制、负载信息收集、作业调度、资源管理、用户管理。

**六个守护进程**（背下缩写和全称）：

| 缩写 | 全称 | 中文 |
| --- | --- | --- |
| `mbatchd` | master batch daemon | 主批处理守护进程 |
| `mbschd` | master batch scheduling daemon | 主批处理调度进程 |
| `sbatchd` | slave batch daemon | 从批处理守护进程 |
| `res` | remote execution service | 远程执行服务 |
| `lim` | load information manager | 负载信息管理器 |
| `pim` | process information manager | 进程信息管理器 |

**基本概念**

- 集群（Cluster）：一组运行 LSF 程序的计算机组合在一起工作，相互之间可以共享资源和负载。集群把异构的机器资源隐藏起来，给用户提供一个单一系统映像（Single-system Image）。分组方式有三种：同管理组主机（属于单一管理域的所有主机，类似 Kubernetes 命名空间）、物理或逻辑单元主机（同一文件服务器或子网）、功能相似主机（执行同类任务，如所有数据库节点）。
- 作业槽（Job Slot）：承载作业的单元。每台主机被配置成一定数量的作业槽，LSF 队列把作业发送到这些槽上。查询命令 `bhosts` 看每台主机或主机组的作业槽情况。
- 作业（Job）：在 LSF 系统中运行的工作单位，用一个 LSF 提交命令提交的一个工作。LSF 根据配置策略负责作业的调度、控制和监视。
- 提交主机：用于提交作业到集群的主机，客户机和服务器主机都可以充当。提交命令是 `bsub`。

提交示例：

```
bsub -n 12 -R "rusage[swp=50:duration=2h:decay=1, license=1:duration=2]" myjob
```

含义：使用 12 个计算资源；需求 50MB swap 空间、预约 2 小时；使用 1 个 license 2 分钟。

**作业状态**

| 状态 | 含义 |
| --- | --- |
| `PEND` | 在作业队列中等待调度和派发 |
| `RUN` | 派发到某主机并开始执行 |
| `DONE` | 正常结束，返回 0 |
| `EXITED` | 结束，返回非 0 |
| `PSUSP` | 在 PEND 阶段被挂起 |
| `USUSP` | 被用户挂起 |
| `SSUSP` | 被 LSF 系统挂起 |
| `POST_DONE` | 后处理结束，返回成功 |
| `POST_ERR` | 后处理结束，返回错误 |
| `WAIT` | 批处理作业的子作业等待运行 |

三种挂起状态的区别是挂起的发起方：P 是在排队阶段被挂起，U 是用户主动挂起，S 是系统挂起。

### LSF 作业生命周期（六步）

1. **提交**。用 `bsub` 从 LSF 客户端或服务器提交作业。没指定队列就进默认队列，等待调度时排在队列里处于 `PEND` 状态。如果配置文件 `lsb.params` 中定义了 `MAX_INFO_DIRS`，作业文件保存在 `LSF_SHAREDIR/cluster_name/logdir/info/` 或其子目录中。提交时 LSF 为每个作业分配唯一的作业 ID；还可以用 `bsub -J` 指定作业名，作业名不要求唯一。

2. **调度**。`mbatchd` 查看队列中的作业，把要调度的作业发给 `mbschd`。调度按预设时间间隔进行，间隔由 `lsb.params` 中的 `JOB_SCHEDULING_INTERVAL` 定义。`mbschd` 依据作业优先级、调度策略、可用资源三项评估作业并做决策，选出最佳主机后把决策送回 `mbatchd`。资源信息由主 `lim` 按预设间隔从各服务器主机的 `lim` 上收集，主 `lim` 传给 `mbatchd`，再传给 `mbschd`。

3. **分配**。`mbatchd` 收到调度决策后立即把作业分配给主机。

4. **运行**。`sbatchd` 从 `mbatchd` 接收请求，为作业创建一个子 `sbatchd`，创建执行环境，通过 `res` 启动作业。LSF 把执行环境从提交主机复制到执行主机，包括环境变量、工作目录、其他系统相关设置（UNIX 和 Linux 上是资源限制和 umask，Windows 上是桌面和 Windows 根目录）。作业在提交用户的账户下运行，状态为 `RUN`。

5. **返回结果**。作业顺利完成则标记 `DONE`，出错无法完成则标记 `EXIT`。`sbatchd` 把作业信息（含错误信息）和输出传给 `mbatchd`。

6. **发送邮件**。`mbatchd` 通过电子邮件把作业输出、作业错误和作业信息返回给提交主机。用 `bsub -o` 和 `-e` 可以把输出和错误写到文件。作业报告包含作业信息（CPU 使用、内存使用、提交账户名）、作业输出、错误。

### 调度策略

分类角度三个：

- 关于作业执行**顺序**：FCFS 等
- 关于作业执行**位置**：data aware scheduling（数据感知调度，对应 08 里的 Data Locality）
- 关于作业执行**时间**：截止时间调度、开始时间调度

调度目标和约束条件有两层，单个作业的执行效率和整个机群的执行效率，两者经常冲突。实际使用的调度策略往往是多个策略的组合，需要考虑冲突调解，并非所有策略都能协同工作。

## 典型题

**Q1. 阻塞通信和非阻塞通信的区别是什么？**

区别在于函数返回后资源是否可用。阻塞通信返回时通信操作已完成，缓冲区可以安全复用或读取；非阻塞通信返回时操作可能还没做完，必须用 `MPI_Wait` 或 `MPI_Test` 确认。用非阻塞是为了让计算和通信重叠，常配合双缓冲使用。

**Q2. MPI 一共有多少种发送操作、多少种接收操作？为什么？**

发送 8 种，接收 2 种。发送支持同步、缓冲、标准、就绪四种通信模式，每种模式各有阻塞和非阻塞两个版本， $4 \times 2 = 8$。接收不区分通信模式，只有阻塞接收和非阻塞接收。

**Q3. Broadcast、Scatter、Gather、Allgather、Alltoall 的关系。**

Bcast 是一对多发同一份；Scatter 是一对多发不同份；Gather 是 Scatter 的逆操作，多对一收集；Allgather 等价于每个进程都当一次 Gather 的 Root；Alltoall 等价于每个进程都当一次 Scatter 的 Root。

**Q4. ZooKeeper 为什么要求节点总数是奇数？**

因为它靠半数以上投票决定状态，半数以上存活才能提供服务。奇数台在同样的容错能力下最省机器：5 台和 6 台都只能容忍 2 台故障，6 台白费一台。

**Q5. 简述 LSF 中一个作业从提交到结束经历的过程。**

按六步答：`bsub` 提交进队列处于 PEND，`mbatchd` 把作业交给 `mbschd` 按优先级、策略、可用资源做调度决策（资源信息由 `lim` 收集），`mbatchd` 分配到主机，`sbatchd` 创建子进程和执行环境并通过 `res` 启动作业进入 RUN，结束后按返回码标记 DONE 或 EXIT，最后 `mbatchd` 把输出和作业信息邮件给提交主机。
