## 3.6 事务与并发控制

### 总览

事务规范了数据库操作的语义，每个事务使得数据库从一个一致的状态原子地转移到另一个一致的状态。

多个事务并发执行时，如果执行结果和按照某种顺序一个接一个串行执行的效果等同，这种隔离级别称为**可串行化**。可串行化是比较理想的情况，商业数据库为了性能往往定义多种隔离级别。

事务的并发控制一般通过锁机制实现，锁可以有不同的粒度：锁住行、锁住数据块、锁住整个表格。

互联网业务中读事务的比例往往远高于写事务，为了提高读事务性能，可以采用写时复制（COW）或多版本并发控制（MVCC）来避免写事务阻塞读事务。

### ACID 属性

**1. 原子性**

事务对数据的修改要么全都执行，要么全都不执行。例：从账户 A 转款项 a 到账户 B，结果必须是 A 扣 a 且 B 增 a，不能只改一个账户。

但原子性并不总能保证修改一定完成了或者一定没有进行。在 ATM 上转账，提交指令后通信中断或数据库主机异常，转账可能完成了也可能没有：如果中断发生前数据库主机完整接收到了指令且后续执行正常，转账成功；如果指令没到达主机，或到达了但后续执行异常（写操作日志失败、账户余额不足），转账没有进行。要确定结果，需要等通信或主机恢复后查询账户交易历史或余额。

原子性也体现在读取上：一个事务对同一数据项的多次读取，结果一定相同。

**2. 一致性**

事务需要保持数据库数据的正确性、完整性和一致性。有时由数据库内部规则保证（数据类型必须正确、数据值必须在规定范围内），有时由应用保证（银行账务余额不能是负数、信用卡消费不能超过信用额度）。

**3. 隔离性**

数据库需要保证每一个事务在它的修改全部完成之前对其他事务不可见，不能让其他事务看到中间状态。例：A 转款项 a 到 B，不能让其他事务（比如账户查询）看到 A 已扣 a 但 B 还没增 a 的状态。

代价是可能造成性能下降。

**4. 持久性**

事务完成后对数据库的影响是永久性的，即使系统出现各种异常也是如此。

### 四种隔离级别

SQL 定义了 4 种隔离级别，出于性能考虑允许使用者牺牲隔离属性换并发度：

1. **读未提交** Read Uncommitted（RU）：读取未提交的数据，即其他事务已经修改但还未提交的数据，最低的隔离级别。
2. **读提交** Read Committed（RC）：读取已提交的数据。但在一个事务中，对同一个项前后两次读取的结果可能不一样，比如第一次读时另一个事务的修改还没提交，第二次读时已经提交了。
3. **可重复读** Repeatable Read（RR）：在一个事务中，对同一个项确保前后两次读取的结果一样。
4. **可串行化** Serializable（S）：数据库的事务是可串行化执行的，就像一个事务执行时没有别的事务在执行，最高的隔离级别。

### 五种读写异常

| 异常 | 缩写 | 描述 |
| --- | --- | --- |
| 第一类丢失更新 | LU | 两个事务同时修改一个数据项，但后一个事务中途失败回滚，前一个事务已提交的修改都可能丢失 |
| 脏读 | DR | 一个事务读取了另一个事务更新却没有提交的数据项 |
| 不可重复读 | NRR | 一个事务对同一数据项的多次读取可能得到不同的结果 |
| 第二类丢失更新 | SLU | 两个并发事务同时读取和修改同一数据项，后面的修改可能使前面的修改失效 |
| 幻读 | PR | 事务执行过程中，前面的查询和后面的查询期间有另一个事务插入数据，后面的查询结果出现了前面结果中未出现的数据 |

课件给了两条结论：

- 所有的隔离级别都保证不会出现第一类丢失更新。
- 在最高隔离级别 Serializable 下，数据不会出现读写的不一致。

按这两条结论把对照表补全，标准的对应关系是：

| 隔离级别 | 第一类丢失更新 | 脏读 | 不可重复读 | 第二类丢失更新 | 幻读 |
| --- | --- | --- | --- | --- | --- |
| 读未提交 RU | 不会 | 可能 | 可能 | 可能 | 可能 |
| 读提交 RC | 不会 | 不会 | 可能 | 可能 | 可能 |
| 可重复读 RR | 不会 | 不会 | 不会 | 不会 | 可能 |
| 可串行化 S | 不会 | 不会 | 不会 | 不会 | 不会 |

区分不可重复读和幻读：前者是同一行读出来变了（被 UPDATE 或 DELETE），后者是多出来一行（被 INSERT）。区分两类丢失更新：第一类是回滚覆盖了别人已提交的修改，第二类是后写的覆盖了先写的（都没回滚）。

### 并发控制：数据库锁

事务分三类：读事务、写事务、读写混合事务。锁相应分两类：读锁和写锁。规则是允许对同一个元素加多个读锁，但只允许加一个写锁，且写事务将阻塞读事务。

这里的元素可以是一行、一个数据块甚至一个表格。事务只操作一行就对该行加锁；操作多行就需要锁住整个行范围。

**例子 1：无冲突**

T1 和 T2 操作不同行，初始 A=B=25，T1 将 A 加 100，T2 将 B 乘以 2。两个事务没有锁冲突，可以并行执行而不破坏一致性。

**例子 2：行范围加锁，T2 等待 T1**

T1 扫描从 A 到 C 的所有行，把结果相加后更新 A，初始 A=C=25。假设 T1 执行过程中 T2 插入一行 B，那么 T1 和 T2 无法做到可串行化。为了保证一致性，T1 执行范围扫描时需要锁住从 A 到 C 这个范围的所有更新；T2 插入 B 时整个范围被锁住，T2 获取锁失败而等待 T1 先执行完成。

这就是幻读要用范围锁（间隙锁）才能挡住的原因。

**例子 3：死锁**

T1 读取 A，然后将 A 的值加 100 后更新 B；T2 读取 B，然后将 B 的值乘以 2 更新 A。初始 A=B=25。T1 持有 A 的读锁、需要获取 B 的写锁，T2 持有 B 的读锁、需要 A 的写锁。两个事务循环依赖，任何一个都无法完成。

解决死锁的两种思路：

1. **超时回滚**：为每个事务设置一个超时时间，超时后自动回滚。其中一个事务回滚后另一个就能成功执行。
2. **死锁检测**：死锁的原因是事务之间互相依赖构成环路。检测到死锁后通过回滚其中某些事务来消除循环依赖。

### 写时复制 COW

互联网业务中读事务占比往往远超写事务，很多应用的读写比例达到 6:1 甚至 10:1。写时复制（Copy-On-Write）让读操作不用加锁，极大提高读取性能。

写时复制 B+ 树执行写操作的三步：

1. **拷贝**：将从叶子到根节点路径上的所有节点拷贝出来。
2. **修改**：对拷贝的节点执行修改。
3. **提交**：原子地切换根节点的指针，使之指向新的根节点。

读操作发生在第 3 步提交之前就读老节点的数据，否则读新节点，读操作不需要加锁保护。

COW 涉及引用计数：对每个节点维护一个引用计数表示被多少节点引用，引用计数变为 0 说明没有节点引用，可以被垃圾回收。

两个问题：每次写操作都需要拷贝从叶子到根节点路径上的所有节点，写操作成本高；多个写操作之间互斥，同一时刻只允许一个写操作。

### 多版本并发控制 MVCC

MVCC 对每行数据维护多个版本，无论事务的执行时间有多长，总是能提供与事务开始时刻相一致的数据。

以 MySQL InnoDB 为例，InnoDB 对每一行维护了两个隐含的列：一列存行被修改的"时间"，另一列存行被删除的"时间"。这里的"时间"指的是与时间对应的数据库系统版本号，并非绝对时间。每当一个事务开始，InnoDB 给这个事务分配一个递增的版本号，所以版本号也可以认为是事务号。对每行查询语句，InnoDB 把查询语句的版本号同遇到的行的版本号对比，再结合隔离级别决定是否返回该行。

四种语句的处理：

| 语句 | 处理方式 |
| --- | --- |
| `SELECT` | 只有同时满足两个条件的行才返回：行的修改版本号小于等于该事务号；行的删除版本号要么没被定义、要么大于事务的版本号 |
| `INSERT` | 新插入行的修改版本号更新为该事务的事务号 |
| `DELETE` | 直接把该行的删除版本号设置为当前事务号，相当于标记删除而不是物理删除 |
| `UPDATE` | 把原来的行复制一份，并把当前事务号作为该行的修改版本号 |

`SELECT` 两个条件的含义：如果行的修改或删除版本号大于事务号，说明这行是被该事务后面启动的事务修改或删除的。在可重复读隔离级别下，后开始的事务对数据的影响不应该被先开始的事务看见，所以要忽略。

MVCC 读取数据时不用加锁，每个查询通过版本检查只获得自己需要的数据版本，大大提高了并发度。代价是必须对每行存储额外的多个版本数据，而且存储引擎还必须定期删除不再需要的版本、及时回收空间。

### COW 与 MVCC 对比

| | 写时复制 COW | 多版本并发控制 MVCC |
| --- | --- | --- |
| 怎么让读不加锁 | 写操作在副本上改，提交时原子切换根指针 | 每行保留多个版本，读按版本号挑 |
| 写的开销 | 拷贝叶子到根的整条路径 | 每行多存两个隐含列和多个旧版本 |
| 写并发 | 互斥，同时只能一个写 | 多个写可以并发（靠行锁） |
| 垃圾回收 | 引用计数为 0 时回收节点 | 定期删除不再需要的版本 |
| 典型实现 | 写时复制 B+ 树 | MySQL InnoDB |

## 3.10 分布式协议

分布式系统涉及的协议很多：租约、复制协议、一致性协议。其中最有代表性的是两阶段提交协议和 Paxos 协议。

- **两阶段提交协议**用于保证跨多个节点操作的**原子性**：跨多个节点的操作要么在所有节点上全部执行成功，要么全部失败。
- **Paxos 协议**用于确保多个节点对某个投票（例如哪个节点为主节点）达成**一致**。

### ZooKeeper 的数据一致性管理

（和 03 里那节是同一份内容，这里放在协议的上下文里重复一遍便于对照）

- 一个 Leader 和多个 Follower，总数为奇数
- 大 ID 胜出、半数投票、先来后到
- Leader 负责协调数据更新，大多数 Server 更新成功即成功
- 半数机制：半数以上 Server 存活即可用

### 两阶段提交协议 2PC

2PC（Two-phase Commit）经常用来实现分布式事务。系统包含两类节点：

- **协调者**（coordinator）：通常一个系统中只有一个
- **事务参与者**（participants、cohorts 或 workers）：一般包含多个

协议假设：每个节点都会记录操作日志并持久化到非易失性存储介质，即使节点发生故障日志也不会丢失。

目的：实现分布式事务的原子性。

**两个阶段**：

- **阶段 1：请求阶段（Prepare Phase）**。协调者通知事务参与者准备提交或者取消事务，然后进入表决过程。参与者告知协调者自己的决策：同意（本地执行成功）或取消（本地执行失败）。
- **阶段 2：提交阶段（Commit Phase）**。协调者基于第一阶段的投票结果决策提交或取消。**当且仅当所有参与者同意提交**，协调者才通知所有参与者提交事务；否则通知所有参与者取消事务。参与者收到消息后执行相应操作。

**爬长城的例子**（课件的招牌例子，答题时可以直接用）：

A 组织 B、C、D 三人去爬长城。所有人都同意则活动举行，有一人不同意则取消。

1. A 是协调者，B、C、D 是参与者。
2. 准备阶段：A 发邮件给 B、C、D，提出下周三去爬山问是否同意，然后等回复。B、C 查日程发现当天没安排，回复同意。D 白天没看邮件，A、B、C 都得等。到晚上 D 看到邮件，查日程发现当天已有别的安排，回复取消。
3. 提交阶段：A 收到所有参与者的邮件，发现 D 不能去，于是通知 B、C、D 活动取消。

这个例子直接暴露了 2PC 的两个问题：

- **参与者迟迟不回复**：A、B、C 不得不一直等待，B 和 C 所持有的资源（下周三这个时段）一直不能释放。解法是引入事务超时机制，比如 A 告诉 D "晚上六点之前不回复活动就自动取消"。
- **协调者宕机**：假如 A 发完邮件后生病住院，即使 B、C、D 都同意，如果 A 没有备份，事务将被阻塞，三个人下周三都不能安排其他活动。

**两种故障的处理**：

| 故障 | 处理方法 |
| --- | --- |
| 事务参与者故障 | 给每个事务设置超时时间，某个参与者一直不响应，到达超时时间后整个事务失败 |
| 协调者故障 | 协调者把事务相关信息记录到操作日志并同步到备用协调者，故障时备用协调者接替完成后续工作。如果没有备用协调者且协调者永久故障，参与者将无法完成事务而一直等待 |

**主要缺陷**：

- 需要阻塞操作，某一个参与者延迟会导致所有人的等待延长。
- 容错性差。

结论：2PC 是阻塞协议，执行过程中需要锁住其他更新，且不能容错，大多数分布式存储系统都采用敬而远之的做法，放弃对分布式事务的支持。

### Paxos 协议

**要解决什么问题**

多个节点之间通过操作日志同步数据。如果只有一个节点为主节点，很容易确保多个节点之间操作日志的一致性。但主节点可能故障，系统需要选举出新的主节点，Paxos 就是用来实现这个需求的。只要保证了多个节点之间操作日志的一致性，就能在这些节点上构建高可用的全局服务，例如分布式锁服务、全局命名和配置服务。

问题在于：网络分区的时候，可能存在多个备节点提议（Proposer，提议者）自己成为主节点。Paxos 协议保证即使同时存在多个 proposer，所有节点最终也能达成一致，选举出唯一的主节点。

**分布式一致性问题的三句话定义**

- 一组节点对一个值达成认同（consensus）
- 这个值是由某一个节点提议的
- 当这个值被认同后，可以被其他节点学习

三个角色：Proposer（提议者）、Acceptor（接受者）、Learner（学习者）。

两个假设：异步网络，无拜占庭错误（不会有节点伪造信息）。

**快速路径（只有一个 proposer 时）**

大多数情况下系统只有一个 proposer，它的提议总是会很快被大多数节点接受，只需两步：

1. **批准（accept）**：Proposer 发送 accept 消息，含序号 `proposal n`，要求所有其他节点（acceptor）接受某个提议值，acceptor 可以接受或者拒绝。
2. **确认（acknowledge）**：如果超过一半的 acceptor 接受，意味着提议值已经生效，proposer 发送 acknowledge 消息通知所有 acceptor 提议生效。

**完整一轮（有多个 proposer 时）**

如果 proposer 第一次发起的 accept 请求没有被 acceptor 中的多数派批准（例如与其他 proposer 的提议冲突），就需要完整地执行一轮 Paxos：

1. **准备（prepare）**：Proposer 选择一个提议序号 $n$，给其他 acceptor 节点发送 prepare 消息。Acceptor 收到后，如果提议序号大于它已经回复的所有 prepare 消息的序号，则把自己上次接受的提议回复给 proposer，并承诺不再回复小于 $n$ 的提议。
2. **批准（accept）**：Proposer 收到多数派对 prepare 的回复后进入批准阶段。如果之前的 prepare 阶段有 acceptor 回复了上次接受的提议，那么 proposer 选择其中序号最大的提议值发给 acceptor 批准；否则 proposer 生成一个新的提议值发给 acceptor 批准。Acceptor 在不违背之前承诺的前提下接受这个请求。
3. **确认（acknowledge）**：如果超过一半的 acceptor 接受，提议值生效。Proposer 发送 acknowledge 消息通知所有 acceptor 提议生效。

**按阶段列的执行细则**（课件第 85 到 86 页，和上面是同一套流程的另一种写法）

Prepare 阶段：

- Proposer 发送 prepare 消息含序号 `proposal n*`
- Acceptor promise，只接收序号大的请求：
  - `n* < n_current`：不回复
  - `n* > n_current`：接受 `n*`，同时回复之前已接受的最大请求号

Accept 阶段：

- Proposer 接收到多数派 promise 消息之后
- 发送被承诺接受的最大请求号给 Acceptor 批准（accept 消息）
- 如未得到承诺接受的请求号，自己生成一个
- Acceptor 在不违背承诺的前提下接受请求
- Proposer 接收到多数 Acceptor 的接受消息后，发送 acknowledge 消息给所有人

**两阶段的一句话总结**

- 第一阶段 prepare：决定可能占优的 Proposer，是摸底阶段。
- 第二阶段 accept：第一步选出的可能 Proposer 进行提议，Acceptor 确认反馈意见，是实施阶段。
- 多数通过，快速朝向统一的意见发展。

**两个性质**

1. **正确性**：只有一个提议值会生效。Paxos 要求每个生效的提议被 acceptor 中的多数派接受，并且每个 acceptor 不会接受两个不同的提议，因此可以保证正确性。
2. **可终止性**：最后总会有一个提议值生效。Paxos **不能严格保证**可终止性。但从执行过程可以看出，只要超过一个 acceptor 接受了提议，proposer 很快就会发现并重新提议其中序号最大的提议值，因此随着协议不断运行，它会往"某个提议值被多数派接受并生效"这一最终目标靠拢。

节点出错场景下的三条结论：

- 不能保证可终止：有 $F$ 个故障节点时，需要 $2F+1$ 个节点才能保证 liveness。
- 一旦能够终止，能保证正确性和一致性：每个提议被多数 Acceptor 接受，每个 Acceptor 只接受一个提议。
- 快速朝向一致性方向靠拢。

### Paxos 与 2PC 对比（重点）

两个协议作用不同：

| | Paxos | 2PC |
| --- | --- | --- |
| 解决什么 | 同一个数据分片的多个副本之间的数据一致性 | 属于多个数据分片上的操作的原子性 |
| 典型场景 | 副本分布到不同数据中心时尤其需要 | 数据分片分布在不同服务器上，要么全成功要么全失败 |
| 是否阻塞 | 不阻塞，多数派即可推进 | 阻塞协议，一个参与者慢就拖住全部 |
| 容错 | 可以容忍少数派故障 | 协调者宕机就整体阻塞 |

Paxos 的两种用法：

1. 实现全局的锁服务或者命名和配置服务，例如 Google Chubby、Apache ZooKeeper。
2. 把用户数据复制到多个数据中心，例如 Google Megastore、Google Spanner。

2PC 最大的缺陷在于无法处理协调者宕机：协调者宕机后每个参与者可能都不知道事务应该提交还是回滚，整个协议被阻塞，执行过程中申请的资源都无法释放。

**常见的组合做法**：把 2PC 和 Paxos 结合起来。用 2PC 保证多个数据分片上操作的原子性，用 Paxos 实现同一个数据分片多个副本之间的一致性；另外用 Paxos 解决 2PC 的协调者宕机问题，协调者出故障时通过 Paxos 选举出新的协调者继续提供服务。

## 典型题

**Q1. 举例说明四种隔离级别下分别可能出现什么异常。**

RU 下什么都可能：事务 T1 把 A 从 25 改成 125 还没提交，T2 就读到了 125，这是脏读；T1 回滚后 T2 手里的 125 是废值。RC 挡住脏读，但 T2 两次读 A 可能分别读到 25 和 125（中间 T1 提交了），这是不可重复读。RR 挡住不可重复读，但 T2 两次范围查询之间 T1 插入了一行 B，第二次查出来多了一行，这是幻读。S 下全部挡住，代价是并发度最低。

**Q2. 死锁怎么产生、怎么解决？用课件的例子说明。**

T1 读 A（持 A 读锁），要把 A+100 写进 B（要 B 写锁）；T2 读 B（持 B 读锁），要把 B×2 写进 A（要 A 写锁）。两者互相等待形成环，都完不成。两种解法：给事务设超时时间，超时自动回滚，另一个就能跑完；或者做死锁检测，画出事务依赖图找环，回滚环上的某个事务打断依赖。

**Q3. COW 和 MVCC 都能让读不加锁，它们的区别是什么？**

COW 是结构上的：写的时候把叶子到根的整条路径复制一份、改副本、最后原子切换根指针，读到的要么是全旧要么是全新。它的代价是每次写都要复制一条路径，而且写之间互斥。MVCC 是数据上的：每行存多个版本并带修改、删除两个版本号，读事务拿自己的事务号去挑可见版本。它的写并发更好，代价是存储膨胀和需要定期清理旧版本。

**Q4. 2PC 和 Paxos 分别解决什么问题？为什么实际系统常常把两者结合？**

2PC 解决跨数据分片的原子性，Paxos 解决同一分片多副本的一致性，两者管的维度不一样。结合的原因是 2PC 自己有个致命伤：协调者宕机后所有参与者卡住、资源不释放。把协调者本身做成一个 Paxos 复制组，协调者挂了就用 Paxos 选出新的接着干，2PC 的阻塞问题就绕开了。Google Spanner 就是这个结构。

**Q5. Paxos 为什么不能保证可终止性？**

因为两个 proposer 可能互相打断：P1 完成 prepare(n=1)，P2 发起 prepare(n=2) 让 acceptor 承诺不再理会小于 2 的提议，P1 的 accept(1) 就被拒绝，P1 改用 n=3 重新 prepare，又把 P2 的 accept(2) 打掉，如此往复。理论上这个过程可以一直持续。实践中靠随机退避或选一个稳定的 leader（只让一个 proposer 发起提议）来避免。课件的结论是：有 $F$ 个故障节点就需要 $2F+1$ 个节点保证活性，而且一旦终止，正确性一定成立。
