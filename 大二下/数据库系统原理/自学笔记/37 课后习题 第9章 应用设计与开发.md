## 习题

### 9.1 Servlet 为什么比 CGI 快

题目：Java 程序一般比 C/C++ 程序跑得慢，可是用 Servlet 写的 Web 程序通常比用 CGI 写的性能更好。主要原因是什么？

思路：比较每处理一个请求要付出的额外开销：CGI 每次开进程，Servlet 只开线程。

解答：

- CGI 每来一个请求就启动一个新进程去处理。创建进程、装载程序、结束进程都要操作系统做大量工作，开销很大。
- Servlet 以线程的形式运行在一个已经存在的进程里，省掉了创建进程的开销。这个进程通常就是 Web 服务器进程本身，Web 服务器和 Servlet 之间也不需要进程间通信。
- 对中小规模的请求，Java 执行慢带来的损失小于省下的进程创建和通信开销，所以 Servlet 整体更快。
- 如果单个请求要做大量 CPU 计算，执行速度成了主要矛盾，这时用 C/C++ 写的 CGI 程序反而可能更快。

### 9.2 无连接协议的优缺点

题目：和保持连接的协议相比，无连接协议（如 HTTP）有哪些优点和缺点？

思路：优点看服务器能同时服务多少客户、能否分流和容错；缺点看每次请求重新建连接、重复发送会话信息的代价。

解答：

优点：

- 一台机器能同时维持的连接数有上限。无连接协议在请求处理完后立即断开，连接很快释放给别的客户，同一时间能服务的客户更多。
- 每个请求都是独立的，可以被转发到多台服务器中的任意一台，便于负载均衡。某台服务器宕机，后续请求交给其他服务器处理，客户基本察觉不到。

缺点：

- 每发一个请求都要重新建立连接，有额外时间开销。
- 服务器不记得客户，会话信息（如登录状态）每次都要随请求带上，通常放在 Cookie 或隐藏表单字段里。需要维护状态的应用因此比保持连接的协议慢。

### 9.3 把价格放在隐藏表单字段里

题目：某购物网站写得很粗心，把每件商品的价格作为隐藏表单变量放进发给顾客的网页里，顾客提交表单后，服务器直接用这个隐藏变量里的价格计算账单。这种做法有什么漏洞？（现实中真有顾客利用过这个漏洞。）

思路：隐藏字段只是不显示，内容完全在客户端手里，可以任意修改。

解答：

- 用户可以保存网页后修改 HTML 源码，或者用浏览器开发者工具、抓包工具改请求，把隐藏变量 `price` 改成任意值（比如 0.01），再提交订单。
- 服务器直接信任这个值来算账单，于是按用户改过的价格成交。
- 正确做法：隐藏字段里最多放商品编号，价格一律在服务器端按商品编号从数据库里重新查出来。

### 9.4 只检查会话、不检查权限

题目：另一个写得粗心的 Web 应用，其 Servlet 只检查是否存在有效会话（用户是否已登录），不检查该用户有没有权限访问这个页面，理由是指向该页面的链接只显示给有权限的用户。这样做有什么风险？（有高校招生网站出过这种事：考生登录后看到了无权查看的信息，后来被发现并被取消录取资格。）

思路：链接藏起来不等于页面受保护，知道 URL 的人登录后直接输入地址就能访问。

解答：

- 没有权限的用户可能通过别的途径得知这个页面的 URL，比如有权限的人转告、Web 代理服务器的日志、浏览器历史等。
- 他正常登录后，在地址栏直接输入该 URL。页面只检查"已登录"，于是把内容返回给他。
- 用 HTTP 的 `Referer` 头检查请求是否来自本站的合法页面，能挡住最简单的尝试。但 `Referer` 由浏览器填写，可以伪造，挡不住有意的攻击者。
- 根本办法是每个页面在服务器端都检查当前用户是否有权访问。

### 9.5 用缓存提高 Web 服务器性能

题目：列举三种利用缓存加快 Web 服务器处理速度的方法。

思路：请求处理的三段（连数据库、执行查询、生成页面）都可以缓存。

解答：缓存利用的是不同请求之间的共性。

1. 连接池：打开数据库连接很耗时。预先建好一批连接放在池里，每个请求从池里借一个用，用完归还，不必每次重新连接。
2. 查询结果缓存：把某个请求产生的查询结果缓存起来。以后同样的请求再来，或者别的请求产生了同样的查询，直接用缓存的结果，不再访问数据库。
3. 页面缓存：把最终生成的网页缓存起来，同样的请求再来时直接返回这个页面。

后两种缓存在底层数据被更新后要失效或刷新，否则会返回过期内容。

### 9.6 用 netstat 检查连接泄漏

题目：`netstat` 命令（Linux 和 Windows 都有）能列出机器上的活动网络连接。说明怎样用它检查某个网页是否没有关闭它打开的数据库连接，或在使用连接池时没有把连接还回池里。注意用了连接池时连接不会马上关闭。

思路：反复访问被测网页，观察到数据库端口的连接数是否最终稳定。

解答：

1. 在数据库服务器或应用服务器上运行 `netstat`，找出所有连到数据库所用机器和端口的连接。应用服务器和数据库服务器分开部署时，两边执行都可以。
2. 反复访问被测网页，可以用 JMeter 之类的工具自动生成大量访问。
3. 观察连接数。连接池会保留一定数量的连接，所以连接数先从 0 涨到某个值，这是正常的；过一段时间后应当不再增长。
4. 如果连接数一直随访问次数增长，就说明这个网页背后的代码没有关闭连接，或者没有把连接还给连接池。

### 9.7 测试 SQL 注入漏洞

题目：

- a. 提出一种方法，测试应用程序的文本输入是否存在 SQL 注入漏洞。
- b. 其他形式的输入会不会发生 SQL 注入？如果会，怎样测试？

思路：注入的根源是把用户输入直接拼进 SQL 字符串，单引号是最直接的探针。

解答：

a. 在应用每个表单的每个文本框里输入含单引号的字符串（如 `O'Brien`），看应用能否原样保存和显示这个值。如果保存的值不对，或者报了 SQL 语法错误，说明输入被直接拼进了 SQL，存在注入漏洞。

例如程序这样拼接查询：

```java
String query = "select * from instructor where name = '" + name + "'";
```

输入 `O'Brien` 时语句变成 `... where name = 'O'Brien'`，引号不配对，数据库报错。攻击者输入 `x' or '1'='1` 就能让条件恒真。用 `PreparedStatement` 传参可以避免：

```java
PreparedStatement ps = conn.prepareStatement(
        "select * from instructor where name = ?");
ps.setString(1, name);
ResultSet rs = ps.executeQuery();
```

b. 会。下拉菜单、单选按钮这类选择型输入，浏览器提交的值也可以被改掉：直接改网页源码、改浏览器里的 DOM 树，或者拦截请求后修改。测试工具应当能修改发往应用的参数值，在里面插入单引号；同时还要把 HTTP `Referer` 头伪造成合法值，绕过应用可能做的来源检查。

### 9.8 为什么加密属性上不能建索引

题目：为了安全，关系中某些属性的值可以加密存放。为什么数据库系统不支持在加密属性上建索引？据此解释为什么数据库系统不允许对主码属性加密。

思路：索引要靠值的比较来组织；加密后要么无法比较，要么同值同密文而泄露统计信息。

解答：

- 一般的加密方案里，同一个值每次加密结果不同，无法按密文建索引。
- 只有让同一个值总是加密成同一个密文，才能按密文建索引，而且只能支持等值查找（密文的大小顺序和原值无关，范围查询用不上）。但这样做有风险：攻击者不用解密，靠统计密文出现的频率就能猜出常见值。防止这种分析要在加密时掺入随机的"盐"，一掺盐索引就建不成了。
- 变通办法一：索引本身不加密。可是索引里存着属性值，等于把值泄露了。
- 变通办法二：索引也加密，数据库系统持有密钥，在用到索引时临时解密。这要改动数据库系统里大量代码，所以数据库一般不支持。

主码的原因：插入元组时数据库要检查主码是否重复。属性值按上面的方式加密后，系统无法判断两个值是否相等，也就查不出违反主码约束的情况。所以支持属性级加密的数据库不允许加密主码属性，外码属性同理（参照完整性检查也要做值的比较）。

### 9.9 整库加密为什么没有这些问题

题目：9.8 讨论的是只加密部分属性。有些数据库系统支持对整个数据库加密。说明整库加密时 9.8 中的问题是怎样避免的。

思路：整库加密只在磁盘读写这一层做加解密，内存里是明文。

解答：

- 整库加密时，数据从磁盘读入内存的时候解密，写回磁盘的时候加密。磁盘上的所有内容（包括索引）都是密文，内存里都是明文。
- 只有数据库系统最底层的数据存取层需要改动来做加解密，上面各层看到的都是明文，不用改。
- 因此索引照常使用，主码、外码约束照常检查，相关代码都不必修改。

### 9.10 冒充公司骗取证书

题目：假设有人冒充某公司，从证书颁发机构拿到了证书。这对"由被冒充公司认证的东西"（如订单、程序）有什么影响？对其他公司认证的东西呢？

思路：离线验证证书时不会去问颁发机构，所以错发的证书收不回来。

解答：

- 设 C 冒充公司 X，骗得颁发机构 A 为 C 的公钥签发了证书，证书上写的主体是 X。
- 用户 Y 验证这张证书时，只能确认它由 A 签发，于是相信其中的公钥属于 X。之后 C 用对应私钥签名的订单、程序，Y 都会当作 X 发出的来接受。Y 可能向 C 泄露机密、接受假订单、运行 C 签名的恶意程序，每种情况都会受害。
- 离线使用证书的最大问题是没法撤回。即使 A 事后发现了冒充，只要 Y 不主动去向 A 核实（协议并不要求核实），Y 就发现不了证书是假的。
- X 自己原有的证书和真正由 X 签发的东西不受影响，但接收方分不清哪些来自真 X、哪些来自 C。
- 其他公司认证的东西不受影响。例外是 X 本身也是一个证书颁发机构：C 可以用假证书继续签发下级证书，这条链上的证书都不可信，不在这条链上的证书仍然可信。

整理补充：实际系统用证书吊销列表（CRL）或在线状态查询（OCSP）来缓解"收不回"的问题，前提是验证方愿意联网检查。

### 9.11 安全存储口令

题目：数据库里最要紧的数据恐怕是控制访问的口令。设计一种安全存储口令的方案，要求系统仍能验证用户登录时输入的口令。

思路：只存加盐后的单向散列值，登录时用同样的盐算一遍再比较。

解答：

1. 每个用户注册时随机生成一串盐，把"口令 + 盐"用单向函数（安全散列函数）变换，存下变换结果和盐。盐的作用是防字典攻击：同样的口令因盐不同而得到不同结果，攻击者没法用一张预先算好的表批量破解。
2. 在用户 ID 上建散列索引，按 ID 快速取出盐和变换结果。
3. 登录时取出该用户的盐，对用户输入的口令做同样的变换，与存储的结果比较，相同则通过。

```sql
create table user_password (
    user_id  varchar(32) primary key,
    salt     char(32),
    pwd_hash char(64)
);
```

这个方案的好处是口令不以明文存放，系统里连"解密"的代码都不需要，所以可以直接用不可逆的散列函数。

官方答案举的单向函数是 SHA-1。（补充：SHA-1 现已被认为不够安全，而且通用散列算得太快，便于暴力穷举；现在存口令一般用 bcrypt、scrypt、Argon2、PBKDF2 这类专门设计得慢的算法。）
