几组判定方法后面反复用到，先集中列一次。

**锁的相容矩阵。** 共享锁 S 用于读，排他锁 X 用于写：

| | S | X |
|---|---|---|
| **S** | 相容 | 冲突 |
| **X** | 冲突 | 冲突 |

两个操作冲突，当且仅当它们要求的锁模式在矩阵里标的是冲突。判断冲突时看的是锁模式，不是操作名字，15.10 加了增量锁之后这条仍然管用。

**两阶段封锁及其变体。**

- 基本 2PL：每个事务分两个阶段，增长阶段只能加锁和升级，收缩阶段只能解锁和降级。第一次解锁的时刻之前，事务获得最后一个锁的那一点叫封锁点。
- 严格 2PL（strict）：所有排他锁持有到事务提交或中止之后才释放。别的事务读不到未提交的数据，调度无级联，因而也可恢复。
- 强 2PL（rigorous）：所有锁，包括共享锁，都持有到事务结束。
- 保守 2PL（conservative，也叫一次封锁法）：事务开始前一次性申请全部需要的锁，拿不全就等着，不持有任何锁地等。这样不会死锁，代价是要预先知道访问哪些数据项，而且锁持有时间最长。
- 锁转换：升级 upgrade（S 变 X）只能发生在增长阶段，降级 downgrade（X 变 S）只能发生在收缩阶段，否则就破坏了两阶段的形式。
- 2PL 保证冲突可串行化，但不保证无死锁，也不保证可恢复。

**树协议的加锁规则**（教材 15.1.5 节，只有排他锁）：

1. 事务的第一个锁可以加在任意结点上。
2. 此后要锁结点 $Q$，必须当前正持有 $Q$ 的父结点上的锁。
3. 任何时候都可以解锁。
4. 一个结点被某事务锁过又解锁之后，这个事务不能再锁它。

树协议保证冲突可串行化并且无死锁，但事务常常要锁上一些自己并不需要的结点（为了走到目标结点），而且它允许的调度和 2PL 允许的调度互不包含。

**时间戳排序的读写规则。** $TS(T_i)$ 是事务 $T_i$ 的时间戳，R-timestamp($Q$)、W-timestamp($Q$) 分别是成功读过、写过 $Q$ 的事务中最大的时间戳。

- $T_i$ 执行 read($Q$)：若 $TS(T_i) < \text{W-timestamp}(Q)$，说明 $T_i$ 要读的值已经被一个更新的事务覆盖了，读被拒绝， $T_i$ 回滚并以新时间戳重启；否则读成功，令 $\text{R-timestamp}(Q) = \max(\text{R-timestamp}(Q),\ TS(T_i))$。
- $T_i$ 执行 write($Q$)：若 $TS(T_i) < \text{R-timestamp}(Q)$，说明 $T_i$ 产生的值本该被某个更新的事务读到，而那个事务已经读了旧值，写被拒绝， $T_i$ 回滚；若 $TS(T_i) < \text{W-timestamp}(Q)$，说明 $T_i$ 写的是个过时的值，写被拒绝， $T_i$ 回滚；否则写成功，令 $\text{W-timestamp}(Q) = TS(T_i)$。
- Thomas 写规则：把上面第二种情况改成直接忽略这次写，事务继续执行。理由是这个过时的值刚写进去就会被已有的新值盖掉，任何事务都读不到它。放宽之后允许了一些视图可串行化但不冲突可串行化的调度。
- 时间戳排序等价的串行顺序就是时间戳顺序，无死锁，但调度不保证可恢复，被拒绝的事务还可能反复重启而饿死。

## 习题

### 15.1 两阶段封锁保证可串行化

题目：证明两阶段封锁协议保证冲突可串行化，并且各事务可以按它们的封锁点排序，得到一个等价的串行调度。

思路：反证。假设优先图有环，沿环比较各事务的封锁点时刻，推出矛盾。

解答：

- 记 $a_i$ 为 $T_i$ 获得最后一个锁的时刻，即 $T_i$ 的封锁点。
- 关键引理：若优先图中有边 $T_i \to T_j$，则 $a_i < a_j$。这条边说明存在一对冲突操作， $T_i$ 的那个在前。冲突意味着两个事务在同一数据项上要求的锁不相容，所以 $T_j$ 必须等 $T_i$ 释放这个锁之后才能加锁。 $T_i$ 释放锁说明它已经进入收缩阶段，即 $a_i$ 已经过去；而 $T_j$ 加这个锁发生在 $a_i$ 之后， $T_j$ 的封锁点又不早于它加这个锁的时刻，所以 $a_j > a_i$。
- 假设两阶段封锁产生了非冲突可串行化的调度，则优先图中有环。不妨设环为 $T_0 \to T_1 \to T_2 \to \cdots \to T_{n-1} \to T_0$。反复用上面的引理得到

$$a_0 < a_1 < a_2 < \cdots < a_{n-1} < a_0$$

- $a_0 < a_0$ 矛盾，所以这样的环不存在，优先图无环，调度冲突可串行化。
- 既然 $T_i \to T_j$ 蕴含 $a_i < a_j$，按封锁点从早到晚给事务排序就是优先图的一个拓扑序，这个顺序对应的串行调度与原调度冲突等价。
- 这个证明只用到"冲突操作要求不相容的锁"，没用到锁的具体模式，所以往相容矩阵里加新的锁模式（比如 15.10 的增量锁）之后结论照样成立。

### 15.2 给事务加锁指令并判断死锁

题目：给下面两个事务加上加锁和解锁指令，使它们遵守两阶段封锁协议。这两个事务的执行会不会产生死锁？

```
T31: read(A); read(B); if A = 0 then B := B + 1; write(B)
T32: read(B); read(A); if B = 0 then A := A + 1; write(A)
```

思路：只读的数据项加共享锁，要写的加排他锁；把所有加锁指令放在第一条解锁指令之前就满足 2PL。死锁看两个事务申请锁的顺序是否相反。

解答：

a. 加锁方案：

```
T31: lock-S(A)            T32: lock-S(B)
     read(A)                   read(B)
     lock-X(B)                 lock-X(A)
     read(B)                   read(A)
     if A = 0                  if B = 0
       then B := B + 1           then A := A + 1
     write(B)                  write(A)
     unlock(A)                 unlock(B)
     unlock(B)                 unlock(A)
```

$T_{31}$ 只读 $A$，加共享锁；要写 $B$，直接加排他锁。两条加锁指令都在第一条 `unlock` 之前，增长阶段和收缩阶段分得开，满足两阶段封锁。 $T_{32}$ 对称。

b. 会死锁。下面这个部分调度就卡住了：

| $T_{31}$ | $T_{32}$ |
|---|---|
| `lock-S(A)` | |
| | `lock-S(B)` |
| | `read(B)` |
| `read(A)` | |
| `lock-X(B)` | |
| | `lock-X(A)` |

$T_{31}$ 申请 $B$ 的排他锁，而 $T_{32}$ 持有 $B$ 的共享锁，S 与 X 不相容， $T_{31}$ 等待。 $T_{32}$ 申请 $A$ 的排他锁， $T_{31}$ 持有 $A$ 的共享锁， $T_{32}$ 也等待。等待图里 $T_{31} \to T_{32} \to T_{31}$ 成环，死锁，只能由系统选一个作牺牲者回滚。

补充几点：

- 死锁的根源是两个事务申请锁的顺序相反（一个先 $A$ 后 $B$，一个先 $B$ 后 $A$），和什么时候解锁无关。把上面的 `unlock` 全挪到提交之后（严格 2PL 或强 2PL），同样会死锁。
- 想避免死锁只能改申请顺序或改申请方式：用保守 2PL，事务开始时一次性申请 $A$、 $B$ 两把锁；或者规定所有事务一律按 $A$、 $B$ 的顺序加锁， $T_{32}$ 就要先 `lock-S(A)` 再 `lock-S(B)`。
- 也可以写成锁转换的形式： $T_{31}$ 先 `lock-S(B)` 读，要写时再 `upgrade(B)` 升级成排他锁。这样读的阶段并发度更高，但死锁反而更容易发生，因为两个事务可能都先拿到共享锁，然后互相等对方放锁才能升级。

（整理补充：答案 PDF 的 a 小问把两个事务写作 $T_{34}$、 $T_{35}$，b 小问又写作 $T_{31}$、 $T_{32}$，指的是同一对事务，教材正文用的是 $T_{31}$、 $T_{32}$，这里统一按后者。）

### 15.3 强两阶段封锁的好处

题目：强两阶段封锁（rigorous two-phase locking）能带来什么好处？它和其他形式的两阶段封锁相比如何？

思路：先分清三种 2PL 各自约束了什么，再看放宽或收紧带来的性质差别。

解答：

- 三者的区别只在解锁时机。基本 2PL 只要求加锁都在解锁之前；严格 2PL 额外要求排他锁持有到事务提交或中止之后；强 2PL 要求所有锁，共享锁也在内，都持有到事务结束。
- 严格 2PL 已有的好处，强 2PL 全有：排他锁持有到最后，别人读不到未提交的数据，调度是无级联的，也是可恢复的。
- 强 2PL 多出来的性质：两个冲突事务的提交顺序就是它们的可串行化顺序。因为冲突的两个事务在同一数据项上要求不相容的锁，先持锁的那个一直持有到提交，后者必须等它提交才能加锁，所以串行顺序在前的事务一定先提交。
- 这条性质在实际系统里有用。外部观察到的提交顺序和数据库内部的逻辑执行顺序一致，用户不会看到"先提交的事务在逻辑上反而排在后面"这种反直觉的现象；按提交顺序传播日志的复制、时间点恢复也因此好实现。
- 代价是共享锁也要持有到事务结束，锁持有时间比严格 2PL 更长，并发度低一些。
- 只满足基本 2PL 的调度虽然可串行化，但事务可以在提交前就放掉排他锁，别人读到未提交的值，一旦它回滚就要级联回滚，所以实际系统基本不用。
- 这题是历年卷的常客，答的时候三层递进的关系要写清楚：2PL 管可串行化，严格 2PL 管无级联，强 2PL 管提交顺序等于串行顺序。

### 15.4 插入哑结点提高树协议的并发度

题目：数据库组织成一棵有根树。假设在每一对父子结点之间插入一个哑结点，说明在新树上使用树协议比在原树上使用树协议能获得更好的并发度。

思路：树协议里锁子结点要求当前持有父结点的锁。等子结点的时候，父结点的锁就被扣着不放，哑结点的作用是把这个等待从父结点挪走。

解答：

- 原树上， $A$ 是 $B$ 的父结点。 $T_1$ 持有 $A$ 的锁并想锁 $B$，但 $B$ 被 $T_2$ 占着。按规则 $T_1$ 在拿到 $B$ 的锁之前不能释放 $A$，于是 $T_1$ 等 $T_2$ 的同时，把 $A$ 也扣住了。这时第三个事务 $T_3$ 想锁 $A$，只能跟着一起等，哪怕它要访问的是 $A$ 下面另一条完全无关的分支。
- 在 $A$ 和 $B$ 之间插入哑结点 $D$ 之后，树变成 $A \to D \to B$。 $T_1$ 持有 $A$ 的锁时先锁 $D$，这一步不会被 $T_2$ 挡住，拿到 $D$ 之后立刻释放 $A$，然后持有 $D$ 去等 $B$。 $T_3$ 马上就能锁住 $A$ 并往下走。
- 效果是等待被压到更低的层次上。事务等子结点时扣住的不再是真正的父结点，而是一个不存数据的哑结点，上层结点能更早放给别人。
- 正确性不受影响。哑结点不存任何数据，锁它不产生冲突，新树仍是一棵有根树，树协议在新树上照样保证冲突可串行化和无死锁。
- 代价是树变高了，每个事务从根走到叶要多加、多放几把锁，锁管理开销变大。哑结点插得越密，并发度越好，开销也越大。
- 这个思路的推广是给边加锁而不是给结点加锁，见 Buckley 和 Silberschatz 的 "Concurrency Control in Graph Protocols by Using Edge Locks"（ACM PODS，1984）。

### 15.5 树协议与 2PL 允许的调度互不包含

题目：举例说明存在树协议允许但 2PL 不允许的调度，也存在 2PL 允许但树协议不允许的调度。

思路：树协议允许解锁之后继续加锁，这是 2PL 禁止的；2PL 不管加锁对象之间有没有父子关系，这是树协议禁止的。各造一个调度即可。

解答：

数据库图取成一条链， $A$ 是根， $B$ 是 $A$ 的孩子， $C$ 是 $B$ 的孩子：

```
A
|
B
|
C
```

树协议允许但 2PL 不允许的调度：

| $T_1$ | $T_2$ |
|---|---|
| `lock(A)` | |
| `lock(B)` | |
| `unlock(A)` | |
| | `lock(A)` |
| `lock(C)` | |
| `unlock(B)` | |
| | `lock(B)` |
| | `unlock(A)` |
| | `unlock(B)` |
| `unlock(C)` | |

验证树协议： $T_1$ 第一个锁加在 $A$ 上（任意结点都可以），锁 $B$ 时持有父结点 $A$ 的锁，锁 $C$ 时持有父结点 $B$ 的锁，没有解锁后重新加锁，合法。 $T_2$ 第一个锁加在 $A$ 上，锁 $B$ 时持有 $A$ 的锁，合法。

违反 2PL： $T_1$ 在 `unlock(A)` 之后又执行了 `lock(C)`，收缩阶段里加锁。

2PL 允许但树协议不允许的调度：

| $T_1$ | $T_2$ |
|---|---|
| `lock(A)` | |
| | `lock(B)` |
| `lock(C)` | |
| | `unlock(B)` |
| `unlock(A)` | |
| `unlock(C)` | |

验证 2PL： $T_1$ 先加 $A$、 $C$ 两把锁，再依次解锁，两个阶段分得开。 $T_2$ 加一把锁再解锁，也合法。

违反树协议： $T_1$ 锁 $C$ 时并不持有 $C$ 的父结点 $B$ 的锁（ $B$ 在 $T_2$ 手里），而 $C$ 又不是 $T_1$ 的第一个锁。

结论是两个协议允许的调度集合互不包含。树协议放松了加锁解锁的先后次序，收紧了加锁的对象；2PL 正好相反。

### 15.6 允许共享锁的树协议

题目：考虑树协议的下述扩展，同时允许共享锁和排他锁：每个事务要么是只读事务，只申请共享锁，要么是更新事务，只申请排他锁；两类事务都遵守树协议的规则；只读事务的第一个锁可以加在任意结点上，更新事务的第一个锁必须加在根结点上。证明这个协议保证可串行化且无死锁。

思路：先看清"更新事务必须从根开始"这条限制在防什么，再看形式证明的骨架。

解答：

完整证明在 Kedem 和 Silberschatz 的 "Locking Protocols: From Exclusive to Shared Locks"（JACM 30:4，1983），原树协议的证明在 Silberschatz 和 Kedem 的 "Consistency in Hierarchical Database Systems"（JACM 27:1，1980）。下面先说明那条限制为什么不能去掉。

如果允许更新事务也从任意结点开始加锁，会出现非可串行化的执行。设数据图为 $a \to b \to c$：

1. 只读事务 $T_0$ 读 $a$，然后共享锁住 $b$ 并长时间持有。
2. 更新事务 $T_1$ 更新 $a$ 并提交。 $T_0$ 读 $a$ 在 $T_1$ 写 $a$ 之前，得到 $T_0 \to T_1$。
3. 只读事务 $T_2$ 读 $a$，读到的是 $T_1$ 写的值，得到 $T_1 \to T_2$。
4. $T_2$ 继续共享锁住 $b$ 和它的孩子 $c$，读 $c$ 并提交。共享锁之间相容，所以 $T_2$ 能和 $T_0$ 同时持有 $b$ 的锁，这在只有排他锁的原树协议里不可能发生， $T_2$ 就这样"越过"了还在 $b$ 上磨蹭的 $T_0$。
5. 更新事务 $T_3$ 更新 $c$ 并提交。 $T_2$ 读 $c$ 在 $T_3$ 写 $c$ 之前，得到 $T_2 \to T_3$。
6. 最后 $T_0$ 才共享锁住 $c$ 并读它，读到 $T_3$ 写的值，得到 $T_3 \to T_0$。

于是 $T_0 \to T_1 \to T_2 \to T_3 \to T_0$ 成环，不可串行化。直观地说，两个只读事务 $T_0$ 和 $T_2$ 对同一对更新事务 $T_1$、 $T_3$ 看到了相反的先后顺序。

要求更新事务必须从根开始就堵住了这条路。上例中 $T_3$ 想更新 $c$，必须先排他锁住根 $a$，再往下到 $b$，而 $b$ 还被 $T_0$ 共享锁着， $T_3$ 只能等。 $T_0$ 于是先锁到 $c$ 并读完，变成 $T_0 \to T_3$，环不再存在。

形式证明按调度中只读事务的个数 $k$ 归纳，要证明优先图中没有最小环 $T_0 \to T_1 \to \cdots \to T_{m-1} \to T_0$：

- 环中每个只读事务两侧必定都是更新事务，因为两个只读事务都只加共享锁，彼此不冲突，连不出边，所以 $m \ge 2k$。
- $k = 0$：全是更新事务，只有排他锁，协议退化成原来的树协议，已证明保证可串行化和无死锁。
- $k = 1$：把唯一的只读事务的共享锁看成排他锁，调度仍然符合原树协议（原树协议允许第一个锁加在任意结点），归结到上一种情况。
- $k > 1$：取环中一个只读事务 $T_i$，它两侧的 $T_{i-1}$、 $T_{i+1}$ 都是更新事务，且由 $m \ge 2k \ge 4$ 知 $T_{i-1}$ 和 $T_{i+1}$ 不是同一个事务。两个更新事务都锁过根结点，锁集必相交，而排他锁互不相容，所以它们之间一定有冲突，即 $T_{i-1} \to T_{i+1}$ 或 $T_{i+1} \to T_{i-1}$。前者说明 $T_i$ 可以从环里删掉，后者说明存在一个更短的环，两种情况都与"最小环"矛盾。

无死锁看等待图：更新事务之间， $T_j$ 等 $T_i$ 说明 $T_i$ 比 $T_j$ 更早锁住根结点；更新事务等只读事务、只读事务又只能等更新事务（共享锁只会被排他锁挡住），传递下来仍然是先锁根的排在前面。所以老的更新事务不会直接或间接地等年轻的更新事务，等待图无环。

（整理补充： $m \ge 2k$ 这一步官方答案只给了结论，理由是只读事务之间不产生冲突边，环里的只读事务必须被更新事务隔开。）

### 15.7 有向无环图上的多数父结点协议

题目：考虑下面这个只有排他锁的封锁协议，作用在有根有向无环图形式的数据图上：事务的第一个锁可以加在任意顶点上；此后要锁某个顶点，必须持有该顶点半数以上父结点的锁。证明该协议保证可串行化且无死锁。

思路：证明的关键是一条引理，两个事务共同锁过的顶点里层次最浅的那个，一定是其中某个事务加的第一把锁。

解答：

完整证明在 Kedem 和 Silberschatz 的 "Controlling Concurrency Using Locking Protocols"（IEEE FOCS，1979），推导相当繁琐，这里只记关键部分。

记号：

- $L(T_i)$ 是 $T_i$ 锁过的顶点集合， $E(T_i)$ 是 $T_i$ 锁的第一个顶点。
- $h: V \to \{1, 2, 3, \dots\}$ 是层次函数，图中有边 $\langle u, w \rangle$ 就有 $h(u) < h(w)$。有向无环图一定存在这样的函数（拓扑排序）。
- $F(T_i, T_j)$ 是 $L(T_i) \cap L(T_j)$ 中使 $h$ 最小的那个顶点。

引理 1：若 $L(T_i) \cap L(T_j) \neq \varnothing$，则 $F(T_i, T_j) \in \{E(T_i), E(T_j)\}$。

证明思路：反设 $v = F(T_i, T_j)$ 既不是 $T_i$ 的第一个锁也不是 $T_j$ 的第一个锁。那么两个事务都是按第二条规则锁住 $v$ 的，各自持有 $v$ 的半数以上父结点的锁。同一个父结点集合的两个"半数以上"的子集必定相交，于是存在一个父结点同时属于 $L(T_i)$ 和 $L(T_j)$，而父结点的 $h$ 比 $v$ 小，与 $v$ 使 $h$ 最小矛盾。

引理 2： $T_i$ 和 $T_j$ 在它们共同锁过的每个顶点上的先后关系都一致，都由 $F(T_i, T_j)$ 上的先后决定。也就是说，一对事务之间的冲突方向是唯一的，不可能在一个顶点上 $T_i$ 在前、在另一个顶点上 $T_j$ 在前。证明对 $h$ 归纳，用的正是引理 1 给出的"共同顶点必有共同的更浅祖先"这一性质。

有了引理 2，长度为 2 的环立刻被排除。更长的最小环 $T_0 \to T_1 \to \cdots \to T_{m-1} \to T_0$ 分两种情况讨论：

- 各个 $F(T_i, T_{i+1})$ 不全相异，说明某三个事务的锁集有公共顶点，于是环上可以抄近路，环不是最小的。
- 各个 $F(T_i, T_{i+1})$ 互不相同，那么沿环走一圈， $h(F(T_i, T_{i+1}))$ 不可能一直增大，必定存在某个 $i$ 使 $h(F(T_i, T_{i+1})) < h(F(T_{i+1}, T_{i+2}))$ 且 $h(F(T_{i+1}, T_{i+2})) > h(F(T_{i+2}, T_{i+3}))$。由前一个不等式知 $F(T_{i+1}, T_{i+2}) \neq E(T_{i+1})$，由后一个知 $F(T_{i+1}, T_{i+2}) \neq E(T_{i+2})$，与引理 1 矛盾。

所以优先图无环，协议保证可串行化，同样的论证用在等待图上给出无死锁。

考试不会考这个证明，记住协议的两条规则和"两个半数以上的子集必定相交"这一步就够了。

### 15.8 有向无环图上的全访问父结点协议

题目：考虑另一个只有排他锁、作用在有根有向无环图上的封锁协议：事务的第一个锁可以加在任意顶点上；此后要锁某个顶点，必须已经访问过该顶点的全部父结点，并且当前持有其中至少一个父结点的锁。证明该协议保证可串行化且无死锁。

思路：和 15.7 一样，先验证引理 1 成立，后面的推导可以照搬。

解答：

- 完整证明在 Silberschatz 和 Kedem 的 "A Family of Locking Protocols for Database Systems that Are Modeled by Directed Graphs"（IEEE Trans. on Software Engineering，SE-8:6，1982），过程比 15.7 更复杂，答案 PDF 没有展开。
- 这里"访问过"指的是曾经锁过。于是两个事务都锁住同一个非起始顶点 $v$ 时，它们各自都锁过 $v$ 的全部父结点， $v$ 的所有父结点都落在 $L(T_i) \cap L(T_j)$ 里，而父结点的 $h$ 更小。这正好说明 15.7 里的引理 1 在这个协议下同样成立：两个事务共同锁过的最浅顶点必是其中一方的第一把锁。
- 引理 1 成立之后，15.7 的引理 2 和最小环的讨论可以原样搬过来，可串行化和无死锁都随之得到。两个协议的证明共用同一套骨架，区别只在怎样论证引理 1。
- 两个协议的取舍：本题的规则要求锁过全部父结点，加的锁更多；15.7 的规则只要求半数以上，但要求同时持有这半数以上的锁。前者持锁少、加锁多，后者持锁多、加锁少，哪个并发度高取决于图的形状。

### 15.9 用页访问保护机制实现封锁

题目：持久化程序设计语言里不显式写加锁语句，对象（或者说对象所在的页）在被访问时才需要被锁住。现代操作系统允许设置页的访问权限（不可访问、只读、可读写），违反权限的内存访问会触发保护异常，例如 UNIX 的 `mprotect`。说明怎样用这套访问保护机制实现页级封锁。

思路：把"第一次访问某页"变成一次可以捕获的异常，在异常处理程序里申请锁，申请到再放宽该页的权限并重试那条指令。

解答：

读的处理：

1. 事务开始时用 `mprotect` 把所有相关页的权限设成不可访问。
2. 进程访问某页中的地址时触发保护异常。
3. 异常处理程序从出错地址算出是哪一页，向锁管理器申请这一页的共享锁，必要时等待。
4. 拿到锁后用 `mprotect` 把该页改成可读，从异常处理程序返回，重新执行刚才那条访问指令，这次正常完成。
5. 该页以后的读不再触发异常，也就没有额外开销。

写的处理完全类似：拿到共享锁之后页的权限只放到可读，第一次写这一页会再触发一次保护异常，处理程序这时申请排他锁，拿到后把权限放到可读写，再返回重试。

事务结束释放锁时，把这些页的权限重新设回不可访问，下次访问才会重新走一遍申请流程。

这样应用代码里一条加锁语句都没有，加锁完全藏在异常处理里，程序员看到的只是普通的对象访问。代价有两条：每页每种访问模式第一次都要付一次保护异常的开销；封锁粒度被硬件页大小定死，同一页上两个互不相干的对象会产生假冲突。

（整理补充：官方答案只写了读的流程，说写的处理"类似"。实际上写要多一层，先设成只读拿共享锁、再设成可写拿排他锁，这一步是这套机制能区分读锁和写锁的关键，所以上面写全了。）

### 15.10 增量锁模式

题目：数据库系统除 read 和 write 外还支持原子的增量操作。设 $X$ 的当前值为 $V$，`increment(X) by C` 把 $X$ 的值原子地置为 $V + C$；除非事务另外执行 read($X$)，否则它看不到 $X$ 的值。锁的相容矩阵里有共享模式 S、排他模式 X 和增量模式 I：

| | S | X | I |
|---|---|---|---|
| **S** | 相容 | 冲突 | 冲突 |
| **X** | 冲突 | 冲突 | 冲突 |
| **I** | 冲突 | 冲突 | 相容 |

- a. 证明如果所有事务都按相应模式给访问的数据加锁，两阶段封锁保证可串行化。
- b. 说明增量模式的引入提高了并发度。

思路：a 只要说明"两个增量操作可以交换"，让它们像两个读一样不算冲突，剩下的照搬 15.1。b 举一个大量事务只做加减的场景。

解答：

a.

- 两个事务同时在 $X$ 上持有 I 锁时，它们的增量操作可以交换先后：加法可交换，交换之后 $X$ 的最终值不变；而且增量操作不把 $X$ 的值返回给事务，事务读不到中间结果，交换也不会改变任何事务看到的值。所以一对增量操作不构成冲突，地位和一对 read 一样。
- 于是冲突的定义仍然是"两个操作要求的锁模式不相容"，也就是矩阵里标冲突的那些组合：S 与 X、X 与 X、S 与 I、X 与 I。
- 接下来的论证和 15.1 一字不差：任何一对冲突操作都要求两个事务在同一数据项上持有不相容的锁，先做的那个事务的封锁点必在后者之前；优先图若有环则得到 $a_0 < a_1 < \cdots < a_0$，矛盾。所以调度冲突可串行化，而且按封锁点排序就是一个等价的串行顺序。

b.

- I 与 I 相容，多个只做增量的事务可以同时持有同一数据项的锁并发推进。教材里的例子是银行的支票结算，大量事务往同一个账户或同一个分行的总额上加减金额，从不需要读出当前值。
- 没有 I 模式时，每次增量都要申请排他锁，而 X 与 X 不相容，这些本可以并行的事务只能一个接一个排队，锁等待时间变长，整个调度的推进速度被拖慢。
- 一般规律是相容矩阵里相容的格子越多并发度越高，吞吐量越好，前提是新增的相容项确实对应一对可交换的操作，否则可串行化就保不住了。
- 增量锁的限制也在这里：事务想读出 $X$ 的值必须另外申请 S 锁，而 S 与 I 不相容，得做锁转换；只有加减这类可交换的操作能享受这个待遇。

### 15.11 W-timestamp 的两种定义

题目：在时间戳排序协议中，W-timestamp($Q$) 定义为成功执行 write($Q$) 的所有事务中最大的时间戳。如果改成定义为最近一个成功执行 write($Q$) 的事务的时间戳，会有区别吗？

思路：看写规则允许哪些写成功，判断 W-timestamp 是不是单调增。

解答：

- 基本时间戳排序下没有区别。写规则要求 $TS(T_i) \ge \text{W-timestamp}(Q)$ 时写才成功，否则 $T_i$ 回滚。所以每一次成功的写都不会让 W-timestamp($Q$) 变小，它随时间单调不减。
- 既然单调不减，"最近一个写成功的事务"的时间戳就是"所有写成功的事务中最大的"那个，两种定义给出同一个值。
- 题目给出的写协议本身保证了最近一个写某数据项的事务也正是写过它的事务中时间戳最大的那个。

（整理补充：官方答案只有"没有区别"一句。用了 Thomas 写规则时这句话要加限定。该规则下 $TS(T_i) < \text{W-timestamp}(Q)$ 的写不再导致回滚，而是被直接忽略，事务继续往下走。这种被忽略的写不算"成功执行了 write($Q$)"，绝不能拿它的时间戳去更新 W-timestamp($Q$)。举例：W-timestamp($Q$) 已是 $5$， $T_3$ 的写被忽略；若据此把 W-timestamp($Q$) 改成 $3$，后来时间戳为 $4$ 的事务写 $Q$ 就会通过检查，把 $T_5$ 写的值覆盖掉，可串行性被破坏。所以两种定义在 Thomas 写规则下并不等价，必须按"写成功"理解，写被忽略时不动 W-timestamp。）

### 15.12 多粒度封锁与单一粒度的锁数量

题目：多粒度封锁有时比只有单一封锁粒度的系统需要更多的锁，有时更少。各举一个例子，并比较两者允许的并发度。

思路：拿"扫描整个关系"和"只改一个元组"两种事务分别算一下两种方案各要几把锁。

解答：

先回忆多粒度协议。数据被组织成层次：数据库 → 区域 → 关系 → 元组。锁模式有 IS、IX、S、SIX、X。规则是：第一个锁加在根上；要给某结点加 S 或 IS，父结点必须已被该事务以 IX 或 IS 模式锁住；要加 X、SIX 或 IX，父结点必须已被 IX 或 SIX 锁住；整个事务必须两阶段；解锁自底向上进行。

- 多粒度用锁更少的情形：事务要扫描整个关系 $r$， $r$ 有 $n$ 个元组。单一粒度取元组级时要加 $n$ 把锁；多粒度只要在数据库上加 IS、区域上加 IS、 $r$ 上加 S，一共 3 把。 $n$ 很大时差距悬殊，锁表的空间和加解锁的 CPU 开销都省下来了。
- 多粒度用锁更多的情形：事务只更新一个元组。单一粒度取元组级时 1 把 X 锁就够；多粒度要沿路径加 IX（数据库）、IX（区域）、IX（ $r$），再给元组加 X，一共 4 把。
- 并发度的比较分三种情况看：
  - 单一粒度取得细（元组级）时并发度最高，但大事务的锁开销大到无法接受。
  - 单一粒度取得粗（关系级）时锁少，但两个只改一行的事务也会互相阻塞，并发度很差。
  - 多粒度让每个事务自己挑合适的层次，大事务锁粗结点、小事务锁细结点，兼顾了两头。相对元组级单一粒度，它在大事务身上损失了并发度（一个事务在 $r$ 上加了 S，别的事务就不能再在 $r$ 内加 IX 改元组，哪怕改的是完全不相干的行）；相对关系级单一粒度，它把小事务的并发度救了回来。意向锁本身的维护是额外成本。

（整理补充：官方答案只有两句话，说多粒度方案里数据项一起加锁、一起解锁，锁开销低但并发度也降低，既没有给出题目要求的两个例子，也没有说清降低是相对于哪一种单一粒度。上面按题意补全。）

### 15.13 验证协议的时间戳该取哪个时刻

题目：在 15.5 节基于有效性检查的并发控制中，说明把 Validation($T_i$) 而不是 Start($T_i$) 取作事务 $T_i$ 的时间戳，在事务间冲突率确实很低的前提下能得到更好的响应时间。

思路：写出验证条件，看两种取法各自把串行顺序钉死在什么上面。

解答：

- 验证协议把事务分成读阶段、验证阶段、写阶段三段，对应三个时刻 Start($T_i$)、Validation($T_i$)、Finish($T_i$)。取 $TS(T_i) = \text{Validation}(T_i)$ 时， $T_i$ 通过验证的条件是：对所有 $TS(T_k) < TS(T_i)$ 的事务 $T_k$，下面两条之一成立：
  1. $\text{Finish}(T_k) < \text{Start}(T_i)$， $T_k$ 在 $T_i$ 开始之前就全部做完了；
  2. $\text{Start}(T_i) < \text{Finish}(T_k) < \text{Validation}(T_i)$，并且 $T_k$ 的写集合与 $T_i$ 的读集合不相交。
- 取 Start($T_i$) 当时间戳，等于要求"先开始的必须排在前面"，串行顺序被事务开始的先后钉死。一个开始得早、执行得慢的事务，会逼着所有比它晚开始却早早做完的事务都排在它后面，这些事务只要读过它写的数据就验证不过，只能回滚重做，哪怕它们实际执行时并没有真正的冲突。
- 取 Validation($T_i$) 当时间戳，串行顺序按进入验证阶段的先后来定，这正是事务实际完成的顺序，只有真正发生了读写冲突的事务才会验证失败。
- 所以用 Start($T_i$) 允许的调度集合是用 Validation($T_i$) 允许的调度集合的子集，后者限制更松，不必要的回滚更少，响应时间更好。
- 冲突率低是这个结论的前提。验证协议本身就假定冲突很少，此时回滚基本都是被过严的排序规则逼出来的，换成 Validation 取法正好消掉这部分浪费；争用激烈时两种取法都会大量回滚，验证协议本身就不适用了。

### 15.14 各并发控制协议的适用场合

题目：对下面每种协议，说明实际应用中哪些特点会让你选择它，哪些特点会让你避开它：两阶段封锁；带多粒度封锁的两阶段封锁；树协议；时间戳排序；有效性检查（验证）；多版本时间戳排序；多版本两阶段封锁。

思路：每种协议抓两条，一条是它解决了什么问题，一条是它把代价转嫁到哪里。

解答：

| 协议 | 适合 | 不适合 |
|---|---|---|
| 两阶段封锁 | 单一封锁粒度够用的一般应用 | 有大的只读事务（多版本协议更好）；必须杜绝死锁（树协议更好） |
| 2PL + 多粒度封锁 | 负载混杂，一部分事务访问单条记录，一部分访问整个关系或其大部分 | 2PL 的缺点它一样有 |
| 树协议 | 所有应用访问数据的次序都符合某个固定的偏序 | 事务常要锁上自己并不需要的结点；数据没有天然的树形访问次序时用不了 |
| 时间戳排序 | 要求执行结果等价于某个特定的串行顺序（比如事务到达的顺序），而不是任意串行顺序 | 冲突靠回滚而不是等待来解决；调度不可恢复，要做成可恢复的得付额外开销和响应时间；有长只读事务时它们会被反复回滚而饿死。无死锁 |
| 验证（有效性检查） | 两个并发事务发生冲突的概率很低 | 争用激烈时大量工作白做 |
| 多版本时间戳排序 | 时间戳排序本来就合适，同时希望读请求永不等待 | 时间戳排序的其他缺点它都有 |
| 多版本两阶段封锁 | 有大量只读事务，希望它们永不等待、总能提交；更新事务走 2PL，冲突靠等待解决，调度可恢复 | 死锁又回来了（只读事务不会卷进去）；多版本要额外的空间和时间开销，冲突本来就少时普通 2PL 更划算 |

几点补充说明：

- 时间戳排序里长只读事务饿死的原因是它的时间戳很旧，随便一个新事务写了它要读的数据，它的读就会被拒绝而回滚，重启之后又赶不上，见 15.16。
- 多版本两阶段封锁给只读事务分配的是"读一个一致快照"的语义，它们不申请锁、不参与死锁，这是它相对普通 2PL 最主要的好处。
- 选型的主线是：冲突多就用封锁（冲突靠等待解决），冲突少就用验证（冲突靠回滚解决），读多写少就加多版本（读不等待）。

### 15.15 先不加锁跑一遍再用严格 2PL 重跑

题目：解释下面的事务执行方式为什么可能比直接用严格两阶段封锁性能更好：先像基于验证的技术那样，不申请任何锁、也不向数据库写任何东西地把事务执行一遍，但既不做验证也不写数据库；然后用严格两阶段封锁把这个事务重新执行一遍。（提示：考虑对磁盘 I/O 的等待。）

思路：把事务的等待拆成等磁盘和等锁两类，看这个做法把两类等待分别放到了哪个阶段。

解答：

- 事务的等待有两个来源：磁盘 I/O 和获取锁。写一般不等，因为缓冲管理器异步写盘，事务只改内存中的副本；真正要等的是读。
- 第一遍执行不加锁、不写库，把事务需要而缓冲区里还没有的数据块全部从磁盘读进来。几乎所有磁盘读等待都发生在这个阶段，而这时事务一把锁都没持有。
- 第二遍用严格 2PL 重新执行。需要的数据基本都在内存里了，这一阶段几乎不做磁盘 I/O，等待时间几乎全花在申请锁上。
- 好处一是锁持有时间大幅缩短。持锁期间不再夹着磁盘 I/O 的等待，别的事务排队等锁的时间跟着变短，并发度提高。
- 好处二是磁盘吞吐量可能提高。直接用严格 2PL 时常出现这种局面：事务在等锁，磁盘空着，还有数据块没读进来，磁盘带宽白白浪费。新做法里第一遍读盘不需要任何锁，磁盘可以一直有活干。
- 适用条件是事务的计算量小、时间主要花在磁盘 I/O 和等锁上，这正是磁盘驻留数据库的常态。事务计算密集时，重新执行一遍就是白做功。
- 一个优化：第一遍把更新结果存进一个临时缓冲区，第二遍不重新执行整个事务，只在拿到锁之后把各数据项的当前值和第一遍读到的值逐个比较。全都相同就直接把缓冲的更新写进数据库，有不同才重新执行事务。
- 少数情况下第二遍仍要等 I/O：第二遍开始之前，缓冲管理器把某个需要的块换出了内存。

（更正：官方答案这一句写作"a disk block that the transaction needs is flushed to memory"，按上下文应是从内存中换出（flushed out of memory），写进内存不会造成任何等待。）

### 15.16 时间戳检查失败引起的级联中止与活锁

题目：考虑时间戳排序协议，两个事务，一个写数据项 $p$ 和 $q$，另一个读这两个数据项。给出一个调度，使得某个写操作的时间戳检查失败、第一个事务被回滚，并进而引起另一个事务的级联中止。说明这怎样导致两个事务都饿死。（这种情形称为活锁。）

思路：让读事务插在两个写操作中间，把 $q$ 的 R-timestamp 抬高，回头卡住写事务对 $q$ 的写。

解答：

调度如下，设 $TS(T_1) < TS(T_2)$：

| $T_1$ | $T_2$ |
|---|---|
| `write(p)` | |
| | `read(p)` |
| | `read(q)` |
| `write(q)` | |

逐步检查，设 $p$、 $q$ 的两个时间戳初值都是 $0$：

1. $T_1$ 的 `write(p)`： $TS(T_1)$ 既不小于 R-timestamp($p$) 也不小于 W-timestamp($p$)，写成功， $\text{W-timestamp}(p) = TS(T_1)$。
2. $T_2$ 的 `read(p)`： $TS(T_2) > \text{W-timestamp}(p) = TS(T_1)$，读成功， $\text{R-timestamp}(p) = TS(T_2)$。注意 $T_2$ 读到的是 $T_1$ 尚未提交的值。
3. $T_2$ 的 `read(q)`： $q$ 还没被写过，读成功， $\text{R-timestamp}(q) = TS(T_2)$。
4. $T_1$ 的 `write(q)`：检查发现 $TS(T_1) < \text{R-timestamp}(q) = TS(T_2)$。意思是一个比 $T_1$ 新的事务已经读走了 $q$ 的旧值，而 $T_1$ 现在才要写 $q$，这个写来晚了。写被拒绝， $T_1$ 回滚。
5. $T_1$ 回滚使它写进 $p$ 的值作废，而 $T_2$ 已经读了这个值， $T_2$ 只能跟着中止。时间戳排序本身不保证可恢复，这种级联中止正是它的代价。

两个事务都以新的时间戳重启， $T_1$ 先重启所以仍有 $TS'(T_1) < TS'(T_2)$。如果调度器每次都按同样的次序调度这两个事务，上面的过程会原样重演，两个事务谁也做不完，这就是活锁。

避免办法：事务因时间戳检查失败而回滚时不分配新时间戳，保留原来的旧时间戳，重启后它在所有事务里最"老"，优先级最高，下一轮就能做完；或者按重启次数提高优先级，达到同样的效果。

（整理补充：官方答案只给了调度和活锁的现象，没有说怎么破。保留旧时间戳是标准做法，道理和死锁处理里给牺牲者加"老化"计数是一样的，都是防止同一个事务被反复选中。）

### 15.17 用时间戳避免幻象现象

题目：设计一个基于时间戳的协议，避免幻象现象。

思路：幻象的根源是冲突发生在"满足某个谓词的元组有哪些"这条信息上，而这条信息不是一个被读写的数据项。解决办法是给它找一个实实在在的数据项做替身，再对这个替身套用时间戳规则。

解答：

- 幻象是什么： $T_1$ 用谓词查询读出一批元组（比如某个系的全部教师）， $T_2$ 插入一条满足该谓词的新元组并提交。两个事务没有读写同一个已有元组，优先图上看不出冲突，但执行结果不可串行化， $T_1$ 再查一次会多出一行。
- 教材在封锁方案里给了两个办法：一是粗粒度地锁住整个关系；二是锁住 B+ 树索引中覆盖查询范围的那些叶结点。两个办法都能移植到时间戳协议上。
- 粗粒度方案：把关系本身当作一个数据项，给它配一对 R-timestamp 和 W-timestamp。事务查询关系中的元组之前，先按 read 规则检查并更新关系的 R-timestamp；插入或删除元组之前，按 write 规则检查并更新关系的 W-timestamp。查询和插入于是在关系这个数据项上产生真实的读写冲突，时间戳规则自动把它们排好序。
- 索引方案：把 B+ 树的每个索引桶当作一个数据项，各带一对时间戳，并要求所有读访问都必须经过索引。
  - $T_i$ 要读某个查找码区间内的全部元组时，必须读遍该区间覆盖的所有索引桶，按 read 规则更新这些桶的 R-timestamp。
  - 任何在这个区间内插入或删除元组的事务，一定要修改其中某个索引桶，按 write 规则检查该桶的时间戳，不合规就回滚。
  - 于是逻辑上的谓词冲突被转换成索引桶上的读写冲突，幻象消失。
- 两个方案的差别是粒度。粗粒度方案简单但假冲突多，关系里任何一处插入都会挡住任何一个查询；索引方案只在码值落在同一个桶里时才产生冲突，并发度高得多，代价是所有读必须走索引。

### 15.18 B+ 树插入时提前释放锁

题目：假设用 15.1.5 节的树协议来管理对 B+ 树的并发访问。由于插入引起的分裂可能一路传到根，看上去插入操作在整个操作完成之前不能释放任何锁。在什么情况下可以提前释放锁？

思路：一个结点不满时，它的子树里发生的插入传不到它的祖先，祖先的锁就可以放掉了。

解答：

先说清这里的树协议指的是 15.1.5 节那个只有排他锁、锁子结点须持父结点锁的协议，不是 15.3 节的多粒度协议，也不是 15.10 节专门为 B+ 树设计的并发协议。

关键概念是结点的安全性：一个结点没有满时，在它的子树中插入一个码最多引起它的子结点分裂并往它里面插入一项，不会让它自己分裂，因此波及不到它的祖先。

释放策略是从根往下走，每到一个结点做一次判断：

- 当前结点的子结点不满：可以把除当前结点外已持有的所有锁全部释放；申请子结点的排他锁，拿到之后再释放当前结点的锁，然后下降到子结点。
- 当前结点的子结点是满的：保留已持有的全部锁，申请子结点的排他锁，拿到之后下降。
- 到达叶结点后开始执行插入。

这样下来，事务只在从叶结点往上一直到第一个不满结点（含这个结点）的这一段路径上持锁，再往上的祖先早就放掉了。树协议不允许放锁之后重新加锁，所以只能这样自上而下地判断、边走边放，不能先全放了再回头补。

还有一个优化，用预先分裂换更少的锁：即使子结点是满的，也先释放除当前结点外的所有锁；拿到子结点的排他锁之后立刻把它分裂（这时父结点还锁着，可以安全地往父结点插入分隔码），然后释放父结点的锁，只保留分裂后应该继续下降的那半个子结点的锁，把它当作新的当前结点。用这个办法，任何时刻最多只持有父子两把锁。代价是有些本来不必分裂的结点被提前分裂了，B+ 树的空间利用率略降。

### 15.19 快照隔离的验证步骤

题目：快照隔离在事务 $T$ 写某数据项之前要做一个验证步骤，检查与 $T$ 并发的事务是否已经写过这个数据项。

- a. 一种直接的实现是给每个事务记开始时间戳和提交时间戳，再记一个更新集合（该事务更新过的数据项集合）。说明怎样用这些时间戳和更新集合完成先提交者获胜（first-committer-wins）的验证。可以假定验证和其他提交处理步骤是串行执行的，一次只处理一个事务。
- b. 改成每个数据项带一个写时间戳，说明先提交者获胜的验证步骤怎样作为提交处理的一部分实现。同样可以假定验证串行执行。
- c. 先更新者获胜（first-updater-wins）可以用同样的时间戳实现，区别是验证在取得排他锁之后立即进行，而不是等到提交时。
  - i. 怎样给数据项分配写时间戳。
  - ii. 说明取得锁之后的验证不必在提交时再做一遍。
  - iii. 说明为什么两个事务不会同时对同一数据项做验证。

思路：先提交者获胜要回答"有没有并发事务抢先提交了同一个数据项的更新"，a 用集合相交来判断，b 把这个信息预先压缩到数据项的写时间戳里，c 则用排他锁把判断时机提前到写发生的那一刻。

解答：

a. 记 $T_i$ 的两个时间戳为 $\text{Start}(T_i)$、 $\text{Commit}(T_i)$，更新集合为 $\text{update-set}(T_i)$。 $T_i$ 通过验证，当且仅当对每个满足 $\text{Commit}(T_k) < \text{Commit}(T_i)$ 的已提交事务 $T_k$，下面两条之一成立：

- $\text{Commit}(T_k) < \text{Start}(T_i)$： $T_k$ 在 $T_i$ 开始之前就提交了，两者不并发， $T_i$ 的快照已经包含 $T_k$ 的全部更新，不存在冲突；
- $\text{Start}(T_i) < \text{Commit}(T_k) < \text{Commit}(T_i)$，并且 $\text{update-set}(T_i) \cap \text{update-set}(T_k) = \varnothing$： $T_k$ 与 $T_i$ 并发且抢先提交，但两者改的不是同一批数据项。

只要存在一个与 $T_i$ 并发、先提交、且更新集合与 $T_i$ 相交的 $T_k$， $T_i$ 就必须中止，这就是"先提交者获胜"。因为验证和提交处理串行进行，检查期间这些集合不会再变化。实现上不必保留所有历史事务的更新集合，提交时间戳早于当前所有活跃事务中最小的 Start 的那些，以后不会再被任何验证用到，可以丢掉。

（更正：答案 PDF 的第一条写作 $\text{Commit}(T_k) < \text{Start}(T_k)$，比较的是 $T_k$ 自己的两个时间戳，这个条件永远不成立，显然是 $\text{Commit}(T_k) < \text{Start}(T_i)$ 的笔误。）

b. 给每个数据项 $Q$ 配一个写时间戳 W-timestamp($Q$)。 $T_i$ 提交时，把它写过的每个 $Q$ 的写时间戳置为 $\text{Commit}(T_i)$。

$T_i$ 通过验证的条件是：对 $T_i$ 写过的每个数据项 $Q$，都有 $\text{W-timestamp}(Q) < \text{Start}(T_i)$。

道理是 $\text{W-timestamp}(Q) \ge \text{Start}(T_i)$ 意味着有一个事务在 $T_i$ 开始之后才提交，并且写过 $Q$，它与 $T_i$ 并发且抢先提交，按先提交者获胜的规则 $T_i$ 必须中止。这个写法不用保存历史事务的更新集合，验证的代价只和 $T_i$ 自己写的数据项个数有关。

c.

i. $T_i$ 要写 $Q$ 时先申请 $Q$ 的排他锁，拿到锁后立即验证，验证通过就把 W-timestamp($Q$) 置为这次写发生的时刻，不等到提交。这样后来的事务一申请到锁就能看到" $Q$ 已经被一个还没提交的事务改了"。

ii. 排他锁一直持有到事务结束，所以从验证通过到提交这段时间里，没有别的事务能修改 $Q$，验证所依据的 $Q$ 的写时间戳不会变。既然依据不变，提交时再验证一次结果必然一样，没有必要重做。

iii. 同一个数据项上的排他锁在同一时刻只能被一个事务持有，而验证是在拿到锁之后做的，所以对同一数据项的验证天然是串行的。a、b 两种做法需要额外假定"验证和提交处理串行执行"，先更新者获胜靠锁就把这件事保证了，这是它的一个好处。另一个好处是冲突在写发生的那一刻就被发现，事务立刻中止，不必把后面的工作白做完再在提交时被拒。

（整理补充：官方答案的 i 只说写时间戳取写发生的时刻，没有交代事务中止的情形。 $T_i$ 中止时必须把它改过的那些 $Q$ 的写时间戳恢复成原值，否则一个中止了的事务会平白挡住后来的事务。教材对先更新者获胜的表述也是"若该数据项已被某个并发的、已提交的事务更新过则中止"，中止的事务不该算数。）
