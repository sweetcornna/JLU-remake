# 存储与索引

整理自 `笔记/数据库系统原理笔记.pdf` 第 123–125 页。原笔记第 10 章"存储和文件结构"只有标题，内容都在第 11 章"索引与散列"，而且只讲了索引，没有散列。

## 本章要点

- 索引是为了加快查找而对某些字段的值建立的"目录"，里面存着指向数据记录的指针。
- 作用：加快查询、连接、分组和排序；唯一索引还能保证数据不重复。
- 代价：占额外的磁盘空间；插入、修改数据时索引也要跟着改，写操作变慢。
- 五种索引：普通索引、唯一索引、主键索引、全文索引、组合索引。
- 主键索引是唯一索引的特例，定义主键时自动创建。
- 该建索引的：主键、外键、连接字段、常出现在 `where` 里的字段、选择性高的小字段。不该建的：重复值多的、更新太频繁的、大文本字段。

## 1. 索引的概念

- 索引是一种特殊的文件，包含指向数据表中记录的引用指针。
- 通俗地说，索引就像一本书的目录。
- 没有索引时，要找 200 条数据里符合条件的，数据库得把 200 条全部遍历一遍；有了索引，直接在索引里查符合条件的项。

## 2. 索引的作用

建索引是为了加快对表中记录的查找或排序：

- 数据库借助索引快速定位记录，查询速度大大加快。这是建索引最主要的原因。
- 表很大或查询涉及多张表时，索引能把查询速度提高成千上万倍。
- 降低数据库的 IO 成本和排序成本。
- 建唯一索引可以保证表中每行数据唯一。
- 加快表与表之间的连接。
- 查询里用了分组、排序子句时，能明显减少分组和排序的时间。

## 3. 索引的副作用

- 索引要占额外的磁盘空间。MyISAM 引擎的索引文件和数据文件是分开的，索引文件里存数据记录的地址；InnoDB 引擎的表数据文件本身就是索引文件。
- 插入和修改数据要多花时间，因为索引也要随之变动。

## 4. 索引的分类

### 普通索引

最基本的索引，没有唯一性之类的限制。

### 唯一索引

- 和普通索引类似，但索引列的每个值只能出现一次。
- 表里已经有重复的键值时，大多数数据库不允许建这个唯一索引。
- 建好之后，数据库也会阻止插入会造成重复键值的新数据。
- 例：在员工表的姓（`name`）上建唯一索引，任何两个员工就不能同姓。

### 主键索引

- 主键是一种唯一索引，但必须指定为 `PRIMARY KEY`。
- 给表定义主键时会自动创建主键索引。它是唯一索引的特定类型，要求主键的每个值都唯一。

### 全文索引

- 索引类型为 `FULLTEXT`，适合模糊查询，可以在文章里检索文本信息。
- MySQL 5.6 以前只有 MyISAM 引擎支持 `FULLTEXT` 索引，5.6 以后 InnoDB 也支持。
- 可以建在 `CHAR`、`VARCHAR`、`TEXT` 类型的列上。
- 原文说每个表只允许有一个全文索引。（更正：这是 SQL Server 的规定。MySQL 一张表可以建多个 `FULLTEXT` 索引。）

### 组合索引（单列索引与多列索引）

- 索引可以建在单列上，也可以建在多列上。
- 某一列有重复值时，多列索引可以借助其他列把这些行区分开。
- 经常同时按两列或多列搜索、排序时，多列索引很有用。例如查询里经常同时给姓和名设条件，就在这两列上建一个多列索引。

## 5. 创建索引的原则

索引能提升查询速度，但不是哪里都适合建。有索引时，数据库先查索引再定位到数据行；索引用得不当，反而增加负担。笔记列出的原则：

| 应该建索引 | 理由 |
| --- | --- |
| 表的主键、外键 | 主键值唯一，查询时能快速定位行；外键一般关联另一个表的主键，多表查询时也能快速定位 |
| 记录数超过 300 行的表 | 没有索引就要全表遍历，严重影响性能 |
| 经常与其他表连接的表，在连接字段上 | 加快连接 |
| 经常出现在 `where` 子句里的字段，尤其是大表的 | 加快条件查询 |
| 选择性高的字段 | 相同值很少、不同值很多，按索引一查就能缩小到很少几行 |
| 小字段 | 索引本身小，查得快 |

| 不适合建索引 | 理由 |
| --- | --- |
| 唯一性太差的字段（重复值多） | 提升不了查询速度，反而变慢 |
| 更新太频繁的字段 | 每次增删改索引都要跟着动，占用过多系统资源 |
| 大文本字段、超长字段 | 索引太大，得不偿失 |

## 易混对比

### 五种索引

| 索引 | 值能重复吗 | 怎么产生 | 典型用途 |
| --- | --- | --- | --- |
| 普通索引 | 能 | 手动创建 | 一般的加速查询 |
| 唯一索引 | 不能 | 手动创建 | 加速查询，同时保证列值不重复 |
| 主键索引 | 不能 | 定义 `PRIMARY KEY` 时自动创建 | 按主键定位行 |
| 全文索引 | 能 | 手动创建，类型 `FULLTEXT` | 在 `CHAR`、`VARCHAR`、`TEXT` 列里做模糊的文本检索 |
| 组合索引 | 看是否声明为唯一 | 手动在多列上创建 | 多列同时作为查询条件或排序依据 |

### 唯一索引与主键索引

| | 唯一索引 | 主键索引 |
| --- | --- | --- |
| 关系 | 大类 | 唯一索引的特定类型 |
| 怎么来 | 自己建 | 定义主键时自动建 |
| 要求 | 列值唯一 | 主键的每个值唯一 |

### MyISAM 与 InnoDB 的索引存放

| | MyISAM | InnoDB |
| --- | --- | --- |
| 索引和数据 | 索引文件和数据文件分开 | 表数据文件本身就是索引文件 |
| 索引里存什么 | 数据记录的地址 | 数据直接组织在索引里 |

## 典型题与解答

### 题 1：索引的利与弊

为什么建索引能加快查询？索引有什么代价？

思路：利用书的目录类比说作用，代价从空间和写操作两方面说。

解答：索引像书的目录，数据库先在索引里找到满足条件的项，再按指针直接定位数据行，不用全表遍历，所以查询、连接、分组、排序都会变快，唯一索引还能保证值不重复。代价是索引要占额外磁盘空间，而且插入、修改数据时索引也要更新，写操作变慢。

### 题 2：哪些字段适合建索引

学生表 `student(ID, name, gender, dept_name, remarks)` 有几万行，`ID` 是主键，经常按 `dept_name` 和系表 `department` 连接，`gender` 只有两种取值，`remarks` 是很长的备注文本。哪些字段适合建索引？

思路：逐个对照第 5 节的原则。

解答：

- `ID`：主键，必须有索引（定义主键时自动建）。
- `dept_name`：连接字段，也常出现在 `where` 里，适合建。
- `gender`：只有两种值，唯一性太差，不适合。
- `remarks`：大文本字段，不适合。
- `name`：如果经常按姓名查询，可以建普通索引；学生会重名，不能建唯一索引。

### 题 3：唯一索引的后果

在员工表的 `name` 列上建唯一索引，会有什么后果？

思路：唯一索引要求列值只出现一次，建之前和建之后各有影响。

解答：如果表里已经有同名员工，大多数数据库会拒绝建这个索引；建成功之后，再插入一个与已有员工同名的人会被拒绝。所以不应该在可能重复的列上建唯一索引。

### 题 4：写建索引的语句（整理补充，MySQL 写法）

在 `employee` 表上：(1) 给 `name` 建普通索引；(2) 给 `email` 建唯一索引；(3) 给 `last_name`、`first_name` 建组合索引；(4) 给 `article` 表的 `content` 列建全文索引。

解答：

```sql
create index idx_name on employee(name);
create unique index idx_email on employee(email);
create index idx_full_name on employee(last_name, first_name);
alter table article add fulltext index ft_content (content);
```

主键索引不用单独写，建表时声明 `primary key` 就自动有了。
