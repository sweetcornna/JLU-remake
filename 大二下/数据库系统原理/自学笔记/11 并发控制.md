# 并发控制

整理自 `笔记/数据库系统原理笔记.pdf` 第 141–144 页（第 15 章 并发控制），并合入 `笔记/数据库期末复习题整理.pdf` 第 87–88 页"事务与锁相关整理"中的锁相容矩阵、两阶段封锁的例子和死锁恢复。典型题里有一道简答题取自课程目录 `README.md` 里回忆的往届考题。读写操作记作 `read(A)`、`write(A)`。

## 本章要点

- 两种锁：共享锁 S 只能读，排他锁 X 能读能写。只有 S 和 S 相容。
- 加锁、解锁用 `lock-S(Q)`、`lock-X(Q)`、`unlock(Q)`。读完就放锁保证不了可串行化。
- 授予锁时要同时满足：没有别的事务持有冲突的锁，也没有比它先申请、还在等的事务。这样可以避免饿死。
- **两阶段封锁协议**：增长阶段只加锁不放锁，缩减阶段只放锁不加锁。它保证冲突可串行化，按封锁点排序就是等价的串行顺序。
- 两阶段封锁防不了死锁，也防不了级联回滚。
- 严格两阶段封锁：排他锁一直持有到提交或中止，避免级联回滚。强两阶段封锁：所有锁都持有到提交，事务按提交顺序串行化。
- 锁转换：升级（S 变 X）只能在增长阶段，降级（X 变 S）只能在缩减阶段。
- 死锁处理分预防、检测与恢复两类。检测用**等待图**，图中有环就有死锁；恢复要选牺牲者回滚。
- 原笔记在本章末尾单独列出了"两阶段锁协议的概念"和"用资源图判断死锁"两条，复习时优先看这两块。

## 1. 锁

为了保持隔离性，系统必须控制并发事务之间的相互作用，这套机制叫并发控制。确保隔离性的方法之一，是让事务以互斥的方式访问数据项。

### 两种锁

- 共享锁（S）：事务 T1 在数据项 Q 上拿到共享锁，T1 可以读 Q，不能写 Q。
- 排他锁（X）：事务 T1 在 Q 上拿到排他锁，T1 既能读又能写 Q。

每个事务要按自己对 Q 的操作类型，向并发控制管理器申请合适的锁，申请被授予后才能继续执行。

锁相容矩阵（原课程笔记的截图没导出来，这里按复习题整理稿第 87 页的教材图 15-1 给出）：

| 已持有 \ 申请 | S | X |
| --- | --- | --- |
| S | 相容 | 不相容 |
| X | 不相容 | 不相容 |

规则：

- 事务要访问一个数据项，得先给它加锁。
- 申请的锁和其他事务在这个数据项上已经持有的锁都相容，才可能授予。
- 任意多个事务可以同时持有同一数据项的共享锁；只要有一个事务持有排他锁，其他事务就不能持有这个数据项上的任何锁。
- 锁授予不了，申请的事务就等待，直到其他事务持有的不相容锁全部释放。
- 事务只要还在访问某个数据项，就必须一直持有它上面的锁。
- 延迟锁释放：等事务结束后才释放锁。

操作写法：

- `lock-S(Q)`：申请 Q 上的共享锁。
- `lock-X(Q)`：申请 Q 上的排他锁。
- `unlock(Q)`：释放 Q 上的锁。

### 例：光加锁不够

原笔记这里的截图缺失，下面按笔记文字和教材同一例子补全（整理补充）。设 A = 100，B = 200。T1 从 B 向 A 转 50，T2 显示 A + B。两个事务都是用完一个数据项马上解锁：

| T1 | T2 |
| --- | --- |
| `lock-X(B)` | |
| `read(B)` | |
| `B := B - 50` | |
| `write(B)` | |
| `unlock(B)` | |
| | `lock-S(A)` |
| | `read(A)` |
| | `unlock(A)` |
| | `lock-S(B)` |
| | `read(B)` |
| | `unlock(B)` |
| | `display(A + B)` |
| `lock-X(A)` | |
| `read(A)` | |
| `A := A + 50` | |
| `write(A)` | |
| `unlock(A)` | |

T2 读到的是 A = 100 和已经扣过钱的 B = 150，显示 250，正确值应是 300。锁都按规矩加了，但 T1 在转账中途放掉了 B 的锁，T2 正好在 A、B 更新之间读了它们。所以只加锁保证不了可串行化。

### 死锁

死锁是循环等待导致每个事务都不能继续执行的状态。例（按笔记文字补全）：

| T3 | T4 |
| --- | --- |
| `lock-X(B)` | |
| `read(B)` | |
| `B := B - 50` | |
| `write(B)` | |
| | `lock-S(A)` |
| | `read(A)` |
| | `lock-S(B)`（等 T3 释放 B） |
| `lock-X(A)`（等 T4 释放 A） | |

T4 申请 `lock-S(B)`，要等 T3 释放 B 上的排他锁；T3 申请 `lock-X(A)`，要等 T4 释放 A 上的共享锁。谁都走不下去。发生死锁时，系统必须回滚其中一个事务，释放它的锁。

### 封锁协议

- 封锁协议是所有事务申请、释放锁时都要遵守的一组规则，规定事务什么时候可以对数据项加锁、解锁。
- 封锁协议限制了可能出现的调度。对一个给定的封锁协议，它允许的调度集合是所有可串行化调度的一个真子集。

## 2. 锁的授予与饿死

并发控制管理器设计得不好，事务可能被饿死。例：T2 持有 Q 的 S 锁，T1 申请 Q 的 X 锁只能等；T2 还没放，T3 又来申请 S 锁，和 T2 的 S 锁相容，马上被授予；T2 放锁时 T3 还拿着，T4 又来申请 S 锁……T1 可能一直等下去。

避免饿死的授予条件：事务 Ti 申请对 Q 加 M 型锁时，同时满足下面两条才授予：

1. 不存在其他事务在 Q 上持有与 M 型锁冲突的锁。
2. 不存在在 Ti 之前申请对 Q 加锁、现在还在等待的事务。

## 3. 两阶段封锁协议

### 定义

每个事务分两个阶段申请加锁和解锁：

1. 增长阶段（上升阶段，growing phase）：可以获得锁，不能释放锁。
2. 缩减阶段（下降阶段，shrinking phase）：可以释放锁，不能获得新锁。

复习题整理稿给的理解方式：

- 对任何数据读、写之前，事务先要获得它上面的锁。
- 释放了一个锁之后，事务就不能再获得任何锁。事务一开始处在增长阶段，按需加锁；一旦释放了某个锁，就进入缩减阶段，不能再申请加锁。

例（复习题整理稿第 87–88 页）：

- 事务 1 的封锁序列：`Slock A ... Slock B ... Xlock C ... Unlock C ... Unlock B ... Unlock A`。所有加锁都在第一次解锁之前，遵守两阶段封锁。
- 事务 2 的封锁序列：`Slock A ... Unlock A ... Slock B ... Xlock C ... Unlock C ... Unlock B`。先 `Unlock A` 又 `Slock B`，释放锁后再加锁，不遵守。

### 能保证什么

- 两阶段封锁协议保证**冲突可串行化**。
- 封锁点：事务在调度中获得最后一个锁的位置，也就是增长阶段结束的地方。
- 把各事务按封锁点排序，得到的顺序就是这组事务的一个可串行化顺序。
- 并发执行的事务都遵守两阶段封锁，它们的任何并发调度都是可串行化的。
- 遵守两阶段封锁是可串行化的**充分条件，不是必要条件**：可串行化的调度里，不一定每个事务都遵守两阶段封锁。

### 不能保证什么

- 不能避免死锁。前面的 T3、T4 其实都能写成两阶段的：T3 先后拿到 B、A 的锁再统一释放，T4 先后拿到 A、B 的锁再统一释放，照样死锁。
- 不能避免级联回滚。例（整理补充）：

| T5 | T6 | T7 |
| --- | --- | --- |
| `lock-X(A)` | | |
| `read(A)` | | |
| `lock-S(B)` | | |
| `read(B)` | | |
| `write(A)` | | |
| `unlock(A)` | | |
| | `lock-X(A)` | |
| | `read(A)` | |
| | `write(A)` | |
| | `unlock(A)` | |
| | | `lock-S(A)` |
| | | `read(A)` |

三个事务都遵守两阶段封锁（T5 拿完 A、B 的锁才开始放锁）。但 T5 还没提交就放了 A 的排他锁，T6 读到了 T5 写的 A，T7 又读到了 T6 写的 A。如果这时 T5 失败，T6、T7 都得跟着回滚。

### 严格两阶段封锁与强两阶段封锁

- 严格两阶段封锁（strict 2PL）：在两阶段的基础上，事务持有的**所有排他锁**必须保持到事务提交或中止才释放。未提交事务写的数据一直被排他锁锁住，别的事务读不到，所以不会级联回滚。放到上面的例子里，T6 要等 T5 提交才能锁 A。
- 强两阶段封锁（rigorous 2PL）：事务提交之前不得释放**任何锁**，共享锁也不行。在强两阶段封锁下，事务可以按提交的顺序串行化。

### 锁转换

两阶段封锁协议允许锁转换：

- 升级（upgrade）：共享锁变排他锁，只能发生在增长阶段。
- 降级（downgrade）：排他锁变共享锁，只能发生在缩减阶段。

升级相当于拿到一把更强的锁，所以只能在还能加锁的增长阶段做；降级相当于放掉一部分锁，所以只能在缩减阶段做。

用处（整理补充）：事务 T 要先读 a1、a2、…、an，最后才写 a1。没有锁转换时，T 一开始就得对 a1 加排他锁，别的事务在这段时间里连读 a1 都不行。有了升级，T 先对 a1 加共享锁，别的事务也能读；到真要写时再升级为排他锁，并发度更高。

## 4. 死锁处理

如果存在一个事务集合，集合里每个事务都在等集合里的另一个事务，系统就处于死锁状态。处理方法主要有两种：

1. 死锁预防：保证系统永远不进入死锁。
2. 死锁检测与死锁恢复：允许进入死锁，检测到了再恢复。

### 死锁预防

原笔记这一小节只写了"不考"。为了配合易混对比和练习，下面简要补充教材里的做法（整理补充）：

- 每个事务开始前一次性锁住它要用的所有数据项，要么全锁上，要么一个都不锁；或者规定所有数据项的加锁顺序，事务只能按这个顺序加锁。
- 用时间戳决定是等待还是回滚。每个事务开始时分配一个时间戳，时间戳小的是老事务。设 Ti 申请的数据项正被 Tj 持有：
  - wait-die（非抢占）：Ti 比 Tj 老，Ti 等待；Ti 比 Tj 新，Ti 回滚（die）。一句话：老的等新的，新的自己回滚。
  - wound-wait（抢占）：Ti 比 Tj 老，Tj 被回滚（wound，Ti 抢走锁）；Ti 比 Tj 新，Ti 等待。一句话：老的抢占新的，新的等老的。
  - 两种方案里被回滚的事务重启时保留原来的时间戳，它会越来越"老"，最终不会再被回滚，所以不会饿死。
- 锁超时：申请锁的事务最多等一段时间，超时就回滚重启。

### 死锁检测

死锁可以用等待图精确描述（原笔记叫"资源等待图"）：

- 等待图 G = (V, E)。顶点集 V 是系统中所有事务，边集 E 的每个元素是有序对 Ti → Tj。
- Ti → Tj 表示 Ti 在等 Tj 释放它需要的数据项。
- Ti 申请的数据项正被 Tj 持有时，插入边 Ti → Tj；Tj 不再持有 Ti 需要的数据项时，删除这条边。
- **等待图中有环，系统就存在死锁**；没有环就没有死锁。环上的每个事务都处于死锁。
- 为了检测死锁，系统要维护等待图，并周期性地调用一个在图中找环的算法。

例（原笔记图片缺失，按教材同一例子补全，事务重新编号）：等待图有边 T1 → T2、T1 → T3、T3 → T2、T2 → T4，没有环，系统不在死锁状态。之后 T4 申请 T3 持有的数据项，加入边 T4 → T3，形成环 T2 → T4 → T3 → T2，T2、T3、T4 死锁。T1 不在环上，但它在等死锁中的事务，也走不下去。

### 从死锁中恢复

检测到死锁后，要回滚一个或多个事务来打破死锁。复习题整理稿第 88 页列了要考虑的三件事：

1. 选择牺牲者：选回滚代价最小的事务。代价可以看：这个事务已经算了多久；已经用了多少数据项；完成它还需要多少数据项；回滚它会牵连多少事务。
2. 回滚多远：彻底回滚，也就是中止后重启；或者部分回滚，只回滚到能解除死锁为止。
3. 避免饿死：不能让同一个事务每次都因为代价最小被选中。最常用的办法是把被回滚的次数算进代价里。

## 易混对比

### 共享锁与排他锁

| | 共享锁 S | 排他锁 X |
| --- | --- | --- |
| 持有者能做什么 | 只读 | 读和写 |
| 申请 | `lock-S(Q)` | `lock-X(Q)` |
| 与已有的 S 锁 | 相容 | 不相容 |
| 与已有的 X 锁 | 不相容 | 不相容 |
| 同一数据项上能有几个事务持有 | 任意多个 | 只能一个，且此时不能有别的锁 |

### 三种两阶段封锁

| | 两阶段封锁 | 严格两阶段封锁 | 强两阶段封锁 |
| --- | --- | --- | --- |
| 规则 | 增长阶段只加锁，缩减阶段只放锁 | 两阶段 + 排他锁持有到提交或中止 | 两阶段 + 所有锁持有到提交 |
| 冲突可串行化 | 保证 | 保证 | 保证 |
| 避免级联回滚 | 不能 | 能 | 能 |
| 避免死锁 | 不能 | 不能 | 不能 |
| 串行化顺序 | 按封锁点 | 按封锁点 | 按提交顺序 |

### 锁升级与降级

| | 升级 | 降级 |
| --- | --- | --- |
| 变化 | S 变 X | X 变 S |
| 允许在 | 增长阶段 | 缩减阶段 |
| 理由 | 相当于获得更强的锁 | 相当于释放一部分锁 |

### wait-die 与 wound-wait

设 Ti 申请 Tj 持有的数据项。

| | Ti 比 Tj 老（时间戳小） | Ti 比 Tj 新（时间戳大） | 类型 |
| --- | --- | --- | --- |
| wait-die | Ti 等待 | Ti 回滚 | 非抢占 |
| wound-wait | Tj 回滚，Ti 拿到锁 | Ti 等待 | 抢占 |

两种方案里被回滚的都是较新的事务，重启时保留原时间戳。

### 死锁预防与死锁检测

| | 死锁预防 | 死锁检测与恢复 |
| --- | --- | --- |
| 思路 | 让系统永远进不了死锁 | 允许死锁发生，发现后再处理 |
| 做法 | 一次锁全部数据项、按序加锁、wait-die、wound-wait、锁超时 | 维护等待图，周期性找环；有环就选牺牲者回滚 |
| 代价 | 可能回滚本来不会死锁的事务 | 维护等待图、运行检测算法；死锁期间事务白等 |
| 适合 | 死锁很容易发生的系统 | 死锁比较少见的系统 |

### 死锁与饿死

| | 死锁 | 饿死 |
| --- | --- | --- |
| 现象 | 一组事务互相等待，谁都走不下去 | 某个事务一直拿不到锁或一直被选作牺牲者，其他事务照常执行 |
| 原因 | 循环等待 | 锁授予策略不公平，或牺牲者选择不考虑回滚次数 |
| 办法 | 预防，或检测后回滚 | 锁授予时让先来的先得；选牺牲者时计入回滚次数；时间戳方案重启保留原时间戳 |

## 典型题与解答

### 题 1：两阶段封锁协议是什么，为什么要有严格两阶段锁和强两阶段锁

课程目录 `README.md` 里回忆的往届简答题。

思路：先答定义和保证，再指出它的两个缺陷，最后说两个变体分别补了什么。

解答：

1. 两阶段封锁协议要求每个事务分两个阶段加锁、解锁：增长阶段只能获得锁、不能释放锁；缩减阶段只能释放锁、不能获得锁。它保证调度是冲突可串行化的，按各事务的封锁点排序就是等价的串行顺序。
2. 它的问题是不能避免级联回滚：事务在缩减阶段放掉排他锁后、提交之前，别的事务就能读到它写的数据，它一旦失败，读过的事务都要跟着回滚。它也不能避免死锁。
3. 严格两阶段封锁要求排他锁一直持有到事务提交或中止，未提交的数据别人读不到，从而避免级联回滚。
4. 强两阶段封锁要求所有锁（包括共享锁）都持有到提交，除了避免级联回滚，事务还可以直接按提交顺序串行化。

### 题 2：判断是否遵守两阶段封锁

"例：光加锁不够"里的 T1、T2 遵守两阶段封锁吗？怎么改？

思路：找有没有"放锁之后又加锁"。

解答：都不遵守。T1 先 `unlock(B)` 后 `lock-X(A)`；T2 先 `unlock(A)` 后 `lock-S(B)`。改法是把所有加锁挪到第一次解锁之前：

```text
T1: lock-X(B); read(B); B := B - 50; write(B);
    lock-X(A); read(A); A := A + 50; write(A);
    unlock(B); unlock(A)
T2: lock-S(A); read(A); lock-S(B); read(B);
    display(A + B); unlock(A); unlock(B)
```

T1 的封锁点在 `lock-X(A)`，T2 的封锁点在 `lock-S(B)`。改完后两个事务无论怎么交错执行都是冲突可串行化的，T2 显示的一定是 300。不过像 T3、T4 那样交错时仍可能死锁。

### 题 3：锁能不能授予（整理补充）

T1 持有 Q 上的 S 锁。接着依次发生：T2 申请 Q 的 S 锁；T3 申请 Q 的 X 锁；T4 申请 Q 的 S 锁。按"避免饿死"的授予条件，哪些申请能立即授予？

思路：每次申请都检查两条：有没有冲突的锁，有没有比它早申请、还在等的事务。

解答：

- T2：S 与 T1 的 S 相容，前面没人等，立即授予。
- T3：X 与 T1、T2 的 S 都不相容，等待。
- T4：S 与已持有的 S 锁相容，但 T3 比它先申请、还在等，不满足第 2 条，T4 也要等。这样 T1、T2 放锁后 T3 能先拿到 X 锁，不会被后面源源不断的 S 锁饿死。

### 题 4：用等待图判断死锁（整理补充）

某时刻：T1 持有 A 的 X 锁，T2 持有 B 的 X 锁，T3 持有 C 的 S 锁。随后 T1 申请 B 的 S 锁，T2 申请 C 的 X 锁，T3 申请 A 的 S 锁。系统死锁了吗？如果 T3 申请的是没有任何事务持有的 D，而不去申请 A 呢？

思路：每个"申请被持有者挡住"画一条申请者 → 持有者的边，再找环。

解答：

- T1 申请 B 的 S 锁，和 T2 的 X 锁不相容，边 T1 → T2。
- T2 申请 C 的 X 锁，和 T3 的 S 锁不相容，边 T2 → T3。
- T3 申请 A 的 S 锁，和 T1 的 X 锁不相容，边 T3 → T1。

等待图有环 T1 → T2 → T3 → T1，死锁。

如果 T3 申请的是没人持有的 D，锁立即授予，T3 不等任何人，图里只有 T1 → T2、T2 → T3 两条边，无环，不死锁。T3 执行完释放 C 上的锁后，T2 拿到 C 继续执行，T2 结束放掉 B，T1 再继续。

### 题 5：wait-die 与 wound-wait（整理补充）

T1、T2、T3 的时间戳分别是 5、10、15。(1) T1 申请 T2 持有的数据项；(2) T3 申请 T2 持有的数据项。分别按 wait-die 和 wound-wait 说明谁等待、谁回滚。

思路：时间戳小的老。wait-die 里申请者老就等、新就死；wound-wait 里申请者老就抢、新就等。

解答：

| 情况 | wait-die | wound-wait |
| --- | --- | --- |
| (1) T1（5）申请 T2（10）的数据项，申请者更老 | T1 等待 | T2 回滚，T1 拿到数据项 |
| (2) T3（15）申请 T2（10）的数据项，申请者更新 | T3 回滚 | T3 等待 |

被回滚的 T2 或 T3 重启后仍用原来的时间戳 10 或 15。

### 题 6：级联回滚与严格两阶段封锁

第 3 节 T5、T6、T7 的例子里，如果 T5 在最后失败，哪些事务要回滚？改用严格两阶段封锁后呢？

思路：顺着"谁读了谁写的数据"找依赖链。

解答：T6 读了 T5 写的 A，T7 读了 T6 写的 A，所以 T6、T7 都要回滚，这就是级联回滚。改用严格两阶段封锁后，T5 的 A 上的排他锁要保持到它提交或中止，T6 的 `lock-X(A)` 只能等着；T5 失败回滚后 T6 才能拿到锁，读到的是回滚后的正确值，T6、T7 都不受影响。

### 题 7：判断对错

1. 遵守两阶段封锁协议的事务不会发生死锁。
2. 调度是可串行化的，其中的事务就一定都遵守两阶段封锁协议。
3. 两阶段封锁协议下，事务可以在缩减阶段把共享锁升级为排他锁。
4. 等待图中有环，系统一定处于死锁状态。
5. 强两阶段封锁下，事务可以按提交顺序串行化。

解答：

1. 错。T3、T4 的例子就是两阶段的，仍然死锁。
2. 错。遵守两阶段封锁是可串行化的充分条件，不是必要条件。
3. 错。升级只能在增长阶段，缩减阶段只能降级。
4. 对。有环当且仅当存在死锁。
5. 对。
