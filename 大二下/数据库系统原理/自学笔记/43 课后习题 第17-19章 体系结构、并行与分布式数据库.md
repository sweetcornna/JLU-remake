## 第17章 数据库系统体系结构

### 17.1 把共享结构放进专门进程

题目：一种替代做法是不用共享内存，而把锁表等共享结构放在某个专门进程的本地内存里，其他进程通过进程间通信访问它。这种体系结构有什么缺点？

思路：每次加锁都要走进程间通信，比直接读写内存慢得多，这个进程还会成为瓶颈。

解答：

- 申请一次锁至少要两条进程间消息：一条发请求，一条确认授予。进程间通信比访问共享内存贵得多，加锁的开销随之上升。
- 所有进程都要找这一个进程，它容易成为性能瓶颈。
- 这种结构也有好处：只有这个进程能改锁表，锁表不容易被其他进程的错误写坏。

### 17.2 客户机和服务器性能相同

题目：通常服务器比客户机强得多。如果客户机和服务器性能完全相同，还有必要做成客户-服务器系统吗？为什么？哪种情形更适合数据服务器体系结构？

思路：客户机很强时仍然值得用客户-服务器结构，强客户机正好适合数据服务器结构，由客户机承担计算。

解答：

- 仍然有必要，比做成完全集中式的系统好。采用数据服务器结构时，耗时长、计算量大的事务处理可以全部放到客户机上做，服务器只负责响应读写请求。
- 即使用事务服务器结构，用户界面相关的工作也在客户机上完成，这部分计算量本身就不小。
- 客户机很强时，完全分布式的系统看上去也可行。客户-服务器结构的优势在于并发控制和恢复只需要在服务器一处实现，比分散到所有机器上简单。
- 所以客户机性能强的情形更适合数据服务器体系结构。

### 17.3 元组传输与页传输

题目：客户-服务器系统中服务器充当数据服务器。

- a. 客户机和服务器之间的网络速度，对选择元组传输还是页传输有什么影响？
- b. 采用页传输时，客户机上的缓存可以按页组织，也可以按元组组织。假设元组比页小，说出元组缓存相对页缓存的一个好处。

思路：慢网络按需传元组，快网络的瓶颈在消息次数，适合整页传；元组缓存粒度细，命中率和并发度都可能更高。

解答：

- a. 假设一页能放下多个元组。
  - 网络慢时选元组传输。页传输会把很多可能用不到的元组一起发过来，浪费传输时间。
  - 网络快时，瓶颈变成每条消息的通信开销和延迟，传输的数据量反而不重要，一次发一整页更划算，选页传输。
- b. 元组缓存有两个好处（答出一个即可）：
  - 缓存满了以后可以按元组淘汰，不必整页换出。粒度更细，缓存命中率可能更高。
  - 服务器可以要求客户机交还那些持有但用不到的元组锁（锁降级），并发度更高。按页缓存时做不到这一点。

### 17.4 只并行 SQL 部分的加速比

题目：一个用 C 加嵌入式 SQL 写的事务，80% 的时间花在 SQL 上，20% 花在 C 代码上。如果只对 SQL 部分做并行，最多能期望多大的加速比？

思路：套用 Amdahl 定律，不能并行的 20% 决定了上限。

解答：设 SQL 部分用 $n$ 个处理器并行，加速比为

$$\frac{1}{0.2 + 0.8/n} < \frac{1}{0.2} = 5$$

加速比总是小于 5，处理器再多也达不到。

### 17.5 超线性加速比

题目：连接之类的操作，在数据（比如参与连接的某个关系）能放进内存和放不进内存时，速度差别很大。说明这一点如何解释超线性加速比现象，即应用获得的加速比超过所分配资源的倍数。

思路：资源增加后每台机器分到的数据变少，能整个放进内存，从磁盘算法换成内存算法，节省的时间超过资源增加的倍数。

解答：官方答案缺（PDF 里只有占位词 FILL），以下为整理补充。

- 单机做连接时，如果关系放不进内存，只能用基于磁盘的算法，比如先把两个关系散列划分写到磁盘再逐个分区连接，或者用块嵌套循环连接，大量时间花在磁盘 I/O 上。
- 换成 $n$ 个处理器后，关系被划分成 $n$ 份，每台机器上的分片可能已经能整个装进内存，直接做内存中的散列连接，省掉了多轮磁盘读写。
- 于是每台机器的处理时间远小于原来的 $1/n$，总的加速比超过 $n$。

### 17.6 交换机级联的互连结构

题目：并行系统常把每 n 个处理器接到一台以太网交换机上，这些交换机再接到另一台交换机上。这对应总线、网格还是超立方体结构？如果都不是，应该怎样描述这种互连结构？

思路：三种都不是，它是以交换机为内部结点的树形（分层）结构。

解答：官方答案缺（PDF 里只有占位词 FILL），以下为整理补充。

- 不属于总线结构：处理器之间没有共享同一条通信介质，交换机可以同时转发多对通信。
- 不属于网格或超立方体结构：处理器之间没有直接相连的链路，通信都要经过交换机。
- 它是树形（分层）结构：处理器是叶子，第一级交换机是中间结点，上一级交换机是根。
- 同一台交换机下的两个处理器通信只经过一台交换机；挂在不同交换机下的处理器要经过"下级交换机、上级交换机、下级交换机"三跳。跨组流量都挤在上级交换机和各条上行链路上，那里容易成为瓶颈。

## 第18章 并行数据库

### 18.1 范围选择只访问一个磁盘

题目：在范围划分的属性上做范围选择时，可能只需要访问一个磁盘。说明这一特性的好处和坏处。

思路：结果少时开销小、有利于吞吐量；结果多时没有并行，还会形成热点。

解答：

- 好处：查询范围内的元组很少时，每个查询在一个磁盘上就能很快完成，不用在多个磁盘上启动查询，开销小，其他磁盘可以同时服务别的查询。
- 坏处：查询范围内的元组很多时，整个查询只在一个磁盘上执行，没有查询内的并行，耗时长。部分磁盘还可能变成热点，访问集中在它们上面，响应时间进一步变长。
- 折中办法是混合范围划分：先按值划成很多小范围（每个只有几块），再把这些小范围轮转分配到各个磁盘，兼得范围划分的好处，又避开上面的缺点。

### 18.2 选择哪种并行

题目：下面两种任务中，查询间并行、操作间并行、操作内并行哪一种最重要？

- a. 提高有大量小查询的系统的吞吐量。
- b. 磁盘和处理器数量很多时，提高只有少量大查询的系统的吞吐量。

思路：小查询多靠查询间并行；大查询靠查询内并行，处理器很多时主要是操作内并行。

解答：

- a. 查询间并行。小查询本身很快，再把每个查询拆开并行只会增加启动开销，响应时间也缩短不了多少。
- b. 查询内并行，其中主要是操作内并行。查询通常只有几个操作，但每个操作要处理大量元组；处理器和磁盘很多时，只有把单个操作拆到多个处理器上执行，才能用满这些硬件。

### 18.3 流水线上的操作放在同一处理器

题目：流水线并行时，即使有很多处理器，把流水线上的几个操作放在同一个处理器上执行也常常是好主意。

- a. 为什么？
- b. 如果机器是共享内存结构，a 的理由还成立吗？
- c. 独立并行时（操作之间不是流水线关系）a 的理由还成立吗？也就是说，是否存在操作不构成流水线、处理器也很多，但把几个操作放在同一处理器上仍然更好的情况？

思路：要看算子之间传元组的代价，共享内存下这个代价很小；独立操作的输出若汇到同一个算子，放在一起同样省传输。

解答：

- a. 每个算子产生的元组都要交给它的消费算子。两者在不同处理器上时，每个元组都要跨处理器传输，这部分开销会抵消并行带来的加速。
- b. 基本不成立。共享内存结构下，在算子之间传递元组只是内存操作，代价很低。
- c. 可能成立。两个操作彼此独立，但如果它们的输出都送给同一个第三个算子，把三个算子放在同一处理器上，可能比跨处理器传元组更快。

### 18.4 带状连接的优化

题目：用对称分片复制加范围划分做连接。如果连接条件形如 $|r.A - s.B| \le k$（ $k$ 是小常数，这种连接称为带状连接），怎样优化计算？

思路： $r$ 的第 $i$ 个分片只可能和 $s$ 的相邻几个分片匹配，每个分片只需复制到 3 个处理器上。

解答：

- 用同一个划分向量把 $r$ 按 $A$、 $s$ 按 $B$ 各划分成 $n$ 份，得到 $r_0, \dots, r_{n-1}$ 和 $s_0, \dots, s_{n-1}$，并让每个范围的宽度都不小于 $k$（官方答案没有写出这个前提，整理时补上）。
- 这样 $r_i$ 中的元组只可能与 $s_{i-1}$、 $s_i$、 $s_{i+1}$ 中的元组满足连接条件。处理器 $P_{i,j}$ 负责计算 $r_i$ 与 $s_j$ 的连接，只需要保留下标相差不超过 1 的那些处理器：

| | $s_0$ | $s_1$ | $s_2$ | $s_3$ | … | $s_{n-2}$ | $s_{n-1}$ |
| --- | --- | --- | --- | --- | --- | --- | --- |
| $r_0$ | $P_{0,0}$ | $P_{0,1}$ | | | | | |
| $r_1$ | $P_{1,0}$ | $P_{1,1}$ | $P_{1,2}$ | | | | |
| $r_2$ | | $P_{2,1}$ | $P_{2,2}$ | $P_{2,3}$ | | | |
| … | | | | … | … | | |
| $r_{n-1}$ | | | | | | $P_{n-1,n-2}$ | $P_{n-1,n-1}$ |

- 一般的对称分片复制需要 $n^2$ 个处理器，这里约为 $3n$ 个。处理器数目相同时，可以把关系划分成更多、更小的分片，每个局部连接都更快。

### 18.5 用直方图构造均衡的范围划分

题目：直方图常用来构造负载均衡的范围划分。

- a. 某直方图的取值在 1 到 100 之间，分成 10 个区间 1-10、11-20、……、91-100，频数依次为 15、5、20、10、10、5、5、20、5、5。给出把这些值分成 5 个分区的均衡范围划分函数。
- b. 给定含 n 个区间的频数直方图，写出计算 p 个分区的均衡范围划分的算法。

思路：总共 100 个元组，每个分区应有 20 个，按累计频数找分界点，区间内部假设各个值出现的可能性相同。

解答：

a. 各区间累计频数：到 10 为 15，到 20 为 20，到 30 为 40，到 40 为 50，到 50 为 60，到 60 为 65，到 70 为 70，到 80 为 90，到 90 为 95，到 100 为 100。

| 分区 | 取值范围 | 元组数 |
| --- | --- | --- |
| 1 | 1-20 | 15 + 5 = 20 |
| 2 | 21-30 | 20 |
| 3 | 31-50 | 10 + 10 = 20 |
| 4 | 51-75 | 5 + 5 + 10 = 20 |
| 5 | 76-100 | 10 + 5 + 5 = 20 |

第 4 个分区要从 71-80 区间的 20 个元组里取一半，假设区间内均匀分布，取 71-75。划分向量为 $[21, 31, 51, 76]$，向量中每个值是下一个分区的起始值。

b. 设第 $j$ 个区间的取值为 $[s_j, e_j]$，频数为 $f_j$，元组总数 $N = \sum_{j=1}^{n} f_j$。第 $i$ 个分界点（ $i = 1, \dots, p-1$）应落在第 $k_i = iN/p$ 个元组上。先找出第 $k_i$ 个元组所在的区间 $j$，再在区间内按均匀分布插值：

$$v_i = s_j + (e_j - s_j) \cdot \frac{k_i - \sum_{l=1}^{j-1} f_l}{f_j}$$

```text
N = f[1] + ... + f[n]
cum = 0                      // 已经跳过的区间的频数之和
j = 1
for i = 1 to p-1:
    k = i * N / p
    while cum + f[j] < k:    // 第 k 个元组不在区间 j 中，跳到下一个区间
        cum = cum + f[j]
        j = j + 1
    v[i] = s[j] + (e[j] - s[j]) * (k - cum) / f[j]
    // 取值为整数时，v[i] 约等于第 i 个分区的最后一个值，
    // 划分向量中放 floor(v[i]) + 1
return [v[1], ..., v[p-1]]
```

用 a 的数据验算： $i = 4$ 时 $k = 80$，落在 71-80 区间，此前累计 70， $v_4 = 71 + 9 \times 10/20 = 75.5$，取整加 1 得 76，与 a 的结果一致。

（更正：官方答案说划分向量是 $[k_1, k_2, \dots, k_{p-1}]$，这些只是元组的序号；向量中应放第 $k_i$ 个元组对应的属性值，也就是上面的 $v_i$。）

### 18.6 备份副本分散存放

题目：大规模并行数据库会把每个数据项在另一个处理器的磁盘上多存一份，以免某个处理器故障时丢失数据。

- a. 为什么把一个处理器上数据项的副本分散到多个处理器上，比全部放在一个备份处理器上更好？
- b. 怎样用虚拟处理器划分高效地实现 a 中副本的分散存放？
- c. 用 RAID 存储代替为每个数据项多存一份副本，有哪些好处和坏处？

思路：故障后的负载要分摊；虚拟处理器把数据切成很多小块，每块的副本可以放到不同处理器上；RAID 只防磁盘损坏，不防处理器故障。

解答：官方答案缺（PDF 里只有占位词 FILL），以下为整理补充。

- a. 某个处理器故障后，原本由它处理的请求要转给存放副本的处理器。副本全在一台备份处理器上时，这台机器的负载会突然翻倍，成为瓶颈；副本分散在多台处理器上时，额外负载也分摊到多台机器，每台只增加一小部分。
- b. 先把数据划分给数量远多于实际处理器的虚拟处理器。每个虚拟处理器的主副本映射到一个实际处理器，备份副本映射到另一个实际处理器，并让同一实际处理器上各个虚拟处理器的备份映射到不同的实际处理器（例如按轮转方式错开分配）。这样一台处理器上数据的副本自然就分散在多台处理器上。
- c. RAID 的好处：用奇偶校验（如 RAID 5）时，存储开销比完整副本小；单块磁盘损坏可以在本机恢复，不需要其他处理器参与。坏处：RAID 只能应对磁盘故障，处理器或整个结点出故障时，它磁盘上的数据照样访问不到，要等结点修复；RAID 5 每次写还要更新校验块，写开销较大。

### 18.7 对划分后的关系建索引

题目：要给一个已经划分的大关系建索引。划分（包括虚拟处理器划分）的思想能用在索引上吗？分两种情况说明（为简单起见，划分和索引都只针对单个属性）：

- a. 索引建在关系的划分属性上。
- b. 索引建在划分属性以外的属性上。

思路：索引同样可以划分；索引属性就是划分属性时各分片建局部索引即可，否则要在索引属性上单独划分索引。

解答：官方答案缺（PDF 里只有占位词 FILL），以下为整理补充。

- 可以。索引本身也能按索引码划分到多个处理器上，虚拟处理器划分同样适用。
- a. 索引属性就是划分属性时，每个处理器为本地分片建局部索引，整个索引的划分方式与关系一致。按这个属性查询时，先用划分向量（或散列函数）确定分片所在的处理器，再查那台机器上的局部索引。
- b. 索引属性不是划分属性时，有两种做法：
  - 每个分片各建局部索引。查询时无法根据索引属性的值判断元组在哪个分片，要把请求发给所有处理器。
  - 建一个全局索引，按索引属性单独做范围划分或虚拟处理器划分，索引项中记录元组所在的处理器和位置。查询先定位到一个索引分区，再到相应处理器取元组。代价是更新关系时，可能要同时修改另一台处理器上的索引分区。

### 18.8 划分失衡后重新划分

题目：为某关系选好的均衡范围划分向量，在关系更新后变得不均衡。即使使用虚拟处理器划分，某个虚拟处理器更新后也可能分到大量元组，需要重新划分。

- a. 某虚拟处理器的元组明显过多（比如是平均值的两倍）。说明怎样通过拆分这个分区、增加虚拟处理器的数目来重新划分。
- b. 如果虚拟处理器不按轮转方式分配给实际处理器，而是可以任意分配，并用一张映射表记录分配情况。某个结点负载过重时，怎样重新均衡负载？
- c. 假设没有更新。重新划分或重新分配虚拟处理器时，必须停止查询处理吗？

思路：拆分过大的范围、迁移虚拟处理器、先复制再切换映射。

解答：官方答案缺（PDF 里只有占位词 FILL），以下为整理补充。

- a. 取该虚拟处理器所含元组在划分属性上的中位数作为新的分界值，把它的范围一分为二，一半留给原虚拟处理器，另一半交给新增的虚拟处理器。在划分向量中插入这个分界值，再把新虚拟处理器分配给某个实际处理器，把相应元组搬过去。
- b. 在映射表中挑出过载结点上的若干虚拟处理器，改为映射到负载较轻的结点，并迁移这些虚拟处理器的数据。可以反复挑选，直到各结点负载大致相当。
- c. 不必停止。没有更新时数据不变，可以先把要迁移的数据复制到新位置，复制期间查询继续按旧的划分向量或映射表访问旧位置；复制完成后一次性（原子地）切换到新的向量或映射表，之后的查询访问新位置，最后删除旧数据。

### 19.1 局域网与广域网上的分布式数据库

题目：为局域网设计的分布式数据库，和为广域网设计的分布式数据库，可能有什么不同？

思路：局域网传输快，复制和分片对性能的帮助不如在广域网上大，主要用来提高可靠性和可用性。

解答：

- 局域网上的数据传输比广域网快得多。因此在局域网上，复制和分片带来的吞吐量和加速比提升不如在广域网上明显。
- 即使在局域网上，复制仍然有用，可以提高系统的可靠性和可用性。

### 19.2 分布式系统中的故障类型

题目：

- a. 列出分布式系统中可能发生的故障类型。
- b. a 中哪些故障在集中式系统中也会发生？

思路：站点故障、磁盘故障、通信故障，前两种集中式系统也有。

解答：

- a. 站点故障；磁盘故障；通信故障，即链路断开使一个或多个站点与网络失去联系。教材正文在分布式系统的故障类型中还单独列出了消息丢失和网络分割。
- b. 站点故障和磁盘故障。

### 19.3 两阶段提交如何应对故障

题目：事务执行 2PC 的过程中发生故障。针对 19.2 a 中列出的每一类故障，说明 2PC 怎样保证事务的原子性。

思路：所有参与站点回复 ready 之后，提交还是中止只由协调者决定，其他站点必须直接或间接得知这个决定才行动，所以各站点的结果不会冲突。

解答：

官方答案给的是一个统一的论证：所有站点都写了 `<ready T>` 之后，只有协调者能决定提交或中止；任何站点之后的提交或中止，都必须先直接从协调者、或间接从其他站点确认协调者的决定。

一个站点写 `<abort T>` 只可能是下面三种情况：

1. 它还没有写 `<ready T>`。协调者没有、以后也不会收到它的 ready 消息，只能做出中止决定。
2. 它已写 `<ready T>`，询问后发现另一个站点有 `<abort T>`。那个站点一定是确认了协调者的中止决定才中止的，所以跟着中止是正确的。
3. 它本身就是协调者。提交决定只能由协调者做出，其他站点不可能已经提交或将来提交。

一个站点写 `<commit T>` 只可能是下面两种情况：

1. 它已写 `<ready T>`，询问后发现另一个站点有 `<commit T>`。那个站点一定是确认了协调者的提交决定。
2. 它本身就是协调者。中止决定也只能由协调者做出，其他参与站点不会已经中止。

因此不会出现一部分站点提交、另一部分站点中止的情况。按故障类型对照如下（整理补充，依据教材中 2PC 的故障处理规则）：

| 故障 | 2PC 的处理 |
| --- | --- |
| 参与站点故障 | 协调者在收到它的 ready 之前发现它故障，就中止事务。该站点恢复后查日志：有 commit 记录就重做；有 abort 记录就撤销；只有 ready 记录就向协调者或其他站点询问结果；什么控制记录都没有就撤销 |
| 协调者故障 | 活跃站点中有站点写了 commit 就提交，有站点写了 abort 就中止，有站点没写 ready 也中止；如果所有活跃站点都只有 ready 记录，只能等协调者恢复（阻塞问题） |
| 通信链路故障、网络分割 | 与协调者在同一分割中的站点，把联系不上的站点当作站点故障处理；不在同一分割中的站点，把它当作协调者故障处理，同样可能阻塞 |
| 磁盘故障 | 日志写在稳定存储上，ready、commit、abort 这些控制记录不会因单块磁盘损坏而丢失，恢复时仍能按上面的规则处理 |

### 19.4 A 能否区分 B 的几种状况

题目：分布式系统中有 A、B 两个站点。A 能否区分下面三种情况：B 宕机；A 与 B 之间的链路断开；B 负载极重，响应时间是平时的 100 倍？这对分布式系统的恢复有什么启示？

思路：通信恢复之前区分不了，所以恢复策略必须在三种情况下都正确。

解答：

- 在与 B 恢复通信之前，A 无法区分这三种情况，它看到的都是 B 没有回应。
- 启示：B 联系不上期间，A 采取的动作必须不论实际是哪种情况都正确；而且要保证通信恢复后，B 能以一致的方式重新加入分布式系统。

### 19.5 用序号代替时间戳的持久消息

题目：本章的持久消息方案依赖时间戳，并丢弃过旧的已接收消息。给出一个基于序号的替代方案。

思路：按（发送站点，接收站点）编连续序号，接收方按序接收并确认，发送方重传直到收到确认。

解答：

- 每条消息带一个序号，序号对每一对（发送站点，接收站点）唯一；同一对站点之间每发一条新消息，序号加 1。
- 接收站点只有在已收到所有更小序号的消息时，才把新消息存入已接收消息关系，并发送确认。
- 发送站点反复重传一条消息，直到收到的确认中的序号不小于该消息的序号，然后把它从发送队列中删除。
- 接收站点收到的消息序号如果小于该发送站点最近一条已存消息的序号，就直接丢弃（这是重复消息）。消息在本地处理完之后，已接收消息关系中对每个发送站点只需保留最近一条消息的序号。
- 开销对比：序号方案在接收站点为每个发送站点保存固定的少量信息，与收到多少条消息无关；时间戳方案要为每条消息占用额外空间。超时时间内收到的消息数比站点数少时，时间戳方案的存储开销更小，否则序号方案更小。

### 19.6 读一个副本、写所有可用副本的错误

题目：举例说明"读一个副本、写所有可用副本"方法会导致错误的状态。

思路：宕机站点恢复后没有追上期间的更新，事务从它那里读到了旧值。

解答：

- 某账户余额复制在 N 个站点上，当前各站点都是 100。事务 $T_1$、 $T_2$ 先后各存入 10，正确结果应为 120。
- $T_1$ 执行时站点 s 宕机， $T_1$ 只把 110 写到了其他可用站点。
- s 恢复后没有追上这次更新。 $T_2$ 恰好从 s 读余额，读到 100，加 10 后把 110 写到所有可用站点。
- 最终余额是 110， $T_1$ 的存款丢了。

### 19.7 数据复制与远程备份的区别

题目：分布式系统中的数据复制，和维护一个远程备份站点，有什么区别？

思路：远程备份只在主站点执行事务、靠发送日志同步，不需要 2PC；复制系统在多个站点执行事务，可用性更高，开销也更大。

解答：

| 对比项 | 远程备份 | 分布式数据复制 |
| --- | --- | --- |
| 事务在哪里执行 | 只在主站点 | 所有站点都执行事务代码 |
| 如何保持同步 | 主站点把所有日志记录发给备份站点 | 更新各个副本，用两阶段提交保证数据一致 |
| 故障时 | 主站点故障后由备份站点接管 | 其他站点上的副本继续提供服务 |
| 可用性与代价 | 可用性较低，但成本和执行开销小，没有 2PC 的开销 | 多份副本，可用性更高，但要承担 2PC 等开销 |

### 19.8 惰性复制导致不一致

题目：举例说明，即使更新都要在主副本上加排他锁，惰性复制仍可能使数据库进入不一致状态。

思路：事务读的是还没同步的旧副本，再把基于旧值算出的结果写回主副本。

解答：

- 某账户余额复制在 N 个站点上，当前各处都是 100。事务 $T_1$、 $T_2$ 先后各存入 10，正确结果是 120。
- $T_1$ 在主副本上加排他锁，把余额改为 110 后提交。由于是惰性复制，站点 s 上的副本暂时还是 100。
- $T_2$ 从站点 s 读余额，得到 100，然后在主副本上加排他锁，写入 110。
- 主副本最终是 110。排他锁只保证两个写操作不同时进行，挡不住 $T_2$ 从过期副本读数。

### 19.9 分布式死锁检测算法的正确性

题目：考虑下面的死锁检测算法。站点 $S_1$ 上的事务 $T_i$ 向站点 $S_3$ 上的 $T_j$ 请求资源时，发出带时间戳 $n$ 的请求消息，并在 $S_1$ 的局部等待图中插入边 $(T_i, T_j, n)$；只有当 $T_j$ 已收到请求且不能立即授予时，才在 $S_3$ 的局部等待图中插入边 $(T_i, T_j, n)$。同一站点内的请求按通常方式处理，边上不带时间戳。中心协调者向各站点发起检测，各站点把局部等待图发给它；每张局部图反映的是该站点某一瞬间的状态，站点之间并不同步。协调者构造的图中，每个事务对应一个顶点；边 $(T_i, T_j)$ 存在当且仅当某张局部等待图中有边 $(T_i, T_j)$，或者某条边 $(T_i, T_j, n)$ 出现在不止一张局部等待图中。证明：构造的图中有环，则系统处于死锁状态；构造的图中无环，则算法开始执行时系统不处于死锁状态。

思路：构造出的图中每条边都对应真实的等待，所以有环即死锁；算法开始时已存在的死锁环，其边在算法结束前不会消失，一定会被收集到。

解答：

有环则死锁。设构造的图中有环 $T_i \to T_j \to \cdots \to T_m \to T_i$，环上的边分两类：

- 局部边 $(T_k, T_l)$，确实表示 $T_k$ 在等待 $T_l$。
- 分布式边 $(T_k, T_l, n)$。它出现在两个站点的图中，说明 $T_k$ 的请求已经到达 $T_l$ 所在站点且不能立即授予， $T_k$ 确实在等待 $T_l$。

环上每条边都是真实的等待关系，构成循环等待，系统处于死锁（官方答案说详细证明见 Stuart 等人 1984 年的文献）。

无环则算法开始时无死锁，证明它的逆否命题：开始时有死锁，则构造的图中有环。一旦发现 $T_k$ 在等待 $T_l$：

- 两者在同一站点，就加入局部边 $(T_k, T_l)$；
- 两者在不同站点，两个站点都会加入边 $(T_k, T_l, n)$。

如果能在同一瞬间收集到所有局部等待图，当时存在的循环等待一定会在构造的图中形成环。实际上各图不是同一瞬间收集的，但算法开始时已经存在的循环等待，环上的事务都在等待，谁也不会释放资源，这些边在算法结束前都不会消失。所以算法开始前已存在的环一定会被检测到。

### 19.10 按工厂水平分片的查询策略

### 19.12 适合与不适合云的应用

### 19.14 同一时刻只有一个全局事务的多数据库

题目：一个多数据库系统保证任一时刻最多只有一个活跃的全局事务，并且每个局部站点保证局部可串行化。

- a. 提出能保证任一时刻最多只有一个活跃全局事务的方法。
- b. 举例说明，即使满足这些假设，仍可能产生不可串行化的全局调度。

思路：用一把全局锁让全局事务排队执行；反例是局部事务在两个站点上把两个全局事务排成相反的顺序。

解答：

a. 在某个站点上设一个特殊数据项，全局事务开始前必须先获得它上面的锁，事务结束后释放，这样同一时刻只会有一个全局事务在运行。为了不依赖这一个站点始终正常，可以用选举算法从当前正常的站点中选出协调者，规定这把锁加在协调者站点上的特殊数据项上。

b. 两个站点、四个事务： $T_1$ 是站点 1 的局部事务， $T_2$ 是站点 2 的局部事务， $T_{G1}$、 $T_{G2}$ 是跨两个站点的全局事务； $X_1$、 $Y_1$ 在站点 1， $X_2$、 $Y_2$ 在站点 2。按时间顺序执行：

| 步骤 | $T_1$ | $T_2$ | $T_{G1}$ | $T_{G2}$ |
| --- | --- | --- | --- | --- |
| 1 | write($Y_1$) | | | |
| 2 | | | read($Y_1$) | |
| 3 | | | write($X_2$) | |
| 4 | | read($X_2$) | | |
| 5 | | write($Y_2$) | | |
| 6 | | | | read($Y_2$) |
| 7 | | | | write($X_1$) |
| 8 | read($X_1$) | | | |

- $T_{G2}$ 在 $T_{G1}$ 结束之后才开始，满足"最多一个活跃全局事务"。
- 站点 1： $T_1$ 写 $Y_1$ 后 $T_{G1}$ 读 $Y_1$，得 $T_1 \to T_{G1}$； $T_{G2}$ 写 $X_1$ 后 $T_1$ 读 $X_1$，得 $T_{G2} \to T_1$。局部可串行化，串行顺序为 $T_{G2} \to T_1 \to T_{G1}$。
- 站点 2： $T_{G1}$ 写 $X_2$ 后 $T_2$ 读，得 $T_{G1} \to T_2$； $T_2$ 写 $Y_2$ 后 $T_{G2}$ 读，得 $T_2 \to T_{G2}$。串行顺序为 $T_{G1} \to T_2 \to T_{G2}$。
- 两个站点对 $T_{G1}$、 $T_{G2}$ 先后的要求相反，全局优先图有环，全局调度不可串行化。

### 19.15 全局事务都只读的多数据库

题目：一个多数据库系统中，每个局部站点保证局部可串行化，所有全局事务都是只读的。

- a. 举例说明这样的系统仍可能出现不可串行化的执行。
- b. 说明怎样用票据（ticket）方案保证全局可串行化。

思路：只读的全局事务也会因局部事务的写形成跨站点的环；票据让全局事务在每个站点上必然冲突，再由全局事务管理器统一它们的先后。

解答：

a. 沿用 19.14 的站点和数据项，两个全局事务都只读：

| 步骤 | $T_1$ | $T_2$ | $T_{G1}$ | $T_{G2}$ |
| --- | --- | --- | --- | --- |
| 1 | | | | read($X_1$) |
| 2 | write($X_1$) | | | |
| 3 | | | read($X_1$) | |
| 4 | | | read($X_2$) | |
| 5 | | write($X_2$) | | |
| 6 | | | | read($X_2$) |

站点 1 的串行顺序是 $T_{G2} \to T_1 \to T_{G1}$，站点 2 的串行顺序是 $T_{G1} \to T_2 \to T_{G2}$。两个站点各自可串行化，合起来形成环，全局调度不可串行化。

b. 局部可串行化已经得到保证，所以全局优先图中的环必然跨越至少两个站点，并涉及至少两个不同的全局事务。票据方案在每个站点设一个票据数据项，保证任意两个全局事务只要访问同一站点的数据，就会在该站点的票据上冲突。全局事务管理器控制各全局事务访问票据的次序，使全局事务在所有站点上的串行化顺序一致，于是它们不可能出现在全局优先图的环中。
