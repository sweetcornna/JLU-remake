## 查询与关系代数

### 1. 要查询计算机学院学生的选课信息，有下面两种关系代数表达式，请分析它们的优劣。

① $\sigma_{\mathit{dept\_name}=\text{'Comp. Sci.'}}(\mathit{student} \bowtie \mathit{takes})$

② $\sigma_{\mathit{dept\_name}=\text{'Comp. Sci.'}}(\mathit{student}) \bowtie \mathit{takes}$

出处：2020-2021 学年第 1 学期 分析题第 3 题。

答案要点：

1. 两个表达式结果相同。选择条件只涉及 `dept_name`，而 `takes` 里没有这个属性，所以选择可以先在 `student` 上做。
2. ① 先把全部学生和全部选课记录做自然连接，再筛选计算机学院。连接产生的中间结果包含所有学生的选课记录，`student`、`takes` 都很大时，这个中间结果很大，费时间和存储。
3. ② 先从 `student` 中选出计算机学院的学生，再和 `takes` 连接。参加连接的元组少，中间结果小，一般更快。
4. 依据的等价规则：选择条件 $\theta$ 只涉及 $E_1$ 的属性时，$\sigma_\theta(E_1 \bowtie E_2) = \sigma_\theta(E_1) \bowtie E_2$。尽早做选择是启发式优化的基本规则，DBMS 的查询优化器会自动把 ① 改写成 ②。
5. 如果两张表都很小，或者计算机学院学生占全校学生的比例很大，两种写法差别不大。

## 表设计与完整性约束

### 2. 在学生表中，将学号（ID）和姓名（name）的组合设计为该表的主键是否合理？为什么？

出处：2019-2020 学年第 2 学期 分析题第 1 题。

答案要点：

1. 不合理。
2. 学号单独就能唯一标识学生，`(ID, name)` 是超码，但不是最小的，不是候选码。主码应该从候选码里选。
3. 主键是 `(ID, name)` 时，数据库只保证"学号加姓名"的组合不重复，同一个学号配不同姓名的两条记录也能插进去，学号唯一这条规则就守不住了。
4. 姓名可能重复、可能修改，也比学号长。其他表（如选课表）用外键参照学生时，还得多带一个姓名列。
5. 正确做法是只用学号做主键：

```sql
create table student (
    ID        varchar(10),
    name      varchar(20) not null,
    dept_name varchar(20),
    tot_cred  numeric(3,0),
    primary key (ID)
);
```

第 1、2 条是原稿答案的意思，其余为整理补充。

### 3. 我校本科生入学后被定义了多种唯一标识：教学号、考试号、一卡通编号，此外还有学生本人的身份证号。假设这些编号都是学生实体集的属性，它们在 Data Model 中被称为什么？反映在 SQL 的 DDL 中对应哪个关键字？你认为应选择哪个属性作为学生实体集的主码？

出处：2013-2014 学年第 2 学期 数据库系统原理 第 3 题。

答案要点：

1. 每个编号单独都能唯一标识一个学生，而且没有多余属性，它们都是学生实体集的候选码。
2. DDL 中，被选作主码的那个用 `primary key` 声明；其余候选码用 `unique` 声明，一般再加 `not null`。
3. 原稿选一卡通编号作主码。这题是开放题，写出理由即可。选主码的原则：所有学生都有、在校期间不变、简短、不涉及隐私。
4. 身份证号涉及个人隐私，留学生等可能没有，不适合做主码。教学号、一卡通编号都满足上面的原则，选哪个都说得通。
5. 示例（列类型为整理时假设）：

```sql
create table 学生 (
    一卡通编号 varchar(20),
    教学号     varchar(20) not null unique,
    考试号     varchar(20) not null unique,
    身份证号   varchar(18) unique,
    姓名       varchar(20) not null,
    primary key (一卡通编号)
);
```

### 4. 用户到银行开了一个储蓄账户（`account` 表），可以随时存钱、取钱，分别对应数据库中的什么操作？在 ATM 机上取钱，卡内余额不足时 ATM 机不做任何支付，如何将此规则定义在该表上？

出处：2015 年 数据库原理A 分析题第 3 题。

答案要点：

1. 开户：`insert`，插入一条账户记录。
2. 存钱：`update`，增加 `balance`。
3. 取钱：`update`，减少 `balance`。
4. 查余额：`select`；销户：`delete`。
5. 题目要求"定义在该表上"，应该用约束：给 `balance` 加 `check (balance >= 0)`。取款会让余额变负时，`update` 违反约束被拒绝，事务回滚，ATM 收到失败结果，不出钞。

表结构假设为 `account(account_number, balance)`：

```sql
alter table account
    add constraint balance_nonneg check (balance >= 0);

-- 取 500 元，余额不足时这条语句报错，余额不变
update account
set balance = balance - 500
where account_number = 'A-101';
```

6. 注意 MySQL 从 8.0.16 起才真正执行 `check` 约束，更早的版本会解析但忽略。老版本只能用触发器实现同样的规则。

### 5. 某学校教务管理系统有学生表（学号，姓名，出生日期，学院编号）和选课信息表（学号，课程编号，成绩）。规定某学生退学后，自动删除该生的所有选课记录，该如何定义此业务逻辑？

出处：2018-2019 学年第 2 学期 分析题第 4 题。

答案要点：

1. 最直接的办法是在选课信息表上定义外键，并指定级联删除 `on delete cascade`。删除学生表中的某个学生时，选课信息表里参照他的记录被自动删除，同时还保证了参照完整性。

```sql
create table 选课信息 (
    学号     varchar(20),
    课程编号 varchar(20),
    成绩     numeric(4,1),
    primary key (学号, 课程编号),
    foreign key (学号) references 学生(学号)
        on delete cascade
);
```

2. 也可以用触发器（原稿作者的答案）：在学生表上定义删除触发器，删除一个学生时，删除选课信息表中学号等于该生学号的元组。

```sql
create trigger 退学删除选课 after delete on 学生
referencing old row as orow
for each row
begin atomic
    delete from 选课信息
    where 学号 = orow.学号;
end;
```

MySQL 写法：

```sql
create trigger 退学删除选课
before delete on 学生
for each row
    delete from 选课信息 where 学号 = old.学号;
```

3. 两种办法的取舍：能用外键级联就用级联，声明式、不用写代码；规则更复杂（比如删除前先把成绩归档）时再用触发器。
4. 如果选课信息表上已经有不带 `cascade` 的外键，删除学生时外键检查会先报错，MySQL 里要用 `before delete` 触发器先删掉选课记录。

### 6. 吉林大学一卡通实现了与银行卡的绑定，当一卡通内余额小于某一设定金额时，可以通过银行卡直接转账。请问如何实现自动转账？转账的金额在数据库端如何设定？

出处：2015 年 数据库原理A 分析题第 4 题。

答案要点：

1. 关键词是"自动"，用触发器实现（原稿答案）：在一卡通表上建触发器，一卡通余额被修改时触发；修改后的余额低于设定金额，就执行转账操作：银行卡账户扣钱，一卡通加钱。
2. 触发器里的操作和引起触发的消费操作在同一个事务中执行，转账的扣款和到账要么都成功、要么都不做。
3. 金额的设定（整理补充）：不要把阈值和转账金额写死在触发器里，而是建一张绑定设置表，每张一卡通一行，记录绑定的银行账户、触发转账的阈值、每次转账金额。用户修改设置就是对这张表 `update`，触发器执行时从表里读取。
4. 转账前要检查银行卡余额是否足够，不够就不转，避免因为转账失败把正常消费也回滚掉。

表结构为整理时假设：`card(card_id, balance)` 一卡通表，`bank_account(account_id, balance)` 银行账户表，`card_bind(card_id, account_id, threshold, amount)` 绑定设置表。MySQL 不允许触发器再修改触发它的那张表，所以这里用 `before update` 触发器直接改写 `new.balance`：

```sql
delimiter //
create trigger auto_transfer
before update on card
for each row
begin
    declare v_threshold decimal(10,2);
    declare v_amount    decimal(10,2);
    declare v_account   varchar(20);

    select threshold, amount, account_id
      into v_threshold, v_amount, v_account
      from card_bind
     where card_id = new.card_id;

    if new.balance < v_threshold
       and (select balance from bank_account
             where account_id = v_account) >= v_amount then
        update bank_account
           set balance = balance - v_amount
         where account_id = v_account;
        set new.balance = new.balance + v_amount;
    end if;
end //
delimiter ;

-- 用户设定：余额低于 20 元时自动转入 100 元
update card_bind
set threshold = 20, amount = 100
where card_id = 'C01';
```

没有绑定记录的卡，查出的阈值是 `null`，`if` 条件为 `unknown`，不会转账。

### 7. 某银行对不同储蓄金额执行不同利率：低于 10 万元一年支付 4.2% 的利息，10 万元以上（包括 10 万）一年支付 4.5% 的利息。储蓄账户表为 `account(aid, balance, branch_name)`，写出与上述业务对应的 SQL 语句，如何保证其执行结果的正确性？

出处：2016-2017 学年第 2 学期 数据库原理 简答题第 7 题；2015 年 数据库原理A 简答题第 7 题。

答案要点：

1. 写法一：两条 `update`，必须先给高余额账户计息，再给低余额账户计息。

```sql
start transaction;

update account
set balance = balance * 1.045
where balance >= 100000;

update account
set balance = balance * 1.042
where balance < 100000;

commit;
```

2. 顺序不能反。若先执行 `balance < 100000` 那条，余额 9.8 万的账户加息后变成 102116 元，跨过了 10 万，第二条语句又会按 4.5% 给它加一次，被重复计息。先给高余额加息，这些账户余额只增不减，仍然不低于 10 万，第二条语句不会再选中它们。
3. 写法二：用 `case` 一条语句完成。每个元组只被更新一次，条件按更新前的旧值判断，不存在顺序问题，更推荐。

```sql
update account
set balance = case
                  when balance < 100000 then balance * 1.042
                  else balance * 1.045
              end;
```

4. 保证正确性的要点：
   - 两条语句的写法注意先后顺序，或者直接用 `case`；
   - 把计息放在一个事务里，中途出错整体回滚，不会出现一部分账户加了息、另一部分没加；
   - 计息期间有别的事务在存取款时，靠并发控制（加锁或可串行化隔离级别）避免丢失更新。

第 1、3 条的两种写法是原稿给出的，第 2、4 条的解释为整理补充。

## 视图与授权

### 8. 某学校教务管理系统为每个学院提供了固定的上课教室，系统规定不同学院的教务办负责人员登录后，只能有权支配各自学院的教室资源。需要定义哪种数据库对象实现此需求？为什么？

出处：2018-2019 学年第 2 学期 分析题第 3 题。

答案要点：

1. 定义视图，再配合授权（原稿作者答案）：为每个学院建一个只包含本学院教室的视图，把这个视图上的权限授予对应学院的教务负责人。负责人没有基表的权限，只能通过视图看到和修改本学院的教室。
2. 用角色管理权限（原稿 gpt 答案的意思）：为每个学院建一个角色，把视图上的权限授给角色，再把角色授给该学院的教务人员。人员变动时只要授予或收回角色。
3. 视图加 `with check option`，防止通过视图把教室改到别的学院名下。

表结构为整理时假设：`教室(教室号, 楼号, 容量, 学院编号)`，以计算机学院（编号 `CS`）为例：

```sql
create view 计算机学院教室 as
select 教室号, 楼号, 容量, 学院编号
from 教室
where 学院编号 = 'CS'
with check option;

create role 计算机学院教务;
grant select, update on 计算机学院教室 to 计算机学院教务;
grant 计算机学院教务 to cs_admin;   -- cs_admin 为计算机学院教务负责人的数据库账号
```

SQL 部分为整理补充。

### 9. 学校所有学生的数据都存在同一张表中，但各个学院的教务管理人员登录后只能看到自己学院的学生。在数据库端是如何实现的？

出处：2014 年 数据库原理A 分析题第 4 题。

答案要点：

1. 用视图实现行级的访问控制：为每个学院建一个视图，视图只选出该学院的学生。
2. 用授权控制访问：不给教务管理人员学生基表的查询权限，只把本学院视图的 `select` 权限授给他们（可以先授给角色，再把角色授给人员）。
3. 管理人员登录后只能查询分配给他的视图，看不到其他学院的学生。
4. 学院多时，也可以另建一张"数据库账号与学院"的对照表，只定义一个视图，在视图条件里用 `current_user` 和对照表连接，按登录账号过滤出本学院学生（整理补充，各系统写法有差别，这里只说思路）。

### 10. 假设表学生（学号，姓名，出生日期，籍贯，学院）存放所有学院的学生数据，用户 U1 已拥有在该表上查询的权限，如何限制 U1 只查询"计算机学院"的学生数据？请写出相应 SQL 语句。

出处：2013-2014 学年第 2 学期 数据库系统原理 第 1 题。原稿只抄了题目，没有答案。

答案要点（整理补充）：

1. 先建一个只含计算机学院学生的视图。
2. 收回 U1 在学生基表上的查询权限。只授予视图权限不够，U1 原来的基表权限还在，仍然能查全表。
3. 把视图上的查询权限授给 U1。

```sql
create view 计算机学院学生 as
select 学号, 姓名, 出生日期, 籍贯, 学院
from 学生
where 学院 = '计算机学院';

revoke select on 学生 from U1;

grant select on 计算机学院学生 to U1;
```

4. 注意：
   - `revoke` 要由当初授权给 U1 的用户（或 DBA）执行；
   - 如果 U1 的权限是通过 `public` 或某个角色得到的，要从那里收回；
   - 如果 U1 已经把基表查询权限转授给了别人，大多数系统默认级联收回，那些人的权限也一起没了；语句末尾写 `restrict` 时，存在转授就会收回失败。

### 11. 吉林大学的 BBS 系统，用户可以以游客身份浏览其他人的留言帖，但如果想发言或回复留言，必须先登录。为什么？在数据库端如何实现？

出处：2014 年 数据库原理A 分析题第 1 题。

答案要点：

1. 为什么：浏览只读数据，不会改变数据库；发言、回复要向数据库插入数据，必须先确认用户身份，只有通过身份验证的正式用户才被授予写入权限。这样发帖记录能对应到具体用户，便于管理和追责。
2. 数据库端的实现：
   - 游客对应一个只有查询权限的账号或角色，只授予帖子表的 `select`；
   - 注册用户登录后使用另一个角色，在 `select` 之外再授予 `insert`；
   - 修改、删除只能针对自己的帖子，这类行级限制要靠应用程序检查，或者通过视图、存储过程控制，不要直接把帖子表的 `update`、`delete` 权限授给所有用户。

表名为整理时假设，`帖子` 表存放留言：

```sql
create role 游客;
create role 注册用户;

grant select on 帖子 to 游客;
grant select, insert on 帖子 to 注册用户;

grant 游客 to guest_account;
grant 注册用户 to member_account;
```

（更正：原文作 `grant insert update delete on jluBBS to user`，语法上少了逗号；而且把整张表的 `update`、`delete` 权限授给普通用户，任何用户都能改删别人的帖子。）

## 事务与恢复

### 12. 转账做到一半系统故障：数据库处于什么状态？如何解决？

三套卷的问法：

- 张三通过汇款转给李四 200 元。张三的账户已经减掉 200 元后系统发生故障，李四账户没有增加 200 元。请问数据库出现了什么样的状态？这个问题该怎么解决？数据库通过什么手段实现该操作？（2019-2020 学年第 2 学期 分析题第 2 题。原题金额单位"元""美元"混用，这里统一为元。）
- 从银行卡向学校一卡通转账，转账金额已从银行卡扣除、一卡通还未到账时，机器死机无法正常工作。请问数据库处于什么状态？这样的问题如何解决？（2014 年 数据库原理A 分析题第 2 题）
- 顾客 C1 在银行柜台办理业务，要把账户 B1 中的 50 万元转入账户 B2，柜员已把 B1 中的存款转出、还未存入 B2 时系统意外死机，数据库系统将如何处理这种故障？（2013-2014 学年第 2 学期 数据库系统原理 第 2 题，原稿无答案）

答案要点：

1. 状态：
   - 转账事务只执行了一半，没有提交。数据库处于不一致状态：转出方已经扣钱，转入方没到账，两个账户余额之和少了一笔。
   - 从事务状态看，这个事务没能到达提交状态，因故障进入失败状态，恢复时回滚后进入中止状态。
2. 解决办法：回滚这个未完成的事务，把转出方扣掉的钱加回来，数据库回到转账前的一致状态。之后由用户或柜员重新发起转账。
3. 手段：日志和恢复机制。
   - 事务每修改一个数据项，先写日志记录 `<T, X, 旧值, 新值>`，日志先于数据写到稳定存储上（先写日志规则）。
   - 死机属于系统故障，内存内容丢失，磁盘数据还在。系统重启后，恢复子系统扫描日志：重做阶段按日志重放更新；日志里只有 `<T start>`、没有 `<T commit>` 或 `<T abort>` 的事务进入撤销表。
   - 撤销阶段用日志中的旧值把这些事务的修改全部撤销，并写入 `<T abort>`。转账事务就在这一步被撤销，B1 余额恢复原值。
   - 如果事务在死机前已经写入 `<T commit>`，则重做它的修改，保证持久性。
   - 检查点可以缩小重启时需要扫描的日志范围。
4. 整个过程保证了事务的原子性：要么转账全部完成，要么像没发生过一样。

原稿第一问答"数据库处于不一致状态，应事务回滚，利用日志实现"，第二问补充了"事务处于失败状态"和日志恢复，这里合并展开。

### 13. 事务由哪几个状态组成？某人在移动支付时输入正确的支付密码并提交后发生断网，导致支付失败，该事务经历了哪几个状态？此时事务处于何种状态？

出处：2018-2019 学年第 2 学期 分析题第 2 题（问经历了哪几个状态）；2016-2017 学年第 2 学期 数据库原理 简答题第 13 题、2015 年 数据库原理A 简答题第 13 题（问由哪几个状态组成、此时处于何种状态）。

答案要点：

1. 事务的五个状态：
   - 活动状态：事务开始执行后的初始状态；
   - 部分提交状态：最后一条语句执行完之后；
   - 失败状态：发现正常执行不能继续之后；
   - 中止状态：事务回滚、数据库恢复到事务开始前的状态之后；
   - 提交状态：事务成功完成之后。
2. 支付事务经历的状态：活动 → 部分提交 → 失败 → 中止。
   - 输入密码、执行扣款等操作时，事务处于活动状态；
   - 用户点了提交，最后一条语句执行完，进入部分提交状态，但提交还没真正完成；
   - 这时断网，提交无法完成，事务进入失败状态；
   - 系统回滚该事务，撤销它的修改，进入中止状态。
3. 问"此时处于何种状态"：断网导致支付失败的那一刻处于失败状态，随后系统回滚，事务进入中止状态。
4. 中止后系统可以重启事务（断网这类与事务内部逻辑无关的错误适合重启，即用户重新支付），或者杀死事务。

（更正：原文简答题版本只答了"事务处于失败状态"。失败状态之后系统一定会回滚事务，事务最终进入中止状态，要把这一步也答出来。）

## 并发控制

### 14. 两个人分别在去哪儿网和携程网上购买 2017 年 7 月 2 日 CZ6147 次航班（长春飞往北京）的机票，该航班经济舱只剩一张票，两人同时下单，数据库中要如何控制？

出处：2015 年 数据库原理A 分析题第 1 题。

答案要点：

1. 问题：两人同时读到"余票 1"，都认为有票，各自把余票改成 0 并出票，结果一张票卖了两次。这是丢失更新。
2. 把"查余票、扣余票、生成订单"放在一个事务里，由并发控制保证两个事务的执行效果等价于某种串行顺序：先完成的人买到票，后一个人看到余票为 0，下单失败。
3. 悲观控制（加锁）：读余票时就对该记录加排他锁，直到事务提交或回滚才释放。另一个事务要等锁释放后才能读，读到的已经是 0。

表结构为整理时假设：`flight(flight_no, fly_date, remain)`，`remain` 为经济舱余票。`select ... for update` 是 MySQL、Oracle 等系统的写法：

```sql
start transaction;

select remain
from flight
where flight_no = 'CZ6147' and fly_date = '2017-07-02'
for update;
-- 应用程序判断：remain > 0 才继续，否则 rollback 并提示无票

update flight
set remain = remain - 1
where flight_no = 'CZ6147' and fly_date = '2017-07-02';

-- 插入订单记录
commit;
```

4. 乐观控制：读的时候不加锁，更新时检查余票（或版本号）有没有被改过，没改过才更新，否则提示票已售出。常用写法是带条件的更新，根据影响行数判断是否抢到：

```sql
update flight
set remain = remain - 1
where flight_no = 'CZ6147' and fly_date = '2017-07-02'
  and remain > 0;
-- 影响行数为 1：抢到票，继续生成订单并提交
-- 影响行数为 0：已经没票，回滚
```

5. 再给 `remain` 加 `check (remain >= 0)` 作为兜底。

悲观锁、乐观锁两种思路是原稿答案，SQL 为整理补充。

### 15. 支付宝账号与某银行卡绑定，该卡不可透支，目前卡内余额 100 元。一人在网上用该支付宝账号付款 100 元的同时，另一人用这张银行卡刷卡消费 100 元，能否都支付成功？若不可以，在数据库端如何控制？

出处：2014 年 数据库原理A 分析题第 3 题。

答案要点：

1. 不能都成功，只能成功一笔。先完成扣款并提交的那一笔成功，另一笔因余额不足失败。
2. 不加控制会出错：两个事务都读到余额 100，都判断够付，各自写回 0，结果付出去 200 元，账户只扣了 100 元，发生丢失更新。
3. 数据库端的控制：
   - 每笔支付作为一个事务执行；
   - 用封锁保证隔离性：读余额时加排他锁（或直接用带条件的 `update`，更新时自动加排他锁），另一个事务必须等前一个提交后才能读到新余额；
   - 或者把隔离级别设为可串行化；
   - 在余额上加 `check (balance >= 0)` 约束，防止透支。

表结构为整理时假设：`card_account(card_no, balance)`。

```sql
start transaction;

update card_account
set balance = balance - 100
where card_no = 'K001' and balance >= 100;
-- 影响行数为 1：扣款成功，commit
-- 影响行数为 0：余额不足，rollback，提示支付失败

commit;
```

4. 后执行的 `update` 要等先执行的事务释放锁，拿到锁后按最新余额 0 重新判断条件，不满足，扣款失败。

原稿只写了"设置事务隔离级别和锁来控制"，其余为整理补充。

### 16. 很多在线手机游戏支持离线操作，网络不通时可以离线玩，联网之后再进行数据同步。这个过程可能涉及数据库的哪些概念？

出处：2015 年 数据库原理A 分析题第 2 题。原稿没有答案。

答案要点（整理补充，开放题，言之有理即可）：

1. 事务：离线时每一步游戏操作（如购买道具、获得金币）作为本地事务提交；联网同步时，一批离线操作要作为一个整体上传，要么全部同步成功，要么全部不生效（原子性）。
2. 日志：客户端把离线期间的操作记在本地日志里，联网后按日志把操作重放到服务器数据库上；同步到一半又断网，靠日志回滚或者从断点继续。
3. 持久性和恢复：离线时已经完成的操作要写到本地存储，手机重启后不丢失。
4. 数据复制与一致性：客户端和服务器各有一份数据副本，离线期间两份不一致，同步后要重新达到一致。
5. 并发控制和冲突处理：离线期间，服务器上的同一数据可能被其他设备或其他玩家改过。同步时要检测冲突，思路和乐观并发控制（有效性检查、时间戳、版本号）一样：提交时检查数据在此期间有没有被别人改过，有冲突就按规则处理，如以服务器数据为准、以最后修改为准，或者合并。
6. 完整性约束和安全性：服务器在接收同步数据时要校验，如金币数不能为负、道具数量不能超过上限，防止客户端篡改数据作弊。

## 证明题

Armstrong 公理的三条规则（$\alpha, \beta, \gamma, \delta$ 为属性集）：

- 自反律：若 $\beta \subseteq \alpha$，则 $\alpha \to \beta$。
- 增补律：若 $\alpha \to \beta$，则 $\gamma\alpha \to \gamma\beta$。
- 传递律：若 $\alpha \to \beta$ 且 $\beta \to \gamma$，则 $\alpha \to \gamma$。

由这三条可以推出合并律、分解律、伪传递律。原稿第 22–23 页把三条推导律的证明写在一起。

### 17. 请用 Armstrong 公理证明合并律：若 $\alpha \to \beta$ 和 $\alpha \to \gamma$ 成立，则 $\alpha \to \beta\gamma$ 成立。每一步写出依据。

出处：2019-2020 学年第 2 学期 分析题第 3 题（原稿第 32 页只抄了题目，证明在第 22 页）。

证明：

1. $\alpha \to \beta$（已知）
2. $\alpha\gamma \to \beta\gamma$（由 1，两边增补 $\gamma$，增补律）
3. $\alpha \to \gamma$（已知）
4. $\alpha\alpha \to \alpha\gamma$，即 $\alpha \to \alpha\gamma$（由 3，两边增补 $\alpha$，增补律；$\alpha\alpha = \alpha$）
5. $\alpha \to \beta\gamma$（由 4 和 2，传递律）

证毕。

说明：题目原文作"阿姆斯特朗三定律（分解律、增强律和传递律）"。Armstrong 公理是自反律、增补律（增强律）、传递律，括号里的"分解律"应为自反律；分解律本身是要由公理推出的结论。上面的证明只用到增补律和传递律。

### 18. 请证明分解律：若函数依赖 $\alpha \to \beta\gamma$ 成立，则 $\alpha \to \beta$、$\alpha \to \gamma$ 成立。

出处：2020-2021 学年第 1 学期 分析题第 1 题。

证明：

1. $\alpha \to \beta\gamma$（已知）
2. $\beta\gamma \to \beta$（因为 $\beta \subseteq \beta\gamma$，自反律）
3. $\beta\gamma \to \gamma$（因为 $\gamma \subseteq \beta\gamma$，自反律）
4. $\alpha \to \beta$（由 1 和 2，传递律）
5. $\alpha \to \gamma$（由 1 和 3，传递律）

证毕。

### 19. 利用 Armstrong 公理证明伪传递律：若有 $A \to B$，$CB \to D$，则有 $AC \to D$。

出处：2016-2017 学年第 2 学期 数据库原理 简答题第 20 题；2015 年 数据库原理A 简答题第 20 题。原稿在这两处只有题目，第 22–23 页给了一般形式的证明。

一般形式：若 $\alpha \to \beta$ 且 $\gamma\beta \to \delta$，则 $\alpha\gamma \to \delta$。

证明（按本题字母）：

1. $A \to B$（已知）
2. $AC \to BC$，即 $AC \to CB$（由 1，两边增补 $C$，增补律）
3. $CB \to D$（已知）
4. $AC \to D$（由 2 和 3，传递律）

证毕。

### 20. 证明：如果关系 $r(R)$ 和 $s(S)$ 不含有任何相同属性，即 $R \cap S = \varnothing$，那么 $r \bowtie s = r \times s$。

出处：2018-2019 学年第 2 学期 分析题第 1 题。

证明：

1. 自然连接的定义：设 $R \cap S = \{A_1, A_2, \dots, A_n\}$，则

$$r \bowtie s = \Pi_{R \cup S}\left(\sigma_{r.A_1 = s.A_1 \land r.A_2 = s.A_2 \land \cdots \land r.A_n = s.A_n}(r \times s)\right)$$

2. 当 $R \cap S = \varnothing$ 时，$n = 0$，选择条件是空的合取式，恒为真，所以 $\sigma(r \times s) = r \times s$，一个元组都不删。
3. $r \times s$ 的属性就是 R 的属性加上 S 的属性。两者没有同名属性，没有重复列需要合并，所以 $R \cup S$ 正好是 $r \times s$ 的全部属性，投影 $\Pi_{R \cup S}$ 不去掉任何列，结果不变。
4. 因此 $r \bowtie s = r \times s$。

也可以从元组角度说明：元组 t 属于 $r \bowtie s$，当且仅当存在 $t_r \in r$、$t_s \in s$，使 $t[R] = t_r$、$t[S] = t_s$，并且 $t_r$、$t_s$ 在公共属性上取值相同。没有公共属性时最后一个条件自动满足，r 和 s 的任意一对元组都能拼成结果元组，这正是笛卡儿积的定义。

证毕。

原稿答案的思路：自然连接是在笛卡儿积的基础上，按公共属性取值相同筛选元组；没有公共属性就不用删除元组，结果和笛卡儿积一样。上面按定义写成了完整步骤。
