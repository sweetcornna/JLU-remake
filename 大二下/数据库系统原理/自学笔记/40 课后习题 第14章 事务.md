# 课后习题 第14章 事务

题目和解答依据 `数据库系统概念课后习题答案.pdf` 第 105–108 页整理，对应《数据库系统概念》第 6 版第 14 章的练习题（Practice Exercises）。题意为中文转述，解答为重新整理的中文要点。

## 本章导读

这一章的习题围绕事务的 ACID 性质、调度的可串行化与可恢复性、隔离级别和快照隔离。14.5 到 14.8 和调度判断直接相关，最值得动手做：14.6 练优先图，14.7 分清可恢复和无级联，14.8 用具体调度说明丢失更新在哪个隔离级别会出现。14.9、14.10 是快照隔离下写偏斜（write skew）的例子，做完就明白快照隔离为什么不保证可串行化。

课程笔记 `笔记/数据库系统原理笔记.pdf` 讲了第 14 章和第 15 章的锁协议、死锁处理；知识点整理见 `10 事务.md`、`11 并发控制.md`，历年调度题见 `24 事务调度题.md`。答案 PDF 只收了章末练习题 14.1–14.11，教材后面的习题（14.12 起）没有答案，这里不收。

几个判定方法先放在这里，后面反复用到：

- 冲突：两个不同事务对同一数据项的操作，且至少一个是写。
- 冲突可串行化：画优先图， $T_i$ 的操作先于与之冲突的 $T_j$ 的操作就连边 $T_i \to T_j$，无环即冲突可串行化，拓扑序就是等价的串行顺序。
- 可恢复： $T_j$ 读了 $T_i$ 写的数据，则 $T_i$ 必须先于 $T_j$ 提交。
- 无级联： $T_j$ 读 $T_i$ 写的数据之前， $T_i$ 已经提交。无级联一定可恢复。

## 习题

### 14.1 永不故障的系统是否需要恢复管理器

题目：假设有一个永远不会出故障的数据库系统，它还需要恢复管理器吗？

思路：系统故障只是需要撤销修改的原因之一，事务自己也会中止。

解答：

- 需要。系统不崩溃，事务照样会中止：程序逻辑错误、违反完整性约束、用户主动回滚、被并发控制选为死锁牺牲者。
- 中止的事务已经写进数据库的修改必须撤销，才能保证原子性。撤销要用日志里记下的旧值，这部分工作由恢复管理器负责。

### 14.2 文件系统中的原子性与持久性

题目：以你熟悉的操作系统中的文件系统为例：

- a. 创建文件、删除文件、向文件写数据分别包含哪些步骤？
- b. 原子性和持久性对这几种操作分别有什么意义？

思路：把一次文件操作拆成对几个磁盘结构的修改，再看这些修改只做一半会怎样。

解答：

a. 以 UNIX 文件系统为例：

- 创建文件：给文件分配存储空间；分配一个唯一的 i 节点号（i-number）；在 i 节点表（i-list）中插入这个 i 节点；在所在目录里加一个目录项，把文件名和 i 节点号对应起来。
- 删除文件：步骤反过来，删目录项，释放 i 节点，回收数据块。
- 写数据（整理补充，官方答案没有写这一问）：需要时从空闲空间分配新数据块，把数据写进块，再更新 i 节点中的块指针、文件长度、修改时间，以及空闲块记录。

b.

- 对文件系统的使用者：持久性显然重要，写好的文件不能丢。原子性一般谈不上，文件系统本身不提供事务，写到一半断电，文件里可能新旧内容混在一起，只能由应用自己处理。
- 对文件系统的实现者：很多内部操作必须具有事务语义。创建、删除文件涉及的那几步必须原子地完成，否则会留下没有任何目录项引用的文件（占着空间却访问不到），或者出现无法再使用的磁盘区域。现代文件系统用日志（journaling）保护元数据更新，崩溃后重放或丢弃没做完的操作。

### 14.3 数据库比文件系统更重视 ACID 的原因

题目：数据库系统的实现者比文件系统的实现者更重视 ACID 性质，可能是什么原因？

思路：从任务的性质和支持 ACID 的代价两方面比较。

解答：

- 数据库系统常承担关键任务，操作结果直接作用于现实世界且要长期有效，比如转账、订座。这类操作必须原子、持久，所以要保证 ACID。
- 文件系统的大多数用户不愿意为 ACID 付出代价，包括性能、磁盘空间和金钱成本。

### 14.4 什么情况下并发执行更重要

题目：说明下面这句话为什么成立：数据需要从（慢速）磁盘读取或事务很长时，事务的并发执行更重要；数据都在内存中且事务很短时，并发执行就没那么重要。

思路：并发执行要解决的是等待时间长和 CPU 空闲两个问题，看这两个问题在哪种情况下明显。

解答：

- 事务很长，或者要从慢速磁盘取数据时，一个事务要执行很久。没有并发的话，其他事务只能排队等，平均响应时间变长。
- 事务在等磁盘读数据时 CPU 是空闲的，串行执行浪费资源。并发执行可以让别的事务趁这段时间使用 CPU，提高吞吐量。
- 事务很短、数据都在内存里时，每个事务很快结束，几乎不等 I/O，上面两个问题都不突出，串行执行的损失很小。

### 14.5 为什么强调冲突可串行化

题目：每个冲突可串行化调度都是视图可串行化的，为什么我们强调冲突可串行化，而不强调视图可串行化？

思路：比较两者的判定代价，再看实际协议用的是哪一种。

解答：

- 实际使用的并发控制协议（两阶段封锁、时间戳排序、有效性检查）都以冲突可串行化为基础，而且只允许冲突可串行化调度中的一部分。
- 冲突可串行化用优先图查环就能判断，多项式时间。一般形式的视图可串行化判定是 NP 完全问题，代价很高，并发控制只用到它很受限的一种形式（例如 Thomas 写规则）。
- 视图可串行化但不冲突可串行化的调度一定包含盲写（不读就写），实际中不常见，为这点额外的并发度付出判定代价不划算。

### 14.6 由优先图判断冲突可串行化

题目：教材图 14.16 给出了某个调度的优先图（结点为 $T_1$ 到 $T_5$）。对应的调度是冲突可串行化的吗？说明理由。

思路：优先图无环则冲突可串行化，拓扑排序得到等价的串行调度。

解答：

- 优先图中没有环，所以对应的调度是冲突可串行化的。
- 对优先图做拓扑排序，就得到一个与之冲突等价的串行调度。官方答案给出的顺序是 $T_1, T_2, T_3, T_4, T_5$。
- 拓扑排序的做法：每次挑一个入度为 0 的结点输出，删掉它和它的出边，重复到图空。一个图可能有多种拓扑序，每一种都对应一个合法的等价串行调度。

（存疑：答案 PDF 说优先图附在答案下方，但页面上没有图，教材原图也不在资料里，这里没法逐条核对边，只能沿用官方"图中无环"的结论。）

### 14.7 无级联调度

题目：什么是无级联调度？为什么希望调度是无级联的？有没有什么情况下允许非无级联调度反而更好？说明理由。

思路：先写定义，再从级联回滚的代价和并发度两头权衡。

解答：

- 定义：对任意一对事务 $T_i$ 和 $T_j$，如果 $T_j$ 读取了 $T_i$ 之前写入的数据项，那么 $T_i$ 的提交操作必须出现在 $T_j$ 的这个读操作之前。简单说，事务只读已提交的数据。
- 好处：一个事务失败回滚时，不会连带其他事务一起回滚，避免了级联回滚带来的大量撤销工作。
- 代价：并发度降低。
- 如果故障很少发生，可以偶尔承受级联回滚的开销，换取平时更高的并发度，这时非无级联调度是可取的。放宽的只是无级联，调度仍然要可恢复。

### 14.8 丢失更新

题目：如果事务 $T_j$ 读了某数据项，接着另一个事务 $T_k$ 写了这个数据项（写入值可能基于它之前读到的值），之后 $T_j$ 又写这个数据项，就称发生了丢失更新： $T_j$ 写入时没有考虑 $T_k$ 写的值， $T_k$ 的更新就丢了。

- a. 给出一个出现丢失更新的调度。
- b. 给出一个调度，说明读已提交（read committed）隔离级别下仍可能丢失更新。
- c. 解释为什么可重复读（repeatable read）隔离级别下不会丢失更新。

思路：a、b 按定义排出"先读、别人写、再写"的顺序。b 用锁实现读已提交，共享锁读完就放；c 的共享锁要一直持有到事务结束。

解答：

a. 一个丢失更新的调度：

| $T_1$ | $T_2$ |
|---|---|
| `read(A)` | |
| | `read(A)` |
| | `write(A)` |
| `write(A)` | |

$T_1$ 最后写 A 时用的是自己早先读到的旧值， $T_2$ 写入的值被 $T_1$ 覆盖，丢了。

b. 读已提交用锁来实现：读之前加共享锁，读完马上释放；写要加排他锁。

| $T_1$ | $T_2$ |
|---|---|
| `lock-S(A)` | |
| `read(A)` | |
| `unlock(A)` | |
| | `lock-X(A)` |
| | `read(A)` |
| | `write(A)` |
| | `unlock(A)` |
| | `commit` |
| `lock-X(A)` | |
| `write(A)` | |
| `unlock(A)` | |
| `commit` | |

这个加锁方式满足读已提交： $T_1$ 读到的 A 没有被未提交事务改过。但 $T_1$ 写 A 时仍基于自己之前读到的值， $T_2$ 的更新被覆盖。

c.

- 可重复读用锁实现时， $T_1$ 读 A 加的共享锁要持有到 $T_1$ 结束。
- 其他事务 $T_2$ 要写 A 必须拿到排他锁，只能等 $T_1$ 结束才行。于是等价的串行顺序被固定为 $T_1, T_2$， $T_2$ 写入的值不会被 $T_1$ 覆盖。
- 套到 a 的调度上看（整理补充）： $T_1$、 $T_2$ 都读了 A，都持有 A 的共享锁，谁想升级成排他锁都得等对方，形成死锁。系统回滚其中一个，另一个正常完成，更新也不会丢。

### 14.9 快照隔离下银行的非可串行化执行

题目：某银行的数据库系统使用快照隔离。描述一个具体场景：出现了非可串行化的执行，并给银行带来问题。

思路：两个事务读同一组数据、各自检查约束，然后分别写不同的数据项。快照隔离只拦截写写冲突，两个事务都能提交，这就是写偏斜。

解答：

- 设银行规定：同一客户的支票账户余额与储蓄账户余额之和不能为负。某客户支票账户 100 元，储蓄账户 200 元。
- 事务 $T_1$ 读两个余额，检查约束后从支票账户取 200 元。并发事务 $T_2$ 同样读两个余额，检查约束后从储蓄账户取 200 元。
- 两个事务都在自己的快照上检查约束，各自算出取款后总额为 100 元，认为不违反约束。它们写的是不同数据项，没有写写冲突，快照隔离允许两者都提交。
- 结果支票账户 $-100$ 元，储蓄账户 0 元，总额 $-100$ 元，约束被破坏，客户多取走了钱。任何串行顺序下，后执行的那个事务都会发现总额不够而拒绝取款，所以这个执行不可串行化。

（更正：官方答案写的是两个事务都从支票账户取款，同时又说它们更新的是不同数据项，前后矛盾。两笔取款都改支票余额的话存在写写冲突，快照隔离的"先提交者胜"规则会让后提交的事务中止，问题不会出现。第二笔取款应改为从储蓄账户取。）

### 14.10 快照隔离下航空公司可接受的非可串行化执行

题目：某航空公司的数据库系统使用快照隔离。描述一个出现非可串行化执行的场景，但航空公司为了获得更好的整体性能，可能愿意接受这种情况。

思路：还是写偏斜，这次写的是插入新元组；再说明超售的后果有补救办法。

解答：

- 网上订票系统有大量并发请求：查询航班列表、查询余座、订票。某航班只剩一个座位，用户 A 和 B 同时在订这趟航班。
- A、B 的订票事务分别为 $T_3$、 $T_4$。每个事务先统计该航班已订座位数，还有空位就插入一条订票记录。两个事务从各自快照看到都剩一个座位，于是各自插入一条新记录。
- 两个事务没有更新同一个元组，快照隔离允许两者都提交，结果多订出一个座位，超售了。
- 这种情况通常不严重：经常有乘客退票，冲突自己就消失了；到起飞时仍然超售，航空公司可以给其中一位乘客安排别的航班，并给补偿让他接受。
- 换来的好处是订票事务只从快照读数据，不阻塞其他并发事务，系统整体性能更好。

### 14.11 多处理器上操作无法全序排列

题目：调度的定义假设所有操作可以按时间排成全序。考虑运行在多处理器上的数据库系统，不同处理器上执行的操作之间有时无法确定先后，但同一个数据项上的操作总能排成全序。这会给冲突可串行化的定义带来问题吗？说明理由。

思路：冲突只发生在同一数据项上的操作之间，优先图只用到这些操作的先后。

解答：

- 不会带来问题。冲突可串行化只需要同一数据项上各操作的先后顺序，不同数据项上的操作谁先谁后不影响结论。
- 例子：

| $T_1$ | $T_2$ |
|---|---|
| `read(A)` | |
| | `read(B)` |
| `write(B)` | |

这个调度要判断冲突可串行化，唯一需要的顺序是 $T_2$ 的 `read(B)` 在 $T_1$ 的 `write(B)` 之前（对应优先图的边 $T_2 \to T_1$）。`read(A)` 和 `read(B)` 谁先都可以。

- 所以只要每个数据项上的操作能排成全序，优先图就画得出来，冲突可串行化的定义在这种多处理器系统上照样成立。
