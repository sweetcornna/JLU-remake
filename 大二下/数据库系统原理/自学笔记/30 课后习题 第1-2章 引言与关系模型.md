## 习题

### 1.1 数据库系统的缺点

题目：本章讲了数据库系统的不少优点，请说出它的两个缺点。

思路：从投入成本和运行性能两个方面想。

解答：

1. 搭建数据库系统需要更多的专业知识、资金、技术和时间。
2. 数据库本身很复杂，可能导致性能不够好。

### 1.2 类型声明与 DDL 的区别

题目：列出 Java、C++ 这类语言的类型声明系统和数据库的数据定义语言（DDL）之间的五点不同。

思路：从"声明之后有没有真正产生对象""能不能表达约束和权限""类型是否丰富""描述的对象是什么"几个角度对比。

解答：

1. 执行 DDL 会在数据库里真正创建对象；程序里的类型声明只是程序内部使用的抽象。
2. DDL 可以声明一致性约束，例如域约束、参照完整性约束，程序语言的类型系统一般不支持。
3. DDL 支持授权，可以给不同用户不同的访问权限。程序语言的类型系统没有这种保护，最多限制一个类的属性不被别的类的方法访问。
4. 程序语言的类型系统通常比 SQL 的丰富得多。多数数据库只支持各种数值、字符串这类基本类型，少数支持数组、对象等复杂类型。
5. DDL 的重点是说明关系中各个属性的类型；程序语言则可以创建对象以及对象的集合。

### 1.3 建立数据库的六个步骤

题目：为某个企业建立数据库，列出你会采取的六个主要步骤。

思路：按设计的先后顺序排，从需求一路做到建库。

解答：

1. 明确企业的高层需求，这一步产出系统需求规格说明书。
2. 定义一个模型，包含所有需要的数据类型以及数据之间的联系。
3. 定义数据上的完整性约束。
4. 定义物理层。
5. 对每个需要经常处理的问题（比如职员或 Web 用户要完成的操作），设计完成该任务的用户界面，并编写实现界面的应用程序。
6. 创建并初始化数据库。

### 1.5 视频网站与文件处理系统的弊端

题目：要做一个类似 YouTube 的视频网站。对照 1.2 节列出的文件处理系统的各项弊端，逐条讨论它们对视频数据本身、以及对视频元数据（标题、上传者、标签、谁看过）是否要紧。

思路：视频内容上传后基本不再修改，很多弊端只和元数据有关。逐条过一遍即可。

解答：

| 弊端 | 分析 |
| --- | --- |
| 数据冗余和不一致 | 对元数据有一定影响；视频数据不会被更新，基本无关。这里的联系很少，也不会造成冗余 |
| 数据访问困难 | 如果只通过少数固定接口访问视频（现在的视频网站就是这样），问题不大。如果要按关键词以外的具体条件查找，而元数据又存在文件里，不专门写程序就很难找到，这时用数据库很有必要 |
| 数据孤立 | 数据通常是新建而不是更新，连"谁看过哪些视频"本质上也只是追加，所以不是主要问题。如果加上授权，授权信息的并发更新可能出问题 |
| 完整性问题 | 除主码外很难想到重要的完整性约束；数据分布存储时，维护主码约束可能有困难。总体不是主要问题 |
| 原子性问题 | 上传视频时，视频和它的元数据必须原子地一起加入，否则数据会不一致，需要底层的恢复机制在故障时保证原子性 |
| 并发访问异常 | 数据不会被更新，基本不会出现 |
| 安全性问题 | 系统支持授权时需要考虑 |

### 1.6 Web 关键词查询和数据库查询的区别

题目：从查询怎样表达、查询结果是什么两个方面，说出 Web 搜索的关键词查询和数据库查询的主要区别。

思路：分"输入"和"输出"两栏对比。

解答：

| | Web 关键词查询 | 数据库查询 |
| --- | --- | --- |
| 表达方式 | 给出一组关键词，没有特定语法 | 有明确的语法，能表达复杂查询 |
| 查询结果 | 通常是一个有序的 URL 列表，附带每个页面内容的片段摘要 | 在关系模型中结果总是一张表 |

### 2.1 雇员库的主码

题目：给出雇员库中 `employee`、`works`、`company` 三个关系合适的主码。

思路：主码要能唯一标识一个元组。`works` 以 `person_name` 为主码，相当于假设每个人只在一家公司工作。

解答：`employee` 的主码是 `person_name`，`works` 的主码是 `person_name`，`company` 的主码是 `company_name`。

### 2.2 违反外码约束的插入和删除

题目：`instructor` 的 `dept_name` 参照 `department` 关系。分别举出会违反这个外码约束的插入和删除操作。

思路：插入时，参照关系里出现被参照关系中没有的值；删除时，被参照关系删掉了仍在被引用的元组。

解答：

- 插入：向 `instructor` 插入 `(10111, Ostrom, Economics, 110000)`，而 `department` 中没有 Economics 系。
- 删除：从 `department` 删除 `(Biology, Watson, 90000)`，而还有学生或教师的 `dept_name` 是 Biology。

### 2.3 `time_slot` 的主码为什么含 `day` 和 `start_time`

题目：同一个时间段编号在一周里可以对应多次上课。解释为什么 `day` 和 `start_time` 是 `time_slot` 主码的一部分，而 `end_time` 不是。

思路：看哪些属性不同就会形成不同的元组，哪些属性已经被其他属性唯一确定。

解答：一门课很可能一周上好几天，甚至一天上不止一次，只有加上 `day` 和 `start_time` 才能区分这些元组。某一天某个时刻开始的一次课只可能有一个结束时间，`end_time` 由前面的属性决定，不用放进主码。

### 2.4 实例中没有重名，name 能否作超码

题目：图中 `instructor` 的实例里没有两位教师同名。能否据此认为 `name` 可以作为 `instructor` 的超码（或主码）？

思路：码是对模式所有合法实例都成立的约束，不能从某一个实例推出来。

解答：不能。这个实例里姓名恰好不重复，一般情况下不能保证。除非学校规定教师不许重名，而这不太现实。

### 2.5 `student` 与 `advisor` 的积再按 `s_ID = ID` 选择

题目：先求 `student` 和 `advisor` 的笛卡尔积，再用谓词 `s_ID = ID` 做选择，即 $\sigma_{s\_ID=ID}(student \times advisor)$，结果是什么？

思路：选择条件让每个学生只和"以他为 `s_ID`"的 advisor 元组配对，效果等于按学号连接。

解答：结果的属性是 `student` 的全部属性后接 `advisor` 的全部属性。每个有导师的学生对应一行：先是该学生的各个属性，然后是与学生 `ID` 相同的 `s_ID`，最后是导师编号 `i_ID`。没有导师的学生不会出现在结果中；有多个导师的学生会出现相应的多次。

### 2.6 说出关系代数表达式的含义

题目：用文字说明下面每个表达式做了什么。

- a. $\sigma_{year \ge 2009}(takes) \bowtie student$
- b. $\sigma_{year \ge 2009}(takes \bowtie student)$
- c. $\Pi_{ID,\,name,\,course\_id}(student \bowtie takes)$

思路：a 和 b 的区别只是先选择还是先连接。选择条件只涉及 `takes` 的属性，放在连接前后结果一样。

解答：

- a：对每个在 2009 年及以后至少选过一门课的学生，列出学生信息，以及他在这些年份所选课程的信息。结果属性为 `ID, name, dept_name, tot_cred, course_id, sec_id, semester, year, grade`。（更正：官方答案说的是"在 2009 年选过课"，而条件是 $year \ge 2009$，应包括 2009 年以后；属性列表中的 `section_id` 应为 `sec_id`。）
- b：结果与 a 相同，选择可以在连接之前做。
- c：列出所有选过课的学生的 `ID`、`name` 和所选课程的 `course_id`。

### 2.7 雇员库上的关系代数查询

题目：在雇员库上写关系代数表达式：

- a. 找出住在 Miami 的所有雇员的名字。
- b. 找出工资高于 100000 美元的所有雇员的名字。
- c. 找出住在 Miami 并且工资高于 100000 美元的所有雇员的名字。

思路：居住城市在 `employee` 里，工资在 `works` 里。c 要先按 `person_name` 把两个关系自然连接，再同时选择两个条件。

解答：

$$\Pi_{person\_name}(\sigma_{city=\text{'Miami'}}(employee))$$

$$\Pi_{person\_name}(\sigma_{salary>100000}(works))$$

$$\Pi_{person\_name}(\sigma_{city=\text{'Miami'} \wedge salary>100000}(employee \bowtie works))$$

（更正：官方答案三小题都是对 `employee` 做选择再投影 `name`。本题用的是 2.1 的雇员库，`employee` 里没有 `name` 和 `salary` 属性，名字属性叫 `person_name`，工资在 `works` 中，b、c 必须用到 `works`。）

### 2.8 银行库上的关系代数查询

题目：在银行库上写关系代数表达式：

- a. 找出位于 Chicago 的所有支行的名字。
- b. 找出在 Downtown 支行有贷款的所有借款人的名字。

思路：b 中 `borrower` 和 `loan` 通过 `loan_number` 自然连接，支行名在 `loan` 里。

解答：

$$\Pi_{branch\_name}(\sigma_{branch\_city=\text{'Chicago'}}(branch))$$

$$\Pi_{customer\_name}(\sigma_{branch\_name=\text{'Downtown'}}(borrower \bowtie loan))$$
