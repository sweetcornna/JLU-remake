日志记录的种类：

```
<Ti start>              事务 Ti 开始
<Ti, X, V1, V2>         更新记录：Ti 把 X 从旧值 V1 改成新值 V2
<Ti, X, V>              只含新值的 redo-only 记录，回滚时写的补偿日志记录就是这种
<Ti commit>             Ti 提交
<Ti abort>              Ti 回滚完毕
<checkpoint L>          检查点，L 是做检查点时还活跃的事务
```

- 正常运行时回滚 Ti：从日志尾往前扫，遇到 `<Ti, X, V1, V2>` 就把 X 写回 V1，并追加一条 `<Ti, X, V1>`；扫到 `<Ti start>` 后追加 `<Ti abort>`。
- 做检查点：暂停更新，把内存里的日志记录和修改过的缓冲块都写到磁盘，再写 `<checkpoint L>`。所以检查点之前的更新都已经在磁盘上。
- 崩溃后的重做阶段：找到最后一个 `<checkpoint L>`，undo 表初值设为 L，从检查点往后顺着扫到日志尾。遇到更新记录或 redo-only 记录就把新值写回去，不管这个事务最后有没有提交，这叫**重复历史**。遇到 `<Ti start>` 把 Ti 加进 undo 表，遇到 `<Ti commit>` 或 `<Ti abort>` 把 Ti 移出。
- 崩溃后的撤销阶段：从日志尾往前扫。遇到 undo 表中事务的更新记录，按正常回滚的做法写回旧值、追加 redo-only 记录；遇到 undo 表中事务的 `<Ti start>`，追加 `<Ti abort>` 并把 Ti 移出。undo 表空了就停。L 中的事务是在检查点之前开始的，所以撤销阶段可能要越过检查点继续往前扫。

## 习题

### 16.1 撤销倒着做、重做顺着做

题目：恢复时，undo 表中事务的日志记录为什么必须从后往前处理，而重做却要从前往后做？

思路：假设同一个数据项被改了好几次，分别按两种顺序写回旧值或新值，看最后留下的是哪个值。

解答：

- 撤销要让数据项回到事务开始前的值，也就是最早那条更新记录里的旧值。设 Ti 先把 A 从 10 改成 20，又从 20 改成 30：

```
<Ti, A, 10, 20>
<Ti, A, 20, 30>
```

- 倒着撤销：先写回 20，再写回 10，结果 10，正确。顺着撤销：先写回 10，再写回 20，A 停在 20，错了。
- undo 表里如果有几个事务先后改过同一个数据项，道理相同，也要按时间倒序撤销才能回到最早的值。
- 重做要让数据项停在最后一次写入的值。还是上面两条记录，假设 Ti 已经提交：顺着重做先写 20 再写 30，结果 30；倒着重做会停在 20。

### 16.2 检查点的作用与频率

题目：检查点机制有什么用？应该多久做一次？检查点做得多或少，分别怎样影响：

- 没有故障时的系统性能；
- 系统崩溃后恢复所需的时间；
- 介质（磁盘）故障后恢复所需的时间。

思路：检查点相当于在日志里记下"在这之前的更新都已落盘"，恢复时就不必从头扫。代价是做检查点要写盘，简单方案下还要暂停更新。

解答：

- 作用：没有检查点，崩溃后要扫描整个日志，所有事务都要判断一遍，再重做或撤销。日志里大多数事务早就提交了，结果也早在磁盘上，全部重做很浪费时间。有了检查点，重做只要从最后一个检查点开始，更早的记录基本可以不看（只有 L 中事务在检查点之前的记录，撤销时还会用到）。检查点还决定了哪些旧日志可以删除，稳定存储空间不够时尤其需要（见 16.3）。
- 频率：没有固定值，要在正常运行的开销和恢复时间之间折中。要求恢复快，就多做；稳定存储空间小，也只能多做；恢复慢一点无所谓，就少做。
- 对无故障时的性能：每次检查点都要把修改过的缓冲块和日志写盘，简单方案下还要暂停更新。做得越频繁，正常运行损失的性能越多。
- 对崩溃恢复时间：做得越频繁，最后一个检查点离日志尾越近，重做阶段要扫的日志越少，恢复越快。
- 对介质故障恢复时间：没有影响。磁盘坏了，检查点时写进去的数据也一起没了。介质故障要先用最近一次归档转储（archival dump）装回数据库，再用转储之后的日志重做。在这里起检查点作用的是转储，转储做得越勤，要重做的日志越少。

### 16.3 普通日志与归档日志什么时候能删

题目：有的数据库系统让管理员在两种日志方式中选择：普通日志用于系统崩溃后的恢复，归档日志用于介质（磁盘）故障后的恢复。按 16.4 节的恢复算法，这两种情况下日志记录分别在什么时候可以删掉？

思路：看恢复算法会读到哪些记录。重做从最后一个检查点开始；撤销要一直往前，找到 undo 表中每个事务的 start 记录。

解答：

普通日志，下面这些记录不能删：

1. 最后一个 `<checkpoint L>` 记录，以及它之后的所有记录，重做阶段要用。
2. L 中事务在检查点之前写的记录，一直往前到它们各自的 `<Ti start>`。崩溃时这些事务如果还没结束，撤销阶段要靠这些记录里的旧值。

其余记录都可以删：检查点之前已经结束的事务，更新在做检查点时已经写到磁盘，恢复时不会再用到它们的记录。每做一个新检查点，能删的范围就往后推一段。

（补充：L 中的事务如果在检查点之后已经提交或回滚完毕，它在检查点之前的记录其实也用不到了。官方答案把 L 中事务的记录一律算作不能删，偏保守，结论没有错。）

实际系统不会在日志中间零散地删记录，那样日志里会出现空洞，处理起来麻烦。一般是找一个位置，把它之前的整段删掉：L 为空时从检查点记录处截断，L 不为空时从 L 中最早开始的事务的 `<Ti start>` 处截断。日志通常分成多个文件存放，一个文件里的记录都能删时，整个文件删掉。

归档日志：

- 规则和上面一样，把"最后一个检查点"换成"最后一次归档转储"。介质故障后先装回转储，再用转储之后的日志重做，转储时还活跃的事务还要撤销，所以这两部分记录要留着。
- 归档转储要把整个数据库写出去，做得比检查点少得多，所以归档日志要保留的记录比普通日志多很多。

### 16.4 在恢复算法中实现保存点

题目：说明怎样修改 16.4 节的恢复算法，使它支持保存点（savepoint），并能回滚到某个保存点。（保存点在教材 16.8.3 节介绍。）

思路：保存点就是日志里的一个标记。回滚到保存点沿用正常回滚的做法，只是扫到这个标记就停，不用一直扫到 start 记录。

解答：

- 建立保存点：给事务 Ti 追加一条日志记录 `<savepoint Ti>`。一个事务要设多个保存点时，给记录带上名字，如 `<savepoint Ti, S1>`。
- 回滚到保存点：从日志尾往前扫 Ti 的记录，处理方法和正常回滚一样。遇到 `<Ti, X, V1, V2>` 就把 X 写回 V1，并追加 redo-only 记录 `<Ti, X, V1>`；扫到 `<savepoint Ti>` 停下。不写 `<Ti abort>`，事务接着往下执行。
- 例子：

```
<T1 start>
<T1, A, 100, 90>
<savepoint T1>
<T1, B, 50, 60>
<T1, C, 30, 0>
```

回滚到保存点，依次把 C 写回 30、B 写回 50，日志追加：

```
<T1, C, 30>
<T1, B, 50>
```

A 仍是 90，T1 继续执行。

- 崩溃恢复不用改。部分回滚时写的补偿记录是 redo-only 记录，重做阶段照常重放；撤销阶段遇到 `<savepoint Ti>` 直接跳过。已经回滚过的那几条更新会被再撤销一次，因为是倒序处理，最后仍回到 Ti 开始前的值，只是多做了点工作。
- 想多次回滚到同一个保存点：回滚完后再写一条新的保存点记录，下次回滚扫到它就停，不必把已经撤销过的更新再撤销一遍。
- 回滚越过某个保存点以后，就不能再回滚到这个保存点了，它之前那部分更新已经被撤销，撤销操作没法反过来重做。

（存疑：官方答案要求建立保存点时先把 Ti 在内存中的日志记录写到稳定存储。回滚到保存点只发生在事务运行期间，系统崩溃后整个事务都会被撤销，按理说保存点记录不刷盘也不影响正确性。）

### 16.5 延迟修改技术

题目：数据库采用延迟修改（deferred modification）技术，即事务提交之前不修改数据库。

- a. 更新日志记录里的旧值部分还需要吗？为什么？
- b. 日志里不存旧值，事务显然无法撤销。恢复的重做阶段要怎样改？
- c. 延迟修改的一种实现：事务更新过的数据项保存在事务自己的局部内存里，没有更新过的数据项直接从数据库缓冲区读。怎样高效地实现读操作，保证事务能读到自己写过的值？
- d. 如果事务要做大量更新，上面的实现会出现什么问题？

思路：延迟修改下，没提交的事务从没碰过数据库。恢复时要做的只剩一件事：把已提交事务的更新重做到数据库里。

解答：

a. 不需要。

- 事务已经提交的，以后不会再撤销，旧值用不上。
- 事务崩溃时还没提交的，数据库里的值根本没被它改过，磁盘上存的就是旧值，不用去日志里找。

b. 16.4 节的重做阶段会把所有更新都重放一遍，包括未提交事务的，再靠撤销阶段撤掉。现在没法撤销，要改成只重做已提交事务：

- 先确定哪些事务在日志里有 `<Ti commit>`，比如先从日志尾往前扫一遍收集起来。
- 然后顺着扫，只重放这些事务的更新记录，其他事务的记录跳过。不用维护 undo 表，也没有撤销阶段。
- 重做的起点要注意（整理补充）：做检查点时还没把修改写进数据库的事务（L 中的事务都属于这种），更新记录写在检查点之前，真正改数据库却发生在检查点之后，检查点刷盘时这些修改还不在缓冲区里。所以重做要从这些事务中最早的 `<Ti start>` 开始扫，只从检查点开始会漏掉。

（更正：官方答案只说重做阶段不再需要维护 undo 表。光这样改不够，原来的重做阶段会把未提交事务的新值也写进数据库，没有旧值就再也改不回来。重做阶段必须只重放已提交事务的记录。）

c. 给每个事务的局部内存建一个散列表，以数据项标识为键：

- 写 X：把新值放进散列表，已有就覆盖。
- 读 X：先查散列表，查到就返回局部副本，这是事务自己写过的值；查不到再去数据库缓冲区读。
- 提交：写完 commit 日志记录后，把散列表里的数据项逐个写进数据库。

官方答案的做法是查不到时把数据项从缓冲区复制进局部内存再返回，以后再读就不用访问缓冲区。这样只读的数据项也要占局部内存，d 里的问题会更严重。

d. 更新很多时，局部内存可能装不下所有修改过的数据项副本，事务会耗尽内存。只能中止事务，或者把副本换出到磁盘，读写都变慢。提交时还要一次把大量修改写进数据库，提交耗时也长。

### 16.6 用 B+ 树表示影子页表

题目：影子分页（shadow paging）方案需要复制页表。假设页表用 B+ 树表示。

- a. 假设只修改叶结点中的项，没有插入和删除，怎样让新副本和影子副本共享尽可能多的结点？
- b. 即使做了上面的优化，对只做少量更新的事务，日志方案还是比影子副本方案便宜得多。为什么？

思路：写时复制，每次只复制从根到被改叶结点的那一条路径。

解答：

a.

- 事务开始时只复制根结点。新根的指针全部指向影子树里原来的子结点，树的其余部分完全共享。
- 要修改某个叶结点中的项时，把从根到这个叶结点路径上还没复制过的结点各复制一份，在副本上修改，并让父结点副本的指针改指向子结点副本。路径上已经复制过的结点直接在副本上改。
- 不在任何被修改路径上的结点都和影子树共享。树高为 $h$ 时，一次更新最多新增 $h$ 个结点副本。
- 提交时把指向页表根的指针原子地换成新根。

b.

- 影子方案改一个数据项，数据页本身要复制一份写到新位置，页表路径上的几个结点（每个都占一整页）也要复制并写盘，一次小更新就是好几页的 I/O。
- 日志方案每次更新只追加一条很短的日志记录，许多记录挤在同一个日志页里，事务提交时通常只需写一两个日志页，数据页可以留在缓冲区晚点再写。
- 日志是顺序追加的，前后几个事务提交时写出的日志页在磁盘上是挨着的，磁头几乎不用移动；影子方案写出的新页散落在磁盘各处。

### 16.7 回滚时不写日志会出什么错

题目：假设把 16.4 节的恢复算法（错误地）改成：事务回滚时做的操作不写日志。这样崩溃恢复时，之前已经回滚过的事务会被放进 undo 表，再回滚一次。举例说明恢复的撤销阶段会把数据库弄成错误状态。（提示：考虑一个数据项先被某个中止的事务更新，之后又被一个提交了的事务更新。）

思路：第二次撤销写回的旧值已经过时，会盖掉后面已提交事务写的值。

解答：

设 A 初值 500。T1 把 A 改成 400 后回滚，A 恢复成 500，但回滚过程没写任何日志，连 abort 记录也没有。接着 T2 把 A 改成 800 并提交，然后系统崩溃。日志里只有：

```
<T1 start>
<T1, A, 500, 400>
<T2 start>
<T2, A, 500, 800>
<T2 commit>
```

恢复过程：

1. 重做阶段：依次重放，A 先变成 400，再变成 800。T1 只有 start，没有 commit 或 abort，留在 undo 表；T2 提交了，移出。
2. 撤销阶段：撤销 T1 的更新，把 A 写回 500。

最后 A = 500，已提交的 T2 写入的 800 丢了，违反持久性。

按正确的算法，T1 回滚时要写补偿记录和 abort 记录：

```
<T1 start>
<T1, A, 500, 400>
<T1, A, 500>
<T1 abort>
<T2 start>
<T2, A, 500, 800>
<T2 commit>
```

重做阶段 A 依次变为 400、500、800；T1 有 `<T1 abort>`，不在 undo 表里，撤销阶段什么都不做，A 最终为 800。

### 16.8 回滚时不释放已分配的磁盘空间

题目：事务给文件分配的磁盘空间，即使事务回滚也不应该释放。说明原因，并说明 ARIES 怎样保证这类操作不被回滚。

思路：空间一旦分配出去，别的事务马上就能往里写，回滚时收回会破坏别人的数据。ARIES 用补偿日志记录里的 UndoNextLSN 让回滚跳过这段操作。

先补一点 ARIES 的背景：

- 每条日志记录有一个日志序号 LSN。每个页上记着 PageLSN，即最后一次修改这个页的日志记录的 LSN。重做时，某条记录的 LSN 不大于页上的 PageLSN，说明这次修改已经在页上了，跳过。
- 脏页表记录缓冲区里每个脏页的 RecLSN，即这个页变脏以来第一条相关日志记录的 LSN。
- 恢复分三个阶段。分析阶段从最后一个检查点往后扫，重建脏页表和活跃事务表，脏页表中最小的 RecLSN 就是重做起点。重做阶段从这个起点往后重复历史，页不在脏页表里、或记录的 LSN 小于该页的 RecLSN、或不大于 PageLSN 的，都跳过。撤销阶段回滚分析阶段结束时仍活跃的事务。
- 回滚时写补偿日志记录（CLR），CLR 里的 UndoNextLSN 指向这个事务下一条要撤销的记录。撤销时遇到 CLR 就按 UndoNextLSN 往前跳，已经撤销过的操作不会再撤销一遍。

解答：

- 原因：事务 T 给某个关系分配了一个新页。分配操作做完后，空闲空间信息很快就对其他事务可见，在 T 提交之前，别的事务可能已经往这个页里插入了记录。T 回滚时如果把页释放掉，这些记录就跟着丢了，或者这个页以后再分配出去时被覆盖。反过来，T 回滚后留下一个没人用的已分配页，并不影响数据正确，最多浪费一点空间。
- ARIES 把这类操作做成**嵌套顶层动作**（nested top action），可以看成撤销动作为空的操作：
  - 操作本身的日志照常写，重做阶段照常重放，保证分配结果持久。
  - 操作做完后写一条哑 CLR（dummy CLR），它的 UndoNextLSN 指向这个操作开始之前 T 的最后一条日志记录。
  - T 回滚时从后往前撤销，碰到这条哑 CLR 就直接跳到操作开始之前，空间分配产生的日志记录一条都不撤销。

### 16.9 删除释放的空间被另一个事务占用

题目：事务 T1 删除了一条记录，在 T1 提交之前，腾出的空间就被分配给了另一个事务 T2 插入的记录。

- a. 如果 T1 需要回滚，会出什么问题？
- b. 改用页级封锁代替元组级封锁，这个问题还会出现吗？
- c. 在保留元组级封锁的前提下给出解决办法：把提交之后要做的动作记在专门的日志记录里，提交后再执行。方案要保证这些动作恰好执行一次。

思路：物理撤销会把被删元组写回原来的位置，而这个位置已经被 T2 占了。解决办法是把"释放空间"推迟到提交之后。

解答：

a.

- T1 回滚要把被删的元组恢复回来。按普通的物理撤销，用日志里的旧值把那块空间写回原样，就会覆盖 T2 刚插入的元组，页内的槽目录等结构也会被弄乱。
- 想不覆盖，只能做逻辑撤销：重新执行一次插入，把元组放到别的空位上。恢复过程因此变复杂。
- 如果 T2 插入的元组和被删元组主码相同，T1 回滚把元组插回来后会违反主码约束。

b. 不会。页级封锁下，T1 删除时持有整个页的排他锁，一直到提交才释放。T1 提交前 T2 没法往这个页里插入，腾出的空间不会被别人用上。

c. 做法如下。

1. 删除时不马上释放空间，只把元组标记为已删除，同时在日志里记下提交后要做的动作，例如"释放页 P 中槽 s 的空间"。这些信息可以写成单独的日志记录，也可以附在 `<T1 commit>` 记录里。
2. T1 如果回滚，撤销删除标记就行，提交后动作作废，不执行。
3. T1 的 commit 记录写到稳定存储以后，执行这些提交后动作。执行过程当作一个普通事务来做，照常写更新日志；全部做完后写一条"提交后处理完成"的记录，如 `<T1 post-commit done>`。
4. 恢复时，某个事务有带提交后动作的 commit 记录，却找不到对应的完成记录，说明动作可能只做了一部分：先按普通撤销把做了一半的效果回滚掉，在恢复结束时把全部提交后动作重新执行一遍，再写完成记录。已经有完成记录的，不再执行。

这样每个提交后动作要么随完成记录一起生效（重做阶段会把它恢复出来），要么被整体回滚后重新执行，不会漏做，也不会做两遍。

主码冲突的问题另外处理：T1 在被删元组的主码值上加码级锁，持有到 T1 结束，在此之前其他事务不能插入同一主码的元组。

### 16.10 交互式事务的恢复

题目：为什么交互式事务的恢复比批处理事务难？有没有简单的办法应对？（提示：考虑在自动取款机上取现金的事务。）

思路：数据库能撤销自己的修改，但撤销不了已经发生在外部世界的输出。

解答：

- 难在哪：交互式事务执行过程中会向外输出，有些输出收不回来，比如取款机已经吐出了现金，或者程序已经触发了某个物理设备的动作。事务中途失败，数据库把账户余额回滚了，钱却已经在顾客手里。批处理事务的结果只落在数据库里，回滚就能恢复原状。
- 最简单的办法：把输出语句都放到事务末尾，事务确定能提交了再输出。事务中途中止时外界什么都还没看到。
- 输出本身尽量做成原子的。取款机一般先在机器内部把钞票点好，最后一次性送出，不会一张一张地吐。
- 输出实在没法原子完成时，给输出过程留物理记录，比如磁盘上的事件日志，甚至现场录像，事后人工处理，例如核实后把没吐出的钱退回顾客账户。

### 16.11 撤销已提交的错误事务

题目：有时事务提交之后才发现执行错了（比如银行柜员输错了数据），需要撤销。

- a. 举例说明用普通的事务撤销机制撤销这种事务，可能让数据库不一致。
- b. 一种办法是把整个数据库恢复到错误事务提交之前的状态，叫做时间点恢复（point-in-time recovery），之后提交的事务的效果也一起被撤掉。说明怎样利用数据库转储修改 16.4 节的恢复算法，实现时间点恢复。
- c. 之后那些没有错的事务，如果它们的更新以 SQL 形式保存着，可以逻辑地重新执行，但不能用它们的日志记录重新执行。为什么？

思路：日志记录存的是物理的旧值和新值，这些值是在"已经包含错误事务影响"的数据库状态上算出来的。

解答：

a. 账户 A 余额 500。柜员操作错误的事务 T1 给 A 存入 100 并提交，随后正常事务 T2 从 A 取出 50 并提交：

```
<T1 start>
<T1, A, 500, 600>
<T1 commit>
<T2 start>
<T2, A, 600, 550>
<T2 commit>
```

只想撤销 T1，普通撤销会把 A 写回日志里的旧值 500，T2 的取款也被一并抹掉了。正确的余额应为 450。

b. 设错误事务为 $T_e$。

1. 找到 `<Te start>` 之前最近的一次归档转储 D，用它装回数据库。
2. 重做阶段：从 D 对应的日志位置往后扫，重放记录，一直做到 `<Te commit>` 之前停下。停下时还没结束的事务留在 undo 表里，包括 $T_e$ 本身，以及和 $T_e$ 并发、这时还没提交的事务，把后者记为集合 $S_1$。
3. 撤销阶段：把 $T_e$ 和 $S_1$ 中的事务全部回滚。数据库回到 $T_e$ 提交之前的状态，时间点恢复完成。
4. 停止点之后的旧日志已经和数据库对不上，不能再拿来做以后的崩溃恢复，要截掉或另起新日志（整理补充）。
5. 如果每个事务都记下了可以逻辑重做的信息，还可以接着往后扫日志，找出 `<Te commit>` 之后开始的事务，记为 $S_2$，再把 $S_1$、 $S_2$ 中的事务逻辑地重新执行一遍。

c.

- 日志记录是物理的。`<T2, A, 600, 550>` 记的是"把 A 写成 550"，550 是在 A = 600（含 T1 错存的 100）的基础上算出来的。时间点恢复后 A = 500，重放这条记录 A 又变成 550，等于把 T1 的错误又带回来了。
- SQL 形式记的是操作本身，比如 `update account set balance = balance - 50 where account_number = 'A'`。在当前状态 500 上重新执行，得到 450，是对的。
