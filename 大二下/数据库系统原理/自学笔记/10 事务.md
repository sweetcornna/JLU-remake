## 本章要点

- 事务是构成单一逻辑工作单元的操作集合。数据库系统要保证事务的 **ACID** 特性：原子性、一致性、隔离性、持久性。
- 原子性和持久性由恢复系统负责，主要手段是日志；隔离性由并发控制系统负责；单个事务的一致性要靠写事务的程序员保证。
- 事务有五个状态：活动、部分提交、失败、中止、提交。提交或中止了叫"已经结束"。已提交的事务只能用补偿事务撤销。
- 调度是指令的执行顺序，必须包含所有指令，并保持每个事务内部的指令顺序。等价于某个串行调度的叫可串行化调度。
- 两条指令冲突：属于不同事务、访问同一数据项、至少一条是 `write`。
- 优先图无环，调度就是冲突可串行化的，拓扑排序给出等价的串行顺序；有环就不是。
- 冲突可串行化一定视图可串行化，反过来不成立；视图可串行化但冲突不可串行化的调度一定含**盲目写**。
- 可恢复：Tj 读了 Ti 写的数据，Ti 必须先于 Tj 提交。无级联：Ti 必须在 Tj 读之前就提交。无级联一定可恢复。
- SQL 标准的四个隔离级别从低到高：未提交读、已提交读、可重复读、可串行化。四个级别都不允许脏写。

## 1. 事务概念与 ACID

- 构成单一逻辑工作单元的操作集合称为事务。事务是访问并可能更新各种数据项的一个程序执行单元，由 `begin transaction` 和 `end transaction` 之间的全部操作组成。
- 即使有故障，数据库也要保证事务要么整个执行，要么一个操作都不执行。
- 事务并发执行时，数据库要用不会引入不一致的方式来管理。

### 原子性（Atomicity）

- 事务的所有操作要么全部在数据库中正确反映出来，要么完全不反映，事务不可分割。
- 基本思路：事务要写某个数据项之前，系统先在磁盘上记下它的旧值，这些信息记在叫**日志**的文件里。事务没能执行完，就从日志里恢复旧值，看起来就像事务从没执行过。

### 一致性（Consistency）

- 在没有其他事务并发执行的情况下，单独执行一个事务要保持数据库的一致性，也就是把数据库从一个一致状态变到另一个一致状态。
- 一致性包括显式的完整性约束（主键、外键），也包括隐式约束。例如银行里，所有账户余额之和减去所有贷款金额，必须等于手头现金。
- 事务开始时看到的数据库必须是一致的；执行期间可以暂时不一致；成功结束时必须恢复一致。
- 事务逻辑写错了，也会导致不一致。

### 隔离性（Isolation）

- 多个事务可以并发执行，但对任意一对事务 Ti 和 Tj，在 Ti 看来，Tj 要么在 Ti 开始前已经执行完，要么在 Ti 结束后才开始。每个事务都感觉不到别的事务在并发执行。
- 最简单的办法是串行执行，一个接一个来。隔离性要求的是：并发执行后的状态，和这些事务按某种次序串行执行后的状态等价。
- 保证隔离性是**并发控制系统**的责任。

### 持久性（Durability）

事务成功完成后，它对数据库的修改必须永久保留，即使系统出故障。做到下面任意一条即可：

1. 事务做的更新在事务结束前已经写入磁盘。
2. 有关更新的信息已经写到磁盘上，而且足够充分，系统故障重启后能据此重新构造这些更新。

## 2. 一个简单的事务模型

- 简单模型里，每个数据项只有一个值，用一个名字标识。
- 事务用两个操作访问数据：
  - `read(X)`：把数据项 X 从数据库读到事务自己主存缓冲区里的同名变量 X 中。
  - `write(X)`：把事务缓冲区里变量 X 的值写回数据库中的数据项 X。
- 不一致状态：系统状态不再反映数据库本应描述的现实世界的真实状态。

转账例子，从源账户转一笔钱到目标账户：

```sql
begin transaction
read(source_account)
source_account = source_account - transfer_amount
write(source_account)
read(target_account)
target_account = target_account + transfer_amount
write(target_account)
commit transaction
```

放到 ACID 里看：

- 原子性：扣款成功后存款失败，整个事务回滚，源账户余额恢复原样。
- 一致性：事务开始和结束时，所有账户的总余额相同。
- 隔离性：另一个事务同时也从源账户扣款时，两个事务要被合理地排好先后，不能互相干扰。
- 持久性：提交后，即使系统故障，转账结果也保留。

如果因为故障或并发冲突，源账户扣了钱、目标账户没收到，系统就进入了不一致状态。ACID 就是为了防止这种情况。

`COMMIT TRANSACTION` 用来结束事务，并把事务中的所有修改永久保存到数据库。原笔记说 `END TRANSACTION` 在 SQLite 等系统里只标记事务结束、不提交。（更正：SQLite 里 `END TRANSACTION` 就是 `COMMIT` 的别名，PostgreSQL 的 `END` 也等同于 `COMMIT`，都会提交。教材里的 `end transaction` 只是标出事务边界的记法。）

## 4. 事务原子性、持久性与事务状态

### 中止与回滚

- 中止：事务没有成功执行完。中止事务对数据库做过的任何修改都必须撤销。
- 回滚：中止事务造成的修改被撤销后，就说事务已回滚。
- 事务中止由恢复机制管理，典型方法是维护日志：每个修改先记日志，记下执行修改的事务标识符、被修改的数据项标识符、旧值和新值，然后才真正修改数据库。

### 五个状态

1. 活动的（active）：初始状态，事务执行时处于这个状态。
2. 部分提交的（partially committed）：最后一条语句执行完之后。事务已经执行完了，但实际输出可能还暂存在主存里，这时硬件故障仍可能让它无法成功完成，事务仍有可能不得不中止。
3. 失败的（failed）：发现正常执行无法继续之后，比如出了硬件错误或逻辑错误。这种事务必须回滚。
4. 中止的（aborted）：事务回滚、数据库恢复到事务开始前的状态之后。系统此时有两种选择：
   - 重启事务：只在中止是由硬件错误、或者不是事务内部逻辑造成的软件错误引起时才重启。重启后的事务被看成一个新事务。
   - 杀死事务：通常因为事务内部逻辑有错，只有改写应用程序才能修正；或者输入有误；或者需要的数据在数据库里找不到。
5. 提交的（committed）：成功完成之后。事务进入部分提交状态后，往磁盘写足够的信息，保证出故障后重启也能重建它的更新；最后一条这样的信息写完，事务就进入提交状态。

几个说法要分清：

- 只有进入提交状态才叫**已提交**，只有进入中止状态才叫已中止。提交或中止了的事务都叫已经结束的。
- 已提交的事务使数据库进入新状态，即使系统故障也必须保持。它的影响不能再用中止来撤销，唯一办法是执行一个**补偿事务**，做与原事务相反的操作。比如原事务插入了一行，补偿事务就删掉这行；原事务删了一行，补偿事务就把它插回去。

### 状态转换

教材图 14-1 的状态图有 5 条边：

- 活动 到 部分提交：最后一条语句执行完。
- 活动 到 失败：执行中发现无法继续。
- 部分提交 到 提交：足够的恢复信息已写到磁盘。
- 部分提交 到 失败：写完这些信息之前出了故障。
- 失败 到 中止：回滚完成。

提交和中止是终点，没有出边。

### 可见的外部写

复习题整理稿第 89 页从教材摘了一段"外部写"，这里压缩一下：

- 外部写是对数据库系统外部有影响的操作，比如在用户屏幕上显示信息、发邮件、ATM 吐钞。它们一旦发生就撤销不了，所以大多数系统只允许事务提交之后再做。
- 实现办法：先把外部写要用的数据临时存到非易失性存储器上，事务提交后再真正执行。如果事务已提交、外部写还没做完系统就崩了，重启后用存下的数据把外部写补做完。
- 有些情况补做没有意义。比如 ATM 还没吐钞系统就故障了，重启后用户可能早走了，这时应该执行补偿事务，把钱存回用户账户。
- 网上预订时，事务刚提交，数据库或应用服务器就崩了，或者用户断网了，事务已提交但用户没看到结果。应用要设计成用户重新连上后能查到自己的事务有没有成功。

## 5. 事务隔离性与调度

### 为什么要并发

- 提高吞吐量和资源利用率。例如一个事务在用 CPU，另一个事务同时在读写磁盘。
- 减少等待时间。

并发控制机制控制并发事务之间的交互，防止它们破坏数据库一致性，以此实现隔离性。

### 调度

- 调度是一串指令，表示指令在系统中执行的时间顺序。
- 一组事务的调度必须包含这些事务的全部指令，并保持每个事务内部的指令顺序。
- 成功执行完的事务，最后一条指令是提交；没能成功执行完的，最后一条是中止。
- 串行调度：属于同一事务的指令在调度里紧挨在一起。
- 并发控制部件要保证执行的任何调度都让数据库处于一致状态。办法是让调度在某种意义上等价于一个串行调度，这种调度叫**可串行化调度**。

### 例子

T1 从账户 A 向 B 转 50，T2 从 A 向 B 转 A 余额的 10%：

```text
T1: read(A); A := A - 50; write(A); read(B); B := B + 50; write(B)
T2: read(A); temp := A * 0.1; A := A - temp; write(A); read(B); B := B + temp; write(B)
```

下面设初始 A = 1000，B = 2000，A + B = 3000。

调度 1（教材图 14-2）：串行调度，T1 之后执行 T2。

| T1 | T2 |
| --- | --- |
| `read(A)` | |
| `A := A - 50` | |
| `write(A)` | |
| `read(B)` | |
| `B := B + 50` | |
| `write(B)` | |
| `commit` | |
| | `read(A)` |
| | `temp := A * 0.1` |
| | `A := A - temp` |
| | `write(A)` |
| | `read(B)` |
| | `B := B + temp` |
| | `write(B)` |
| | `commit` |

结果 A = 855，B = 2145，和为 3000。

调度 2（教材图 14-3）：串行调度，先把 T2 整个执行完再执行 T1，指令顺序和上表相同，只是两块对调。结果 A = 850，B = 2150，和为 3000。两个串行调度结果不同，但都保持了 A + B 不变。

调度 3（教材图 14-4）：不是串行调度，但和调度 1 等价。

| T1 | T2 |
| --- | --- |
| `read(A)` | |
| `A := A - 50` | |
| `write(A)` | |
| | `read(A)` |
| | `temp := A * 0.1` |
| | `A := A - temp` |
| | `write(A)` |
| `read(B)` | |
| `B := B + 50` | |
| `write(B)` | |
| `commit` | |
| | `read(B)` |
| | `B := B + temp` |
| | `write(B)` |
| | `commit` |

T2 读 A 时 T1 已经写好了 A，T2 读 B 时 T1 也已经写好了 B，所以结果和调度 1 一样：A = 855，B = 2145。

调度 4（教材图 14-5）：导致不一致的并发调度。

| T1 | T2 |
| --- | --- |
| `read(A)` | |
| `A := A - 50` | |
| | `read(A)` |
| | `temp := A * 0.1` |
| | `A := A - temp` |
| | `write(A)` |
| | `read(B)` |
| `write(A)` | |
| `read(B)` | |
| `B := B + 50` | |
| `write(B)` | |
| `commit` | |
| | `B := B + temp` |
| | `write(B)` |
| | `commit` |

T1、T2 读到的都是 A = 1000。T2 写的 A = 900 被 T1 写的 950 覆盖；T1 写的 B = 2050 又被 T2 写的 2100 覆盖。最后 A = 950，B = 2100，和为 3050，凭空多出 50。

## 6. 可串行化

- 一组事务串行执行能保持数据库一致。
- 一个（可能是并发的）调度如果等价于某个串行调度，它就是可串行化的。
- 按"等价"的定义不同，分成**冲突可串行化**和**视图可串行化**。

复习题整理稿提醒的两点：

1. n 个事务有 n! 种串行调度，各自的执行结果可能不一样（比如调度 1 和调度 2），可串行化只要求和其中某一个等价。
2. 所以两个可串行化调度彼此不一定等价。

### 事务的简化视图

- 只看 `read` 和 `write` 指令，忽略其他操作。
- 假设事务在 `read` 和 `write` 之间可以对本地缓冲区里的数据做任意计算。
- 简化后的调度只包含 `read` 和 `write`。

### 冲突指令

事务 Ti 的指令 li 和事务 Tj 的指令 lj 冲突，条件是：它们访问同一个数据项 Q，并且至少有一条是 `write(Q)`。

| li | lj | 冲突吗 | 原因 |
| --- | --- | --- | --- |
| `read(Q)` | `read(Q)` | 不冲突 | 不管谁先，读到的值一样 |
| `read(Q)` | `write(Q)` | 冲突 | li 在前，读到的是原来的 Q；li 在后，读到的是 lj 写的新值 |
| `write(Q)` | `read(Q)` | 冲突 | 理由同上 |
| `write(Q)` | `write(Q)` | 冲突 | 数据库里只留下后一次写的结果，调度中下一条 `read(Q)` 读到的值会受影响，类似覆盖 |

直观上，两条冲突指令之间必须有一个（逻辑上的）先后顺序；不冲突的相邻指令交换顺序不影响结果。

### 冲突等价与冲突可串行化

- 调度 S 经过一系列相邻非冲突指令的交换，能变成调度 S'，就说 S 和 S' **冲突等价**。
- 不是所有串行调度彼此都冲突等价，比如调度 1 和调度 2。
- S 与某个串行调度冲突等价，S 就是冲突可串行化的。

例：调度 3 只保留读写指令（教材图 14-6）：

| T1 | T2 |
| --- | --- |
| `read(A)` | |
| `write(A)` | |
| | `read(A)` |
| | `write(A)` |
| `read(B)` | |
| `write(B)` | |
| | `read(B)` |
| | `write(B)` |

T2 的 A 操作和 T1 的 B 操作访问的数据项不同，互不冲突，可以一对对交换：

1. T2 的 `write(A)` 与 T1 的 `read(B)` 交换，得到调度 5（教材图 14-7），见下表。
2. T2 的 `read(A)` 与 T1 的 `read(B)` 交换。
3. T2 的 `write(A)` 与 T1 的 `write(B)` 交换。
4. T2 的 `read(A)` 与 T1 的 `write(B)` 交换。

| T1 | T2 |
| --- | --- |
| `read(A)` | |
| `write(A)` | |
| | `read(A)` |
| `read(B)` | |
| | `write(A)` |
| `write(B)` | |
| | `read(B)` |
| | `write(B)` |

四步换完，T1 的四条指令全部排到 T2 前面，得到串行调度 6（教材图 14-8）：T1 的 `read(A)`、`write(A)`、`read(B)`、`write(B)`，然后是 T2 的同样四条。所以调度 3 是冲突可串行化的。

反例，调度 7（教材图 14-9）：

| T3 | T4 |
| --- | --- |
| `read(Q)` | |
| | `write(Q)` |
| `write(Q)` | |

T4 的 `write(Q)` 和 T3 的两条指令都冲突，挪不到 T3 前面也挪不到后面，得不到 `<T3, T4>` 或 `<T4, T3>`，所以调度 7 不是冲突可串行化的。

### 优先图

判断冲突可串行化用优先图 G = (V, E)：

- 顶点集 V：参与调度的所有事务。
- 边集 E：满足下面任一条件就有边 Ti → Tj：
  1. Ti 执行 `write(Q)` 在 Tj 执行 `read(Q)` 之前；
  2. Ti 执行 `read(Q)` 在 Tj 执行 `write(Q)` 之前；
  3. Ti 执行 `write(Q)` 在 Tj 执行 `write(Q)` 之前。

  合起来记：两个事务访问同一数据项、至少一个写，谁的操作在前，边就从谁指出去。

规则：

- 有边 Ti → Tj，则任何与 S 等价的串行调度里，Ti 都必须在 Tj 前面。
- 优先图**无环**，调度就是冲突可串行化的；有环就不是。
- 无环时，对图做拓扑排序就得到串行化顺序。
- 两个事务之间有多对冲突、而且都是 T1 的操作在前，只画一条 T1 → T2 就够了。边只表示有没有先后依赖，不表示数量。
- 同时有 T1 → T2 和 T2 → T1，就成环了，先执行哪个都满足不了依赖。多个事务形成的环同理。

拓扑排序的例子（教材图 14-12）：优先图有边 Ti → Tj、Ti → Tk、Tj → Tm、Tk → Tm。Tj 和 Tk 之间没有边，所以串行化顺序有两种：Ti、Tj、Tk、Tm，或 Ti、Tk、Tj、Tm。

套到前面的调度上：

- 调度 3：T1 的 `write(A)` 在 T2 的 `read(A)` 前，T1 的 `write(B)` 在 T2 的 `read(B)` 前，只有 T1 → T2 方向的边，无环，等价串行顺序是 `<T1, T2>`。
- 调度 7：T3 的 `read(Q)` 在 T4 的 `write(Q)` 前，得 T3 → T4；T4 的 `write(Q)` 在 T3 的 `write(Q)` 前，得 T4 → T3。有环，不是冲突可串行化的。

另外，可能有两个调度结果相同，但不冲突等价，一个是冲突可串行化的，另一个不是。

### 视图等价与视图可串行化

S 和 S' 包含同一组事务。对每个数据项 Q，满足下面三条，S 和 S' 就**视图等价**：

1. 在 S 中 Ti 读的是 Q 的初始值，在 S' 中 Ti 读的也必须是 Q 的初始值。
2. 在 S 中 Ti 执行 `read(Q)` 读到的是 Tj 写的值，在 S' 中 Ti 读到的也必须是 Tj 的同一条 `write(Q)` 写的值。
3. 在 S 中执行最后一条 `write(Q)` 的事务，在 S' 中也必须执行最后一条 `write(Q)`。

条件 1、2 保证每个事务读到相同的值，从而做相同的计算；三条合起来保证两个调度最后得到相同的系统状态。

- 视图等价也完全基于 `read` 和 `write` 操作，判断视图可串行化就直接用上面的定义。
- S 与某个串行调度视图等价，S 就是视图可串行化的。
- 冲突可串行化的调度一定是视图可串行化的。复习题整理稿给的理由是"冲突可串行化的调度操作之间没有冲突"。（更正：冲突可串行化的调度照样有冲突操作，只是这些冲突的先后次序和某个串行调度一致。交换相邻的非冲突指令，不会改变每条 `read` 读到的是谁写的值，也不会改变每个数据项最后由谁写，视图等价的三条都保持，所以它一定视图可串行化。）
- 视图可串行化但不是冲突可串行化的调度，一定包含盲目写：事务写入的值不依赖它之前读过的任何值（通常是没读就写）。

例：

| T1 | T2 | T3 |
| --- | --- | --- |
| `read(Q)` | | |
| | `write(Q)` | |
| `write(Q)` | | |
| | | `write(Q)` |

- 冲突可串行化吗？T1 的 `read(Q)` 在 T2 的 `write(Q)` 前，得 T1 → T2；T2 的 `write(Q)` 在 T1 的 `write(Q)` 前，得 T2 → T1；另有 T1 → T3、T2 → T3。T1、T2 成环，不是冲突可串行化的。
- 视图可串行化吗？和串行调度 `<T1, T2, T3>` 比：两个调度里都是 T1 读 Q 的初始值，都没有别的读，最后一次写 Q 的都是 T3。三条都满足，所以视图等价于 `<T1, T2, T3>`，是视图可串行化的。
- T2 和 T3 都是没读就写，属于盲目写。T1、T2 的写最后都被 T3 覆盖了，笔记图里把它们标成"无用的写操作"。

### 其他等价概念

有的调度和串行调度结果相同，但既不冲突等价，也不视图等价。判断这种等价要分析读写之外的操作（比如加减法可以交换次序）。原笔记这里的截图缺失，下面按教材同一例子补全（整理补充）。T5 从 B 向 A 转 10：

| T1 | T5 |
| --- | --- |
| `read(A)` | |
| `A := A - 50` | |
| `write(A)` | |
| | `read(B)` |
| | `B := B - 10` |
| | `write(B)` |
| `read(B)` | |
| `B := B + 50` | |
| `write(B)` | |
| | `read(A)` |
| | `A := A + 10` |
| | `write(A)` |

设 A = 1000，B = 2000，这个调度和串行调度 `<T1, T5>` 的结果都是 A = 960，B = 2040。但 T5 的 `write(B)` 在 T1 的 `read(B)` 前，T1 的 `write(A)` 在 T5 的 `read(A)` 前，优先图有环，不冲突等价；在 `<T1, T5>` 里 T1 读的是 B 的初始值，这里读的是 T5 写的 B，也不视图等价。

## 7. 可恢复调度与无级联调度

### 可恢复调度

定义：事务 Tj 读取了事务 Ti 之前写入的数据项，那么 Ti 的提交必须出现在 Tj 的提交之前。

例（调度 9）：

| T6 | T7 |
| --- | --- |
| `read(A)` | |
| `write(A)` | |
| | `read(A)` |
| | `commit` |
| `read(B)` | |

- T7 读完 A 立刻提交，这个调度是不可恢复的。它也是一个部分调度。（更正：原文和复习题整理稿第 85 页都解释成"只执行了 read 操作"。部分调度是指调度里没有列出 T6 的提交或中止，只给出了一部分。）
- T7 提交时 T6 还是活动的。如果 T6 在提交前出故障，T7 就读到了（还可能已经展示给用户）一个不一致的数据库状态。
- T7 读了 T6 写的 A，T7 **依赖于** T6。为了保证原子性应该中止 T7，但 T7 已经提交，无法中止，于是出现 T6 故障后无法正确恢复的情况。
- 要让调度可恢复，T7 应推迟到 T6 提交之后再提交。

### 无级联调度

- 即使调度是可恢复的，从 Ti 的故障中恢复时，也可能要回滚好几个事务。
- 级联回滚：一个事务失败，导致一连串事务回滚。

例（调度 10，教材图 14-15）：

| T8 | T9 | T10 |
| --- | --- | --- |
| `read(A)` | | |
| `read(B)` | | |
| `write(A)` | | |
| | `read(A)` | |
| | `write(A)` | |
| | | `read(A)` |
| `abort` | | |

T9 读了 T8 写的 A，T10 读了 T9 写的 A。T8 中止，T9 必须回滚；T9 回滚，T10 也必须回滚。三个事务都没提交，所以调度仍是可恢复的，但发生了级联回滚。

无级联调度：不会发生级联回滚。定义是，对每一对事务 Ti 和 Tj，如果 Tj 读取了 Ti 之前写入的数据项，那么 Ti 的提交必须出现在 Tj 的这个读操作之前。

**每个无级联调度也是可恢复的**。

## 8. 事务隔离性级别

SQL 标准规定了四个隔离性级别，从高到低：

1. 可串行化：通常保证可串行化调度，能防止所有并发问题。（更正：原文说"要求所有事务一个接一个地执行"。可串行化不要求真的串行执行，只要求并发执行的结果等价于某个串行执行。）
2. 可重复读：只能读已提交的记录，而且一个事务两次读同一数据项之间，其他事务不得更新它。不要求与其他事务可串行化。能防止脏读和不可重复读，但可能出现幻读。
3. 已提交读：只能读已提交的记录，但连续两次读可能得到不同的（都已提交的）值，不要求可重复读。能防止脏读，可能出现不可重复读和幻读。（更正：原文说"事务开始后只能看到在事务开始之前已经提交的更新"，这描述的是快照。已提交读每次读都能看到读那一刻已经提交的数据，包括事务开始后才提交的修改，所以才会不可重复读。）
4. 未提交读：允许读未提交的记录，是允许的最低一致性级别，可能出现脏读。

以上所有级别都**不允许脏写**：一个数据项已经被另一个还没提交、也没中止的事务写过，就不允许再对它执行写操作。（更正：原笔记第二遍解释和复习题整理稿第 86 页都写成"尚未提交或已中止的事务"。应该是既没提交也没中止，也就是还在活动中的事务。）

脏数据指被某个事务修改了但还没提交的数据。别的事务在它提交前读了这些数据，就是脏读，可能看到不一致的结果。

不可重复读说的是修改（update）：同一个事务里对同一组数据读两次，中间另一个事务改了这些数据并提交，两次读到的结果不同。幻读说的是插入：两次查询之间别的事务插入了满足条件的新行。

复习题整理稿第 89 页把"丢失更新"也算进各级别的问题里，说未提交读、已提交读、可重复读都还存在丢失更新，可串行化"一般不使用"。核对如下：

- SQL 标准只用脏读、不可重复读、幻读三种现象来定义隔离级别，没有把丢失更新列进去。
- 按基于锁的理解，可重复读下事务读过的数据在它结束前别人不能改，"两人先读后写、后写的覆盖先写的"这种丢失更新不会发生；未提交读和已提交读下仍可能发生。（更正：原稿说可重复读还存在丢失更新，按标准的定义不成立。个别产品例外，比如 MySQL InnoDB 的可重复读用快照实现，程序先普通 `select` 读出值、算好再 `update` 写回时，仍可能覆盖掉别人已提交的修改。）
- 可串行化并发度最低、开销最大，原稿说一般不用。常见数据库的默认级别确实是已提交读（如 Oracle、SQL Server、PostgreSQL）或可重复读（如 MySQL InnoDB）。

## 9. 隔离性级别的实现

实现隔离性主要靠三类技术：

1. 锁：共享锁允许多个事务同时读同一资源，但不许任何事务写；排他锁让一个事务读写资源时挡住其他事务的访问。第 15 章细讲。
2. 时间戳：每个事务开始时分配一个唯一时间戳，系统比较时间戳来决定执行顺序。事务不用等锁，所以不会死锁。（更正：原文说还能避免脏读。基本的时间戳排序协议可能产生不可恢复的调度，要避免读到未提交数据得另加措施。）
3. 多版本和快照隔离：多版本并发控制（MVCC）为数据保留多个版本，每个事务操作的是事务开始时数据库的一个一致"快照"，读不用等其他事务完成。并发性能高，但要多占存储空间保存各个版本。

并发控制机制的目的：在获得高并发度的同时，保证产生的调度是冲突可串行化或视图可串行化的、可恢复的，并且最好是无级联的。

串行调度天然满足后两条：

- 可恢复：每个事务在下一个事务开始前就提交了，不存在依赖未提交事务结果的情况。
- 无级联：没有事务会读到另一个还没提交的事务写的数据，一个事务失败不会连累别人回滚。

笔记补充的几个概念：

- 并发控制的两种基本策略：一次只允许一个事务访问数据，简单但效率低；允许多个事务同时访问，吞吐量和资源利用率高，但需要更复杂的机制防止冲突。
- 并发事务可能导致的问题见下面"易混对比"里的表。
- 常见并发控制技术：锁（给数据项加锁，不让别的事务同时访问）、时间戳（按开始时分配的时间戳决定执行顺序）、乐观技术（假设冲突很少，事务执行时不加锁，提交时再检查有没有冲突）、多版本技术（每个数据项维护多个版本，不同事务看到不同版本）。

## 易混对比

### ACID 由谁保证

| 特性 | 含义 | 由谁负责 | 靠什么 |
| --- | --- | --- | --- |
| 原子性 | 事务的操作要么全做，要么全不做 | 恢复系统 | 日志记旧值，失败时恢复 |
| 一致性 | 单独执行事务，数据库从一个一致状态到另一个一致状态 | 编写事务的程序员（系统负责检查显式的完整性约束） | 正确的事务逻辑 |

| 持久性 | 提交后的修改永久保留 | 恢复系统 | 提交前把更新或足够的日志写到磁盘 |

### 事务的五个状态

| 状态 | 什么时候进入 | 接下来 |
| --- | --- | --- |
| 活动 | 事务开始执行 | 执行完最后一条语句进入部分提交；无法继续进入失败 |
| 部分提交 | 最后一条语句执行完 | 恢复信息写到磁盘后进入提交；写完前出故障进入失败 |
| 失败 | 发现正常执行无法继续 | 回滚完成后进入中止 |
| 中止 | 回滚完毕，数据库恢复到事务开始前 | 重启（算新事务）或杀死 |
| 提交 | 恢复信息全部写到磁盘 | 结束，只能用补偿事务撤销影响 |

### 中止、回滚与补偿事务

| | 中止 | 回滚 | 补偿事务 |
| --- | --- | --- | --- |
| 是什么 | 事务没能成功执行完 | 撤销中止事务造成的修改 | 执行与已提交事务相反的操作 |
| 针对 | 未提交的事务 | 未提交的事务 | 已提交的事务 |

### 冲突可串行化与视图可串行化

| | 冲突可串行化 | 视图可串行化 |
| --- | --- | --- |
| 等价标准 | 通过交换相邻的非冲突指令能变成串行调度 | 读初始值、读谁写的值、最后写者三条都与某个串行调度一致 |
| 判定方法 | 画优先图，无环即是 | 按定义逐个串行顺序比对 |
| 范围 | 较小 | 较大，包含全部冲突可串行化调度；多出来的那些一定含盲目写 |

### 可恢复与无级联

| | 可恢复 | 无级联 |
| --- | --- | --- |
| 条件 | Tj 读了 Ti 写的数据，则 Ti 先于 Tj **提交** | Tj 读了 Ti 写的数据，则 Ti 的提交在 Tj 的**读**之前 |
| 防止什么 | 已提交的事务依赖了后来失败的事务，无法恢复 | 一个事务失败引起一串事务回滚 |
| 关系 | 不一定无级联 | 一定可恢复 |

### 并发事务的问题

| 问题 | 怎么发生 |
| --- | --- |
| 丢失修改 | 两个事务改同一数据项，一个的修改被另一个覆盖（调度 4） |
| 脏读 | 读到另一个事务还没提交的修改 |
| 不可重复读 | 一个事务两次读之间，别的事务修改了这个数据，两次读到的不一样 |
| 幻读 | 一个事务两次查询之间，别的事务插入了满足条件的新行，两次查询结果不一样 |
| 脏写 | 写一个被别的活动事务写过、还没提交的数据项；四个隔离级别都不允许 |

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 未提交读 | 可能 | 可能 | 可能 |
| 已提交读 | 不会 | 可能 | 可能 |
| 可重复读 | 不会 | 不会 | 可能 |
| 可串行化 | 不会 | 不会 | 不会 |

## 典型题与解答

### 题 1：算调度的结果

T1、T2 如第 5 节。设 A = 1000，B = 2000，分别求调度 1、调度 2、调度 3、调度 4 执行后的 A、B，并说明哪个调度破坏了一致性。

思路：按表从上往下走，注意 `read` 是从数据库读当前值，赋值只改事务本地的变量，`write` 才写回数据库。

解答：

| 调度 | A | B | A + B |
| --- | --- | --- | --- |
| 调度 1（T1 后 T2） | 855 | 2145 | 3000 |
| 调度 2（T2 后 T1） | 850 | 2150 | 3000 |
| 调度 3 | 855 | 2145 | 3000 |
| 调度 4 | 950 | 2100 | 3050 |

调度 4 破坏了一致性。T1 在 T2 写 A 之前读了 A，之后又用旧值算出的 950 覆盖了 T2 写的 900；T2 在 T1 写 B 之前读了 B，之后用旧值算出的 2100 覆盖了 T1 写的 2050。两次修改都丢了。

### 题 2：调度 4 是冲突可串行化的吗

思路：只看读写指令，找不同事务之间对同一数据项、至少一个写的指令对，画优先图。

解答：对 A，T1 的 `read(A)` 在 T2 的 `write(A)` 之前，得 T1 → T2；T2 的 `read(A)` 在 T1 的 `write(A)` 之前，得 T2 → T1。已经成环，不是冲突可串行化的。这和题 1 的结果吻合：它和两个串行调度的结果都不同。

### 题 3：画优先图，求等价串行调度（整理补充）

(1) 判断下面的调度是否冲突可串行化，是的话给出所有等价的串行顺序。

| 步 | T1 | T2 | T3 |
| --- | --- | --- | --- |
| 1 | | `read(A)` | |
| 2 | `read(B)` | | |
| 3 | | `write(A)` | |
| 4 | | | `read(A)` |
| 5 | `write(B)` | | |
| 6 | | | `read(B)` |
| 7 | | | `write(B)` |

(2) 如果在第 8 步加上 T2 的 `read(B)`，结论怎样？

思路：按数据项分开找冲突对，每对按先后画边，再看有没有环。

解答：

(1) 数据项 A：T2 的 `write(A)`（第 3 步）在 T3 的 `read(A)`（第 4 步）前，得 T2 → T3。两条 `read(A)` 不冲突。数据项 B：T1 的 `read(B)`（2）在 T3 的 `write(B)`（7）前，T1 的 `write(B)`（5）在 T3 的 `read(B)`（6）和 `write(B)`（7）前，都得 T1 → T3。

优先图只有 T1 → T3、T2 → T3 两条边，无环，是冲突可串行化的。T1、T2 之间没有边，拓扑排序有两种：`<T1, T2, T3>` 和 `<T2, T1, T3>`。

(2) 新增的 T2 `read(B)`（8）在 T1 的 `write(B)`（5）之后，得 T1 → T2；在 T3 的 `write(B)`（7）之后，得 T3 → T2。加上原来的 T2 → T3，出现环 T2 → T3 → T2，不再是冲突可串行化的。

### 题 4：调度 7 是视图可串行化的吗

调度 7：T3 `read(Q)`，T4 `write(Q)`，T3 `write(Q)`。

思路：两个事务只有两种串行顺序，逐个按视图等价的三条比对。

解答：

- 和 `<T3, T4>` 比：调度 7 里最后写 Q 的是 T3，`<T3, T4>` 里是 T4，第 3 条不满足。
- 和 `<T4, T3>` 比：调度 7 里 T3 读的是 Q 的初始值，`<T4, T3>` 里 T3 读的是 T4 写的值，第 1 条不满足。

两个都不视图等价，所以调度 7 不是视图可串行化的。T4 的写是盲目写，可见含盲目写只是"视图可串行化但冲突不可串行化"的必要条件，有盲目写不代表一定视图可串行化。

| `commit` | |

S2：

| T1 | T2 |

S3：

| T1 | T2 |

| --- | --- | --- | --- |
| S1 | 否 | 否 | T2 先于 T1 提交，T1 若之后失败，T2 已无法回滚 |
| S2 | 是 | 否 | T1 先提交，满足可恢复；但 T2 读 A 时 T1 还没提交，T1 若在提交前失败，T2 要跟着回滚 |
| S3 | 是 | 是 | T2 读 A 时 T1 已经提交 |

### 题 6：判断对错

1. 冲突可串行化的调度一定是视图可串行化的。
2. 视图可串行化的调度一定是冲突可串行化的。
3. 无级联调度一定是可恢复的。
4. 可恢复调度一定是无级联的。
5. 事务进入部分提交状态后就一定能提交。
6. 已提交的事务出了问题，可以通过中止它来撤销影响。

解答：

1. 对。
2. 错。第 6 节 T1、T2、T3 的例子是视图可串行化的，但优先图有环。
3. 对。
4. 错。题 5 的 S2 可恢复但不是无级联的。
5. 错。部分提交时输出可能还在主存里，这时出硬件故障，事务会进入失败状态并中止。
6. 错。已提交事务不能再中止，只能执行补偿事务。

### 题 7：事务中止后怎么处理

事务中止后，系统什么时候重启它、什么时候杀死它？

思路：看中止原因在不在事务自身的逻辑里。

解答：中止是硬件错误，或者不是事务内部逻辑造成的软件错误引起的，就重启事务，重启后算一个新事务。中止是事务内部逻辑错误（只能改写程序修正）、输入错误、或者需要的数据在库里找不到造成的，就杀死事务，重启了也还会失败。

### 题 8：隔离级别与异常（整理补充）

事务 T 在已提交读级别下两次执行 `select balance from account where account_number = 'A-101'`，两次之间另一个事务把 A-101 的余额改了并提交。

1. T 两次读到的值一样吗？
2. 把 T 的隔离级别改成可重复读呢？
3. 在可重复读级别下，T 两次执行 `select count(*) from account where balance > 1000`，两次之间另一个事务插入了一个余额 5000 的新账户并提交，两次结果一样吗？

思路：已提交读每次读都看当前已提交的数据；可重复读锁住的是读过的数据项，管不住新插入的行。

解答：

1. 不一样，这是不可重复读。已提交读只保证不读未提交的数据。
2. 一样。可重复读规定两次读同一数据项之间其他事务不能更新它。
3. 可能不一样，第二次多数出一行，这是幻读。可重复读防不了幻读，要升到可串行化。

### 题 9：转账中途故障

张三给李四汇款 200 元。张三的账户已经扣了 200 元，系统发生故障，李四的账户还没加上。数据库处于什么状态？怎么解决？靠什么手段实现？（`数据库期末复习题整理.pdf` 第 89 页）

思路：扣款和入账属于同一个事务，只做了一半，违反原子性。

解答：数据库处于不一致状态，现实中这 200 元凭空消失了。应该回滚这个事务，把张三账户里扣掉的 200 元加回来，看起来就像转账从没发生过。回滚靠日志实现：修改前日志里记了事务标识、数据项、旧值和新值，系统重启后恢复系统根据日志把未完成事务的修改撤销。（原稿这题金额单位前后混写了"元"和"美元"，这里统一成元。）
