# 应用开发、触发器与授权

整理自 `笔记/数据库系统原理笔记.pdf` 第 111–123 页（第 9 章 应用设计和开发），`老师资料/SQL复习 (1).docx` 的 2.21 节"权限与角色"和 2.23 节"触发器"，以及 `笔记/数据库期末复习题整理.pdf` 第 103 页（触发器补充）、第 108–111 页（授权）和第 114–116 页"作业"里的 MySQL 用户与权限题。

## 本章要点

- 数据库应用分前端和后端：前端给用户界面，后端连数据库。应用架构经历了主机、个人计算机、Web 三个时代。
- HTTP 是无连接、无状态的，服务器靠 Cookie 里的会话标识符认出同一个用户的连续请求。
- 三层 Web 结构把 Web 服务器、应用服务器、数据库服务器分开；两层结构把应用程序直接放进 Web 服务器，开销更小。Servlet 在 Web 服务器进程里运行，CGI 每个请求都要开新进程。
- 触发器按**事件-条件-动作**模型工作。事件只能是 `insert`、`delete`、`update`，不能是 `select`；时机分 `before`、`after`；`referencing new row as` / `old row as` 引用新旧行。触发器能引用其他表，`check` 不能；能用外键级联、物化视图、内置复制工具解决的事，就别用触发器。
- 授权：`grant <权限> on <表或视图> to <用户>`。加 `with grant option`，被授权人才能再转授。
- 收回：`revoke <权限> on <表或视图> from <用户>`。`cascade` 连带收回转授出去的权限（默认行为），`restrict` 遇到需要级联收回的情况就报错，什么都不收。
- 角色是权限的集合：`create role` 建角色，权限可以授给角色，角色可以授给用户，也可以授给别的角色。
- 视图创建者只能拿到不超出自己原有权限的那部分视图权限；函数和过程用 `execute` 权限授权；声明外键要有 `references` 权限。
- MySQL 里权限分全局（`*.*`）、库、表等级别，`revoke` 要和 `grant` 在同一级别才能撤销。
- SQL 注入：程序把用户输入直接拼进 SQL 字符串，攻击者就能让程序执行自己构造的语句。

## 1. 应用程序和用户界面

应用程序是支持用户与数据库交互的软件，分两部分：

- 前端（front end）：提供用户界面。
- 后端（back end）：提供数据库接口。

应用架构的演变：

| 时代 | 计算在哪里做 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 主机时代 | 大型主机做全部计算，用户用没有处理能力的哑终端连上去输命令、看结果 | 集中管理，资源利用率高 | 不灵活，难扩展 |
| 个人计算机时代 | 每人一台 PC，应用在本地运行 | 灵活，可以按自己需要装软件 | 每台机器各有处理器和存储，资源浪费；每台都要单独管理维护，成本高 |
| Web 时代 | 应用跑在服务器上，用户用浏览器访问 | 代码都在服务器上，好维护；加服务器就能扛更多请求 | 离不开网络，有安全和隐私问题 |

## 2. 数据库的 Web 界面

### URL

统一资源定位符（Uniform Resource Locator）标识网上的一项资源，由协议类型、服务器地址（IP 或域名）、服务器上的资源位置三部分组成。比如 `https://www.example.com/path/to/myfile.html`：协议是 `https`，服务器是 `www.example.com`，资源位置是 `/path/to/myfile.html`。

### HTML

超文本标记语言，用标签描述网页里的文本、图片、链接等元素。网页由嵌套的元素组成，一个元素由开始标签、内容、结束标签构成，例如 `<p>Hello, world!</p>` 是一个段落。

### HTTP

- 应用层协议，万维网数据通信的基础，走客户端-服务器模型：客户端发请求，等服务器响应。
- 无状态：服务器不在两次请求之间保留数据。这让协议简单，服务器能快速处理大量请求。
- 用 URI 标识资源，最常见的 URI 就是 URL。
- 常用请求方法：`GET` 获取资源，`POST` 提交数据，`PUT` 更新资源，`DELETE` 删除资源。
- 响应里带状态码，告诉客户端成功与否。例如 200 表示成功，404 表示找不到资源。

### 客户端脚本

在文档里嵌入程序，让网页"动起来"。

- Java 小程序（applet）：嵌在 HTML 页面里、在浏览器中运行的 Java 程序，能做动态图形、播放音频、处理输入。因为安全和兼容性问题，现在基本被 JavaScript 取代。
- 客户端脚本语言：在用户浏览器上运行，响应点击按钮、提交表单这类交互，不用从服务器重新加载页面就能更新网页。
- JavaScript：最常用的客户端脚本语言，可以嵌进 HTML，通过操作 DOM（文档对象模型）改页面内容、响应用户事件、和服务器通信。

## 3. Web 服务器

### Web 服务器做什么

- 是安装在服务器（物理机或虚拟机）上的软件，负责处理客户端（通常是浏览器）的请求并返回响应。
- 在浏览器输入 URL 回车，浏览器就向 Web 服务器发一个 HTTP 请求。
- 服务器处理完生成 HTML 文档，放在 HTTP 响应里发回，浏览器解析后显示成网页。
- 除了静态 HTML，还能执行服务器端程序（PHP、Python、Java 等）生成动态页面，也能访问数据库。
- 公共网关接口（Common Gateway Interface，CGI）规定了 Web 服务器和服务器端程序怎么通信：服务器通过 CGI 运行程序，再把程序输出作为 HTTP 响应发给浏览器。

### 三层与两层结构

笔记里贴的是教材图 9-6、图 9-7，用文字描述如下：

- 三层结构（图 9-6）：浏览器通过网络用 HTTP 访问服务器端，服务器端依次是 Web 服务器、应用服务器、数据库服务器，数据库服务器下面是数据。
- 两层结构（图 9-7）：Web 服务器和应用服务器合成一层，下面是数据库服务器。

多一级服务器就多一份开销。CGI 还要为每个请求开一个新进程，开销更大。所以现在大多数 Web 应用用两层结构，应用程序直接运行在 Web 服务器里。

### 会话与 Cookie

- 用户登录计算机或连上数据库时创建会话。一个会话里可以有多对连续的请求和响应，用户退出或超时后结束。
- 会话信息包括用户标识符、参数等，用来跟踪用户活动，比如浏览过哪些页面、购物车里有什么。
- HTTP 是无连接协议，每个请求都是独立的，服务器不记得之前的请求，所以需要会话机制来跟踪用户。（更正：原文把"无连接"解释成数据包各自独立路由，那是网络层数据报的概念。这里的"无连接"指服务器回复完一个请求就关闭连接、忘掉这次请求；HTTP 底下用的 TCP 本身是面向连接的。）
- Cookie 是网站通过浏览器存在用户电脑上的一小段文本。之后每次访问这个网站，浏览器都把 Cookie 带回去，网站据此识别用户、跟踪会话。（更正：原文说 Cookie 在 HTTP 1.0 中引入。Cookie 并不在 HTTP/1.0 规范里，是浏览器厂商加的扩展，后来才单独标准化。）

笔记"补充"部分的几点：

- 为了实现会话，客户端要保存额外信息，并在会话的每个请求里带给服务器，服务器据此判断请求属于哪个会话。
- Cookie 常用来保存偏好设置。例如网站设一个名为 `prefs` 的 Cookie，记下语言偏好和每页显示多少条结果，下次访问时读出来用。
- 会话标识符是一种特殊的 Cookie。应用生成一个唯一的标识符，存在名为 `sessionid` 的 Cookie 里，浏览器每次请求都带上，服务器检查它的值是否对应一个已知的有效会话。
- 安全性：需要可靠认证身份的应用，只在用户认证成功（比如用户名密码正确）后才设置 Cookie；新闻网站这类要求不高的应用，Cookie 可以长期存在浏览器里；安全要求更高的应用，会在会话过期或用户注销后让会话失效。

### Servlet

Java Servlet 是运行在 Web 服务器或应用服务器上的 Java 程序，夹在浏览器请求和数据库、应用程序之间。

- 用户请求某个 Servlet 时，服务器加载并初始化它（之前没加载过的话），然后调用它的 `service` 方法处理请求。
- 可以查数据库，把结果转成 HTML 返回，也就是根据请求和查询结果动态生成页面。

相比 CGI 的优势：

1. 性能好。Servlet 在 Web 服务器的地址空间里执行，不用为每个请求单独开进程。
2. 跨平台，因为是 Java 写的。
3. 服务器上的 Java 安全管理器会限制它能动的资源，所以可信。
4. 能用 Java 类库的全部功能，可以通过 socket 和 RMI 与 applet、数据库等软件交互。

### 服务器脚本

服务器在把网页发出去之前，先执行嵌在 HTML 里的脚本。脚本执行时往页面里加文本（也可能删掉内容），脚本源代码会从页面中去掉，所以客户端看不出页面原来有代码。脚本里可以有在数据库上执行的 SQL。

| 技术 | 说明 |
| --- | --- |
| JSP（Java Server Pages） | 用 JSP 标签在 HTML 里插 Java 代码，本质上是一种 Servlet，主要做 Java Web 应用的界面部分 |
| ASP（Active Server Pages） | 微软的技术，在 IIS 里运行，文件里可以有文本、HTML、XML 和脚本 |
| PHP（Hypertext Preprocessor） | 开源的通用脚本语言，可嵌入 HTML，在服务器端执行，语法和 C 类似，常用来写网站 |

## 4. 触发器

触发器是数据库内容发生变化时自动执行的语句。老师资料的说法：由触发事件发生而自动执行的一段代码，触发事件可以是 `insert`、`delete`、`update`，**不可以是 `select`**。

### 事件-条件-动作模型

| 部分 | 含义 | 电商例子 |
| --- | --- | --- |
| 事件 | 触发规则的操作，数据库里就是插入、更新、删除 | 订单状态被更新 |
| 条件 | 规则执行的前提，满足才执行动作 | 新状态是"已发货" |
| 动作 | 被触发后要做的事：改数据、调用其他规则或触发器、发通知等 | 给客户发通知邮件 |

### 基本概念与语法要素

触发器是一种特殊的存储过程，特定事件发生时自动执行，不用显式调用，也没有输入输出参数。

| 要素 | 写法 | 说明 |
| --- | --- | --- |
| 触发事件 | `insert` / `delete` / `update` | 插入、删除、更新时触发 |
| 触发源 | `on 表名`；`of 属性名 on 表名` | 作用于整张表；只在更新指定属性时触发 |
| 触发时机 | `before` / `after` | 在事件之前或之后执行 |
| 引用值 | `referencing old row as 名字`；`referencing new row as 名字` | 引用修改前的行、修改后的行 |
| 粒度 | `for each row` | 对受影响的每一行执行一次 |
| 条件 | `when (条件)` | 条件为真才执行动作 |
| 动作 | 一条语句，或 `begin atomic ... end` 包起来的多条语句 | `begin atomic` 里的语句作为一个整体执行 |

引用值可以在动作里使用。比如更新后比较新旧值，或者插入后使用新值。（更正：原文说 `old` 和 `new` 不能在 `instead of` 触发器里用，理由是它在实际操作之前执行。这不对。`before` 触发器同样在操作之前执行，照样能用 `new`；SQL Server 的 `instead of` 触发器可以读 `inserted`、`deleted` 两张表，Oracle 视图上的 `instead of` 触发器也能用 `:OLD`、`:NEW`。）

触发器的实现没有统一标准。下面的例子用的是教材的 SQL 标准写法，SQL Server、MySQL、Oracle 的具体语法各不相同。

### 例 1：空字符串换成 null

笔记的例子，表 `r` 更新时，如果新行的电话号码是空串就改成 `null`：

```sql
create trigger setnul_trigger before update on r
referencing new row as nrow
for each row
when (nrow.phone_number = ' ')
set nrow.phone_number = null
```

（更正：原文 `when` 子句作 `nrow.phone number`，Markdown 导出时丢了下划线，列名应为 `phone_number`。另外原题目说的是"插入行"，但触发器写的是 `before update`，只在更新时生效；要让插入也生效，得再建一个 `before insert on r` 的触发器。）

作用：保证 `r` 表的 `phone_number` 列不会存进空串。

老师资料里的同一类例子，`takes` 表的成绩是空格时改成 `null`：

```sql
create trigger setnull_trigger before update on takes
referencing new row as nrow
for each row
when (nrow.grade = ' ')
begin atomic
    set nrow.grade = null;
end;
```

（更正：老师资料原文作 `before update of takes`，这是教材第 6 版原例的笔误。`of` 后面应该跟属性名，`on` 后面跟表名，所以要写 `before update on takes`，或者只监视 `grade` 列时写 `before update of grade on takes`。原文的弯引号也已改成直引号。）

### 例 2：账户透支时转成贷款

账户余额更新后变成负数，就把余额置 0，同时建一笔贷款，贷款金额是透支额：

```sql
create trigger overdraft_trigger after update on account
referencing new row as nrow
for each row
when nrow.balance < 0
begin atomic
    -- 把这个账户的储户加进 borrower，贷款号直接用账号
    insert into borrower
        (select customer_name, account_number
         from depositor
         where depositor.account_number = nrow.account_number);
    -- 新建贷款，金额为透支额（balance 的相反数）
    insert into loan values
        (nrow.account_number, nrow.branch_name, -nrow.balance);
    -- 余额置 0
    update account set balance = 0
        where account.account_number = nrow.account_number;
end
```

（更正：原文 `borrower` 那段的 `account number` 丢了下划线，应为 `account_number`。）

三步放在 `begin atomic ... end` 里，要么全做，要么全不做。执行后 `account` 表的 `balance` 不会小于 0。

### 触发器的功能

笔记"补充"部分列了四条：

1. 强化约束
   - 能实现比 `CHECK` 更复杂的约束，可以方便地引用其他表的列做检查。
   - 触发器在 `CHECK` 之后执行。（更正：这句只对 `after` 触发器成立；`before` 触发器在约束检查之前执行，所以它能先把值改好再接受检查。）
   - 一个触发器可以插入、删除、更新多行。
2. 跟踪变化：检测库内操作，禁止未经许可的更新，保证输入数据有效。比如库存系统里，库存降到需要进货的临界值时，触发器提醒管理员或自动生成给供应商的订单。
3. 级联运行：一个操作自动影响到其他表。比如删除主键表里的数据时，把外键表的对应数据改成 `NULL` 或一并删除。
4. 调用存储过程：触发器里可以调用已经定义好的存储过程，复用代码。

### 触发器种类

常用的是 DML 触发器，DDL 触发器用得少。

- DML 触发器：用户用 DML（对表或视图的 `insert`、`delete`、`update`）改数据时执行。系统把触发器和触发它的语句当作一个事务，触发器里检测到错误，整个事务自动回滚。
- DDL 触发器：响应 DDL 事件，用来在数据库里执行管理任务。（更正：原文作"CREATE、INSTERT、UPDATE"事件。DDL 事件是 `CREATE`、`ALTER`、`DROP` 这类语句，`INSERT`、`UPDATE` 属于 DML。）

按执行方式（这部分是 SQL Server 的分类）：

- `after` 触发器：记录修改完之后执行，用来做变更后的处理或检查，发现问题可以用 `ROLLBACK TRANSACTION` 回滚本次操作。一个表可以建多个。（更正：原文说"事务已提交后被触发"。`after` 触发器在语句执行完、事务提交之前执行，所以才能在里面回滚。）
- `instead of` 触发器：不执行原来的 `insert`、`update`、`delete`，改由触发器执行。触发器先检查操作对不对，对了再做，不对就阻止，常用来在数据变更前做校验。原文说一个表只能建一个，准确说是每种操作（`insert`、`update`、`delete`）各只能建一个。

### 触发器与 check 约束

`数据库期末复习题整理.pdf` 第 103 页的补充：

- 标准 SQL 里 `check` 约束只能用本表的列做判断，不能引用其他表；触发器可以引用其他关系的属性。
- 所以触发器能表达比 `check` 更复杂的限制。

原稿还列了约束检查的先后顺序：非空约束、主键约束、唯一约束、`check`，最后执行触发器；触发器里做的修改同样不能违反这些约束。这个顺序是针对 `after` 触发器的说法，约束之间谁先查，各数据库的实现不完全一样，知道"约束先查、`after` 触发器后执行"就够了。

### 什么时候不该用触发器

触发器有用，但有别的办法时最好别用。原稿（第 103 页）举的情形：

- 想用触发器实现外键的 `on delete cascade`：直接在外键上声明级联更省事，用触发器工作量大，别人也更难看懂数据库里到底有哪些约束。
- 想用触发器维护物化视图：很多系统会自动维护，没必要。
- 想用触发器复制或备份数据库：现代数据库有内置的复制工具。
- 很多触发器的用途都能改用合适的存储过程实现。

### 触发器与存储过程的区别

| | 存储过程 | 触发器 |
| --- | --- | --- |
| 是什么 | 创建并存在数据库里的一组 SQL 语句，可以反复调用 | 特殊的存储过程，建在特定表（或列）上，对应的修改发生时触发 |
| 怎么执行 | 用户直接调用（标准 SQL 用 `call`，SQL Server 用 `EXEC`/`EXECUTE`） | 不能直接调用，只在相关事件发生时自动执行 |
| 参数 | 可以有输入参数 | 不能传入参数 |
| 返回值 | 可以返回 0 个或多个值 | 不能返回值 |
| 事务 | 过程里可以使用事务 | 原稿说触发器内不允许事务处理 |
| 常见用途 | 完成用户指定的任务 | 审计、跟踪变化 |

（更正：触发器"不允许事务处理"说得太绝对。触发器运行在触发它的那条语句所在的事务里，不能自己开始或提交事务；但 SQL Server 的触发器里可以用 `ROLLBACK TRANSACTION` 回滚整个事务，上文 `after` 触发器就是这么用的。）

## 5. 授权

授权就是允许用户在数据库里拥有某些操作权限。

### 权限

| 针对 | 权限 |
| --- | --- |
| 数据 | 读数据、插入新数据、修改已有数据、删除数据 |
| 模式 | 创建和删除索引、创建关系模式、修改关系模式、删除关系模式 |

### 授予对象

- 用户：具体的用户名。
- `public`：所有用户。
- 角色：一组权限的集合，可以授给一个或多个用户，便于统一管理。

### grant 语句

```sql
grant <权限列表>
on <关系名或视图名>
to <用户列表>
```

权限列表可以写：

| 权限 | 含义 |
| --- | --- |
| `select` | 查询关系，或通过视图查询 |
| `insert` | 插入元组 |
| `update` | 用 SQL 的 `update` 语句更新 |
| `delete` | 删除元组 |
| `all privileges` | 所有允许的权限的简写 |

例：把 `branch` 的查询权授给 U1、U2、U3（老师资料的例子是 `instructor` 表，写法一样）：

```sql
grant select on branch to U1, U2, U3;
grant select on instructor to U1, U2, U3;
```

### 授权传递：with grant option

```sql
grant <权限列表>
on <关系名或视图名>
to <用户列表>
with grant option
```

加上 `with grant option`，被授权的用户或角色还能把这个权限再授给别人。

例：把 `branch` 的查询权授给 U1，并允许 U1 转授：

```sql
grant select on branch to U1 with grant option;
```

授权图：结点是用户，用户 A 把权限授给 B，就画一条 A 到 B 的边，用来表示权限是怎么一路传下去的。原笔记说"为防止权限滥用，通常要求授权图无环，任何用户不能间接把权限授给自己"。（更正：教材里授权图是允许出现环的，比如 U2、U3 互相授权。图的根是 DBA，判断一个用户有没有权限，看从根到这个用户有没有路径。收回权限后，不在这种路径上的边一并删掉，所以 U2、U3 靠互相授权保不住权限。）

### 角色

- 角色是数据库用户使用数据库的一种身份。一个用户可以有多种身份，也就是拥有一个角色列表。
- 老师资料的说法：角色可以看作权限的集合，用户属于某个角色，就自然得到这个角色的权限。

```sql
-- 创建角色
create role teller;
create role branch_manager;

-- 把权限授给角色：有 teller 角色的用户可以查 branch
grant select on branch to teller;

-- 把角色授给用户
grant teller to Mary;

-- 把角色授给角色：有 branch_manager 角色的用户也拥有 teller 的全部权限
grant teller to branch_manager;
```

老师资料的例子是一条角色链：

```sql
create role instructor;
grant instructor to Amit;
grant select on takes to instructor;

create role teaching_assistant;
grant teaching_assistant to instructor;   -- instructor 继承 teaching_assistant 的全部权限

create role dean;
grant instructor to dean;
grant dean to Satoshi;
```

Satoshi 有 `dean` 角色，`dean` 包含 `instructor`，`instructor` 又包含 `teaching_assistant`，所以 Satoshi 拥有这三个角色的全部权限，其中就有查询 `takes` 的权限。

会话所关联的角色：用 `set role 角色名` 指定当前会话使用哪个角色。指定的角色必须已经授予了这个用户，否则 `set role` 执行失败。

### revoke 语句

```sql
revoke <权限列表>
on <关系名或视图名>
from <用户列表>
```

例：从 John 和 Mary 收回对 `loan` 表 `amount` 属性的修改权；老师资料的例子是收回 U1、U2、U3 对 `branch` 的查询权：

```sql
revoke update (amount) on loan from John, Mary;
revoke select on branch from U1, U2, U3;
```

老师资料（英文截图）里的几条规则：

- 权限列表写 `all`，表示收回被收回者持有的全部权限。
- 用户列表里有 `public` 时，所有用户都失去该权限，但被单独显式授予过的用户除外。
- 同一个权限被两个不同的授权人各授给同一个用户一次，收回其中一次后，这个用户可能仍然保有该权限。（更正：截图原文作 different grantees，按意思应为 grantors，即授权人。）
- 依赖于被收回权限的其他权限也会一起被收回。

级联与非级联：

```sql
-- 级联收回
revoke <权限列表> on <关系名或视图名> from <用户列表> cascade;
-- 非级联收回
revoke <权限列表> on <关系名或视图名> from <用户列表> restrict;
```

- `cascade`：用户已经把权限转授出去的，转授出去的那些也一起收回。不写时默认就是级联。
- `restrict`：原文（课程笔记和复习题整理稿都是这么写的）说"不影响已转授用户的权限"。（更正：`restrict` 的意思是，如果这次收回会引起级联收回，系统就报错，整条 `revoke` 不执行。它不会只收回当前用户、留下下游用户的权限。）

### 视图、函数与过程、外键的授权

这部分来自 `数据库期末复习题整理.pdf` 第 110–111 页。

- 视图：创建视图的用户不一定得到视图上的全部权限，只能得到不超出他原有权限的那些。例如他对定义视图用的关系没有 `update` 权限，就拿不到视图上的 `update` 权限。如果创建者在这个视图上一项权限都拿不到，系统拒绝创建。（更正：原稿写"不需要获得该视图上的所有权限"，"不需要"应为"不一定"。）
- 函数和过程：里面可以有查询和更新。在函数或过程上授予 `execute` 权限，用户就能执行它。默认情况下和视图类似，函数和过程带着创建者拥有的权限执行。
- 模式：SQL 提供 `references` 权限，有了它才能在创建关系时声明引用某个关系的外码。例如 `grant references (dept_name) on department to Mariano;`（例句为整理补充，写法同教材）。这个权限要单独控制，是因为别人一旦建了引用你表的外键，你表上的删除和更新就会受到限制。

### SQL 注入

攻击者在输入里夹带 SQL 代码，设法让应用程序执行攻击者构造的查询，从而窃取、修改或删除数据。

例：程序让用户输入存款账号，再拼出查询字符串（Java 写法）：

```java
String query = "select balance from account where account_number = '" + number + "'";
```

`number` 是用户输入。正常输入账号时，查到的是这个账号的余额。如果用户输入的是 `'; <某个SQL语句>; -- `，拼出来就成了：

```sql
select balance from account where account_number = ''; <某个SQL语句>; -- '
```

后面那条语句会被一起执行，可以删表、改数据，末尾的 `--` 把多出来的引号注释掉了。（更正：原文的拼接字符串引号错乱，写成了三个单引号相连，这里按意思改正。）

防范办法（整理补充）：不要拼接字符串，用预编译语句，输入只当作参数值传进去：

```java
PreparedStatement ps = conn.prepareStatement(
    "select balance from account where account_number = ?");
ps.setString(1, number);
ResultSet rs = ps.executeQuery();
```

## 典型题与解答

### 题 1：为什么需要 Cookie

HTTP 下服务器怎么知道两次请求来自同一个用户？

思路：抓住 HTTP 无连接、无状态这一点。

解答：HTTP 服务器回复完请求就断开、不记状态，单看请求区分不出用户。应用在用户登录后生成唯一的会话标识符，放进 Cookie（如 `sessionid`）存在浏览器里。之后浏览器每次请求都带上这个 Cookie，服务器检查它是否对应一个有效会话，就能把请求归到同一个用户名下。

### 题 2：Servlet 和 CGI

两层 Web 结构里常用 Servlet，它比 CGI 好在哪？

思路：从进程开销说起，再补跨平台和安全。

解答：CGI 为每个请求开一个新进程，开销大。Servlet 在 Web 服务器的地址空间里运行，不用开新进程，性能好。另外它用 Java 写，跨平台；受 Java 安全管理器限制，可信；能用 Java 类库的全部功能。

### 题 3：判断

触发器的触发事件可以是 `select`。

解答：错。老师资料明确说触发事件只能是 `insert`、`delete`、`update`。

### 题 4：透支触发器执行了什么

有例 2 的 `overdraft_trigger`。执行一条 `update` 后，账户 A-101（支行 Downtown）的余额变成 -100，触发器做了哪些事？

思路：先看条件 `nrow.balance < 0` 满不满足，再按 `begin atomic` 里的三条语句顺序走。

解答：条件满足，触发器按顺序执行三步，作为一个整体：

1. 从 `depositor` 找出 A-101 的储户，把 `(customer_name, 'A-101')` 插进 `borrower`。
2. 往 `loan` 插入 `('A-101', 'Downtown', 100)`，贷款金额是透支额 100。
3. 把 `account` 里 A-101 的 `balance` 改成 0。

### 题 5：退学时删除选课记录（整理补充）

学生表 `student(ID, name, dept_name, tot_cred)`，选课表 `takes(ID, course_id, sec_id, semester, year, grade)`，`takes` 没有对 `student` 建外键。写一个触发器：删除学生时，自动删掉他的选课记录。

思路：事件是 `student` 上的 `delete`；被删的行只能用 `old row` 引用；动作是删 `takes` 里 `ID` 相同的行。

解答：

```sql
create trigger drop_student_trigger after delete on student
referencing old row as orow
for each row
begin atomic
    delete from takes
    where takes.ID = orow.ID;
end;
```

如果 `takes.ID` 建了外键，直接在外键上写 `on delete cascade` 也能达到同样效果。

### 题 6：余额不足时拒绝更新（整理补充）

`account(account_number, branch_name, balance)`。更新后余额小于 0 时拒绝这次更新。

思路：要在修改真正生效前拦下来，用 `before update`，检查新行的 `balance`，不满足就抛出错误，整条语句随之失败。

解答（标准 SQL 写法）：

```sql
create trigger balance_check_trigger before update of balance on account
referencing new row as nrow
for each row
when (nrow.balance < 0)
begin atomic
    signal sqlstate '45000';
end;
```

MySQL 写法：

```sql
create trigger balance_check_trigger before update on account
for each row
begin
    if new.balance < 0 then
        signal sqlstate '45000' set message_text = '余额不足';
    end if;
end;
```

这个需求只涉及本行数据，用约束 `check (balance >= 0)` 也能做到；需要查其他表才能判断时，就只能用触发器。

### 题 7：写授权语句

1. 把 `branch` 的查询权授给 U1、U2、U3。
2. 把 `branch` 的查询权授给 U1，并允许 U1 转授。
3. 收回 John、Mary 对 `loan` 表 `amount` 属性的修改权。
4. 建角色 `teller`，给它 `branch` 的查询权，再把它授给 Mary。

思路：`grant ... to`，`revoke ... from`；属性级权限在权限名后面用括号写属性。

解答：

```sql
grant select on branch to U1, U2, U3;

grant select on branch to U1 with grant option;

revoke update (amount) on loan from John, Mary;

create role teller;
grant select on branch to teller;
grant teller to Mary;
```

### 题 8：级联收回（整理补充）

依次执行：

```sql
-- DBA 执行
grant select on branch to U1 with grant option;
-- U1 执行
grant select on branch to U2 with grant option;
-- U2 执行
grant select on branch to U3;
```

问：(1) DBA 执行 `revoke select on branch from U1 cascade;` 后谁还有权限？(2) 改成 `restrict` 呢？(3) 如果一开始 DBA 也直接给 U3 授过这个权限，(1) 的结果有什么变化？

思路：画授权图 DBA → U1 → U2 → U3，看收回后每个用户和根 DBA 之间还有没有路径。

解答：

1. 边 DBA → U1 删掉后，U1、U2、U3 都和 DBA 断开，三人都失去查询权。
2. 收回 U1 的权限会引起对 U2、U3 的级联收回，`restrict` 下系统报错，这条 `revoke` 不执行，三人的权限都保留。
3. U3 还有一条 DBA → U3 的边，所以 U3 保留查询权，U1、U2 失去。这就是老师资料说的"被不同授权人各授予一次，收回后可能仍保有权限"。

### 题 9：角色链

按老师资料的角色链语句执行后，Satoshi 能查询 `takes` 吗？Amit 呢？

思路：顺着角色授予关系往下找，看能不能走到持有 `select on takes` 的角色。

解答：`select on takes` 授给了 `instructor`。Amit 直接拥有 `instructor`，能查。Satoshi 拥有 `dean`，`dean` 被授予了 `instructor`，所以 Satoshi 也能查。

### 题 10：SQL 注入

登录验证用 `"select * from users where name = '" + name + "' and pwd = '" + pwd + "'"` 拼接查询。攻击者密码框输入 `' or '1'='1`，会发生什么？怎么防？

思路：把输入代进字符串，看 `where` 条件变成了什么。

解答：拼出的条件是 `name = '...' and pwd = '' or '1'='1'`。`and` 比 `or` 先算，`'1'='1'` 恒为真，整个 `where` 恒真，查询返回所有用户，攻击者不用密码就能登录。防法是用 `PreparedStatement` 加 `?` 占位符传参数，输入内容只会被当作值，不会被解析成 SQL。

### 题 11：MySQL 用户与权限（作业题）

下面几题来自 `数据库期末复习题整理.pdf` 第 115–116 页的作业，答案按 MySQL 的实际行为逐条核对过。

(1) 如何在 MySQL 中查询当前的用户信息？

解答：

```sql
SELECT USER(), CURRENT_USER();
```

`USER()` 返回客户端连接时报上的用户名和主机，`CURRENT_USER()` 返回服务器实际用来做权限检查的账户，两者可能不同（比如匿名账户匹配时）。想看所有账户可以查 `SELECT user, host FROM mysql.user;`，这需要对 `mysql` 库有查询权限。

(2) 如何删除用户 `aaa`？

解答：

```sql
DROP USER 'aaa'@'%';
```

MySQL 的账户由用户名和主机两部分组成，`'aaa'@'%'` 表示可以从任意主机登录的 `aaa`。只写 `'aaa'` 时主机部分默认就是 `%`。

(3) 给用户 `'aaa'@'%'` 赋予所有数据库所有表的读权限：① 它没有权利给别人赋权；② 它也有权利给别人赋权。

思路：`*.*` 表示全局级别（所有库的所有表）；能不能转授看有没有 `WITH GRANT OPTION`。

解答：

```sql
-- ① 不能转授
GRANT SELECT ON *.* TO 'aaa'@'%';
-- ② 可以转授
GRANT SELECT ON *.* TO 'aaa'@'%' WITH GRANT OPTION;
```

（更正：原稿第 ② 问给出的语句和第 ① 问一模一样，漏了 `WITH GRANT OPTION`。）MySQL 8.0 起 `GRANT` 不会自动创建不存在的用户，要先 `CREATE USER`。

(4) 授权写的是 `GRANT SELECT ON *.* TO 'zje'@'%';`，再执行 `REVOKE SELECT ON zje.aaa FROM 'zje'@'%';`，能撤销 `zje` 对 `zje.aaa` 的查询权吗？

思路：MySQL 按级别分开记录权限：全局权限记在 `mysql.user`，库级记在 `mysql.db`，表级记在 `mysql.tables_priv`。`revoke` 只作用在它写的那个级别上。

解答：不能。这个用户没有表级的授权记录，表级 `REVOKE` 找不到对应的授权，会报错，全局的 `SELECT` 原封不动，`zje` 照样能查 `zje.aaa`。要撤销得在同一级别上写 `REVOKE SELECT ON *.* FROM 'zje'@'%';`。原稿这一问的答案是对的。

补充：MySQL 8.0.16 起打开 `partial_revokes` 系统变量后，可以在全局权限下单独撤销某个库（如 `REVOKE SELECT ON zje.* FROM 'zje'@'%';`），但只支持到库级，单张表仍然不行。

(5) 授权写的是 `GRANT SELECT ON zje.aaa TO 'zje'@'%';`，再执行 `REVOKE SELECT ON *.* FROM 'zje'@'%';`，能撤销 `zje` 对 `zje.aaa` 的查询权吗？

思路：同上，看授权和撤销是不是同一级别。

解答：不能。全局级的 `REVOKE` 只去掉全局权限，表级授权还留在 `mysql.tables_priv` 里，`zje` 仍然能查 `zje.aaa`。（更正：原稿答"可以撤销，这个命令会撤销所有数据库和表的 SELECT 权限，包括 zje.aaa"，这不符合 MySQL 的行为。）正确做法是在表级撤销：

```sql
REVOKE SELECT ON zje.aaa FROM 'zje'@'%';
-- 或者一次去掉这个账户在所有级别上的全部权限
REVOKE ALL PRIVILEGES, GRANT OPTION FROM 'zje'@'%';
-- 撤销后可以用下面的语句检查还剩哪些权限
```
