## 习题

### 5.1 什么时候用嵌入式 SQL

题目：说明在什么情况下，你会选择嵌入式 SQL，而不是只用 SQL 或者只用通用程序设计语言。

思路：SQL 和通用语言各有长处，两方面都需要时就把它们结合起来。

解答：

- 用 SQL 写查询通常比用通用语言实现同样的查询简单得多。
- 但并非所有查询都能用 SQL 写出来；打印报表、和用户交互、把查询结果送到图形界面这类非声明式的操作，SQL 本身也做不了。
- 两方面的能力都需要时，可以选择嵌入式 SQL 或动态 SQL。
- 和 ODBC、JDBC 相比，嵌入式 SQL 的程序里没有一大堆函数调用，写起来更简洁；代价是需要专门的预处理器。

### 5.2 用 JDBC 元数据打印结果集

题目：用 JDBC 的元数据功能写一个 Java 函数，参数是一个 `ResultSet`，把结果以表格形式打印出来，并用合适的列名作表头。

思路：`ResultSet.getMetaData()` 得到 `ResultSetMetaData`，`getColumnCount()` 返回列数，`getColumnName(i)` 返回第 i 列的列名，列下标从 1 开始。先打印一行表头，再用 `next()` 逐行打印每列的 `getString(i)`。

解答：

```java
import java.sql.*;

public class ResultSetPrinter {
    public static void printTable(ResultSet result) throws SQLException {
        ResultSetMetaData metadata = result.getMetaData();
        int numCols = metadata.getColumnCount();

        for (int i = 1; i <= numCols; i++) {
            System.out.print(metadata.getColumnName(i) + "\t");
        }
        System.out.println();

        while (result.next()) {
            for (int i = 1; i <= numCols; i++) {
                System.out.print(result.getString(i) + "\t");
            }
            System.out.println();
        }
    }
}
```

（更正：官方答案有两处错误。一是类声明写作 `implements TabelModel`，接口名拼错了；就算写成 `TableModel`，也得实现这个接口的全部方法才能通过编译，而本题只要求打印，用不着它。二是打印每个值时写成 `result.getString(metadata.getColumnName(i) + " ")`，括号位置不对，把空格拼进了列名，按这个名字找不到列，应为 `result.getString(i) + " "`。）

### 5.3 用 JDBC 元数据列出所有关系

题目：用 JDBC 的元数据功能写一个 Java 函数，打印数据库中所有关系，并对每个关系显示它各个属性的名字和类型。

思路：`Connection.getMetaData()` 得到 `DatabaseMetaData`。`getTables` 列出所有表，结果集的 `TABLE_NAME` 列是表名，`TABLE_SCHEM` 列是所属模式；对每个表调用 `getColumns`，结果集的 `COLUMN_NAME`、`TYPE_NAME` 分别是列名和类型名。

解答：

```java
import java.sql.*;

public class SchemaPrinter {
    public static void printSchema(Connection conn) throws SQLException {
        DatabaseMetaData dbmd = conn.getMetaData();
        ResultSet rs = dbmd.getTables(null, null, "%", new String[] {"TABLE"});
        while (rs.next()) {
            String schema = rs.getString("TABLE_SCHEM");
            String table = rs.getString("TABLE_NAME");
            System.out.println(table);

            ResultSet rs1 = dbmd.getColumns(null, schema, table, "%");
            while (rs1.next()) {
                System.out.println("    " + rs1.getString("COLUMN_NAME")
                                   + " " + rs1.getString("TYPE_NAME"));
            }
            rs1.close();
        }
        rs.close();
    }
}
```

`getTables` 的四个参数依次是目录、模式名模式、表名模式和表类型数组，传 null 表示不按该项筛选，`"%"` 匹配任意表名。

（更正：官方答案有三处无法编译的问题。`getTables()` 没有无参版本，必须给出上面的四个参数；两处 `println` 都少了右括号，其中打印列信息的那处还传了两个参数，`println` 只接受一个；类型名应从列信息结果集 `rs1` 中取，官方答案写成了 `rs`。）

### 5.4 用触发器实施"同一时间段不能在两个教室上课"

题目：用触发器实施约束"一位教师在一个学期的同一时间段内，不能在两个不同的教室讲课"。注意对 `teaches` 和 `section` 的修改都可能破坏这个约束。

思路：原文无答案（官方答案只有 "FILL"）。解题提示：

- 先确定哪些修改会破坏约束：向 `teaches` 插入元组，或修改 `teaches` 的教师或课程段；修改 `section` 的 `semester`、`year`、`time_slot_id`、`building`、`room_number`。向 `section` 插入新课程段时还没有教师，不会破坏约束。
- 在这些表上建 `after insert` / `after update` 的触发器，检查条件直接复用 4.8a 的自连接查询：同一教师、同一学期、同一时间段是否存在教室不同的两个课程段。为了效率，可以只检查与新元组有关的那位教师或那个课程段。
- 查到冲突就 `rollback`。

### 5.5 `section` 到 `time_slot` 的参照完整性（更新）

题目：写触发器，在更新 `section` 和 `time_slot` 时实施从 `section` 到 `time_slot` 的参照完整性。教材图 5.8 中的触发器只处理了插入和删除，没有覆盖更新。

思路：原文无答案（官方答案只有 "FILL"）。更新 `section` 的 `time_slot_id` 时，检查新值在 `time_slot` 中是否存在，这和插入的检查一样。更新 `time_slot` 的 `time_slot_id` 时，相当于删掉了旧值，要检查旧值是否已经在 `time_slot` 中完全消失、却仍被 `section` 引用。`time_slot` 的主码是 `(time_slot_id, day, start_time)`，一个 `time_slot_id` 可能对应多行，所以要检查"已经没有任何一行"。

解答（整理补充，写法仿照教材图 5.8）：

```sql
create trigger timeslot_check3 after update of time_slot_id on section
referencing new row as nrow
for each row
when (nrow.time_slot_id not in (select time_slot_id from time_slot))
begin
    rollback
end;

create trigger timeslot_check4 after update of time_slot_id on time_slot
referencing old row as orow
for each row
when (orow.time_slot_id not in (select time_slot_id from time_slot)
      and orow.time_slot_id in (select time_slot_id from section))
begin
    rollback
end;
```

### 5.6 维护 `student` 的 `tot_cred`

题目：为了维护 `student` 关系的 `tot_cred` 属性：

- a. 修改 `takes` 上的更新触发器（教材图 5.9），让它处理所有会影响 `tot_cred` 的更新。
- b. 写一个触发器处理向 `takes` 的插入。
- c. 在什么假设下，不在 `course` 关系上建触发器是合理的？

思路：原文无答案（官方答案只有 "FILL"）。教材图 5.9 的触发器只处理了一种情况：成绩从 F 或空值改成及格成绩时，给学生加上这门课的学分。

解答（整理补充）：

a. 还要处理反方向的情况：成绩从及格改成 F 或空值时，减去这门课的学分。

```sql
create trigger credits_lost after update of grade on takes
referencing new row as nrow
referencing old row as orow
for each row
when (orow.grade <> 'F' and orow.grade is not null
      and (nrow.grade = 'F' or nrow.grade is null))
begin atomic
    update student
    set tot_cred = tot_cred -
        (select credits from course where course.course_id = orow.course_id)
    where student.ID = orow.ID;
end;
```

如果允许修改 `takes` 的 `ID` 或 `course_id`，还要从旧学生（或按旧课程的学分）扣除，再给新学生（或按新课程的学分）加上。

b. 插入一条及格的选课记录时，加上这门课的学分：

```sql
create trigger credits_earned_insert after insert on takes
referencing new row as nrow
for each row
when (nrow.grade <> 'F' and nrow.grade is not null)
begin atomic
    update student
    set tot_cred = tot_cred +
        (select credits from course where course.course_id = nrow.course_id)
    where student.ID = nrow.ID;
end;
```

c. 假设课程的学分 `credits` 在有学生修过这门课之后不会再修改。否则修改学分时，所有已修过这门课的学生的 `tot_cred` 都要重新计算，这就需要 `course` 上的触发器。

### 5.7 用触发器维护物化视图

题目：在银行数据库上定义视图 `branch_cust`：

```sql
create view branch_cust as
    select branch_name, customer_name
    from depositor, account
    where depositor.account_number = account.account_number;
```

假设这个视图被物化（计算出来并存储）。写触发器在 `depositor` 或 `account` 发生插入和删除时维护视图，不用考虑更新。

思路：视图是 `depositor` 和 `account` 的连接。`depositor` 插入一批新元组时，把这批元组和 `account` 连接的结果插入视图；`account` 插入时对称处理。删除时同理，改为从视图中删掉相应的行。用语句级触发器，通过 `referencing new table` / `old table` 拿到这批插入或删除的元组。

解答：官方答案用"主动规则"的形式写成 `define trigger`，并假设规则立即执行（immediate binding）。下面按教材第 5 章的 `create trigger` 语法整理：

```sql
create trigger branch_cust_ins_depositor after insert on depositor
referencing new table as inserted
for each statement
    insert into branch_cust
        select branch_name, customer_name
        from inserted, account
        where inserted.account_number = account.account_number;

create trigger branch_cust_ins_account after insert on account
referencing new table as inserted
for each statement
    insert into branch_cust
        select branch_name, customer_name
        from depositor, inserted
        where depositor.account_number = inserted.account_number;

create trigger branch_cust_del_depositor after delete on depositor
referencing old table as deleted
for each statement
    delete from branch_cust
    where (branch_name, customer_name) in
          (select branch_name, customer_name
           from deleted, account
           where deleted.account_number = account.account_number);

create trigger branch_cust_del_account after delete on account
referencing old table as deleted
for each statement
    delete from branch_cust
    where (branch_name, customer_name) in
          (select branch_name, customer_name
           from depositor, deleted
           where depositor.account_number = deleted.account_number);
```

为什么要假设立即执行：如果规则延迟执行，同一批里新插入的 `account` 元组和新插入的 `depositor` 元组的连接结果会被两个插入触发器各插一次，视图里出现重复。

（更正：官方答案的两个删除规则写成 `delete from branch_cust select ...`，`delete` 语句后面不能直接跟 `select`，需要用 `where (...) in (子查询)` 指明要删的行。）

（存疑：同一客户在同一支行有多个账户时，视图里会有重复的 `(branch_name, customer_name)`。按值删除会把其他账户对应的那一份也删掉；严格维护需要记录每个组合出现的次数。官方答案没有讨论这种情况。）

### 5.8 删除账户时清理 depositor

题目：在银行数据库上写一个 SQL 触发器：删除一个账户时，对该账户的每个户主，检查他是否还有别的账户，没有的话就把他从 `depositor` 中删除。

思路：行级 `after delete` 触发器，用 `old row` 拿到被删账户的账号。`depositor` 中账号不等于被删账号的行代表"还剩下的账户"，名字不在这些行里的客户就是没有其他账户的人。

解答：

```sql
create trigger check_delete_trigger after delete on account
referencing old row as orow
for each row
delete from depositor
where depositor.customer_name not in
      (select customer_name
       from depositor
       where account_number <> orow.account_number);
```

这条 `delete` 只会删掉那些所有 `depositor` 记录都指向被删账户的客户，其他客户至少还有一条别的记录，不受影响。题目只要求处理没有其他账户的户主；仍有其他账户的户主，他指向被删账户的那一行 `depositor` 记录会留下，实际应用中一般靠外码的 `on delete cascade` 清理。

（更正：官方答案的触发器名写作 `check-delete-trigger`，标识符里不能有连字符；末尾多了一个没有对应 `begin` 的 `end`。）

### 5.9 用 rollup 表示 cube

题目：只用一个 `group by` 子句，用 `rollup` 表示 `group by cube(a, b, c, d)`。

思路：`rollup(a)` 产生两个分组 `(a)` 和 `()`。`group by` 中并列多个分组结构时，结果是它们的笛卡尔积。四个 `rollup(x)` 相乘，恰好得到 a、b、c、d 所有 2^4 = 16 个子集，也就是 cube。

解答：

```sql
group by rollup(a), rollup(b), rollup(c), rollup(d)
```

### 5.10 用排名找总分前 n 名

题目：给定关系 S(student, subject, marks)，用排名函数找出总分前 n 名的学生。

思路：先按学生分组求总分，再按总分降序排名。窗口函数在 `group by`、`having` 之后才计算，所以不能在 `having` 里引用排名结果，要套一层子查询，在外层用 `where` 过滤。

解答：

```sql
select student, total, trank
from (select student, sum(marks) as total,
             rank() over (order by sum(marks) desc) as trank
      from S
      group by student) as T
where trank <= n;
```

并列时 `rank` 给出相同名次，和第 n 名总分相同的学生都会返回，所以结果可能多于 n 个。

（更正：官方答案直接写 `having trank <= n`，还在 `over` 子句里引用同一层 `select` 定义的别名 `total`。这两处在标准 SQL 中都不允许，在 SQLite 上执行会报错。）

### 5.11 不用 cube 计算 cube

题目：对 5.6 节的 `sales` 关系，不使用 `cube` 结构，写一个 SQL 查询计算 cube 运算的结果（即教材图 5.21 中的关系）。

思路：cube 就是对维度属性的每个子集各分组一次，再用 `union` 合并；没有参与分组的属性位置填 `'all'`。两个维度有 4 个子集，所以是 4 个查询。

解答（沿用官方答案的属性名 `color`、`size`、`number`）：

```sql
select color, size, sum(number)
from sales
group by color, size
union
select color, 'all', sum(number)
from sales
group by color
union
select 'all', size, sum(number)
from sales
group by size
union
select 'all', 'all', sum(number)
from sales;
```

（更正：官方答案把按 `size` 分组的那个查询重复写了两遍。`union` 会去重，结果不受影响，但多出来的一段没有意义。）

（存疑：官方答案的属性名 `size`、`number` 和第 6 版教材 5.6 节 `sales` 关系的属性名（`item_name`、`color`、`clothes_size`、`quantity`）对不上，维度选择也需要对照教材图 5.21 核对。方法不变：对要做 cube 的每个属性子集写一个分组查询，再 `union` 起来，k 个维度共 2^k 个查询。）
