## 22 级原题

出处：课程目录 README.md（22 级回忆）。原回忆里的解释较长，下面按整理稿压缩重写。

### 1. validation & verification

- verification 验证：保证软件**正确地实现了某个特定要求**的一系列活动，问的是"东西做对了没有"（you built it right），实质是检查实现的质量。
- validation 确认：保证软件**确实满足了用户需求**的一系列活动，问的是"做的是不是用户要的东西"（you built the right thing）。
- 区别：验证对照规格说明和设计检查内部正确性，确认对照用户的真实需要检查外部有效性。V 模型里系统测试验证系统设计，验收测试确认需求。两者合称 V&V，第一个 V 是验证。

### 2. configuration management & baseline

- configuration management 软件配置管理（SCM）：软件系统发展过程中管理和控制变化的规范，目的是针对变化、控制变化。五项任务：标识配置对象、版本控制、变化控制、配置审计、配置状态报告。
- baseline 基线：已经**通过了正式复审**的规格说明或中间产品，可以作为进一步开发的基础，只有通过正式的变化控制过程才能改变。简单说，基线就是通过了正式复审的软件配置项（SCI）。
- 关系：基线是配置管理的控制点。配置项成为基线之前只需非正式的变化控制；经正式技术复审并获批准就创建基线，存入项目数据库；此后改动要走项目级的变化控制。另外，配置管理和软件维护是两回事。

### 3. coupling & cohesion

- coupling 耦合：不同模块之间互相依赖的紧密程度。从低到高：非直接、数据、标记、控制、外部、公共、内容耦合。
- cohesion 内聚：一个模块内部各元素彼此结合的紧密程度，也就是模块专注做一件事的程度。从低到高：偶然、逻辑、时间、过程、通信、顺序、功能内聚。
- 关系：两者都是衡量模块独立性的定性标准，耦合看模块之间，内聚看模块内部。设计目标是**高内聚、低耦合**。

### 4. deliverable & artifact

- artifact 工件：开发过程中活动产生的工作产品，如用例、代码、计划、测试用例、测试结果。
- deliverable 可交付成果：工件中需要移交给用户或客户、由他们查看和评价的那部分，通常在合同或项目计划里写明。可交付成果以量化的方式描述项目目标的组成部分，WBS 就以可交付成果为导向。
- 关系：deliverable 包含于 artifact。（更正：期末复习稿第 1 页原文作"软件开发过程中产生了各种各样的数据文档和程序，就叫 architect"，应为 artifact，即工件。）

### 5. regression test

- regression test 回归测试：重新执行已经做过的测试的某个子集，保证调试或其他修改没有带来非预期的软件行为或新的错误。
- 回归测试集包括三类用例：检测软件全部功能的代表性用例；针对可能受修改影响的功能的附加测试；针对被修改过的软件成分的测试。

## 英文定义辨析

期末复习稿第 73 页抄了 10 句英文定义并附中文翻译，第 6、7 句本身是错的，译文也照错句翻了。下面逐句判断并改正错句。（更正：第 1 句原文作 thefaults，第 4 句原文用破折号连接，第 9 句原文作 aotivitiesconstraints and recourses，这里已改正拼写和标点。）

1. Fault identification is the process of determining what fault or faults caused the failure, and fault correction or removal is the process of making changes to the system so the faults are removed.
   - 判断：对。缺陷识别是找出导致这次失效的一个或几个缺陷；缺陷改正（排除）是修改系统把这些缺陷去掉。原译文把 fault 和 failure 都译成"故障"，按易混词组里的区分，fault 译"缺陷"、failure 译"失效"更清楚。
2. Two classes are associated when they occur together, and when the relationship must be preserved for some period of time.
   - 判断：对。两个类一起出现，并且这种关系要保持一段时间，它们之间就是关联关系。
3. Design is the creative process of transforming the problem into a solution.
   - 判断：对。设计是把问题转化为解决方案的创造性过程。
4. A milestone is the completion of an activity: a particular point in time.
   - 判断：对。里程碑是某个活动完成的标志，是一个特定的时间点；活动才耗费时间。
5. An abstraction is a description of the problem at some level of generalization that allows us to concentrate on the key aspects of the problem without getting mired in the details.
   - 判断：对。抽象是在某个概括层次上对问题的描述，让人抓住关键方面，不陷入细节。
6. We say that two components are loosely coupled when there is a great deal of dependence between them.
   - 判断：错。组件之间依赖很多是紧密耦合，松散耦合指组件间虽有依赖但联系很弱。原译文"存在大量依赖时称为松散耦合"也是错的。
   - 改正：We say that two components are **highly coupled** when there is a great deal of dependence between them.
7. Module testing is the process of verifying that the system components work together as described in the system and program design specifications.
   - 判断：错。验证各组件按系统设计和程序设计规格说明协同工作的是集成测试。模块测试（单元测试）把每个模块当作单独实体测试，主要查编码和详细设计的错误。
   - 改正：**Integration testing** is the process of verifying that the system components work together as described in the system and program design specifications.
8. A system is a collection of objects and activities.
   - 判断：基本对，但不完整。完整说法还要加上把对象和活动联系在一起的关系描述，即 plus a description of the relationships that tie the objects and activities together（整理补充）。
9. We can think of a set of ordered tasks as a process: a series of steps involving activities, constraints and resources that produce an intended output of some kind.
   - 判断：对。一组有序的任务可以看成过程，它是由活动、约束和资源构成的一系列步骤，产生某种预期的输出。
10. The results of decomposition form composite parts called modules or components.
    - 判断：对。分解得到的组成部分叫模块或构件，对应第5章的模块化。
