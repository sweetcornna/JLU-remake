### 3. 大楼管理系统

请为上海中心大厦设计一个大楼管理系统。大厦由地上 118 层主楼、5 层裙楼和 5 层地下室组成。大厦分为 5 大功能区域，包括大众商业娱乐区域，办公区域，企业会馆区域，精品酒店区域和顶部功能体验空间。要求：能够对整幢大厦的管线和房间进行按层查看，比如展示楼房某一层的房间分布及管线状态（注：有在地板下面的水平管线，也有垂直管线）。请给出设计思路及所采用的设计模式，画出类图，并写出关键代码。

答案：**组合模式**（文件B p357-359）。文件B 注明这是开放性题目，也可以结合迭代器、工厂、原型等模式。

设计思路：

- 大厦、功能区域（含裙楼、地下室）、楼层是一层套一层的容器，房间和管线是叶子，整体是一棵树：大厦 → 功能区域 → 楼层 → 房间、管线；
- 所有节点继承同一个抽象构件，都有 `display()`。"按层查看"就是先找到某个楼层节点，再调用它的 `display()`，楼层会递归显示其中的房间和管线；
- 水平管线在地板下，只属于一层，直接作为该层的叶子；垂直管线穿过多层，可以在它经过的每一层都挂同一个管线对象，这样查看任何一层都能看到它的状态。

```java
abstract class BuildingPart {                              // 抽象构件
    protected final String name;
    protected BuildingPart(String name) { this.name = name; }
    public abstract void display(String indent);
    public void add(BuildingPart part) { throw new UnsupportedOperationException(); }
}

class Room extends BuildingPart {                          // 叶子：房间
    public Room(String name) { super(name); }
    public void display(String indent) { System.out.println(indent + "房间 " + name); }
}

class Pipeline extends BuildingPart {                      // 叶子：管线
    private final boolean vertical;
    private String status = "正常";
    public Pipeline(String name, boolean vertical) { super(name); this.vertical = vertical; }
    public void setStatus(String status) { this.status = status; }
    public void display(String indent) {
        System.out.println(indent + (vertical ? "垂直" : "水平") + "管线 " + name + "：" + status);
    }
}

class Composite extends BuildingPart {                     // 容器：功能区域等
    protected final List<BuildingPart> children = new ArrayList<>();
    public Composite(String name) { super(name); }
    @Override
    public void add(BuildingPart part) { children.add(part); }
    public void display(String indent) {
        System.out.println(indent + name);
        for (BuildingPart p : children) p.display(indent + "  ");   // 递归
    }
}

class Floor extends Composite {                            // 容器：楼层，地下室用负数层号
    private final int number;
    public Floor(int number) { super(number + " 层"); this.number = number; }
    public int getNumber() { return number; }
}

class Building extends Composite {                         // 根节点：大厦
    public Building(String name) { super(name); }
    public Floor findFloor(int number) { return find(this, number); }
    private Floor find(Composite node, int number) {
        for (BuildingPart p : node.children) {
            if (p instanceof Floor && ((Floor) p).getNumber() == number) return (Floor) p;
            if (p instanceof Composite) {
                Floor f = find((Composite) p, number);
                if (f != null) return f;
            }
        }
        return null;
    }
}

public class Client {
    public static void main(String[] args) {
        Building tower = new Building("上海中心大厦");
        Composite office = new Composite("办公区域");
        Pipeline fireMain = new Pipeline("消防立管", true);      // 垂直管线，多层共用
        Floor f35 = new Floor(35);
        f35.add(new Room("3501"));
        f35.add(new Pipeline("地板下网线", false));
        f35.add(fireMain);
        office.add(f35);
        tower.add(office);
        tower.findFloor(35).display("");                        // 按层查看
    }
}
```

### 4. 漂流瓶

请模仿 QQ 设计一个漂流瓶。要求给出设计思路、类图及关键代码。

答案：**原型模式 + 职责链模式**（文件B p359-362）。

- 漂流瓶分普通瓶、祝福瓶、真话瓶等，各种瓶子除了类型和内容，其余都一样。每种瓶子准备一个空瓶原型，用户扔瓶子时克隆一个再写内容，加新瓶型只要登记一个新原型。
- 扔出去的瓶子由谁捞到是不确定的，扔瓶子的人和捞瓶子的人也没有关系。把在线玩家组织成一条链，瓶子从链头开始漂，每个玩家决定捞不捞，不捞就传给下一个；整条链都没人捞，瓶子沉底。发送者只把瓶子交给链头，不知道最后谁捞到了。
- 每次扔瓶子前可以把玩家顺序打乱再连成链，捞到的人就是随机的。

```mermaid

        -type String
        -sender String
        -content String

```

| 角色 | 本例中的类 | 职责 |
| --- | --- | --- |
| 抽象原型 | Cloneable | Java 的克隆标记接口 |
| 具体原型 | Bottle | 实现 `clone()`，复制出一个空瓶 |
| 原型管理器 | BottleShop | 按瓶子类型保存原型，取瓶时返回克隆 |
| 抽象处理者 | Player | 保存下家引用；`handle()` 里决定自己捞还是往下传 |
| 具体处理者 | RandomPlayer、BlessingOnlyPlayer | 各自实现"捞不捞"的判断 |

```java
class Bottle implements Cloneable {                         // 原型
    private final String type;                              // 普通瓶、祝福瓶、真话瓶……
    private String sender;
    private String content;
    public Bottle(String type) { this.type = type; }
    public void write(String sender, String content) { this.sender = sender; this.content = content; }
    public String getType() { return type; }
    public String getSender() { return sender; }
    @Override
    public Bottle clone() {
        try {
            return (Bottle) super.clone();
        } catch (CloneNotSupportedException e) {
            throw new AssertionError(e);
        }
    }
}

class BottleShop {                                          // 原型管理器
    private final Map<String, Bottle> prototypes = new HashMap<>();
    public BottleShop() {
        prototypes.put("普通瓶", new Bottle("普通瓶"));
        prototypes.put("祝福瓶", new Bottle("祝福瓶"));
        prototypes.put("真话瓶", new Bottle("真话瓶"));
    }
    public Bottle create(String type) { return prototypes.get(type).clone(); }
}

abstract class Player {                                     // 抽象处理者
    protected final String name;
    private Player next;
    protected Player(String name) { this.name = name; }
    public Player setNext(Player next) { this.next = next; return next; }
    public void handle(Bottle bottle) {
        if (wantToPick(bottle)) {
            System.out.println(name + " 捞到了 " + bottle.getSender() + " 的" + bottle.getType());
        } else if (next != null) {
            next.handle(bottle);                            // 不捞就继续漂
        } else {
            System.out.println("没有人捞起，瓶子沉入海底");
        }
    }
    protected abstract boolean wantToPick(Bottle bottle);
}

class RandomPlayer extends Player {                         // 随手捞
    private final Random random = new Random();
    public RandomPlayer(String name) { super(name); }
    protected boolean wantToPick(Bottle bottle) { return random.nextInt(3) == 0; }
}

class BlessingOnlyPlayer extends Player {                   // 只捞祝福瓶
    public BlessingOnlyPlayer(String name) { super(name); }
    protected boolean wantToPick(Bottle bottle) { return "祝福瓶".equals(bottle.getType()); }
}

public class Client {
    public static void main(String[] args) {
        BottleShop shop = new BottleShop();
        Bottle bottle = shop.create("祝福瓶");
        bottle.write("玩家A", "新年快乐");

        Player head = new RandomPlayer("玩家B");
        head.setNext(new RandomPlayer("玩家C")).setNext(new BlessingOnlyPlayer("玩家D"));
        head.handle(bottle);                                 // 只交给链头
    }
}
```

文件B 的职责链节点只是各自返回一个随机数，由客户端循环取下一个节点，瓶子并没有沿链传递，体现不出职责链；它的 `clone()` 声明为返回 Object 并抛出受检异常，每次调用都要强转和 try-catch。这里重写了这两部分。

**对比分析：**

相同点：

- 都是对象行为型模式，目的都是降低对象之间的耦合；
- 结构上都有一个"中心"对象持有一组其他对象，并逐个调用它们。

不同点：

| | 观察者模式 | 中介者模式 |
| --- | --- | --- |
| 解决的问题 | 一个对象变了，要通知数量不定的其他对象 | 一组对象之间互相调用，关系是网状的 |
| 交互方向 | 单向：目标通知观察者，观察者之间互不相干 | 多向：任何同事都能通过中介者影响其他同事 |
| 中心对象的职责 | 目标只维护列表和广播，不管观察者收到后做什么 | 中介者掌握交互规则（先换汇率再问卖家），是业务逻辑的集中地 |
| 依赖关系 | 目标只依赖抽象观察者 | 同事只依赖中介者，中介者要认识所有具体同事 |
| 扩展 | 加观察者不改目标，符合开闭原则 | 加同事或改交互规则通常要改中介者 |
| 主要缺点 | 观察者多时通知耗时；观察者之间如有循环依赖可能循环调用 | 交互逻辑全堆在中介者里，中介者容易臃肿难维护 |

两者也常一起用：同事对象状态变化时，可以用观察者的方式通知中介者；MVC 里控制器是中介者，模型和视图之间是观察者。

### 2. 带名字的打印机

设计一个"带名字的打印机"（说是打印机，其实只是将文字显示在界面上而已）。在 Main 类中会生成 PrinterProxy 类的实例（即"代理人"）。首先我们会给实例赋予名字 Alice 并在界面中显示该名字。接着会将实例名字改为 Bob，然后显示该名字。在设置和获取名字时，都不会生成真正的 Printer 类的实例（即本人），而是由 PrinterProxy 类代理。最后，直到我们调用 print 方法，开始进入实际打印阶段后，PrinterProxy 类才会生成 Printer 类的实例。给出设计模式的名称，画出类图，写出关键代码。

答案：**代理模式**，准确地说是虚拟代理：真实对象创建开销大，代理先顶着，真正要用时才创建。

- Printable 是抽象主题，声明设置名字、获取名字、打印三个方法；
- Printer 是真实主题，假设创建它很耗时；
- PrinterProxy 是代理，自己保存名字，设置和获取名字都不需要 Printer；调用 `print()` 时才创建 Printer，并把名字交给它。

```mermaid

        <<interface>>
        +setPrinterName(String name) void
        +getPrinterName() String
        +print(String text) void
    }
    class Printer {
        -name String
        +Printer(String name)
    }
    class PrinterProxy {
        -name String
```

| 角色 | 本例中的类 | 职责 |
| --- | --- | --- |
| 抽象主题 | Printable | 声明设置名字、获取名字、打印 |
| 真实主题 | Printer | 真正执行打印，创建开销大 |
| 代理 | PrinterProxy | 自己处理名字；第一次打印时才创建 Printer 并转发 |
| 客户端 | Main | 只面向 Printable 编程 |

```java
interface Printable {                                     // 抽象主题
    void setPrinterName(String name);
    String getPrinterName();
    void print(String text);
}

class Printer implements Printable {                      // 真实主题
    private String name;
    public Printer(String name) {
        this.name = name;
        System.out.println("（创建 Printer 实例，耗时较长）");
    }
    public void setPrinterName(String name) { this.name = name; }
    public String getPrinterName() { return name; }
    public void print(String text) { System.out.println("[" + name + "] " + text); }
}

class PrinterProxy implements Printable {                 // 代理
    private String name;
    private Printer real;                                 // 用到时才创建
    public PrinterProxy(String name) { this.name = name; }
    public synchronized void setPrinterName(String name) {
        if (real != null) real.setPrinterName(name);      // 本人已存在就一起改
        this.name = name;
    }
    public String getPrinterName() { return name; }       // 不需要本人
    public void print(String text) {
        realize();
        real.print(text);
    }
    private synchronized void realize() {
        if (real == null) real = new Printer(name);
    }
}

public class Main {
    public static void main(String[] args) {
        Printable p = new PrinterProxy("Alice");
```

| --- | --- | --- |
| 环境类 | TcsA | 保存当前状态、期望温度和室温，把三条指令委托给当前状态 |
| 抽象状态 | AirState | 声明开启、关闭、设温三条指令 |

```java
interface AirState {                                      // 抽象状态
    void turnOn(TcsA ctx);
    void turnOff(TcsA ctx);
    void setTemperature(TcsA ctx, int t);
}

class OffState implements AirState {                      // 关闭：只接受开启
    public void turnOn(TcsA ctx) {
        ctx.setState(new OnState());
        ctx.regulate();                                   // 读取期望温度 T 并开始调节
    }
    public void turnOff(TcsA ctx) { System.out.println("空调已关闭"); }
    public void setTemperature(TcsA ctx, int t) { System.out.println("关闭状态不接受温度设置"); }
}

class OnState implements AirState {                       // 开启：接受设温和关闭
    public void turnOn(TcsA ctx) { System.out.println("空调已开启"); }
    public void turnOff(TcsA ctx) {
        ctx.setState(new OffState());
        System.out.println("停止温控");
    }
    public void setTemperature(TcsA ctx, int t) {
        ctx.setExpected(t);
        ctx.regulate();
    }
}

class TcsA {                                              // 环境类：一个房间的温控
    private AirState state = new OffState();
    private int expected = 26;                            // 期望温度 T
    private int current;                                  // 当前室温
    public TcsA(int current) { this.current = current; }
    void setState(AirState s) { state = s; }
    void setExpected(int t) { expected = t; }
    void regulate() {
        if (current < expected) System.out.println("升温到 " + expected);
        else if (current > expected) System.out.println("降温到 " + expected);
        current = expected;
    }
    public void turnOn() { state.turnOn(this); }
    public void turnOff() { state.turnOff(this); }
    public void setTemperature(int t) { state.setTemperature(this, t); }
}
```

#### 2. 医院呼叫应答系统 HS（10 分）

```java
class CallCenter {                                        // 中介者
    private final List<Device> devices = new ArrayList<>();
    public void register(Device d) { devices.add(d); }
    public void call(String room) { for (Device d : devices) d.showCall(room); }
    public void answer(String room) { for (Device d : devices) d.stopCall(room); }
}

abstract class Device {                                   // 抽象同事
    protected final CallCenter center;
    protected Device(CallCenter center) {
        this.center = center;
        center.register(this);

    public void showCall(String room) { }                 // 默认不响应
    public void stopCall(String room) { }
}

    public void press() { center.call(room); }
}

class Responder extends Device {                          // 病房呼叫显示应答器
    private final String room;
    public Responder(CallCenter c, String room) { super(c); this.room = room; }
    public void showCall(String r) { System.out.println(room + " 病房显示呼叫 " + r); }
    public void stopCall(String r) { System.out.println(room + " 病房停止显示 " + r); }
    public void answer() { center.answer(room); }          // 医护人员按应答
}

class HallScreen extends Device {
    public HallScreen(CallCenter c) { super(c); }
    public void showCall(String r) { System.out.println("大厅屏幕显示 " + r); }
    public void stopCall(String r) { System.out.println("大厅屏幕清除 " + r); }
}

class HallSpeaker extends Device {
    public HallSpeaker(CallCenter c) { super(c); }
    public void showCall(String r) { System.out.println("语音播报 " + r); }
    public void stopCall(String r) { System.out.println("停止播报"); }
}

public class Client {
```

（2）需要计算每个订单的税费，不同商品的税费及计算方式会有所区别。所以决定在系统中直接调用不同商品供应商提供的税费计算类，但每个供应商的类提供了不同的调用方法。系统设计中需要考虑如果商品更换了供应商，应该尽可能少地在系统中修改或创建新类。

请用恰当的设计模式来满足上述设计要求，画出类图，给出核心代码。

答案：**策略模式 + 对象适配器模式**（文件B p341-346）。[12 简答题精编](<12 简答题精编.md>) 第四部分第 5 题是同一个思路。

- 促销用策略：Promotion 是抽象策略，百分比折扣、现金减免等各是一个具体策略；订单是环境类，用户选了哪种促销就注入哪个策略。促销代码再多再常改，也只改策略类，控制器和订单类不动。
- 税费用适配器：系统定义统一的目标接口 TaxCalculator；各供应商的税费计算类是适配者，方法各不相同；每个供应商配一个适配器实现 TaxCalculator。商品持有 TaxCalculator，商品换供应商时只要换注入的适配器对象，系统其他类不改；新供应商只多一个适配器类。

| --- | --- | --- |

```java
interface Promotion {                                     // 抽象策略
    double apply(Order order);                            // 返回促销后的金额
}

class PercentOff implements Promotion {                   // 百分比折扣
    private final double rate;
    public PercentOff(double rate) { this.rate = rate; }
    public double apply(Order o) { return o.total() * rate; }
}

class CashOff implements Promotion {                      // 满额现金减免
    private final double threshold;
    private final double cash;
    public CashOff(double threshold, double cash) { this.threshold = threshold; this.cash = cash; }
    public double apply(Order o) { return o.total() >= threshold ? o.total() - cash : o.total(); }
}

interface TaxCalculator {                                 // 目标接口
    double tax(double price);
}

class SupplierA {                                         // 适配者：供应商 A 的类（示意）
    public double calcTaxA(double price) { return price * 0.1; }
}

class SupplierB {                                         // 适配者：供应商 B，调用方法不同
    public double computeDuty(double price, int rateLevel) { return price * 0.05 * rateLevel; }
}

class SupplierATaxAdapter implements TaxCalculator {
    private final SupplierA adaptee = new SupplierA();
    public double tax(double price) { return adaptee.calcTaxA(price); }
}

class SupplierBTaxAdapter implements TaxCalculator {
    private final SupplierB adaptee = new SupplierB();
    public double tax(double price) { return adaptee.computeDuty(price, 2); }
}

class Product {
    private final double price;
    private TaxCalculator tax;
    public Product(double price, TaxCalculator tax) { this.price = price; this.tax = tax; }
    public void setTax(TaxCalculator tax) { this.tax = tax; }  // 换供应商
    public double getPrice() { return price; }
    public double tax() { return tax.tax(price); }
}

class Order {                                             // 环境类
    private final List<Product> items = new ArrayList<>();
    private Promotion promotion = o -> o.total();          // 默认不促销
    public void add(Product p) { items.add(p); }
    public void setPromotion(Promotion p) { promotion = p; }
    public double total() {
        double sum = 0;
        for (Product p : items) sum += p.getPrice();
        return sum;
    }
    public double totalTax() {
        double sum = 0;
        for (Product p : items) sum += p.tax();
        return sum;
    }
    public double payable() { return promotion.apply(this) + totalTax(); }
}
```

#### 4. 智能家居的家电自动控制子系统（15 分）

某公司想要开发一个智能家居系统，该系统中的家电自动控制子系统请你负责设计开发。该系统能够识别场景并给出恰当的响应，比如，该系统"看到"主人起床，就自动打开热水器、拉开窗帘、启动扫地机器人等；"看到"主人出门，就自动关闭网络、启动防盗系统等；"看到"主人上床，就自动关闭窗帘、设置空调睡眠模式、关闭电视电脑等。

请用恰当的设计模式实现这个子系统，画出类图，给出核心代码。

答案：**观察者模式**（文件B p346-351，普班参考答案也用观察者）。

- 场景识别器（智能机器人）是观察目标，各种家电是观察者，先登记到识别器上；
- 识别器"看到"一个场景，就把场景广播给所有家电；每个家电在 `onScene()` 里自己决定对这个场景做什么，不相关的场景直接忽略；
- 加新家电只要写一个观察者类并登记，识别器不用改；场景对应的动作也分散在各家电里维护。

```java
enum Scene { GET_UP, GO_OUT, GO_TO_BED }

interface Appliance {                                     // 抽象观察者
    void onScene(Scene scene);
}

class SceneDetector {                                     // 观察目标
    private final List<Appliance> appliances = new ArrayList<>();
    public void attach(Appliance a) { appliances.add(a); }
    public void detach(Appliance a) { appliances.remove(a); }
    public void detected(Scene scene) {                   // "看到"主人的动作后广播
        for (Appliance a : appliances) a.onScene(scene);
    }
}

class Curtain implements Appliance {
    public void onScene(Scene s) {
        if (s == Scene.GET_UP) System.out.println("拉开窗帘");
        else if (s == Scene.GO_TO_BED) System.out.println("关闭窗帘");
    }
}

class AirConditioner implements Appliance {
    public void onScene(Scene s) {
        if (s == Scene.GO_TO_BED) System.out.println("空调进入睡眠模式");
    }
}

class SecuritySystem implements Appliance {
    public void onScene(Scene s) {
        if (s == Scene.GO_OUT) System.out.println("启动防盗系统");
    }
}
// WaterHeater、SweepRobot、Network、TV、Computer 写法相同

public class Client {
    public static void main(String[] args) {
        SceneDetector detector = new SceneDetector();
        detector.attach(new Curtain());
        detector.attach(new AirConditioner());
        detector.attach(new SecuritySystem());
        detector.detected(Scene.GET_UP);
        detector.detected(Scene.GO_TO_BED);
    }
}
```

```cpp
#include <iostream>
#include <list>
#include <string>
using namespace std;

class Observer {                                  // 抽象观察者
public:
    virtual ~Observer() {}
    virtual void Update(const string& scene) = 0;
};

class SmartRobot {                                // 观察目标：智能机器人
public:
    void Add(Observer* o)    { observers.push_back(o); }
    void Remove(Observer* o) { observers.remove(o); }
    void Watch(const string& seen) { SetState(seen); }   // 观察主人的行为
    void SetState(const string& s) { state = s; Notify(); }
private:
    void Notify() {
        for (list<Observer*>::iterator it = observers.begin(); it != observers.end(); ++it)
            (*it)->Update(state);
    }
    string state;
    list<Observer*> observers;
};

class WaterHeater : public Observer {             // 热水器
public:
    void Update(const string& scene) {
        if (scene == "起床") cout << "打开热水器" << endl;
        // 其余行为略
    }
};

int main() {
    SmartRobot robot;
    WaterHeater heater;
    robot.Add(&heater);
    robot.Watch("起床");
    return 0;
}
```

### 二、简答题

**1.** 为什么优先使用对象组合而不是类继承。

要点：合成复用原则；组合是黑箱复用、不破坏封装、耦合低、运行时可替换，缺点是要管理的对象多；继承写起来容易，但破坏封装、父类一改子类跟着改、静态不灵活。答案见 [12 简答题精编](<12 简答题精编.md>) 第一部分第 10 题。

**2.** 请举例说明你对创建型设计模式的理解。

要点：把对象的创建和使用分离，客户不知道具体类、不关心对象怎么创建；类创建型用继承，对象创建型委托给另一个对象；例子是买苹果不用关心产地。答案见 [12 简答题精编](<12 简答题精编.md>) 第二部分第 1 题。

**3.** 请举例说明哪些情况下可以使用组合模式。

要点：整体与部分的层次结构、希望一致对待；树形结构；叶子和容器类型不固定。例子是目录、菜单、组织结构。答案见 [12 简答题精编](<12 简答题精编.md>) 第三部分第 1 题。

**4.** 抽象工厂模式和原型模式有哪些相同和不同，可以联合使用么？

要点：都用来得到新对象；原型关注怎样创建（克隆），抽象工厂关注创建哪一族；可以联用，工厂里用克隆原型来生产产品。答案见 [12 简答题精编](<12 简答题精编.md>) 第二部分第 2 题。

**5.** 请给出一个适合使用策略模式的示例场景，并说明与不使用策略模式相比，有哪些优点？

要点：查找、排序有多种算法；不用策略就是硬编码或 if-else；用了之后符合开闭原则、避免多重条件、算法可复用、用组合代替继承。答案见 [12 简答题精编](<12 简答题精编.md>) 第四部分第 1 题。

#### 1. Word 文档的打开和保存方式（10 分）

```java
class SaveButton extends Trigger {                        // 保存图标

class Shortcut extends Trigger {                          // 快捷键 ctrl+s
    public void press() { fire(); }
}
```

#### 2. 奖金计算系统（10 分）

开发一个系统帮助业务部门实现灵活的奖金计算。对于普通员工，主要有个人当月业务奖金、个人当月回款奖金等，对于部门经理，除了有普通员工的奖金外，还有团队当月业务奖金等。目前各奖金类别的计算规则如下：

- 个人当月业务奖金 = 个人当月销售额 × 3%
- 个人当月回款奖金 = 个人当月回款额 × 0.1%
- 团队当月业务奖金 = 团队当月销售额 × 1%

考虑到业务部门要通过调整奖金计算方式来激励士气，系统应灵活地适应各种需求变化，例如，将来可能会增加个人业务增长奖金、团队当月回款奖金、团队业务增长奖金、团队盈利奖金等奖金类别，也可能增加新的员工岗位；或变更奖金计算规则等。请写出你所选择的设计模式；画出类图，并给出核心代码。

答案：**装饰模式**（参考答案）。这道题也是作业题"奖金计算系统"，详见 [30 作业：创建型与结构型模式](<30 作业：创建型与结构型模式.md>) 第 10 题。

- 一个人的奖金是若干奖金类别的叠加，经理比员工多叠一层。每种奖金类别做成一个装饰类，在被装饰对象算出的奖金上加上自己这一项；
- 普通员工 = 业务奖金 + 回款奖金；部门经理 = 在普通员工的基础上再套一层团队业务奖金；
- 新奖金类别只加一个装饰类；新岗位只是换一种套法；某项规则变了只改对应的一个装饰类。

```java
class SalesData {                                         // 计算用到的当月数据
    double personalSales;
    double personalCollection;
    double teamSales;
}

abstract class Bonus {                                    // 抽象构件
    public abstract double calc(SalesData d);
}

class NoBonus extends Bonus {                             // 具体构件：从 0 开始累加
    public double calc(SalesData d) { return 0; }
}

abstract class BonusDecorator extends Bonus {             // 抽象装饰
    protected final Bonus inner;
    protected BonusDecorator(Bonus inner) { this.inner = inner; }
}

class PersonalSalesBonus extends BonusDecorator {         // 个人当月业务奖金
    public PersonalSalesBonus(Bonus inner) { super(inner); }
    public double calc(SalesData d) { return inner.calc(d) + d.personalSales * 0.03; }
}

class PersonalCollectionBonus extends BonusDecorator {    // 个人当月回款奖金
    public PersonalCollectionBonus(Bonus inner) { super(inner); }
    public double calc(SalesData d) { return inner.calc(d) + d.personalCollection * 0.001; }
}

class TeamSalesBonus extends BonusDecorator {             // 团队当月业务奖金
    public TeamSalesBonus(Bonus inner) { super(inner); }
    public double calc(SalesData d) { return inner.calc(d) + d.teamSales * 0.01; }
}

public class Client {
    public static void main(String[] args) {
        Bonus staff = new PersonalCollectionBonus(new PersonalSalesBonus(new NoBonus()));
        Bonus manager = new TeamSalesBonus(
                new PersonalCollectionBonus(new PersonalSalesBonus(new NoBonus())));
        SalesData d = new SalesData();
        d.personalSales = 100000;
        d.personalCollection = 80000;
        d.teamSales = 500000;
        System.out.println(staff.calc(d));                // 3000 + 80 = 3080.0
        System.out.println(manager.calc(d));              // 3080 + 5000 = 8080.0
    }
}
```

| 抽象装饰 | PhotoEffect | 持有被装饰的照片 |
| 具体装饰 | SoundEffect、LaceBorder | 显示照片后加上音效、花边 |

```java
abstract class AlbumItem {                                 // 抽象构件
    protected final String name;
    protected AlbumItem(String name) { this.name = name; }
    public abstract void show(String indent);
}

class Folder extends AlbumItem {                           // 容器：年、月、日目录
    private final List<AlbumItem> children = new ArrayList<>();
    public Folder(String name) { super(name); }
    public void add(AlbumItem item) { children.add(item); }
    public Folder subFolder(String name) {                 // 找不到就新建
        for (AlbumItem item : children) {
            if (item instanceof Folder && item.name.equals(name)) return (Folder) item;
        }
        Folder f = new Folder(name);
        children.add(f);
        return f;
    }
    public void show(String indent) {
        System.out.println(indent + name);
        for (AlbumItem item : children) item.show(indent + "  ");
    }
}

abstract class PhotoItem extends AlbumItem {               // 照片一侧的抽象
    protected PhotoItem(String name) { super(name); }
    public abstract LocalDate getDate();
}

class Photo extends PhotoItem {                            // 叶子，也是被装饰的具体构件
    private final LocalDate date;
    public Photo(String name, LocalDate date) { super(name); this.date = date; }
    public LocalDate getDate() { return date; }
    public void show(String indent) { System.out.println(indent + "照片 " + name); }
}

abstract class PhotoEffect extends PhotoItem {             // 抽象装饰
    protected final PhotoItem photo;
    protected PhotoEffect(PhotoItem photo) { super(photo.name); this.photo = photo; }
    public LocalDate getDate() { return photo.getDate(); }
}

class SoundEffect extends PhotoEffect {
    public SoundEffect(PhotoItem photo) { super(photo); }
    public void show(String indent) {
        photo.show(indent);
        System.out.println(indent + "  + 音效");
    }
}

class LaceBorder extends PhotoEffect {
    public LaceBorder(PhotoItem photo) { super(photo); }
    public void show(String indent) {
        photo.show(indent);
        System.out.println(indent + "  + 花边");
    }
}

class AlbumGenerator {
    public Folder generate(List<PhotoItem> photos) {
        Folder root = new Folder("电子相册");
        for (PhotoItem p : photos) {
            LocalDate d = p.getDate();
            root.subFolder(d.getYear() + "年")
                .subFolder(d.getMonthValue() + "月")
                .subFolder(d.getDayOfMonth() + "日")
                .add(p);
        }
        return root;
    }
}

public class Client {
    public static void main(String[] args) {
        PhotoItem a = new Photo("海边.jpg", LocalDate.of(2020, 7, 1));
        PhotoItem b = new LaceBorder(new SoundEffect(new Photo("生日.jpg", LocalDate.of(2020, 7, 1))));
        new AlbumGenerator().generate(List.of(a, b)).show("");
    }
}
```

### 二、反驳题

下列每小题的文字叙述中，均存在错误的观点或错误的推断过程和结论，识别并反驳这些错误。注意：反驳不是改错，反驳是需要给出理由的。

作答时先指出错在哪一步，再讲理由，最好带一个例子。

#### 1. 单一职责原则与多接口

单一职责原则的核心内容是：导致一个类变化的因素不应该有多个。若一个类 A 实现了多个接口，则意味着类 A 中包含了来自于不同接口中的多种变化因素，导致类 A 违反了单一职责原则，所以，不应该以一个类实现多个接口的方式解决设计问题。

（原卷无答案，以下为整理补充）

错误在"实现多个接口就意味着有多个变化因素"这一步推断，以及由此得出的结论。

- 单一职责原则衡量的是类承担的职责，也就是引起它变化的原因有几个，和实现了几个接口没有直接关系。接口常常只是从不同角度描述同一个职责。比如 Java 的 ArrayList 实现了 List、RandomAccess、Cloneable、Serializable，它的职责始终只有"动态数组容器"一个，这些接口分别说明它能被当作列表用、支持随机访问、能克隆、能序列化。
- 反过来，只实现一个接口也可能违反单一职责原则。2018 级卷类图分析题的图 a 就是一个接口里塞了连接和数据传递两类职责。
- 结论还和接口隔离原则相矛盾。接口隔离原则主张把大接口拆成多个角色接口，一个类按需要实现其中几个，让不同客户只依赖自己用到的那部分。类适配器同时继承适配者、实现目标接口，也是正常用法。
- 真的发现一个类混进了几种不相关的职责，应当拆分这个类，这和禁止一个类实现多个接口是两回事。

#### 2. 桥接模式与开闭原则

与实现相比，接口是相对稳定的，所以，面向接口编程是实现开闭原则的基本手段之一。但在桥接模式中，允许接口与实现各自独立变化，势必导致接口不稳定，并且可能使得实现与接口之间的不匹配，所以，桥接模式最主要的缺点就是不满足开闭原则。

（原卷无答案，以下为整理补充）

错误在把桥接模式里的"抽象部分、实现部分"等同于"接口、实现"，再由"各自独立变化"推出"接口不稳定"。

- 桥接模式里的抽象部分（Abstraction 及其扩充抽象类）和实现部分（Implementor 及其具体实现类）是两个维度上的两棵继承树。"各自独立变化"指的是两棵树都可以独立地增加子类，例如图形可以加新形状，绘图实现可以加新平台。
- 变化发生在子类层面。抽象类 Abstraction 对外的接口、实现类接口 Implementor 本身都是稳定的，抽象部分只依赖 Implementor 接口，两者之间的"桥"建在抽象层上。
- 因此新增一个扩充抽象类或具体实现类，原有代码都不用改，这正是开闭原则。桥接模式用组合代替多层继承，把 m×n 个子类减少为 m+n 个，本身就是满足开闭原则的典型做法。
- 所有具体实现类都实现同一个 Implementor 接口，抽象部分只调用这个接口里的方法，不存在"实现与接口不匹配"的问题。
- 桥接模式真正的缺点是增加了理解和设计的难度，要求一开始就正确识别出两个独立变化的维度。详见 [03 结构型模式](<03 结构型模式.md>)。

#### 3. 装饰模式与继承

装饰模式中，在遵循同一接口的前提下，装饰类可以对被装饰类中的功能进行加强（扩展），而普通的继承机制下，子类也可以对父类中的功能进行加强（扩展）。因为继承机制已经提供了功能加强（扩展）的能力，并且比装饰模式结构简单，所以装饰模式是多余的，开发时没必要使用。

（原卷无答案，以下为整理补充）

错误在"两者都能扩展功能，所以可以互相替代"。能做到同一件事，不代表在灵活性和代价上一样。

- 继承是静态的，扩展在编译时就定了，而且作用于这个类的所有对象；装饰是动态的，可以在运行时给某一个对象加上或去掉功能，其他对象不受影响。
- 功能需要自由组合时，继承会类爆炸。例如给文本框加滚动条、黑边框、阴影 3 种功能，任意组合要写 7 个子类，还要乘上每一种具体构件；用装饰模式只要 3 个装饰类，组合方式和叠加顺序都在客户端决定。
- 一个装饰类可以装饰同一抽象构件下的任何具体构件，继承则要给每个具体类分别派生子类。被扩展的类声明为 final、不能继承时，只能用装饰这类组合的方式。
- 加新功能只加新装饰类，符合开闭原则和合成复用原则。
- "结构简单"只在扩展单一、固定的时候成立。装饰模式的代价是小对象多、排错时要一层层看，这是取舍问题，不能因此说它多余。详见 [03 结构型模式](<03 结构型模式.md>)。

#### 4. 设计模式是否冗余

程序设计语言自身的定义中，往往存在一些冗余成分，例如：存在不同形式的循环控制语句（for 语句、while 语句、do-while 语句等），这些不同形式的循环控制语句是可以相互替换使用的。设计模式中，也存在若干冗余的设计模式，针对同样的设计问题，冗余的设计模式可以相互替换使用，例如：所有的创建型设计模式都分离了对象的创建过程和对象的使用过程，都可以灵活控制对象的产生，它们是可以互相替换使用的；再如：状态模式与策略模式的模型图相同，只不过角色名称不同而已，在模式应用中，这两个设计模式可以根据开发人员的个人喜好，任选其一使用。

（原卷无答案，以下为整理补充）

错误在类比和两个例子上：由"有共同点"推出"解决同样的问题"，由"结构图相同"推出"是同一个模式"。

- 类比不成立。几种循环语句的语义等价，能机械地互相改写。设计模式由意图、适用场景、解决方案和效果共同定义，区分模式主要看意图，结构图只是方案的一部分。
- 创建型模式的共同点只是"创建和使用分离"，各自解决的问题不同：单例保证只有一个实例；工厂方法让子类决定创建哪种产品；抽象工厂创建一族相互配套的产品；建造者分步骤构造由多个部件组成的复杂对象；原型通过复制已有对象来创建，适合创建代价大或运行时才知道类型的情况。拿原型替换单例，唯一性就没了；拿工厂方法替换建造者，部件和装配顺序就没人管了。它们经常联用（例如工厂做成单例、抽象工厂里用原型生产产品），这也说明彼此不是替代关系。
- 状态模式和策略模式类图相似，意图不同。状态模式里，对象的行为随内部状态改变，状态之间知道彼此并自动转换，客户端一般不用关心当前是什么状态；策略模式里，由客户端主动选择算法，各个策略相互独立、可以互换，没有转换关系。把状态机写成策略，状态转换的判断又会回到客户端或环境类的 if-else 里；把算法选择写成状态，则平白让各个算法互相耦合。
- 结构图相同而意图不同的模式还有好几组，例如代理与装饰、对象适配器与桥接。选模式看要解决的问题，个人喜好不能作为依据。对比详见 [06 模式选择、对比与联用](<06 模式选择、对比与联用.md>)。

### 三、模式应用场景描述题

针对下面每一个设计模式，以文字叙述的形式，分别给出一个适合其应用的情景描述。

1. 对象适配器模式　2. 命令模式　3. 原型方法模式

卷面在题目下给了解答示例，以"桥接模式"为例，只拍到开头半句"若针对'桥接模式'，一个简单的情景描述可以是：'某手写……程序中……"，其余被截掉。

（原卷无答案，以下为整理补充。情景描述要说清楚"有什么现成的东西、要解决什么问题、为什么这个模式合适"，不需要代码。）

**1. 对象适配器模式。** 某系统所有模块都通过自己定义的日志接口 Logger 的 `log(level, message)` 方法写日志，调用点有几百处。现在要改用一个第三方日志库，它的日志类只提供 `write(String text)`，并且有写文件、写控制台、写远程服务器三个子类。第三方库的源码不能改，业务代码也不想动。可以写一个适配器类实现 Logger 接口，内部持有第三方日志类的引用，在 `log()` 里把级别拼进消息再调用 `write()`。适配器持有的是引用，同一个适配器可以适配第三方日志类的所有子类，运行时换哪一个都行。

**2. 命令模式。** 某智能家居 App 的主界面有若干可自定义的按键，每个按键可以绑定"开灯""空调调到 26 度""拉上窗帘"等操作，还要求能撤销上一步操作，并提供"离家模式"一键执行多项操作。按键本身不应该知道自己控制的是哪种电器。可以把每项操作封装成一个命令对象，命令持有对应的电器（接收者）；按键只保存命令并调用 `execute()`；执行过的命令压入栈中，撤销时弹出并调用 `undo()`；"离家模式"是包含多条命令的宏命令。以后新增电器或操作，只需要增加命令类。

**3. 原型方法模式（原型模式）。** 某塔防游戏每一关要刷出成百上千个小怪。同一种小怪的模型、贴图、技能配置都一样，只有出生位置和血量加成不同，而每创建一个小怪都要读配置文件、加载模型资源，开销很大。可以为每种小怪预先创建一个原型对象，放进原型管理器；刷怪时从管理器里按种类取出原型克隆一份，再修改位置和血量。模型、贴图这类只读资源可以在副本之间共享（浅克隆），各自独立变化的属性（如技能冷却）要深克隆。新增一种小怪只要登记一个新原型，刷怪代码不用改。
