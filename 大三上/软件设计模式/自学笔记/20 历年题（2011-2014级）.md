### 一、单选题

**1.** 类设计中，"变化是绝对的，稳定是相对的"，下列哪个不属于这句话中"变化"的范畴？

A. 改变函数参数的类型　B. 增加新的数据成员　C. 改变编程语言　D. 改变对象交互的过程和顺序

答案：C。类设计里的变化指接口、数据表示、交互过程这些，换编程语言不在其中。

**2.** Open-Close 原则的含义是一个软件实体：

A. 应当对扩展开放，对修改关闭　B. 应当对修改开放，对扩展关闭　C. 应当对继承开放，对修改关闭　D. 以上都不对

答案：A。

**3.** 下列关于继承表述**错误**的是：

- A. 继承是一种通过扩展一个已有类的实现，从而获得新功能的复用方法
- B. 泛化类（超类）可以显式地捕获那些公共的属性和方法。特殊类（子类）则通过附加属性和方法来进行实现的扩展
- C. 破坏了封装性，因为这会将父类的实现细节暴露给子类
- D. 继承本质上是"白盒复用"，对父类的修改，不会影响到子类

答案：D。子类依赖父类的实现，父类一改子类往往跟着受影响。

**4.** 在面向对象设计时，应优先使用哪种方式实现既有代码的复用：

A. 组合或聚合　B. 公有继承　C. 保护或私有继承　D. 拷贝、粘贴再修改

答案：A。合成复用原则。

**5.** 下列关于设计模式的说法，**错误**的是：

- A. 设计模式都是开闭基本原则的宏观运用，本质上是没有任何模式的
- B. 设计时可以应用已有的设计模式，也可以应用自己发现的新模式
- C. 应用设计模式时，要考虑应用的具体特点，因为不存在万能的设计模式
- D. 应用设计模式，既可以增强系统的扩展性和灵活性，又可以减少最终的代码量

答案：D。模式一般会引入额外的抽象层，代码量通常是增加的。

**6.** 在继承关系中，方法应向（　）集中，数据应向（　）集中。

A. 父类，子类　B. 子类，父类　C. 子类，子类　D. 父类，父类

答案：A。公共方法上移便于复用和多态调用，数据下移让父类保持抽象。

**7.** 下列关于对象组合/聚合，说法**错误**的是：

- A. 容器类能通过被包含对象的接口来对其进行访问
- B. 属于黑盒复用，封装性好，因为被包含对象的内部细节对外是不可见
- C. 可以在运行时将被包含对象改变成同类型对象，从而改变容器类的行为效果，但没有改变容器类的接口
- D. 比继承关系更加灵活，代价是相比继承关系，增强了类间的耦合度

答案：D。组合比继承灵活，耦合也更低。

**8.** 下面关于工厂方法模式的说法**错误**的是（扫描版题干作"工厂模式"）：

- A. 工厂方法模式可用于分离产品的使用与创建过程
- B. 产品必须有一个唯一的公共基类
- C. 工厂可以是抽象类，也可以是具体类
- D. 简单工厂模式是退化的工厂模式，它要求产品种类稳定

答案：B（扫描版卷面勾的是 D）。D 本身成立：简单工厂是工厂方法的退化形式，加产品要改工厂类，只适合产品种类稳定的场合。B 说得太绝对，产品只要符合工厂方法声明的抽象返回类型即可。

**9.** 孙小美每天都要画好妆再出门，洗脸、打粉底、描眉、上眼影、画眼线、刷睫毛、打腮红、上唇彩，虽然每天都是这个流程，但总有所变化，如昨天"樱桃小口"，今天"性感美女"，明天"卧蚕眉、丹凤眼"，后天"芭比娃娃"了。下面哪种说法是**不恰当**的？

- A. 将"樱桃小口"、"芭比娃娃"等作为具体策略，从而使用策略模式比较合适
- B. 化妆的基本步骤是稳定的，但每个子步骤是易变的
- C. "芭比娃娃"表明变化会同时存在于多个子步骤中
- D. 直接使用模版方法模式可能不合适，因为子步骤的多种组合会造成子类数量激增

答案：A。整套妆容做成一个策略，每个具体策略都要把八个步骤重写一遍，只换一两个步骤也得新建一整套。流程固定、变化分散在子步骤里，应该给易变的子步骤分别配策略再组合。

**10.** "兄弟俩要到操场上玩，临走时，跟妈妈说：'我俩玩去了，饭好了，招呼我们'"。这段话所描述的场景最适合下列哪种模式的应用场景？

A. 访问者模式　B. 中介者模式　C. 策略模式　D. 观察者模式

答案：D。兄弟俩先"订阅"，饭好了（妈妈这个目标的状态变了）就通知他们。

#### 1. 简化版的数值计算程序库

开发了一个用于数值计算的大型程序库，它的功能是强大的，但需要使用者具备较高的数学专业知识。为方便"菜鸟"级用户的使用，需要提供一个简化版的，但同时又不希望影响专业人员的使用。使用哪种设计模式较好？如何设计？

答案：**外观模式**。

- 原程序库的各个类原样保留，作为子系统。
- 新增一个外观类，把菜鸟常用的功能包装成少数几个参数简单的函数，函数内部替用户完成选算法、设精度、组合调用多个库类这些步骤。
- 外观类只是多出来的一个入口，专业人员照旧直接调用库里的类，不受影响。这正是 GoF 说的"外观不阻止用户直接访问子系统"。

```cpp
class SimpleMath {                       // 外观，下面的子系统类名是示意
public:
    double Integrate(double (*f)(double), double a, double b) {
        IntegralSolver solver;           // 专业接口：要自己选方法、定精度
        solver.SetMethod(IntegralSolver::SIMPSON);
        solver.SetPrecision(1e-6);
        return solver.Solve(f, a, b);
    }
    Matrix Inverse(const Matrix& m) {
        LUDecomposer lu(m);              // 菜鸟不用知道要先做 LU 分解
        return lu.Inverse();
    }
};
```

#### 2. 2D 游戏地图的图块

在 2D 游戏的开发中，需要绘制地图，地图是由大量的"一样的图块"拼接而成，而"图块"的种类有限，目前有草地、海洋、沙漠、山地等，未来肯定要增加种类，但不会太多太频繁。采用何种模式设计"图块"类比较好？如何设计？

答案：扫描版卷面和文件B 都写"原型模式/享元模式"。按题意（图块数量多、种类少）首选**享元模式**：

- 图块的种类、贴图、能否通行等是内部状态，同一种图块全地图只存一个对象；
- 图块在地图上的坐标是外部状态，绘制时作为参数传进去；
- 享元工厂用一张表缓存各种图块，要某种图块时先查表，没有才创建；
- 增加新种类只加一个具体图块类，并在工厂里登记（登记可以用配置表加原型克隆，避免在工厂里写 if-else）。

原型模式的思路是每种图块放一个原型，拼地图时逐格克隆。它解决的是"新增种类不改创建代码"，但每一格还是一个对象，省不了内存，所以两者可以配合：原型负责登记和创建种类，享元负责共享。

```cpp
class Tile {                                     // 抽象享元
public:
    virtual ~Tile() {}
    virtual void Draw(int x, int y) const = 0;   // 坐标是外部状态
};

class GrassTile : public Tile {                  // 具体享元，内部状态是草地贴图
public:
    void Draw(int x, int y) const { /* 在 (x, y) 处画草地贴图 */ }
};

class TileFactory {                              // 享元工厂
public:
    Tile* GetTile(const string& kind) {
        map<string, Tile*>::iterator it = pool.find(kind);
        if (it != pool.end()) return it->second; // 已有就共享
        Tile* t = Create(kind);
        pool[kind] = t;
        return t;
    }
private:
    Tile* Create(const string& kind);            // 按登记表创建或克隆原型
    map<string, Tile*> pool;
};
```

#### 3. 使用第三方电子签名软件

在开发一个办公自动化系统时，项目组在 ElectricSignature 类集中实现了电子签名的功能。但在使用中发现该类不能完全满足用户需求，由于财力和人员的限制，决定直接购买第三方电子签名软件，其中的 FZ_ESignet 类功能与 ElectricSignature 的功能一样，但是两个类中的函数名都是不一样的，而且购买的只是二进制代码，没有源代码。现希望使用第三方软件的功能，但又不希望修改 ElectricSignature 的接口。使用哪种设计模式改进较好？如何改进？

答案：**适配器模式**。ElectricSignature 是目标，FZ_ESignet 是适配者，新写一个适配器类继承 ElectricSignature，内部持有 FZ_ESignet 对象，在重写的函数里转调第三方的同功能函数。系统里原来使用 ElectricSignature 的代码不用改，第三方的二进制代码也不用改。

```cpp
class ESignetAdapter : public ElectricSignature {    // 适配器
public:
    ESignetAdapter() : adaptee(new FZ_ESignet) {}
    ~ESignetAdapter() { delete adaptee; }
    bool Sign(const string& doc)   { return adaptee->fz_sign(doc.c_str()); }   // 函数名是示意
    bool Verify(const string& doc) { return adaptee->fz_check(doc.c_str()); }
private:
    FZ_ESignet* adaptee;                              // 对象适配器：关联适配者
};

ElectricSignature* sig = new ESignetAdapter;          // 客户端仍按原接口使用
sig->Sign("contract");
```

要点：ElectricSignature 的这几个函数必须是虚函数，适配器才能覆盖；C++ 也可以写成类适配器 `class ESignetAdapter : public ElectricSignature, private FZ_ESignet`。

#### 4. 减少 MyFunc 中的 case

Example 类的成员函数的实现如下，CheckCondition 为虚函数，由于子类可能增加新的返回数值，所以未来可能会需要在 MyFunc 中增加其它 case 项。请问要改进 MyFunc 的实现，避免未来修改 Example 类，采用哪种模式为好？如何改进设计？

```cpp
void Example::MyFunc( ) {
     switch( CheckCondition( ) ) {
          /* 6个case语句块，略 */
          default: break;
     }
};
```

答案：扫描版卷面和文件B 都写"策略模式/状态模式"。做法是把"返回一个数值再 switch"改成"返回一个对象再多态调用"：

- 每个 case 块搬进一个类，这些类实现同一个接口 Condition 的 `Handle()`；
- CheckCondition 不再返回整数，而是返回对应的 Condition 对象；
- MyFunc 里只剩一行 `CheckCondition()->Handle(*this)`；
- 子类要加新的返回值时，新写一个 Condition 子类，在自己重写的 CheckCondition 里返回它，Example 不用改。

```cpp
class Example;

class Condition {                              // 抽象策略（或抽象状态）
public:
    virtual ~Condition() {}
    virtual void Handle(Example& ex) = 0;      // 原来某个 case 块里的代码
};

class ConditionA : public Condition {
public:
    void Handle(Example&) { /* 原 case 1 的处理 */ }
};

class Example {
public:
    virtual ~Example() {}
    void MyFunc() {                            // 不再有 switch
        Condition* c = CheckCondition();
        if (c != 0) c->Handle(*this);
        delete c;
    }
protected:
    virtual Condition* CheckCondition() { return new ConditionA; }
};

class ConditionNew : public Condition {        // 子类新增的"返回值"
public:
    void Handle(Example&) { /* 新增的处理 */ }
};

class SubExample : public Example {
protected:
    Condition* CheckCondition() { return new ConditionNew; }
};
```

条件取决于对象内部状态、并且会在运行中切换时，就把 Condition 看作状态；条件只是在几种算法中选一种，就看作策略。两者结构一样。

#### 5. 以一致的方式访问各种图书

某书店需要开发一套图书购销存软件。在设计图书类时发现：图书有单行本和成套的，又细分成教辅材料、科学知识、文学著作等。设计时，希望能够以一致的方式访问各种图书，不论是单本的、成套的、IT 类的或古典名著。使用哪种设计模式较好？如何设计？

答案：**组合模式**（扫描版卷面写的是它的另一个译名"合成模式"）。

- 抽象构件 Book 声明所有图书共有的操作，如 `GetPrice()`、`GetName()`，以及管理子节点的 `Add()`、`Remove()`；
- 叶子 SingleBook 是单行本，教辅、科学、文学等类别可以作为它的子类（或作为一个类别属性）；
- 容器 BookSet 是成套书，里面放若干 Book，可以是单本也可以是更小的套装，`GetPrice()` 递归累加；
- 购销存模块只针对 Book 编程，单本和成套一样处理。


| --- | --- | --- |
| 抽象构件 | Book | 统一的图书接口 |

| 容器构件 | BookSet | 成套书，保存子节点，操作时递归处理 |

### 三、用单件模式重新实现 LogManager 类（10 分）

```cpp
class LogManager
{
public:
    LogManager ( ) { ... }
    ~ LogManager ( ) { ... }
    void WriteLog(String ip, String msgType, String msgStr)
        { ... }
    void ImportLog( )  {  …  }  //导入日志
    void ExportLog( )  {  …  }  //导出日志
};
```

答案：三处改动。构造函数（连同析构、拷贝构造、赋值）改成私有，外面就不能随便创建；类里保存唯一的实例；提供一个公有静态函数返回这个实例。

```cpp
class LogManager
{
public:
    static LogManager& Instance() {
        static LogManager instance;     // 第一次调用时才构造，C++11 起保证线程安全
        return instance;
    }
    void WriteLog(String ip, String msgType, String msgStr) { ... }
    void ImportLog() { ... }            // 导入日志
    void ExportLog() { ... }            // 导出日志
private:
    LogManager() { ... }
    ~LogManager() { ... }
    LogManager(const LogManager&);            // 只声明不实现，禁止拷贝
    LogManager& operator=(const LogManager&);
};

// 使用：LogManager::Instance().WriteLog(ip, type, msg);
```

也可以写成教材上的指针版：类里放 `static LogManager* instance;`，`GetInstance()` 里判断为空才 `new`，类外写 `LogManager* LogManager::instance = 0;`。多线程下指针版要加锁（双重检查），文件B p407 给的 Java 版就是双重检查锁定，Java 里要给 instance 加 `volatile`（文件B 的代码漏了）。

### 四、加热器控制软件（30 分，每题 5 分）

某个电器厂商要为加热器产品开发控制软件，由于有多种加热器产品，厂家希望该软件能适用各种加热器产品，并适应未来多种变化需要。基本代码见表 A。

```cpp
// 表A
class Heater {
public:
    Heater(int pw) : maxPower (pw) {}
    virtual ~Heater() { }
    void     SetDestTemperature(int t) { destTemperature  =  t;}
    virtual bool CheckSelf( )     {  /* 自检 */  }
    virtual void QuickHeat( )     { /* 以最大功率加热到目标温度 */ }
    virtual void EconomicHeat( )  { /* 以节能的方式加热到目标温度 */ }
private:
    int maxPower;           //最大功率
    int destTemperature;    //目标温度
};
```

1. 考察 CheckSelf 函数，由于不同产品的自检过程是有着很大差异的，难以给出一致的自检过程。方案 A：需要新的自检过程时，从 Heater 类派生子类，并 override 基类的 CheckSelf。请问采用方案 A，会有怎样的顾虑或不足？
2. 请给出你的设计方案，解决 1 中的问题。
3. 考虑到系列化加热器产品的必然性，某些新产品的 CheckSelf 过程，只需要在已有产品的 CheckSelf 过程上，再增加一些自检行为即可。请在 2 的基础上，应用装饰模式，给出设计方案。

**1. 方案 A 的不足**（扫描版卷面批注只写了"继承的不足"）

- 自检只是加热器的一个方面，EconomicHeat 等也在变。每种变化都靠派生子类，几个维度一组合，子类数量成倍增长（类爆炸）。
- 两个产品的自检过程有相同部分时，只能在子类里复制代码，或者再搭一层继承。
- 继承是静态的，运行时不能给某台加热器换自检过程。
- 为了改一个自检过程而派生整个 Heater，加热器的其他职责也被牵连，违反单一职责和合成复用原则。

**2. 设计方案**：把自检过程从 Heater 中分离出来，定义抽象类 SelfCheck，每种自检过程一个子类。Heater 持有一个 SelfCheck 指针，`CheckSelf()` 委托给它。新的自检过程只加 SelfCheck 子类，Heater 不用派生。本质是策略模式。

**3. 装饰模式**：在 SelfCheck 体系里加一个抽象装饰类 CheckDecorator，它继承 SelfCheck，又持有一个 SelfCheck（被装饰的已有自检过程）。具体装饰类（如 LeakageCheck）先调用被装饰对象的 `Check()`，再做自己追加的检查。新产品的自检写成 `new LeakageCheck(new BasicCheck)`，还可以一层层叠加。

**4. 策略模式**：定义抽象策略 EconomicMode，声明 `Heat(imp, dest)`；每种预设的节能方式（半功率加热、低谷电价时段加热等）一个具体策略。Heater 持有 EconomicMode 指针，提供 `SetEconomicMode()` 让用户选择，`EconomicHeat()` 委托给当前策略。

**5. 桥接模式**：加热器有两个独立变化的维度。

- 抽象部分：面向用户的功能（卖点）。Heater 是抽象类，定时加热等新卖点做成扩充抽象类 TimerHeater，新增 `TimerHeat()`。
- 实现部分：不同型号产品的底层操作。HeaterImp 是实现类接口，声明设定功率、读取温度等基本操作，每个型号一个具体实现类。
- Heater 持有 HeaterImp 指针（桥），卖点功能都用 HeaterImp 的基本操作实现。加卖点只动左边，加型号只动右边。

（文件B 的桥接部分把 TimerHeat 做成实现类，并让 QuickHeat 和 EconomicHeat 都去调用它，定时加热反而替换掉了快速加热和节能加热，这里没有沿用。）

```cpp
#include <iostream>
using namespace std;

// ---------- 实现部分（桥接）：各型号的底层操作 ----------
class HeaterImp {
public:
    virtual ~HeaterImp() {}
    virtual int  MaxPower() const = 0;
    virtual void SetPower(int watt) = 0;        // 0 表示停止加热
    virtual int  ReadTemperature() = 0;
};

class ModelA : public HeaterImp {
public:
    ModelA() : temp(15) {}
    int  MaxPower() const { return 2000; }
    void SetPower(int watt) { if (watt > 0) temp += watt / 400; }   // 模拟升温
    int  ReadTemperature() { return temp; }
private:
    int temp;
};

// ---------- 自检：策略 + 装饰 ----------
class SelfCheck {
public:
    virtual ~SelfCheck() {}
    virtual bool Check(HeaterImp& imp) = 0;
};

class BasicCheck : public SelfCheck {
public:
    bool Check(HeaterImp& imp) { cout << "基本自检" << endl; return imp.MaxPower() > 0; }
};

class CheckDecorator : public SelfCheck {
public:
    CheckDecorator(SelfCheck* c) : inner(c) {}
    ~CheckDecorator() { delete inner; }
    bool Check(HeaterImp& imp) { return inner->Check(imp); }
protected:
    SelfCheck* inner;                           // 被装饰的已有自检过程
};

class LeakageCheck : public CheckDecorator {
public:
    LeakageCheck(SelfCheck* c) : CheckDecorator(c) {}
    bool Check(HeaterImp& imp) {
        if (!CheckDecorator::Check(imp)) return false;
        cout << "追加：漏电检测" << endl;        // 新增的自检行为
        return true;
    }
};

// ---------- 节能加热：策略 ----------
class EconomicMode {
public:
    virtual ~EconomicMode() {}
    virtual void Heat(HeaterImp& imp, int dest) = 0;
};

class LowPowerMode : public EconomicMode {
public:
    void Heat(HeaterImp& imp, int dest) {
        cout << "半功率加热" << endl;
        while (imp.ReadTemperature() < dest) imp.SetPower(imp.MaxPower() / 2);
        imp.SetPower(0);
    }
};

class ValleyMode : public EconomicMode {
public:
    void Heat(HeaterImp& imp, int dest) {
        cout << "等到低谷电价时段再加热" << endl;
        while (imp.ReadTemperature() < dest) imp.SetPower(imp.MaxPower());
        imp.SetPower(0);
    }
};

// ---------- 抽象部分（桥接） ----------
class Heater {
public:
    Heater(HeaterImp* i, SelfCheck* c, EconomicMode* m)
        : imp(i), checker(c), mode(m), destTemperature(20) {}
    virtual ~Heater() { delete imp; delete checker; delete mode; }
    void SetDestTemperature(int t) { destTemperature = t; }
    void SetEconomicMode(EconomicMode* m) { delete mode; mode = m; }   // 用户选择节能方式
    bool CheckSelf() { return checker->Check(*imp); }
    void QuickHeat() {
        while (imp->ReadTemperature() < destTemperature) imp->SetPower(imp->MaxPower());
        imp->SetPower(0);
    }
    void EconomicHeat() { mode->Heat(*imp, destTemperature); }
protected:
    HeaterImp*    imp;
    SelfCheck*    checker;
    EconomicMode* mode;
    int           destTemperature;
};

class TimerHeater : public Heater {             // 扩充抽象：新卖点
public:
    TimerHeater(HeaterImp* i, SelfCheck* c, EconomicMode* m) : Heater(i, c, m) {}
    void TimerHeat(int minutes) {
        cout << minutes << " 分钟后开始加热" << endl;   // 实际产品由定时器触发
        EconomicHeat();
    }
};

int main() {
    TimerHeater heater(new ModelA, new LeakageCheck(new BasicCheck), new LowPowerMode);
    heater.SetDestTemperature(25);
    if (heater.CheckSelf()) {
        heater.QuickHeat();
        heater.SetDestTemperature(30);
        heater.SetEconomicMode(new ValleyMode);
        heater.TimerHeat(30);
    }
    return 0;
}
```

**1)** 输出哪句话同时取决于两个对象的实际类型：哪种动物、哪种水果。C++ 的虚函数只按调用者（`this`）一个对象的实际类型分派，`monkey->Eat(fruit)` 只能确定是猴子在吃，确定不了参数是什么水果，原代码只好用 `dynamic_cast` 做第二次判断。需要按两个对象的类型各分派一次，就是双派分（双重分派）。

**2)** 类定义：

```cpp
class Monkey : public Animal {
public:
    virtual void EatApple(Apple* apple)    { cout << "猴子吃苹果" << endl; }
    virtual void EatBanana(Banana* banana) { cout << "猴子吃香蕉" << endl; }
};

class Baboon : public Animal {
public:
    virtual void EatApple(Apple* apple)    { cout << "狒狒吃苹果" << endl; }
    virtual void EatBanana(Banana* banana) { cout << "狒狒吃香蕉" << endl; }
```

**3)** main 函数里把 `Eat` 换成对应的函数：

```cpp
monkey->EatApple(apple);
monkey->EatBanana(banana);
baboon->EatApple(apple);
baboon->EatBanana(banana);
```

**4)** 原题是 `Eat(fruit)` 一个接口，使用者不用关心手里是什么水果；改写后使用者必须自己知道水果的具体类型，再挑 `EatApple` 还是 `EatBanana`，手里只有一个 `Fruit*` 时根本调不了。从使用者角度看**原题的方式更友好**，接口统一、不暴露类型细节；缺点是原题实现里要靠 RTTI。第 5 问的访问者模式把两者的优点合起来。

**5)** 水果种类稳定，动物会增加，所以 Fruit 体系作为元素，Animal 体系作为访问者：

- Fruit 增加纯虚函数 `BeEaten(Animal*)`（相当于 Accept），Apple 在里面调用 `animal->EatApple(this)`，Banana 调用 `animal->EatBanana(this)`；
- Animal 保留统一接口 `Eat(Fruit*)`，实现为 `fruit->BeEaten(this)`；
- 调用 `monkey->Eat(banana)` 时，第一次分派由 `BeEaten` 的虚函数确定水果类型，第二次分派由 `EatBanana` 的虚函数确定动物类型，没有任何类型判断；

```cpp
    virtual ~Observer() {}
    virtual void Update() = 0;
```

#### 1. 复用已有的 power 类

有一个类（power）实现了数学中的幂次运算，方法中需要传入两个参数，一个是基数 base，另一个是幂次 exp。现在客户端需要一个求平方的函数接口（square），即传入一个数，得到它的平方值。请选择适当的设计模式来设计类，以实现对已经存在的类 power 的复用。

答案：**适配器模式**（文件B p378）。square 是客户要的目标接口，power 是已有的适配者，适配器实现 square，内部调用 power 并把 exp 固定为 2。

```mermaid
classDiagram
    class Square {
        <<interface>>
        +square(double x) double
    }
    class Power {
        +power(double base, double exp) double
    }
    class SquareAdapter {
        -adaptee Power
        +square(double x) double
    }
    Square <|.. SquareAdapter
    SquareAdapter --> Power : 适配者
    Client ..> Square
```

```java
class Power {                                   // 适配者：已经存在的类
    public double power(double base, double exp) { return Math.pow(base, exp); }
}

interface Square {                              // 目标接口
    double square(double x);
}

class SquareAdapter implements Square {         // 对象适配器
    private final Power adaptee;
    public SquareAdapter(Power adaptee) { this.adaptee = adaptee; }
    public double square(double x) { return adaptee.power(x, 2); }
}

public class Client {
    public static void main(String[] args) {
        Square s = new SquareAdapter(new Power());
        System.out.println(s.square(5));        // 25.0
    }
}
```

也可以写成类适配器：`class SquareAdapter extends Power implements Square`，`square()` 里直接调 `power(x, 2)`。文件B 的版本没有定义目标接口，客户端直接依赖 SquareAdapter 类，加上接口后客户端只认 Square。

#### 2. 高温预警系统

在各种预警系统中，当目标对象发生改变的时候，会自动通知相关的其他对象。例如，银行里的防盗系统、高档小区内的监控系统一般都是和公安系统相连的，当防盗系统发生变化（被破坏或者其他异常情况）时，公安系统会马上收到"异常通知"，然后及时地做出相应处理。下面是高温预警系统的结构图。气象部门根据气象卫星获得相关的天气温度信息，当温度超过某一阈值时，向各个单位和个人发出高温警报通知，以及时做好高温防护措施。

原卷结构图是一张流程图：开始，读取温度，判断"温度 ≥ 阈值"，是则分别通知政府、单位、个人，结束。

要求：1）请给出所采用的设计模式并画出相应的类图；2）写出代码框架。

答案：**观察者模式**（文件B p379-382）。气象部门是观察目标，政府、单位、个人是观察者，温度达到阈值时气象部门通知所有登记过的观察者。

```java
interface WarningListener {                          // 抽象观察者
    void onWarning(int temperature, String level);
}

abstract class WeatherSubject {                      // 抽象目标
    private final List<WarningListener> listeners = new ArrayList<>();
    public void attach(WarningListener l) { listeners.add(l); }
    public void detach(WarningListener l) { listeners.remove(l); }
    protected void notifyListeners(int t, String level) {
        for (WarningListener l : listeners) l.onWarning(t, level);
    }
}

class WeatherBureau extends WeatherSubject {         // 具体目标：气象部门
    private final int threshold;
    public WeatherBureau(int threshold) { this.threshold = threshold; }
    public void setTemperature(int t) {              // 卫星数据到达
        if (t >= threshold) notifyListeners(t, level(t));
    }
    private String level(int t) {                    // 分级是示意
        if (t >= 40) return "红色";
        if (t >= 37) return "橙色";
        return "黄色";
    }
}

class Government implements WarningListener {        // 具体观察者
    public void onWarning(int t, String level) {
        System.out.println("政府收到" + level + "高温预警，气温 " + t + " 度，启动应急预案");
    }
}
// Company、Person 写法相同

public class Client {
    public static void main(String[] args) {
        WeatherBureau bureau = new WeatherBureau(35);
        bureau.attach(new Government());
        bureau.attach(new Company());
        bureau.attach(new Person());
        bureau.setTemperature(33);                   // 未到阈值，不通知
        bureau.setTemperature(38);                   // 三方都收到橙色预警
    }
}
```

#### 3. 调色板程序

请选择适当的设计模式来设计一个调色板程序，要求当用户单击调色板上的任意一个方块时，调色板程序将返回一个对应的颜色的实例。

答案：文件B p383-385 用**工厂方法模式**：Color 是抽象产品，RedColor、GreenColor 等是具体产品，每种颜色一个具体工厂。

文件B 的调色板类在 `getColorFactory(x, y)` 里用 if-else 按坐标挑工厂，又把硬编码带回来了，加一种颜色就得改调色板。更好的做法是让每个方块在创建时就关联自己的工厂，单击时直接调这个方块的工厂：

```java
interface Color { String name(); }
class Red implements Color { public String name() { return "Red"; } }
class Green implements Color { public String name() { return "Green"; } }

interface ColorFactory { Color createColor(); }      // 抽象工厂
class RedFactory implements ColorFactory { public Color createColor() { return new Red(); } }
class GreenFactory implements ColorFactory { public Color createColor() { return new Green(); } }

class ColorBlock {                                   // 调色板上的一个方块
    private final ColorFactory factory;
    ColorBlock(ColorFactory factory) { this.factory = factory; }
    Color onClick() { return factory.createColor(); }
}

class Palette {
    private final List<ColorBlock> blocks = new ArrayList<>();
    void addBlock(ColorFactory f) { blocks.add(new ColorBlock(f)); }   // 可按配置文件添加
    Color click(int index) { return blocks.get(index).onClick(); }
}
```

这道题没有标准答案，题意理解不同，选的模式也不同：

- 同一种颜色每次都返回同一个对象（颜色本身不可变）：用**享元**，调色板维护一个颜色池；
- 每次返回一个新颜色，用户拿去还要单独调整：用**原型**，每个方块登记一个颜色原型，单击时返回它的克隆；
- 只强调"单击不同方块得到不同颜色类的实例、以后还会加颜色"：用上面的工厂方法。

考场上选一种，把理由说清楚即可。

#### 4. 网络聊天室

网络聊天室很多人都知道。在一个聊天室中，一个人发送的信息可以被多个人接收，大家在一个聊天室中进行信息交流。它是如何实现的呢？在点对点的通信方式中，每个人既作为服务器也作为客户端，发送信息和接收信息。这时每个人在通信中的位置都是一样的，直接与被通信人进行联系。但是当人数不断增多的时候，一个人与其他人之间的关系就会变得相当复杂，将是多个对象之间一对多的复杂的相互依赖关系。这样的软件体系结构，在设计上也是相当的复杂，不易实现。

问：如果你来设计实现该聊天系统，采用怎样的设计来解决上述问题。要求：1）画出用特定模式求解该问题所对应的类图。2）给出代码框架。

答案：**中介者模式**（文件B p386-387）。聊天服务器（聊天室）是中介者，每个用户是同事对象。用户之间不再互相引用，发消息时交给聊天室，由聊天室转发给其他成员，网状的多对多关系变成了以聊天室为中心的一对多。

```mermaid
classDiagram
    class ChatRoom {
        <<abstract>>
        +register(User u)* void
        +relay(User from, String msg)* void
    }
    class ChatServer {
        -users List~User~
        +register(User u) void
        +relay(User from, String msg) void
    }
    class User {
        <<abstract>>
        #room ChatRoom
        +send(String msg) void
        +receive(String msg)* void
    }
    ChatRoom <|-- ChatServer
    User <|-- Member
    User --> ChatRoom : room
    ChatServer o-- User : users
```

```java
abstract class ChatRoom {                             // 抽象中介者
    public abstract void register(User user);
    public abstract void relay(User from, String msg);
}

class ChatServer extends ChatRoom {                   // 具体中介者
    private final List<User> users = new ArrayList<>();
    public void register(User user) {
        if (!users.contains(user)) users.add(user);
    }
    public void relay(User from, String msg) {
        for (User u : users) {
            if (u != from) u.receive(from.getName() + "：" + msg);
        }
    }
}

abstract class User {                                 // 抽象同事
    protected final ChatRoom room;
    private final String name;
    protected User(String name, ChatRoom room) {
        this.name = name;
        this.room = room;
        room.register(this);
    }
    public String getName() { return name; }
    public void send(String msg) { room.relay(this, msg); }   // 只和中介者打交道
    public abstract void receive(String msg);
}

class Member extends User {                           // 具体同事
    public Member(String name, ChatRoom room) { super(name, room); }
    public void receive(String msg) { System.out.println(getName() + " 收到 " + msg); }
}

public class Client {
    public static void main(String[] args) {
        ChatRoom room = new ChatServer();
        User a = new Member("A", room);
        User b = new Member("B", room);
        User c = new Member("C", room);
        a.send("今晚一起看电影吗？");                   // B、C 收到
    }
}
```

以后要加私聊、屏蔽某人、敏感词过滤，都只改聊天室这个中介者，用户类不用动。

原卷无答案。文件B p388 记了学长的看法：(1) 组合 + 抽象工厂；(2) 状态 + 桥接；(3) 装饰。后面附的 GPT 代码和这些看法对不上，第 3 问的代码还有错，下面按学长的思路重新整理，第 1 问做了调整。

**1. 原型 + 建造者，楼层和房间用组合组织**

- 抽象工厂的产品等级结构是固定的，每加一种房间就要在抽象工厂接口里加一个创建方法，所有具体工厂都得改，不满足"房间种类可能增加"。所以房间的创建改用**原型模式**：每种房间登记一个原型，按种类名克隆，新种类只要新写一个房间类并登记。
- 楼层布局用**建造者模式**的思路：布局写成数据（比如配置文件里每行一个"种类名、坐标"），FloorBuilder 按布局逐个克隆房间、放到指定位置。新布局只是一份新数据，创建楼层的代码不变。
- 楼层包含房间，套房里还可以再含小房间，这部分结构就是学长说的**组合模式**。

```java
class LinenRoom extends Room { }                       // 布草间，其余种类同理

    public Room create(String kind) { return prototypes.get(kind).clone(); }
}

    public List<Room> getRooms() { return rooms; }
```

**3. 装饰模式**

折扣可以叠加（折上折），又可能独立生效，每种组合写一个子类会爆炸。把每种优惠做成一个装饰类，结算时按客人的情况一层层包起来，价格从最里层的基准价开始逐层计算。

```java
interface Price {                                      // 抽象构件
    double get();
}

class RoomPrice implements Price {                     // 具体构件：客房基准价
    private final double base;
    public RoomPrice(double base) { this.base = base; }
    public double get() { return base; }
}

abstract class Discount implements Price {             // 抽象装饰
    protected final Price inner;
    protected Discount(Price inner) { this.inner = inner; }
}

class RateDiscount extends Discount {                  // 打折：金卡 0.8、银卡 0.9、淡季 0.9
    private final double rate;
    public RateDiscount(Price inner, double rate) { super(inner); this.rate = rate; }
    public double get() { return inner.get() * rate; }
}

class StaffDiscount extends Discount {                 // 内部员工：折上再减 50 元
    public StaffDiscount(Price inner) { super(inner); }
    public double get() { return Math.max(0, inner.get() - 50); }
}

class MeetingPrice extends Discount {                  // 会议优惠：独立优惠，固定 120 元
    public MeetingPrice(Price inner) { super(inner); }
    public double get() { return 120; }
}

public class Client {
    public static void main(String[] args) {
        Price standard = new RoomPrice(300);
        Price gold = new RateDiscount(standard, 0.8);            // 240
        Price goldOffSeason = new RateDiscount(gold, 0.9);       // 216
        Price staff = new StaffDiscount(goldOffSeason);          // 166
        Price meeting = new MeetingPrice(standard);              // 120
        System.out.println(staff.get() + " " + meeting.get());
    }
}
```

#### 1. 电子账单系统的广告信

银行信用卡中心的电子账单系统包括了发送器、账单、广告信和发送队列等对象，其中广告信的业务逻辑是：先到数据库中把客户信息一个一个的取出，每个客户都生成一份个性化的邮件，然后交给发送机进行发送处理。请问使用哪种模式设计广告信较好？请画出 UML 设计类图。

答案：**原型模式**（文件B p362-365）。

- 每封广告信的标题、正文完全一样，只有收件人、称呼等少数字段因人而异。先做好一封原型邮件，每取出一个客户就克隆一封，改掉个性化字段后交给发送机。

#### 2. 图形界面组件库

软件公司要开发一个图形界面组件库，界面组件分为两大类，一类是单元控件，例如按钮、文本框等，一类是容器控件，例如对话框、表单等，请问采用何种模式设计比较好？请画出 UML 设计类图。

答案：**组合模式**（文件B p366 只写了模式名）。单元控件是叶子，容器控件是容器，容器里可以放单元控件，也可以再放容器（表单里嵌分组框）。客户端对所有组件统一调用 `display()` 等方法，容器的方法递归调用子组件。


| 角色 | 本例中的类 | 职责 |
| --- | --- | --- |
| 抽象构件 | Component | 所有控件的公共接口 |
| 叶子构件 | Button、TextBox | 单元控件，不能再包含子控件 |
| 容器构件 | Container 及 Dialog、Form | 保存子控件，`display()` 先画自己再逐个画子控件 |

```java
abstract class Component {
    public abstract void display();
    public void add(Component c) { throw new UnsupportedOperationException(); }   // 叶子默认不支持
    public void remove(Component c) { throw new UnsupportedOperationException(); }
}

class Button extends Component {
    public void display() { System.out.println("按钮"); }
}

abstract class Container extends Component {
    private final List<Component> children = new ArrayList<>();
    @Override public void add(Component c) { children.add(c); }
    @Override public void remove(Component c) { children.remove(c); }
    public void display() {
        drawFrame();
        for (Component c : children) c.display();       // 递归
    }
    protected abstract void drawFrame();
}

class Dialog extends Container {
    protected void drawFrame() { System.out.println("对话框"); }
}
```

这里把 `add()` 放在抽象构件里，是透明组合模式；只放在 Container 里就是安全组合模式，客户端要区分叶子和容器。

### 三、程序设计题（10 分）

客户请小王编写一个从键盘读入字符并输出到打印机的程序。小王使用结构化的设计方法，编写了如下代码。该程序包含 3 个子程序，Copy 子程序从 ReadKeyboard 子程序中获取字符，并把字符传递给 WritePrinter 子程序。几个月后，客户说有时希望 Copy 程序能从纸带读入机中读入字符。并且，在未来可能还会从其它种类的输入设备中读入字符，也可能输出到其它种类的输出设备。小王希望他写出的代码既能满足上述要求，又不用每次都改写 Copy 的实现。

```cpp
void Copy( ) {
    int c;
    while ((c=ReadKeyboard( )) != EOF)   //EOF 为宏定义的终结字符
        WritePrinter(c);
}
```

（原卷 while 行末多了一个右括号，这里删掉了。）

1)（3 分）请你从面向对象设计原则的角度分析小王原来的设计存在什么问题？
2)（7 分）请你采用面向对象方法帮小王重新设计 Copy 函数，添加必要的类，使得新设计能够满足小王的愿望。简要说明你的设计思想，给出实现代码。

这道题也是作业 8 的分析题，文件B p81 有答案，详见 [32 分析题与重构练习](<32 分析题与重构练习.md>)。

**1)** 违反**依赖倒置原则**：Copy 是高层模块（复制的业务逻辑），却直接依赖键盘、打印机这两个低层模块的具体函数。结果也违反开闭原则：每加一种输入或输出设备，都得改 Copy，比如加个参数再写 if 判断。

**2)** 在 Copy 和设备之间加一层抽象：Reader 声明 `Read()`，Writer 声明 `Write()`，各种设备分别实现。Copy 只依赖这两个抽象类，由调用者传入具体设备对象。加纸带读入机只要新写一个 Reader 子类，Copy 不改。

```cpp
class Reader {                                  // 抽象输入设备
public:
    virtual ~Reader() {}
    virtual int Read() = 0;
};

class Writer {                                  // 抽象输出设备
public:
    virtual ~Writer() {}
    virtual void Write(int c) = 0;
};

class KeyboardReader : public Reader {
public:
    int Read() { return ReadKeyboard(); }
};

class PaperTapeReader : public Reader {         // 新需求：纸带读入机
public:
    int Read() { return ReadPaperTape(); }
};

class PrinterWriter : public Writer {
public:
    void Write(int c) { WritePrinter(c); }
};

void Copy(Reader& reader, Writer& writer) {     // 只依赖抽象
    int c;
    while ((c = reader.Read()) != EOF)
        writer.Write(c);
}
```

文件B 的思路：（1）把 Rule 抽象成策略，用策略模式，Machine 的方法名称和参数保持不变；（2）桥接。整理时的看法如下，代码编译运行过。

**（1）适配器 + 策略。** 让 Machine 只依赖一个抽象规则接口 Rule，对外只有一个 `Apply(Rule&)`，这是策略的部分。但各规则类来源杂、没有公共基类，有的还改不了源码，不能直接让它们继承 Rule，所以每个规则配一个适配器，把各自的接口转换成 Rule 的接口。加 Rule04 时只加 Rule04Adapter，Machine 不变。

```cpp
class Machine;

class Rule {                                     // 抽象规则（策略 / 适配器的目标）
public:
    virtual ~Rule() {}
    virtual bool ApplyTo(Machine& m) = 0;
};

class Rule01Adapter : public Rule {              // 适配器：Rule01 的接口是 Infer01()（示意）
public:
    Rule01Adapter(Rule01& r) : rule(r) {}
    bool ApplyTo(Machine&) { return rule.Infer01(); }
private:
    Rule01& rule;
};

class Rule02Adapter : public Rule {              // Rule02 来自第三方，接口不同
public:
    Rule02Adapter(Rule02& r) : rule(r) {}
    bool ApplyTo(Machine&) { return rule.DoRule(0); }
private:
    Rule02& rule;
};

class Machine {
public:
    bool Apply(Rule& rule) { return rule.ApplyTo(*this); }   // 稳定的应用接口
};
```

**（2）访问者模式。** 规则种类固定、自动机的功能（Apply、Check……）不断增加，正好是访问者的适用条件：元素稳定，操作常变。每种功能做成一个访问者，针对三种规则各有一个 `Visit` 重载；Machine 只提供一组固定的入口，把规则交给指定的功能处理。加 Check 功能只加一个 CheckOperation 类，Machine 不变。

```cpp
class RuleOperation {                            // 抽象访问者：自动机的一项功能
public:
    virtual ~RuleOperation() {}
    virtual bool Visit(Rule01& r) = 0;
    virtual bool Visit(Rule02& r) = 0;
    virtual bool Visit(Rule03& r) = 0;
};

class ApplyOperation : public RuleOperation {    // 原来的 Apply 功能
public:
    bool Visit(Rule01& r) { return r.Infer01(); }
    bool Visit(Rule02& r) { return r.DoRule(0); }
    bool Visit(Rule03& r) { return r.Infer03(); }
};

class CheckOperation : public RuleOperation {    // 新增的 Check 功能
public:
    bool Visit(Rule01&) { /* 检查 Rule01 */ return true; }
    bool Visit(Rule02&) { /* 检查 Rule02 */ return true; }
    bool Visit(Rule03&) { /* 检查 Rule03 */ return true; }
};

class Machine {
public:
    bool Do(RuleOperation& op, Rule01& r) { return op.Visit(r); }
    bool Do(RuleOperation& op, Rule02& r) { return op.Visit(r); }
    bool Do(RuleOperation& op, Rule03& r) { return op.Visit(r); }
```

答案：文件B 记录了两种看法，一份资料给的是桥接 + 适配器，学长自己认为是**状态模式**，理由是题目里有大量按当前页的条件分支。整理时同意状态模式：当前菜单页就是菜单系统的状态，同一次鼠标点击在不同页里的处理不同，点击又会引起页面切换。

- 每个菜单页一个类，继承抽象状态 MenuPage，把原来各个 switch 里属于这一页的 case 搬进去：`Enter()`、`Leave()`、`MouseClick()`；
- MenuSystem 是环境类，只保存当前页指针，`MouseClick()` 直接委托给当前页，`EnterPage()` 负责调用旧页的 `Leave()` 和新页的 `Enter()`；
- 页面之间怎么跳，写在各页自己的 `MouseClick()` 里；加新页面只加一个类，改跳转关系只改相关页面类。

```cpp
class MenuSystem;

class MenuPage {                                       // 抽象状态
public:
    virtual ~MenuPage() {}
    virtual void Enter(MenuSystem& sys) {}             // 布局、内容、特效
    virtual void Leave(MenuSystem& sys) {}
    virtual void MouseClick(MenuSystem& sys, int x, int y) = 0;
};

class MenuSystem {                                     // 环境类
public:
    MenuSystem(MenuPage* first) : curPage(first) { curPage->Enter(*this); }
    void EnterPage(MenuPage* page) {
        if (curPage == page) return;
        curPage->Leave(*this);
        curPage = page;
        curPage->Enter(*this);
    }
    void MouseClick(int x, int y) { curPage->MouseClick(*this, x, y); }   // 没有 switch
private:
    MenuPage* curPage;
};

class OptionPage;

class MainPage : public MenuPage {                     // 具体状态：第 1 页
public:
    static MainPage* Instance() { static MainPage page; return &page; }
    void MouseClick(MenuSystem& sys, int x, int y);
};

class OptionPage : public MenuPage {                   // 具体状态：第 2 页
public:
    static OptionPage* Instance() { static OptionPage page; return &page; }
    void MouseClick(MenuSystem& sys, int x, int y) {
        if (InRect(x, y, rectLoad)) { Load(); sys.EnterPage(MainPage::Instance()); }
        else if (InRect(x, y, rectCancel)) sys.EnterPage(MainPage::Instance());
    }
};

void MainPage::MouseClick(MenuSystem& sys, int x, int y) {
    if (InRect(x, y, rectStart)) DoStart();
    else if (InRect(x, y, rectOption)) sys.EnterPage(OptionPage::Instance());
    else if (InRect(x, y, rectExit)) DoEnd();
}
```

各页面对象没有自己的数据，用单例共享即可。页面跳转关系如果要做成可配置的，可以再把"按钮到目标页"的映射放进表里。
