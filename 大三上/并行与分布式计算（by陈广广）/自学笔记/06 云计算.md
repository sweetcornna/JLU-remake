## 6.1 什么是云计算

### 1.1 云计算是什么（考点，可以考简述）

- 云计算是**通过互联网（"云"）提供计算服务**，包括服务器、存储、数据库、网络、软件、分析和智能。
- 你只需要在云服务商那里**按需采购，按量付费**；不再需要关注所有实体硬件的购买、连接和维护。
- "云"为你**隐藏了所有的细节**。
- 在云上的**成本要比自己搭建更低**。

按"是什么、怎么做、效果、成本"这四步答就行：是什么 = 通过互联网提供计算服务；怎么做 = 按需采购按量付费；效果 = 隐藏所有细节；成本 = 比自建低。

### 1.2 为什么云的成本更低（3 点，考点）

题干给的线索是采购、利用率、服务器：

1. **大规模采购**，构建成本降低。
2. 由于数据中心**利用时间往往只有 10%~20%**，当引入更多客户时，其利用率可以提高到 **50% 以上**。
3. 由于大部分服务器**不会同时处于峰值状态**，可以**超额配置服务器数量**。

### 1.3 弹性计算（考过，必须会背）

- 弹性计算可快速**扩展或缩减**计算机的**处理、内存和存储资源**，以满足不断变化的需求，从而无需担忧用量高峰的容量计划和工程设计。这是云计算能够提供的非常有吸引力的特性。
- 弹性计算通常由**系统监控工具**控制，**无需中断操作**即可使分配的资源量与实际所需资源量相匹配。
- 通过弹性计算，可以**避免就未用容量或闲置资源付费**，且不必担心投入资金购买或维护额外的资源和设备。

弹性计算是靠虚拟化技术实现的，学完 6.2 再回头看这条。

### 1.4 可靠性：容错、高可用、容灾（考点）

学 Hadoop 时已经知道，大型集群里发生故障是常事。为了完全容忍故障，需要容错；Hadoop 的做法是监控计算任务，失败时在其他节点上重放计算。

| 概念 | 定义 | 业务是否中断 | 典型手段 |
| --- | --- | --- | --- |
| **容错** | 使系统在其某些组件中出现一个或多个故障的情况下能够继续正常运行的属性，此时系统性能可能会下降 | 业务不中断 | 冗余、重放，一般应用于生命关键系统 |
| **高可用** | 让系统更久地保持一定的运行水平，也就是尽可能降低停机时间 | 允许业务短暂中断 | 副本、故障转移 |
| **容灾** | 系统发生灾难时恢复业务的能力 | 灾难后恢复 | 灾备，保护最关键的业务数据部分（数据备份） |

### 1.5 云的高可用（考点）

- 对云服务商的服务，我们一般谈论的是**可用性**。
- 可用性表示为给定年份正常运行时间的百分比，一般用"**几个 9**"表示。
- 例如，Amazon EC2 的每个区域提供 99.99% 的可用性，也就是"四个 9"。

换算一下好记：四个 9 意味着一年最多停机约 52.6 分钟（$365 \times 24 \times 60 \times 0.0001 \approx 52.6$ 分钟）。

### 1.6 云计算的服务模式（考点）

| | IaaS 基础设施即服务 | PaaS 平台即服务 | SaaS 软件即服务 |
| --- | --- | --- | --- |
| 英文 | Infrastructure as a Service | Platform as a Service | Software as a Service |
| 提供什么 | 一切物理级别的硬件资源：计算核心（CPU、GPU、FPGA）、存储、网络等 | 介于 IaaS 与 SaaS 之间。在 IaaS 基础上，把 OS、中间件、DB 等基础软件也作为服务，直接提供一个完整的运行时环境 | 直接把应用程序本身通过网络提供 |
| 怎么用 | 对所有资源按量购买，"组装""选购"一台在云端的服务器 | 拿到运行时环境直接写业务 | 一般通过浏览器即可访问 |
| 常见的 | 弹性计算（Amazon EC2、Aliyun ECS）、块存储、对象存储、专有网络 | aPaaS、iPaaS（见下） | 云办公（各种云文档）、ERP、云游戏 |

- **aPaaS**（Application platform as a service）：减少代码量，降低开发门槛。对应低代码、无服务器计算 FaaS。
- **iPaaS**（Integration platform as a service）：将企业拥有的各种云服务资源进行集成、管理。

## 6.2 虚拟化技术

原稿的 6.2 一直写到存储，篇幅占了大半章。下面按虚拟机、容器、网络虚拟化、存储四块拆开，都属于 6.2。

### 2.1 虚拟化技术的作用（2+2+2+1=7 点，考点）

我们平常用的 PC/Mac 实体机一般由**物理硬件 + 操作系统**两层构成。虚拟机**使用软件模拟硬件功能**，从而在宿主机之上运行多个虚拟的操作系统和应用。除了在个人电脑上跑多系统，虚拟化还有四类用处：

- **分区**
  - 可在一台物理机上运行多个操作系统。
  - 可在虚拟机之间分配系统资源。
- **隔离**
  - 可在**硬件级别**进行故障和安全隔离。
  - 可利用高级资源控制功能保持性能。
- **封装**
  - 可将虚拟机的**完整状态保存到文件中**。
  - 移动和复制虚拟机就像移动和复制文件一样轻松。
- **独立于硬件**
  - 可将任意虚拟机置备或迁移到任意物理服务器上。

### 2.2 一个例子：三个租户共用一台服务器

原稿用这个例子说明虚拟化的价值。假设有一台高性能服务器（16 CPUs，64GB mem），要在上面运行来自 3 个租户的 3 个不同应用。其中有的应用耗费大量计算资源，有的要求高实时性，有的有潜在的安全风险。

- 传统方法：在操作系统中为三个应用设置配额、进程优先级，并严格划分各自的权限。
- 用虚拟化技术，为每个租户的应用建立虚拟机/容器：
  - 在建立虚拟机时就已进行了**资源分配**，程序之间不再会出现资源抢占问题。
  - 各租户应用程序之间**严格隔离**，安全性有保障。
  - 可以更方便地为不同应用配置各自的**运行时环境**，顺带消除了依赖冲突等问题。

把一台服务器扩展为数据中心集群（成千上万台服务器），就是**云计算的基础设施解决方案**。画图时就画一台服务器上叠三个 VM，再把这台服务器复制成一整个机房。

### 2.3 虚拟化技术在云计算中的使用（3 点，考点）

1. 云计算依托于**大型数据中心**，其中包含成千上万台高性能的服务器。
2. 通过虚拟化技术，将所有机器的计算资源**"池化"**，同时提供良好的**隔离以及迁移能力**。
3. 用户可以在大的资源池内**按需选购资源**，组建自己的"云服务器"，在与其他租户高度隔离的前提下，还能方便地进行扩容、迁移。

### 2.4 虚拟化技术的分类（3+2=5 点，考点）

从**资源类型**上，广义地分为：

1. **计算虚拟化**（狭义的虚拟化）
2. **存储虚拟化**
3. **网络虚拟化**

狭义上的虚拟化，根据**虚拟化程度**还可分为：

4. **虚拟机**（硬件虚拟化）
5. **容器**（OS 级虚拟化）

### 2.5 虚拟机与 Hypervisor（考点）

- 虚拟机就是通过在宿主机（host）上"模拟"物理硬件来作为客户机（guest），从而提供一个虚拟化的软件（操作系统）运行环境。
- 虚拟机的核心部件是 **hypervisor**（也称为 **VMM**），也就是**虚拟机的管理器**。
- 由于虚拟机模拟的是硬件机器，因此可以在一台宿主机上运行许多**不同内核**的操作系统（如 Windows 和 Linux）。
- Hypervisor 是**虚拟机的引擎**，负责硬件资源的分配等重要工作。

按 Hypervisor 的位置把虚拟机分两类（要会画）：

| | Type 1 裸金属 bare metal | Type 2 托管 hosted |
| --- | --- | --- |
| Hypervisor 跑在哪 | **直接运行在物理硬件上** | **完全运行在宿主操作系统之上** |
| 层次（自下而上） | HARDWARE → HYPERVISOR → OS | HARDWARE → OS → HYPERVISOR → OS |
| 典型 | ESXi | VirtualBox |

原稿此处有图，PDF 中图片已丢失。画法：Type 1 画三层，最下 HARDWARE 六边形，中间 HYPERVISOR 梯形，上面挂若干朵 OS 云；Type 2 画四层，HARDWARE 上先放一层 OS（宿主操作系统），再放 HYPERVISOR，上面挂若干朵 OS 云。

一条容易被问到的注意事项：这里讨论的虚拟机，主要目的是**在物理机上隔离出多个虚拟环境**，用的还是现有硬件，只是对已有硬件资源进行了重新规划，并做一些必要的最低限度的转换。它**没有**用软件从头到尾实现一个"硬件模拟器"。移动开发常用的 Android/iOS 模拟器才是后者，目标架构与本机架构不同所以需要模拟，效率十分低下。

### 2.6 特权等级带来的问题：全虚拟化与半虚拟化（考点）

现代 CPU 划分了特权等级（Ring0 ~ Ring3）。虚拟机作为应用程序往往运行在用户态（高于 Ring0），但其上的客户操作系统却需要 **Ring0 特权**才能正常运行。按解决方式分两种：

| | 全虚拟化 | 半虚拟化 |
| --- | --- | --- |
| 做法 | 由 Hypervisor 将 guest 的**特权指令捕获并进行处理** | **修改 guest 操作系统**，使其不使用特权指令 |
| guest OS 是否改动 | 不改 | 改（图上标 Modified Guest OS） |

原稿此处有图，PDF 中图片已丢失。两张图结构一样，自下而上是 Hardware → Hypervisor (VMM) → 若干个 Guest OS（每个上面顶一个 Apps），右侧单独一列 Mgmt。区别只在于半虚拟化那张图里 Guest OS 写作 "Modified Guest OS"。

**实现全虚拟化的两种方式**（考点）：

| 方式 | 做法 | 说明 |
| --- | --- | --- |
| **软件辅助** | Hypervisor 捕获客户机特权指令后，将其**翻译为非特权指令**执行 | 纯软件，开销大 |
| **硬件辅助** | 由 CPU 提供支持，将 ring0 继续分为 **root 与 non-root**，让 guest OS 直接跑在 **non-root ring0** 上 | 已被大部分 CPU 支持，如 **Intel VT-x** 和 **AMD-V**。用虚拟机时应优先选择硬件辅助全虚拟化的方案 |

### 2.7 常见的虚拟机（5 种，考点，均支持全虚拟化）

| 虚拟机 | 来源 | 类型 |
| --- | --- | --- |
| **KVM** | 基于 Linux 内核 | Type 1（但作为 Linux 内核的 module） |
| **Hyper-V** | 基于 Windows 内核 | Type 1（但需要 Windows） |
| **Xen** | 依赖于 Linux，安装后启动时会引导到 Xen 的 dom0 | Type 1 |
| **ESXi** | VMware 公司的商业软件 | Type 1，不需要宿主操作系统 |
| **VirtualBox** | Oracle 公司的开源软件 | Type 2 |

记法：这张表里只有 VirtualBox 是 Type 2，其余四个都是 Type 1，但前三个都带括号说明（依附于某个内核或系统），只有 ESXi 是干干净净的裸金属。

### 2.8 虚拟机编排 OpenStack（3 点，考点）

云计算需要在大型集群上按需运行成千上万台虚拟机，靠手工管不过来，于是有了编排。

1. OpenStack 是**一组为云基础设施提供通用服务的软件组件**。
2. 使用 OpenStack，可以在**大型集群**上对虚拟机进行管理。
3. OpenStack 还提供了**存储虚拟化、网络虚拟化、监控、认证、镜像管理**等诸多云计算所必须的基础服务。

### 2.9 虚拟机迁移与 KVM Live Migration（1 段 + 3 步，考点）

虚拟机具有独立于硬件的特性，且其全部内容都封装为**文件**的形式存在于磁盘中，因此可以在虚拟机**关机后**将文件移动到其他宿主机再开启，这就是虚拟机的**迁移**。

开机状态下能不能迁移（**热迁移**）？开机时虚拟机除磁盘内容外，还有许多有关运行状态的信息。**KVM Live Migration** 可以实现热迁移，三步：

1. 虚拟机的**磁盘文件存放在共享的网络位置上**（源、目标主机通过网络可访问）。
2. **暂停**并将 VM 状态打包通过网络发送给目标主机。
3. **目标主机恢复**虚拟机的运行。

## 容器：轻量级虚拟化（6.2 续）

虚拟化技术能带来分区、隔离、封装、硬件独立四个特性，方便分隔不同的用户运行不同的应用程序。虚拟机是**从底层硬件资源角度**进行隔离与分配，模拟了多台实体机，各自跑各自的操作系统和应用程序。但有时我们不想重复安装操作系统（占用空间），只是想**在宿主操作系统上隔离出几个独立的运行环境**。

### chroot：早期解决方案（1982）

- 在类 Unix 操作系统上，`chroot` 是一个**为当前进程及其子进程指定根目录**的操作。一经指定，指定目录外的内容将对该进程及其子进程完全不可见。
- 这种技术只能分隔存储区域来给各个进程创造自己的目录环境，**不能像虚拟化技术一样进行配额（分区），更无法将该环境打包迁移（封装、硬件独立）**。

### 容器

- 容器是一种**操作系统级虚拟化技术**，它允许在**同一个内核**上分隔出多个用户空间实例。
- 从应用程序的角度来看，每一个实例就是一台机器。
- 早先（2008），Linux 基金会为了实现容器化提出了 **LXC**（Linux Container）技术，用来在单个 Linux 内核上提供多个 Linux 系统（容器）。
- LXC 使用 **cgroups** 和 **namespace** 来实现容器化：
  - **cgroups** 用于资源（CPU、内存、IO、网络）的**限制管理**。
  - **namespaces** 用于**控制进程可以看到什么资源**（mnt、pid、net、ipc 等），相当于 chroot 的进阶版。

### Docker：容器化的完全体

- 作为容器技术，Docker 也是用来在一个操作系统内核上提供多个运行环境的工具。
- 在提供 LXC 同样的分区、隔离基础上，Docker 支持将容器**打包为镜像（image）**，从而使得应用程序及其运行环境可以在任何地方运行。

原稿举的部署例子：

- 开发完成后，可以在本地建立一个容器，在其中配置好所有相关的环境，将代码放进去，然后打包为一个"镜像"。
- 只要服务器上装了 Docker，直接把镜像上传并运行即可，无需更改服务器操作系统中的任何内容，也不用担心一失手让服务器崩溃。

Docker 的镜像相当于**一个应用程序及其所有相关软件环境（除操作系统内核）的打包**，在复用内核的同时囊括了程序要运行所需的所有内容，做到"即开即用"。有了镜像就能方便地迁移容器（在另一台服务器上打开容器即可），进一步还能方便地扩容（在多台服务器上运行容器）以增加服务吞吐量，这些正是云计算需要的。

### 容器编排 Kubernetes

三个促使你用 K8s 的场景：

- 网站访问量激增，一台服务器、一个容器的吞吐量不够了。
- 已经部署了很多容器，但改了代码，需要把所有旧容器替换为新容器。
- 容器中的代码或容器所在的服务器在运行过程中崩溃了。

用了云（集群），单兵作战模式（只用一台服务器）已经落后了，容器化后的服务部署也要考虑如何适应集群环境。正如 OpenStack 支持虚拟机在集群上的部署，**K8s 是用来支持容器在集群上部署的软件**。

**Kubernetes 能做到什么**（5 点）：

| 能力 | 说明 |
| --- | --- |
| **自动装箱** | 允许你指定每个容器所需 CPU 和内存（RAM）。K8s 可以自动做出决策，将容器放在集群合适的节点上以最优化利用服务器资源 |
| **服务发现和负载均衡** | 可以使用 DNS 名称或自己的 IP 地址公开容器；如果进入容器的流量很大，K8s 可以负载均衡并分配网络流量，从而使部署稳定 |
| **自动的部署和回滚** | 你可以描述已部署容器需要达到何种新状态（3 个变为 5 个），它以受控的速率将实际状态更改为期望状态。例如自动创建新容器、删除现有容器并将它们的所有资源用于新容器 |
| **自我修复** | 重新启动失败的容器、替换容器、杀死不响应运行状况检查的容器，并且在准备好服务之前不将其通告给客户端 |
| **存储编排** | 允许你自动挂载你选择的存储系统，例如本地存储、公共云提供商等 |

**Kubernetes 基本概念**：

- **Pod**：K8s 中创建和管理的、**最小的可部署的计算单元**。它是一个容器运行环境。每个 Pod 中可能包含多个容器，这些容器共享同一套上下文环境。一般来说你不需要手动创建 Pod，通过一些工作负载，Pod 可以被自动创建（或销毁）。
- **工作负载**：在 K8s 上运行的应用程序，包括
  - **Deployment & ReplicaSet**：用于无状态应用，可以管理多个 Pod 副本，每个副本都是等价的。
  - **StatefulSet**：以某种方式跟踪应用状态的一些 Pod。
  - **DaemonSet**：提供节点本地支撑设施的 Pod。
  - **Job & CronJob**：一次性/定期运行的任务。

原稿给了一个 Deployment 示例，创建一个 ReplicaSet，负责启动三个 nginx Pod：

```yaml
apiVersion: apps/v1          # 版本号，每个版本K8s固定写法
kind: Deployment             # 负载类型，此处为Deployment
metadata:                    # Deployment的元数据
  name: nginx-deployment     # Deployment名称
  labels:                    # 标签
    app: nginx
spec:                        # 指定Deployment要达到的状态
  replicas: 3                # 副本数量
  selector:                  # 选择器，定义 Deployment 如何查找要管理的 Pods
    matchLabels:             # 匹配规则，查找包含对应标签的Pod
      app: nginx
  template:                  # Pod模版
    metadata:                # 元数据
      labels:                # 标签，用于分组，供选择器Selector使用
        app: nginx
    spec:                    # 指定Pod的目标状态
      containers:            # 指定每个Pod中要开启哪些容器
      - name: nginx          # 容器名
        image: nginx:1.14.2  # 容器使用的Docker镜像名
        ports:               # Pod端口声明
        - containerPort: 80  # 暴露容器的80端口
```

执行以下指令创建 Deployment：

```bash
kubectl apply -f nginx-deployment.yaml
```

查看结果（原稿给的输出，Pod 名里的随机后缀保持原样）：

```text
NAME                                READY   STATUS    RESTARTS   AGE   LABELS
nginx-deployment-75675f5897-7ci7o   1/1     Running   0          18s   app=nginx,pod-template-...
nginx-deployment-75675f5897-kzszj   1/1     Running   0          18s   app=nginx,pod-template-...
nginx-deployment-75675f5897-qqcnn   1/1     Running   0          18s   app=nginx,pod-template-...
```

Deployment 所创建的 ReplicaSet 已经启动了三个包含标签 `app=nginx` 的 Pod，并且将会保证未来总是存在三个这样的 Pod。

## 网络虚拟化（6.2 续）

网络是连接数据中心内所有节点的"神经"，"网络即服务"也是云所需要的功能之一，这就需要网络虚拟化技术。

### VLAN

- VLAN（Virtual Local Area Network），中文名"**虚拟局域网**"，是在**二层网络（数据链路层）** 划分和隔离**广播域**的技术。
- 这种技术一般**只适用于大二层网络**，但云数据中心规模往往较大，一般会使用三层网络，所以一般不使用 VLAN 在云上进行网络虚拟化。

### 经典的大型数据中心网络架构

- 一般包括**基于二层交换网络的接入层和汇聚层**，以及**基于三层路由的核心层**。
- 云计算中一个重要的特性是**虚拟机可动态迁移**，而这要求迁移前后虚拟机运行状态不能发生变化（包括 IP 地址）。
- **三层路由的存在会对云中的虚拟机迁移产生阻隔**。

### Overlay 技术

要解决上面这个阻隔问题，要么在硬件层面采用**大二层交换**的网络结构设计，要么使用 **Overlay** 技术。而且就算一个数据中心内用了大二层结构，跨数据中心并网时每个数据中心总归要有一个出口路由，问题还在。

- Overlay 技术就是为了解决这些问题，它**将底层承载网络的复杂结构屏蔽，为上层提供一个清晰简洁的网络模型**。
- Kubernetes 中所必须的 **flannel**，以及 **VXLAN、GRE、GENEVE** 等技术，都属于 Overlay 网络，它们都是为了在复杂网络环境下给上层提供一个大二层网络模型。
- Overlay 技术的本质是**在已有网络上建立一个隧道，将本来的数据帧添加特定的协议头二次打包，然后通过承载网络发出**。

原稿此处有两张图，PDF 中图片已丢失。第一张是上下两个平面：上面蓝色的"Overlay 网络"（含 Overlay 控制平面、数据平面 Payload 封装），下面绿色的"物理承载网络"（含 Overlay 边缘设备、路由器、交换机、主机、承载网络控制平面），两层之间用虚线对应。第二张是 flannel 的封包示意：两台 CoreOS Machine，各自跑几个 Pod（容器地址在 `10.1.x.x/24` 网段），Pod 经 `veth` 接到 `docker0`，再经 `flannel0` 和 `flanneld` 出到 `eth0`（宿主机地址，原图用的是示例地址，这里写成 `192.168.x.x`）；包的结构是 MAC / Outer IP（宿主机之间）/ UDP / Inner IP（容器之间）/ Payload，也就是"二次打包"的直观样子。

### OpenStack 的 neutron

OpenStack 中的网络组件 **neutron** 不止能够提供一个基础的大二层虚拟网络环境。基于一些 Overlay 技术，它还能做到更多"网络即服务"：

- 为不同的项目创建各自的**私有虚拟网络**。
- 为项目提供多个**子网、路由**功能。
- 为项目提供**安全组**功能。

## 存储（6.2 续）

### 计算机内/间的传输速率

原稿给的一组数字（抄录并复核了单位换算）：

| 通道 | 原稿数据 | 核对 |
| --- | --- | --- |
| DDR4 内存 | 序列传输频率约 2133–3200，DIMM 封装一般为 8 字节宽度，带宽约 **17056–25600 MB/s** | $2133 \times 8 = 17064$，$3200 \times 8 = 25600$。（更正：原文作 17056，按 8 字节宽度算应为 17064 MB/s；若按 DDR4-2133 的精确频率 2133.33 MT/s 则是 17067 MB/s，业界标称 PC4-17000） |
| PCIe 3.0 x16 | 时钟 8GHz，位宽 16bit，带宽 **16000 MB/s** | 每 lane 8 GT/s × 16 lane = 16 GB/s 的原始速率；算上 128b/130b 编码开销实际约 15.75 GB/s。原稿的 16000MB/s 是不计编码开销的近似值 |
| PCIe 4.0 x16 | 大约翻倍达到 **32000 MB/s** | 每 lane 16 GT/s，翻倍无误 |
| SSD | 三星 PM9A1 1TB 顺序读取 **7000 MB/s** | 这是 PCIe 4.0 x4 的典型水平 |
| 以太网 | 已经可以达到 40Gbps 甚至 100Gbps，不考虑协议头损耗，约 **5–12.5 GB/s** | $40 \div 8 = 5$，$100 \div 8 = 12.5$，换算正确 |

排个序好记：DDR4（17–25.6 GB/s）> PCIe 4.0（32 GB/s，其实最快）> PCIe 3.0（16 GB/s）> 100G 以太网（12.5 GB/s）> SSD（7 GB/s）> 40G 以太网（5 GB/s）。结论是**网络已经和本地盘一个量级**，所以现在的集群在设计时可能会考虑**存算分离**的架构。

原稿此处有一张数据中心存算分离的图，PDF 中图片已丢失。结构是：最上一条"数据中心互联"横贯全图，下面左半是"计算网络"（两层交换机 + 服务器），右半是"存储网络"（交换机 + 存储设备），服务器在中间被两张网同时接入。

### SAN

- **存储区域网络（SAN）** 是一种专用的高速网络（也可以建构在传统以太网上），可提供对存储的**块级网络访问**。
- SAN 将存储设备呈现给主机，以使**存储看起来是本地连接的**。
- 通过 SAN，我们可以实现**存算分离**，并作为基础支撑云计算下的各类存储服务，实现"存储即服务"。（更正：原文作"存储及服务"，"及"应为"即"。）

### 云计算中的三种存储

在云上，或者说通过网络提供的存储服务一般有三种：文件存储、块存储、对象存储。原稿特别标了一句：**三者并不是并列的**。

| | 文件存储 | 块存储 | 对象存储 |
| --- | --- | --- | --- |
| 提供什么 | 通过网络，以**目录**的组织形式提供对文件的存储 | 直接通过网络（一般是 SAN）对外提供**"块设备"（硬盘）**，其他服务器可以直接挂载该网络硬盘并以操作块的形式使用它 | 以**"对象"** 的形式提供对数据的访问，结构扁平，不存在目录式的层级结构，数据对象的唯一标识符是一个 **Key** |
| 操作的对象 | **文件和目录** | **磁盘** | **"对象"** |
| 面向的用户 | **人** | **文件系统** | **应用程序（代码）** |
| 常用协议/接口 | SMB、NFS | iSCSI | HTTP (RESTful) API，如 Amazon S3 |
| 设备名 | NAS（Network Attached Storage） | SAN | 对象存储服务 |
| 特点 | 对网络文件存储的操作和在本地文件系统上对文件进行操作的方法几乎一样，常用的局域网文件共享就属于这类 | 块（block）是硬盘组织存储空间的形式 | 适用于非结构化数据（本质上是一个大型 KV 数据库），十分易于扩容 |

"三者不是并列的"这句话，原稿用一句话点破：**人能点文件，文件去操作块**。也就是三层叠在一起：人 → 文件存储 → 块存储；对象存储是另起一路，直接给程序用。

### Ceph

- Ceph 是一个**一站式的集群存储解决方案**，是一套开源的云存储软件。
- 使用 Ceph 可以在一个统一的存储系统中提供**文件存储（CephFS，兼容 POSIX）、块存储（RADOS 块设备）和对象存储（兼容 S3）** 服务。
- OpenStack 中也有提供类似功能的组件。

## 6.3 面向服务和云原生

### 3.1 云原生：云上服务的解决方案

- 作为新一代的互联网基础设施，云有着一些传统模式无法比拟的优势，其中一条是**资源的灵活性**。
- 问题是：如何充分利用云的能力，进行云上业务的开发？
- 下面讨论的就是如何在云上以**微服务**的方式开发、部署程序。

### 3.2 服务指什么

- 服务，指履行职务，为一定的对象工作。
- 在我们的语境里，服务方是计算机（服务程序），被服务方是人或计算机（应用程序）。
- 计算机一般不提供物理上的服务，而是提供**信息层面的服务**。
- 服务往往是**一对多**的。

例子：数据库（服务器端）提供格式化数据存取服务；购物网站提供信息展示、多方信息交换服务；Linux X Server 提供图形化界面服务。

### 3.3 SOA 面向服务架构

将服务的思想引入到软件架构中，就是 SOA（Service-Oriented Architecture）。

- 在 SOA 中，存在着许多独立的功能单元，被称为**服务**。
- 服务之间相互依赖，通过**通信**的方式互相调用。

SOA 中服务的定义（四条）：

1. 它在逻辑上表示具有**特定结果的可重复业务活动**。
2. 它是**独立的**。
3. 对于被服务者，它是**黑盒**。
4. 它可能由其他服务组成。

和模块化的关系：把一个大的架构拆解成许多小部分，目的是**解耦合、复用**。SOA 也是这个思想，只不过在更宏观的层面上：SOA 的各个部分（服务）更加独立，可能是单独的进程，甚至可能运行于许多台机器，要通过**通信**（而非函数调用）进行交互。

### 3.4 微服务（SOA 的进化）

- 每一个业务都拆成一个进程，然后它们之间再通过通信的方式互相调用，这样就形成了许多个**高内聚、低耦合**的微服务。
- 由于每个服务都是独立进程，因此可以灵活地针对单个服务进行**弹性扩展、灰度发布、AB 测试**。
- 定义：微服务是一种软件架构风格，它是以专注于**单一责任与功能**的小型功能区块为基础，利用**模块化**的方式组合出复杂的大型应用程序，各功能区块使用**与语言无关的 API 集**相互通信。

微服务该怎么实现？

- 可以直接编写每个服务进程，并配合使用各种进程间通信方式，如 gRPC、HTTP（RESTful）等进行通信。
- 也可以使用框架，如 Java 下的 Spring Boot / Cloud。

### 3.5 通信方式：RESTful

- RESTful API 是一种**基于 HTTP 的接口规范**，常用在 Web 服务之间进行交互的场合。
- 最关键的抽象是**"资源"**，通过 **URI** 标识，一般用 **JSON** 来承载。
- 使用**统一的接口**进行资源访问（HTTP GET / POST / PUT / DELETE）。
- **无状态**，且操作具有**幂等性**。
- RESTful API 定义中给出的约束非常多，实现起来代价很大，不一定适用于你的项目，因此请根据实际情况设计你的接口。

原稿给的两个例子：

```text
查询学生
REQUEST:
GET http://www.example.com/students/123456

RESPONSE: 200 OK
{
    "id":123456,
    "name":"xiaoming",
    "gender":"male"
}
```

```text
添加学生
REQUEST:
POST http://www.example.com/students
{
    "id":123457,
    "name":"xiaohong",
    "gender":"female"
}

RESPONSE: 201 CREATED
```

### 3.6 通信方式：gRPC

- gRPC 是由 Google 开发的一个**高性能、通用的开源 RPC（远程过程调用）框架**。
- 基于 **HTTP/2** 协议标准而设计，包括使用**二进制传输**，支持**多路复用**等特性。
- 使用 **ProtoBuf** 对数据序列化。
- 支持大多数流行的编程语言。

gRPC 对比 RESTful（原稿以表格截图给出）：

| | gRPC | HTTP with JSON |
| --- | --- | --- |
| 序列化方式 | ProtoBuf | JSON |
| 编码格式 | 二进制 | 文本 |
| 底层协议 | HTTP/2 | HTTP |
| 约定 | 需要 | 不需要 |
| 压缩 | 是 | 否 |

### 3.7 微服务的"搭档"们：通信代理

微服务自身完成一个功能的同时，还要与其他服务进行通信。通信的方式千千万，但围绕着通信也产生了许多问题：服务间怎么找到彼此，多个相同服务间如何负载均衡，如何在服务外部通过通信进行健康检查、继而熔断等等。

微服务的搭档们一般有两种：

- 以 **Spring Cloud** 为代表的**与业务代码耦合**的形式。
- **Istio** 等**与业务代码分离**的形式（也称 **Service Mesh**、**Sidecar**）。

### 3.8 Sidecar 与 Service Mesh

- **Service Mesh（服务网格）** 是一个**基础设施层**，用来解决系统架构微服务化后的服务间通信和治理问题。
- **Sidecar**（边三轮、跨斗子）是一种**设计模式**，把上面提到的那些配件放到 Sidecar 中，从而将**业务代码和其他辅助功能解耦合**。

Service Mesh 的两条好处：

- 实现了通信逻辑和业务代码的解耦，屏蔽了通信的复杂性，使开发者能专注于业务逻辑。
- 是**语言无关**的，可以选择任何喜欢的语言编写微服务。

### 3.9 服务发现、负载均衡、流量控制

| 问题 | 解决方案 | 耦合式实现 | 分离式实现 |
| --- | --- | --- | --- |
| 服务们怎么找到彼此 | **服务发现** | Spring Cloud – Eureka | K8s – Service；Istio – Envoy |
| A 服务要访问 B 服务，但 B 部署了 3 个副本，该访问哪个 | **负载均衡** | Spring Cloud – Feign/Ribbon | K8s – Service, Ingress；Istio – Envoy |
| 想实现灰度发布，需要更精细的调度 | **流量控制** | | Istio（分析报文内容如 http header 进行动态路由），还可实现熔断、流量加密 |

负载均衡是初步的流量控制。要做灰度发布就需要更精细的流量控制，这种情况下 Service Mesh 更有优势。

### 3.10 流程的自动化：CI/CD

通过**持续集成 / 持续交付 / 持续部署（CI/CD）**，可以让持续的自动化和监控贯穿于应用的整个生命周期。

### 3.11 状态

在考虑可扩展性时，状态是一个很重要的概念，分两类：

| | 无状态 Stateless | 有状态 Stateful |
| --- | --- | --- |
| 定义 | 程序（段）**没有记忆**，每一次执行只和它当前的输入有关，与之前发生的事无关 | 程序（段）**存在记忆**，每一次执行可能会对未来的执行造成"副作用" |
| 例子 | 只通过参数和返回值与外界沟通（不调用任何外部变量）的函数，也叫**纯函数**；**IP 协议**；一个静态网站的服务器；没有变量、只有方法的对象 | 非纯函数，即通过除参数和返回值以外的渠道和外界交换数据的函数；**TCP 协议**（三握四挥，能画出状态机）；涉及权限认证（用户登录，需要存储 session）的动态网站；有实例变量的对象 |

在云上进行架构时，我们**优先使用无状态的设计**，因为：

1. 无状态具有天然的**线程安全性**。
2. 十分**易于扩展/收缩**（弹性）。
3. 出现问题可以立即被副本替代，几乎不会造成大崩溃（容错/高可用）。

有状态的东西怎么办？一个方案是使用 **Redis**：把有状态的 session 存储到 Redis 中，剩下的服务就是无状态的，于是服务就拥有了可扩展性。

为什么代码无状态、数据有状态，原稿的解释：

- 一个函数、一段代码、一个程序，它本身在运行时是不会被改变的，因此可以被视为无状态的，**不需要常驻内存**。
- 函数/程序所使用的资源（数据）会在运行时被改变，而它的改变会对未来对它的访问产生影响，因此是有状态的。
- 数据本身就是一个被（当下和未来、自己和他人）共享的状态，需要被记住以维持未来运行。
- 如果一个函数只使用了其**局部作用域**内的资源（包括参数和返回值），它对外界的影响就只局限于参数和返回值；对其他任何局部变量的修改从语义上讲不会对外界产生任何影响（局部作用域限制，不存在共享状态）。
- 如果一个函数使用了**外部作用域**中的资源，那么它自然就会对外界有副作用。

### 3.12 FaaS

- 由于无状态服务可以"用后即抛"，它可以被设计为**"事件驱动型"**（有事儿找我，没事儿没我），而非"资源驱动型"（与计算资源锁死）。
- **功能（函数）即服务（Function as a Service, FaaS）**，就是一种基于事件驱动模型的云服务模式。
- 使用 FaaS，你无需预先购买、管理计算资源，只需要编写代码并上传。
- FaaS 可以自动响应任何规模的代码执行请求，从每天十几个事件到每秒数十万个事件不等。
- 只需为使用的**计算时间**付费（按毫秒计算），而不是预先为峰值容量预置基础设施，从而节省成本。

FaaS 就是前面 PaaS 那一节提到的"无服务器计算"，属于 aPaaS。

## 6.4 边缘计算

### 4.1 边缘的定义

- **广义上**：地理位置上更靠近用户侧的设备，可能包含用户的终端设备、用户的路由器、本地边缘服务器、ISP 等。
- **狭义上**：从广义概念中**排除掉用户的终端设备**，也就是介于用户终端与云之间的那些靠近用户侧的设备。
- 经典的边缘应用：**CDN**。

### 4.2 计算位置的变化

| 阶段 | 特征 |
| --- | --- |
| 早期计算 | **集中式**应用程序，仅在一台孤立的计算机上运行 |
| 个人计算 | 本地运行的**去中心化**应用程序 |
| 云计算 | 在**数据中心**运行的集中式应用程序 |
| 边缘计算 | 在**靠近用户的地方**（设备本身或者网络边缘）运行的集中式应用程序 |

### 4.3 云边端一体化

两个方向：

- 云、边可以接管原来在终端上进行的、对计算能力或存储能力要求高的任务，从而**减少终端设备的功耗和体积**。
  - 云端接管终端任务：**Chromebook**（接管了存储和计算）。
  - 边缘接管终端任务：**NAS**（更注重接管存储而非计算，但现在很多 NAS 也能提供计算功能）。
- 边、端接管原来在云上进行的部分**时延/隐私敏感**性计算任务，从而**减少云计算的延迟、增强数据安全性**。
  - 边缘接管云端任务：**云游戏**（能够极大降低操作延迟）。
  - 终端接管云端任务：**联邦学习**（保证数据隐私的同时训练模型）。
